# 5. What Happens When You Enter a URL into a Browser?

When you enter a URL such as:

```text
https://www.example.com/products?id=10
```

into a browser and press **Enter**, the browser performs a chain of operations before the webpage appears.

At a high level:

```text
URL
 ↓
URL Parsing
 ↓
DNS Resolution
 ↓
Connection Establishment
 ↓
TLS Handshake (HTTPS)
 ↓
HTTP Request
 ↓
Server Processing
 ↓
HTTP Response
 ↓
HTML/CSS/JavaScript Processing
 ↓
Layout + Paint
 ↓
Webpage Displayed
```

This process involves concepts from **DNS, TCP/UDP, TLS, HTTP, IP routing, operating systems, servers, and browser rendering**.

---

## 1. URL Is Parsed

First, the browser parses the URL to understand where and how the requested resource should be accessed.

For example:

```text
https://www.example.com/products?id=10
│       │                │       │
│       │                │       └── Query parameter
│       │                └────────── Path
│       └────────────────────────── Hostname
└────────────────────────────────── Scheme
```

The URL contains several components:

| Component       | Example           | Meaning                                                                                       |
| --------------- | ----------------- | --------------------------------------------------------------------------------------------- |
| Scheme/Protocol | `https`           | Specifies how the resource should be accessed                                                 |
| Hostname        | `www.example.com` | Identifies the destination host/domain                                                        |
| Port            | `443`             | Default port for HTTPS                                                                        |
| Path            | `/products`       | Identifies the requested resource/path                                                        |
| Query           | `id=10`           | Additional parameters sent with the request                                                   |
| Fragment        | `#reviews`        | Identifies a section within the resource; normally not sent to the server in the HTTP request |

So:

```text
https://www.example.com/products?id=10
```

means approximately:

```text
Scheme  → HTTPS
Host    → www.example.com
Path    → /products
Query   → id=10
Port    → 443 (default HTTPS port)
```

### Example

If the user enters:

```text
https://shop.example.com/products?id=25
```

the browser understands:

```text
Protocol → HTTPS
Host     → shop.example.com
Path     → /products
Query    → id=25
```

The browser now knows which server/domain it needs to communicate with and which resource is being requested.

---

# 2. DNS Resolution

The browser generally needs an **IP address** to communicate with the destination.

Humans use domain names:

```text
www.example.com
```

while network communication uses IP addresses:

```text
93.x.x.x
```

The browser therefore needs to resolve the hostname into an IP address.

Conceptually:

```text
www.example.com
       ↓
   DNS Resolution
       ↓
    IP Address
```

For example:

```text
www.example.com → 93.x.x.x
```

The actual IP address depends on the domain's DNS configuration and can change.

### Does the browser always perform a DNS query?

No.

The browser and operating system may already have the result cached.

A simplified lookup path can look like:

```text
Browser DNS Cache
       ↓
OS DNS Cache
       ↓
Local/Network DNS Resolver
       ↓
Root DNS Server
       ↓
TLD DNS Server
       ↓
Authoritative DNS Server
       ↓
IP Address
```

The exact process can vary depending on caching, DNS configuration, DNS-over-HTTPS/DNS-over-TLS, and the operating system/browser.

### Example

Suppose:

```text
www.example.com
       ↓
DNS
       ↓
203.0.113.20
```

The browser can now use the resolved IP address to communicate with the destination.

### Important distinction

DNS does **not** download the webpage.

DNS primarily answers questions such as:

```text
"What IP address corresponds to this hostname?"
```

The actual webpage is retrieved later using HTTP/HTTPS.

---

# 3. Connection Is Established

Once the destination IP address is known, the browser needs a way to communicate with the server.

For HTTPS, the connection process depends on the HTTP version being used.

Common possibilities include:

```text
HTTP/1.1 or HTTP/2
        ↓
      TCP
        ↓
      TLS
        ↓
     HTTP
```

Whereas:

```text
HTTP/3
   ↓
 QUIC
   ↓
 UDP
   ↓
 HTTP
```

### Traditional HTTPS: TCP + TLS

For HTTP/1.1 or HTTP/2, a simplified sequence is:

```text
Browser
   │
   │ TCP connection
   ↓
Server
   │
   │ TLS handshake
   ↓
Secure connection
```

Before application data is exchanged over HTTPS, TCP establishes a reliable transport connection.

---

## TCP Three-Way Handshake

A simplified TCP connection establishment is:

```text
Client                         Server
  │                              │
  │ -------- SYN --------------> │
  │ <------- SYN + ACK --------- │
  │ -------- ACK --------------> │
  │                              │
  │     TCP connection ready     │
```

The purpose is to establish the TCP connection and synchronize sequence information.

---

# 4. TLS Handshake for HTTPS

After TCP is established, HTTPS uses **TLS (Transport Layer Security)** to secure the communication.

Conceptually:

```text
TCP Connection
      ↓
TLS Handshake
      ↓
Encrypted Communication
```

TLS provides important security properties such as:

* Encryption
* Server authentication
* Integrity protection

During the TLS handshake, the client and server negotiate cryptographic parameters and establish keys for protecting the connection.

The browser also verifies the server's certificate according to its trusted certificate rules.

### Why is the certificate important?

Suppose you visit:

```text
https://bank.example
```

The browser needs confidence that the server presenting itself as that website is actually authorized for the requested hostname.

The certificate helps establish this identity through a chain of trust.

### Simplified view

```text
Browser
   │
   │ "I want a secure connection."
   ↓
Server
   │
   │ Certificate + handshake information
   ↓
Browser verifies certificate
   │
   ↓
Cryptographic keys established
   │
   ↓
Encrypted communication
```

### Important interview nuance

TLS does **not** simply "encrypt the URL."

It establishes cryptographic protection for the connection/application data. Some metadata, such as the destination IP and certain connection information, can still be visible depending on the protocol and network environment.

---

# 5. HTTP Request Is Sent

Once the required connection/security setup is complete, the browser sends an HTTP request.

For example:

```http
GET /products?id=10 HTTP/1.1
Host: www.example.com
```

A real request can contain many additional headers:

```http
GET /products?id=10 HTTP/1.1
Host: www.example.com
User-Agent: ...
Accept: text/html
Cookie: ...
Accept-Encoding: gzip, br
```

The request may include:

* HTTP method
* Requested path
* Headers
* Cookies
* Query parameters
* Request body, when applicable

For example:

```text
GET /products?id=10
```

means:

> "Retrieve the resource represented by `/products?id=10`."

---

## What happens to the HTTP request?

The HTTP data is passed down through networking layers.

A simplified view is:

```text
HTTP Request
     ↓
TCP Segment / QUIC packet
     ↓
IP Packet
     ↓
Link-Layer Frame
     ↓
Physical/Wireless Transmission
```

Routers then forward IP packets toward the destination network.

For TCP-based HTTP:

```text
HTTP
 ↓
TCP
 ↓
IP
 ↓
Ethernet/Wi-Fi
```

For HTTP/3:

```text
HTTP/3
  ↓
QUIC
  ↓
UDP
  ↓
IP
  ↓
Ethernet/Wi-Fi
```

---

# 6. Server Processes the Request

The request eventually reaches the destination infrastructure.

It may not go directly to one physical server.

A modern architecture could look like:

```text
Browser
   ↓
Internet
   ↓
Load Balancer
   ↓
Web Server
   ↓
Application Server
   ↓
 ┌───────────────┐
 │               │
Database       Cache
 │               │
 └───────────────┘
```

The server/application may perform several operations.

For example, it may:

* Authenticate the user
* Read cookies/session information
* Validate request parameters
* Query a database
* Read cached data
* Call another service/API
* Generate HTML
* Return a static file
* Check authorization
* Perform business logic

### Example

Suppose the request is:

```http
GET /products?id=10
```

The application might perform:

```text
Request
   ↓
Validate product ID
   ↓
Check cache
   ↓
If not cached → Query database
   ↓
Build product information
   ↓
Generate response
```

The response might contain the product page as HTML.

---

# 7. Server Sends an HTTP Response

After processing the request, the server sends an HTTP response.

For example:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: ...
```

followed by the response body.

A simplified response:

```text
HTTP Response
     │
     ├── Status Code
     ├── Headers
     └── Body
```

### Common HTTP status codes

| Status Code                 | Meaning                             |
| --------------------------- | ----------------------------------- |
| `200 OK`                    | Request succeeded                   |
| `201 Created`               | Resource was successfully created   |
| `301 Moved Permanently`     | Permanent redirect                  |
| `302 Found`                 | Temporary redirect                  |
| `304 Not Modified`          | Cached representation can be reused |
| `400 Bad Request`           | Invalid request                     |
| `401 Unauthorized`          | Authentication required/failed      |
| `403 Forbidden`             | Server refuses access               |
| `404 Not Found`             | Resource not found                  |
| `500 Internal Server Error` | Server-side error                   |
| `503 Service Unavailable`   | Service temporarily unavailable     |

For example:

```http
HTTP/1.1 200 OK
Content-Type: text/html
```

means the request was successfully processed and the response contains HTML.

---

## What can the response contain?

The response might contain:

```text
HTML
CSS
JavaScript
Images
Fonts
JSON
Videos
Other resources
```

For example, the initial HTML may contain:

```html
<link rel="stylesheet" href="/style.css">
<script src="/app.js"></script>
<img src="/logo.png">
```

The browser then needs to fetch these additional resources.

---

# 8. Browser Parses and Renders the Page

Receiving HTML is not the final step.

The browser must interpret the returned resources and construct what appears on the screen.

A simplified rendering pipeline is:

```text
HTML
 ↓
DOM
 │
CSS
 ↓
CSSOM
 │
 └──────→ Render Information
              ↓
            Layout
              ↓
             Paint
              ↓
          Compositing
              ↓
          Display
```

---

## HTML → DOM

The browser parses HTML and constructs the:

**DOM — Document Object Model**

For example:

```html
<html>
  <body>
    <h1>Hello</h1>
    <p>Welcome</p>
  </body>
</html>
```

can conceptually become:

```text
Document
   │
  html
   │
  body
  ├── h1
  │    └── "Hello"
  │
  └── p
       └── "Welcome"
```

The DOM represents the document as a tree of objects/nodes.

---

## CSS → CSSOM

The browser parses CSS and constructs the:

**CSSOM — CSS Object Model**

For example:

```css
h1 {
    font-size: 32px;
}
```

The browser uses the CSS rules when determining how elements should be displayed.

---

## DOM + CSSOM → Rendering Information

The browser combines the document structure and styling information to determine what needs to be rendered.

Conceptually:

```text
HTML → DOM
CSS  → CSSOM
        ↓
Rendering Information
        ↓
      Layout
        ↓
       Paint
```

### Layout

The browser calculates things such as:

* Element positions
* Widths
* Heights
* Spacing
* Text positions

For example:

```text
Where should this <div> appear?
How wide should it be?
Where should the text start?
```

### Paint

The browser then paints visual elements such as:

* Text
* Backgrounds
* Borders
* Images
* Shadows

Modern browsers also perform additional stages such as **compositing**, where rendered layers may be combined for display.

---

# 9. JavaScript Can Execute

If the page contains JavaScript:

```html
<script src="/app.js"></script>
```

the browser may execute that JavaScript.

JavaScript can:

* Modify the DOM
* Modify styles
* Respond to user interactions
* Validate input
* Update page content
* Make additional HTTP requests
* Fetch API data
* Store/read browser-side data

For example:

```javascript
document.querySelector("#price").textContent = "₹999";
```

can modify the page after the HTML has already been loaded.

---

# 10. Additional Resources Are Requested

The initial HTML often contains references to other resources.

For example:

```html
<link rel="stylesheet" href="/style.css">

<script src="/app.js"></script>

<img src="/logo.png">
```

The browser may make additional requests for:

```text
HTML
 ├── CSS
 ├── JavaScript
 ├── Images
 ├── Fonts
 └── API requests
```

Conceptually:

```text
             HTML
               │
       ┌───────┼────────┐
       ↓       ↓        ↓
      CSS      JS      Image
                       ↓
                     Font
```

These resources may be fetched using existing connections where possible or through additional connections/streams depending on the protocol and browser behavior.

For example, modern HTTP/2 and HTTP/3 support multiplexing, allowing multiple requests/responses to share a connection/connection context rather than requiring a separate TCP connection for every resource.

# Where Do DNS, TCP, TLS, HTTP and IP Fit?

This question is often used to test whether you understand how networking concepts connect.

```text
Browser
   │
   │ HTTP / HTTP/3
   ↓
Transport
   │
   ├── TCP
   └── QUIC/UDP
   ↓
IP
   ↓
Ethernet / Wi-Fi
```

For traditional HTTPS:

```text
HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
 ↓
Ethernet / Wi-Fi
```

For HTTP/3:

```text
HTTP/3
  ↓
QUIC
  ↓
UDP
  ↓
IP
  ↓
Ethernet / Wi-Fi
```

DNS is involved before the browser can normally connect to the hostname's destination, although DNS itself can use different transport mechanisms such as UDP, TCP, DoH, or DoT depending on the resolver/configuration.

---

# What Happens at Each Networking Layer?

A simplified encapsulation view is:

```text
Application
    ↓
HTTP Request
    ↓
Transport
    ↓
TCP Segment / QUIC Packet
    ↓
Internet
    ↓
IP Packet
    ↓
Link
    ↓
Ethernet/Wi-Fi Frame
    ↓
Bits
```

At the receiving side, the process is reversed:

```text
Bits
 ↓
Frame
 ↓
IP Packet
 ↓
Transport Data
 ↓
HTTP Data
 ↓
Browser
```

This is called **encapsulation and decapsulation**.

---

# Important Interview Nuance

A very common simplified answer is:

```text
URL
 ↓
DNS
 ↓
TCP
 ↓
TLS
 ↓
HTTP
 ↓
Server
 ↓
Response
 ↓
Rendering
```

This is useful and usually acceptable as a high-level explanation.

However, it is **not universally true for every HTTPS request**.

Modern browsers can use:

```text
HTTP/3
  ↓
QUIC
  ↓
UDP
```

instead of:

```text
HTTP/2
  ↓
TLS
  ↓
TCP
```

Therefore:

> **TCP is not mandatory for every HTTPS connection.**

Also, DNS resolution may be avoided through caching, and redirects may cause additional HTTP requests before the final resource is reached.

# Redirect Example

Suppose you enter:

```text
http://example.com
```

The server may respond:

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/
```

The browser then makes another request:

```text
HTTP URL
   ↓
301 Redirect
   ↓
HTTPS URL
   ↓
New secure request
```

So the actual process can involve multiple HTTP requests rather than exactly one request/response pair.

---

# Cookies and Sessions

The browser may also send cookies with a request:

```http
Cookie: session_id=abc123
```

The server can use this information to identify an existing session.

For example:

```text
Browser
   │
   │ Cookie
   ↓
Server
   │
   └── Identify session/user
```

Cookies can therefore affect what content the server returns.

---

# Cache Can Change the Flow

Not every resource necessarily requires a complete trip to the origin server.

The browser may use:

* Browser cache
* HTTP cache
* Service Worker cache
* CDN cache
* Proxy cache

For example:

```text
Browser
   ↓
Cache
   ├── Hit → Use cached resource
   │
   └── Miss → Network request
```

Therefore, the real-world process can be significantly more optimized than the simplified textbook flow.

# Common Interview Mistakes

### ❌ Mistake 1: Saying DNS downloads the webpage

DNS primarily resolves names to addresses.

```text
DNS → Name resolution
HTTP → Resource transfer
```

---

### ❌ Mistake 2: Saying HTTPS always means TCP

Not necessarily.

HTTP/1.1 and HTTP/2 commonly use TCP, while HTTP/3 uses QUIC over UDP.

---

### ❌ Mistake 3: Saying TLS happens before TCP

For traditional TCP-based HTTPS:

```text
TCP connection
      ↓
TLS handshake
      ↓
Encrypted HTTP
```

TLS runs over the established TCP connection.

HTTP/3 is different because QUIC integrates TLS into its connection establishment.

---

### ❌ Mistake 4: Saying the browser receives only HTML

A webpage can require many resources:

```text
HTML
CSS
JavaScript
Images
Fonts
API data
Videos
```

---

### ❌ Mistake 5: Saying the server is always a single machine

Modern applications may involve:

```text
CDN
 ↓
Load Balancer
 ↓
Web Servers
 ↓
Application Servers
 ↓
Cache
 ↓
Database
 ↓
Other Services
```

---

### ❌ Mistake 6: Saying rendering means only HTML → screen

Modern rendering involves several stages:

```text
HTML → DOM
CSS → CSSOM
       ↓
Rendering information
       ↓
Layout
       ↓
Paint
       ↓
Compositing
       ↓
Display
```

JavaScript can modify the DOM/styles and trigger additional rendering work.

# Interview Takeaway

When you enter a URL, the browser first **parses the URL**, resolves the hostname using **DNS**, establishes the appropriate network connection, performs **TLS** for HTTPS when applicable, sends an **HTTP request**, and receives an **HTTP response**.

The server may process the request through components such as a **load balancer, web/application server, cache, and database**. The browser then parses the returned HTML and CSS, constructs the **DOM and CSSOM**, performs **layout**, **paint**, and **compositing**, and displays the result.

The most useful interview-level flow to remember is:

```text
URL
 ↓
DNS
 ↓
TCP + TLS        (HTTP/1.1, HTTP/2)
or
QUIC over UDP    (HTTP/3)
 ↓
HTTP Request
 ↓
Server
 ↓
HTTP Response
 ↓
HTML/CSS/JS
 ↓
DOM + CSSOM
 ↓
Layout
 ↓
Paint
 ↓
Display
```

This single question connects several important Computer Networks concepts:

**DNS + IP + TCP/UDP + TLS + HTTP + routing + caching + client/server architecture + browser rendering.**
