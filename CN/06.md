# 6. What is TCP?

**TCP (Transmission Control Protocol)** is a **connection-oriented transport-layer protocol** that provides **reliable, ordered, and error-checked delivery of data between applications** over an IP network.

TCP is one of the most important protocols in the **TCP/IP protocol suite** and operates at the **Transport Layer**.

```text
Application
    ↓
   TCP              ← Transport Layer
    ↓
   IP               ← Internet Layer
    ↓
Ethernet / Wi-Fi    ← Link Layer
```

TCP is commonly used by applications that need reliable delivery, such as:

* HTTP/1.1
* HTTP/2
* SSH
* Many database connections
* File transfer protocols
* Email protocols

---

# Why Do We Need TCP?

The **IP protocol** is responsible for delivering packets between hosts, but IP itself does not provide reliable end-to-end delivery.

IP is generally a **best-effort, connectionless network-layer protocol**.

IP does not guarantee that packets will:

* Arrive at the destination
* Arrive in the correct order
* Arrive only once
* Be retransmitted if lost
* Be delivered without corruption being detected at the transport layer
* Match application-level delivery requirements

For example, suppose an application sends:

```text
Packet 1
Packet 2
Packet 3
Packet 4
```

The network could potentially deliver:

```text
Packet 1
Packet 2
Packet 4
Packet 3
```

or:

```text
Packet 1
Packet 2
Packet 4
```

where Packet 3 was lost.

TCP provides mechanisms that allow the communicating endpoints to detect and recover from many such problems.

### TCP's basic idea

```text
IP:
"Try to deliver these packets."

TCP:
"I will provide the application with a reliable,
ordered byte stream and handle loss, reordering,
flow control, and congestion control."
```

This distinction is extremely important:

> **IP provides best-effort packet delivery, while TCP provides reliable transport to applications.**

---

# How TCP Works

A simplified TCP communication looks like:

```text
Client                          Server
  │                               │
  │──── SYN ─────────────────────→│
  │←─── SYN + ACK ────────────────│
  │──── ACK ─────────────────────→│
  │                               │
  │──── Data ────────────────────→│
  │←─── ACK ──────────────────────│
  │                               │
```

The first three messages establish the TCP connection.

This process is called the:

## TCP Three-Way Handshake

```text
Client                              Server
  │                                   │
  │ ----------- SYN ----------------> │
  │                                   │
  │ <-------- SYN + ACK ------------- │
  │                                   │
  │ ----------- ACK ----------------> │
  │                                   │
  │       Connection established      │
```

After the handshake, application data can be exchanged.

---

# 1. Connection-Oriented

TCP is **connection-oriented**.

This means TCP establishes a logical connection between the two endpoints before normal application data is exchanged.

For example:

```text
Client
  │
  │ TCP Handshake
  ↓
Server
  │
  │ Connection established
  ↓
Data transfer
```

The connection is identified using information such as:

* Source IP address
* Source port
* Destination IP address
* Destination port

This combination is commonly called the **TCP connection's 4-tuple**.

```text
Source IP
Source Port
Destination IP
Destination Port
```

### Example

Suppose a browser connects to:

```text
Client:
IP   = 192.168.1.10
Port = 51520

Server:
IP   = 93.x.x.x
Port = 443
```

The connection can conceptually be identified as:

```text
192.168.1.10:51520
        ↕
93.x.x.x:443
```

The server can therefore distinguish different TCP connections even when many clients connect to the same server port.

---

# 2. Reliable Delivery

One of TCP's most important features is **reliable delivery**.

TCP uses mechanisms such as:

* Sequence numbers
* Acknowledgments
* Retransmissions
* Timers
* Checksums

to provide reliable delivery of the byte stream.

Suppose the sender has data represented conceptually as:

```text
1 → 2 → 3 → 4
```

If data corresponding to `3` is lost:

```text
Sender                         Receiver

Packet 1  -------------------->
Packet 2  -------------------->
Packet 3  ----X  (lost)
Packet 4  -------------------->

          Receiver detects
          missing data
```

TCP can detect that data is missing and arrange for it to be retransmitted.

A simplified representation:

```text
Sender:
1 → 2 → 3 → 4

Receiver:
1 → 2 → 4
        ↑
   Missing data

        ↓
Retransmission
        ↓

3 arrives
```

### Important nuance

TCP reliability does **not** mean that the physical network can never lose packets.

Instead:

> TCP detects and recovers from many network delivery problems so that the application sees a reliable ordered byte stream.

---

# 3. Sequence Numbers

TCP assigns sequence numbers to bytes in the stream.

These sequence numbers help TCP:

* Identify data
* Detect missing data
* Detect duplicate data
* Reconstruct the correct order
* Support retransmission

Suppose data arrives approximately like:

```text
Segment A
Segment C
Segment B
```

TCP can use sequence numbers to determine that:

```text
A → B → C
```

is the correct order.

The application receives the ordered stream rather than simply receiving packets in whatever order they happened to arrive.

---

# 4. Acknowledgments

TCP uses **ACKs (acknowledgments)** to communicate received data.

Conceptually:

```text
Sender                     Receiver
  │                           │
  │──── Data ───────────────→ │
  │                           │
  │ ←──── ACK ─────────────── │
  │                           │
```

An acknowledgment indicates what data has been received according to TCP's sequence/acknowledgment numbering rules.

If the sender does not receive the expected acknowledgment within an appropriate period, TCP may retransmit the data.

---

# 5. Retransmission

If TCP determines that data has been lost, it can retransmit it.

A simplified example:

```text
Sender                         Receiver
  │                               │
  │──── Segment 1 ──────────────→ │
  │──── Segment 2 ──────────────→ │
  │──── Segment 3 ────X           │
  │──── Segment 4 ──────────────→ │
  │                               │
  │ ←──── ACK information ─────── │
  │                               │
  │──── Retransmit Segment 3 ───→ │
```

TCP uses mechanisms involving acknowledgments, duplicate acknowledgments, timers, and retransmission algorithms.

The exact retransmission behavior is more sophisticated than simply waiting for one missing packet.

---

# 6. Ordered Delivery

TCP provides **ordered delivery**.

Packets may travel through different paths or experience different delays, so data may arrive out of order.

For example:

```text
Sent:

A → B → C → D
```

could arrive as:

```text
A → C → B → D
```

TCP uses sequence numbers to reconstruct the correct byte-stream order:

```text
A → B → C → D
```

The application therefore does not have to manually reorder TCP segments.

---

# 7. Flow Control

TCP provides **flow control** to prevent a fast sender from overwhelming a slower receiver.

For example:

```text
Fast Sender
     │
     │  Too much data
     ↓
Slow Receiver
```

Without flow control, the receiver could run out of available receive buffer space.

TCP uses a **receive window** to communicate how much data the receiver is currently prepared to accept.

Conceptually:

```text
Receiver
   ↓
"I can currently accept approximately
this much additional data."
   ↓
Sender adjusts transmission accordingly
```

### Example

Suppose:

```text
Sender speed   = 100 MB/s
Receiver can process/store = 20 MB/s
```

TCP flow control helps prevent the sender from continuously sending beyond what the receiver can handle.

### Key distinction

**Flow control protects the receiver.**

---

# 8. Congestion Control

TCP also provides **congestion control**.

Flow control and congestion control are related but different.

### Flow control

Protects the:

```text
Receiver
```

### Congestion control

Protects the:

```text
Network
```

Suppose many devices are sending traffic through a congested router:

```text
Sender A ──┐
Sender B ──┼──→ Congested Router ──→ Destination
Sender C ──┘
```

If senders continuously transmit at maximum speed, congestion can become worse.

TCP therefore adjusts its sending behavior based on signals that indicate network congestion.

Important TCP congestion-control concepts include:

* Congestion window (`cwnd`)
* Slow start
* Congestion avoidance
* Fast retransmit
* Fast recovery

The exact algorithms and behavior can vary across TCP implementations.

### Interview distinction

Remember:

```text
Flow Control
     ↓
Protects receiver

Congestion Control
     ↓
Protects network
```

---

# TCP Is a Byte-Stream Protocol

This is one of the **most important TCP interview points**.

TCP provides a:

> **Reliable, ordered byte stream**

TCP does **not** preserve application message boundaries.

Suppose an application performs:

```text
send("Hello")
send("World")
```

The receiver does not necessarily receive:

```text
"Hello"
"World"
```

as two separate messages.

It could conceptually observe the stream as:

```text
"HelloWorld"
```

or receive it through multiple reads, such as:

```text
"Hel"
"loWo"
"rld"
```

The exact segmentation of reads depends on buffering, timing, implementation, and the application API.

### Therefore

If an application needs explicit message boundaries, it must implement a protocol above TCP.

For example, it might use:

```text
Length prefix
+
Payload
```

such as:

```text
[5][Hello]
[5][World]
```

or use delimiters:

```text
Hello\n
World\n
```

The application protocol defines how to interpret the stream.

---

# TCP Segment vs Application Message

This distinction is important:

```text
Application
   ↓
Byte Stream
   ↓
TCP
   ↓
TCP Segments
   ↓
IP Packets
```

TCP may split application data across multiple segments or combine data from multiple application writes.

Therefore:

> **One application write does not necessarily equal one TCP segment, and one TCP segment does not necessarily represent one application message.**

---

# TCP Header

TCP adds a header to transport data.

A simplified TCP segment looks like:

```text
┌──────────────────────────────────┐
│          TCP Header              │
├──────────────────────────────────┤
│                                  │
│       Application Data           │
│                                  │
└──────────────────────────────────┘
```

Important TCP header fields include:

| Field                 | Purpose                                   |
| --------------------- | ----------------------------------------- |
| Source Port           | Identifies sending application endpoint   |
| Destination Port      | Identifies receiving application endpoint |
| Sequence Number       | Tracks position of data in byte stream    |
| Acknowledgment Number | Indicates received data position          |
| Flags                 | Control connection/state behavior         |
| Window                | Advertises receive-window information     |
| Checksum              | Detects corruption in the TCP segment     |
| Options               | Provides additional TCP capabilities      |

Common TCP flags include:

* `SYN`
* `ACK`
* `FIN`
* `RST`
* `PSH`
* `URG`

For example:

```text
SYN → Start connection
ACK → Acknowledge
FIN → Gracefully close connection
RST → Reset connection
```

---

# TCP Connection Termination

TCP also needs to close a connection.

A simplified graceful termination often involves a **four-segment exchange** because each direction of the byte stream is closed independently.

Conceptually:

```text
Client                         Server
  │                              │
  │──────── FIN ───────────────→ │
  │←─────── ACK ──────────────── │
  │                              │
  │←─────── FIN ──────────────── │
  │──────── ACK ───────────────→ │
  │                              │
  │       Connection closed      │
```

The exact sequence can vary depending on which endpoint closes first and the TCP state.

---

# TCP vs UDP

TCP and UDP are both transport-layer protocols, but they provide different services.

| Feature            | TCP                                              | UDP                                          |
| ------------------ | ------------------------------------------------ | -------------------------------------------- |
| Connection         | Connection-oriented                              | Connectionless                               |
| Reliability        | Built-in                                         | No TCP-style built-in reliability            |
| Ordering           | Yes                                              | No guarantee                                 |
| Retransmission     | Yes                                              | No built-in retransmission                   |
| Flow control       | Yes                                              | No TCP-style flow control                    |
| Congestion control | Yes                                              | No TCP-style congestion control              |
| Data model         | Byte stream                                      | Datagrams                                    |
| Handshake          | TCP handshake                                    | No TCP-style connection handshake            |
| Overhead           | Generally higher                                 | Generally lower                              |
| Typical uses       | HTTP/1.1, HTTP/2, SSH, many database connections | DNS, real-time applications, QUIC            |
| Message boundaries | Not preserved                                    | Each UDP datagram is a separate message unit |

### Important nuance

It is an oversimplification to say:

> "UDP is faster than TCP."

UDP has less built-in transport functionality and lower protocol overhead, but actual performance depends on the application, network, congestion, latency, packet loss, and the protocol built on top of UDP.

For example, **QUIC uses UDP** but implements substantial transport functionality above UDP.

# Where TCP Fits in the Network Stack

TCP belongs to the **Transport Layer**.

```text
┌─────────────────────────────┐
│       Application           │
│ HTTP, SSH, DNS, etc.        │
├─────────────────────────────┤
│       TCP / UDP             │ ← Transport
├─────────────────────────────┤
│            IP               │ ← Internet
├─────────────────────────────┤
│     Ethernet / Wi-Fi        │ ← Link
├─────────────────────────────┤
│        Physical Medium      │
└─────────────────────────────┘
```

For example:

```text
HTTP/1.1
   ↓
TCP
   ↓
IP
   ↓
Ethernet/Wi-Fi
```

# TCP and Ports

TCP uses **port numbers** to identify application endpoints.

For example:

```text
Server:
IP   = 93.x.x.x
Port = 443
```

A browser might use:

```text
Client:
IP   = 192.168.1.10
Port = 51520
```

The TCP connection can therefore be represented as:

```text
192.168.1.10:51520
        │
        │ TCP
        ↓
93.x.x.x:443
```

The port helps the operating system deliver received TCP data to the appropriate application/socket.

### Important distinction

```text
IP address
   ↓
Identifies network-layer destination

Port number
   ↓
Identifies transport-layer application endpoint
```

This is why a single server can host many services.

For example:

```text
example.com:80   → HTTP
example.com:443  → HTTPS
example.com:22   → SSH
```

# Example: Opening an HTTPS Website

Suppose you open:

```text
https://example.com
```

A simplified TCP-based flow could be:

```text
Browser
   ↓
DNS resolution
   ↓
Server IP
   ↓
TCP SYN
   ↓
SYN + ACK
   ↓
ACK
   ↓
TCP connection established
   ↓
TLS handshake
   ↓
Secure connection
   ↓
HTTP request
   ↓
HTTP response
```

The TCP layer is responsible for providing the reliable ordered transport used by the application.

# TCP Reliability vs IP Best Effort

A useful way to understand TCP is to compare it with IP.

```text
IP:
"Here is a packet. I will try to forward it."

TCP:
"Here is a reliable ordered byte stream.
I will use acknowledgments, sequence numbers,
retransmission, flow control, and congestion control."
```

Therefore:

```text
Application
     ↓
   TCP
     ↓
    IP
```

TCP builds a richer transport service **on top of IP**.

TCP provides several major features:

```text
TCP
 │
 ├── Connection establishment
 │
 ├── Reliable delivery
 │
 ├── Ordered byte stream
 │
 ├── Error detection
 │
 ├── Retransmission
 │
 ├── Flow control
 │
```

These features make TCP suitable for applications where correctness and reliable delivery are more important than preserving individual packet/message boundaries.

# Common Interview Mistakes

### ❌ Mistake 1: Saying TCP guarantees packet delivery

TCP does not make the underlying network lossless.

A better statement is:

> TCP provides reliable delivery semantics to applications by detecting and recovering from many transmission problems.

---

### ❌ Mistake 2: Saying TCP sends messages

TCP provides a **byte stream**, not message-oriented communication.

```text
TCP → Byte stream
UDP → Datagram/message-oriented transport
```

---

### ❌ Mistake 3: Saying TCP preserves `send()` boundaries

It does not.

```text
send("Hello")
send("World")
```

does not guarantee:

```text
receive("Hello")
receive("World")
```

---

### ❌ Mistake 4: Confusing flow control and congestion control

Remember:

```text
Flow control
→ Protects receiver

Congestion control
→ Protects network
```

---

### ❌ Mistake 5: Saying TCP and IP are the same thing

They operate at different layers:

```text
TCP → Transport Layer
IP  → Internet/Network Layer
```

---

### ❌ Mistake 6: Saying TCP is always used for HTTPS

Modern HTTPS can use HTTP/3 over QUIC:

```text
HTTP/3
  ↓
QUIC
  ↓
UDP
```

HTTP/1.1 and HTTP/2 commonly use TCP.

# Interview Takeaway

**TCP (Transmission Control Protocol)** is a **connection-oriented transport-layer protocol** that provides applications with a **reliable, ordered byte stream** over IP.

It achieves this using mechanisms such as:

* **Sequence numbers**
* **Acknowledgments**
* **Retransmissions**
* **Checksums**
* **Timers**
* **Flow control**
* **Congestion control**

TCP first establishes a connection using the **three-way handshake**, transfers data reliably and in order, and eventually closes the connection.

The most important interview distinction is:

```text
IP
 ↓
Best-effort packet delivery

TCP
 ↓
Reliable + ordered byte-stream transport
```

And remember:

```text
HTTP/1.1, HTTP/2
        ↓
       TCP

HTTP/3
   ↓
  QUIC
   ↓
  UDP
```

So, the shortest accurate definition is:

> **TCP is a connection-oriented transport-layer protocol that provides reliable, ordered, error-checked byte-stream delivery between application endpoints over an IP network.**
