# 7. What is UDP?

**UDP (User Datagram Protocol)** is a **connectionless transport-layer protocol** that sends independent **datagrams** between applications with minimal protocol overhead.

Unlike TCP, UDP does not inherently guarantee that data will:

* Be delivered
* Arrive in order
* Arrive exactly once
* Be retransmitted if lost
* Be protected by TCP-style flow control
* Be protected by TCP-style congestion control

UDP provides a lightweight transport mechanism and leaves many reliability decisions to the application or a higher-level protocol.

```text
Application
     ↓
    UDP
     ↓
    IP
     ↓
Ethernet / Wi-Fi
     ↓
   Network
```

UDP is also part of the **TCP/IP protocol suite**.

---

# Why Do We Need UDP?

TCP provides many useful features:

```text
TCP
 ├── Connection establishment
 ├── Reliability
 ├── Ordering
 ├── Retransmission
 ├── Flow control
 └── Congestion control
```

But not every application needs all of these mechanisms.

Sometimes an application wants:

* Low protocol overhead
* Simple datagram communication
* Application-controlled reliability
* Timely delivery of newer data
* A transport primitive suitable for building another protocol on top

UDP provides this simpler foundation.

For example, consider a real-time game.

If a player's position is:

```text
Player position = (100, 200)
```

and that update is lost, the application may prefer to receive the **new position**:

```text
Player position = (105, 205)
```

rather than wait for the old update to be retransmitted.

For some real-time workloads:

```text
Old data arriving late
        ↓
May be less useful
        ↓
New data is more important
```

UDP can be useful in such designs because it does not automatically retransmit old datagrams.

---

# How UDP Works

A simplified UDP communication looks like:

```text
Application
    ↓
UDP Datagram
    ↓
IP Packet
    ↓
Network
    ↓
IP
    ↓
UDP
    ↓
Receiving Application
```

For example:

```text
Sender Application
       ↓
UDP
       ↓
IP
       ↓
Network
       ↓
IP
       ↓
UDP
       ↓
Receiver Application
```

There is **no TCP-style three-way handshake** before sending UDP datagrams.

The sender can generally construct a UDP datagram and send it immediately.

---

# UDP Datagram Structure

A UDP datagram contains a relatively small header followed by application data.

```text
┌──────────────────────────────────┐
│          UDP Header              │
├──────────────────────────────────┤
│                                  │
│       Application Data           │
│                                  │
└──────────────────────────────────┘
```

The UDP header contains four primary fields:

| Field            | Purpose                                       |
| ---------------- | --------------------------------------------- |
| Source Port      | Identifies the sending application endpoint   |
| Destination Port | Identifies the receiving application endpoint |
| Length           | Length of the UDP datagram                    |
| Checksum         | Error-detection information                   |

This simple structure contributes to UDP's low protocol overhead.

---

# Important UDP Features

## 1. Connectionless

UDP is **connectionless**.

It does not establish a TCP-style connection before sending each datagram.

Conceptually:

```text
Application
     ↓
UDP Datagram
     ↓
Network
```

There is no:

```text
SYN
 ↓
SYN + ACK
 ↓
ACK
```

sequence like TCP uses.

### Example

A DNS client can send a DNS query:

```text
Client
  │
  │──── DNS Query ─────────→
  │
  │←──── DNS Response ──────
```

There is no TCP-style connection establishment required for the usual UDP-based DNS exchange.

---

# 2. Low Overhead

UDP has a small and simple header and does not provide TCP's connection-management machinery.

UDP does not inherently provide:

* TCP connection establishment
* TCP acknowledgments
* TCP retransmission
* TCP-style flow control
* TCP-style congestion control

Therefore, the protocol itself is relatively lightweight.

### Simplified comparison

```text
TCP
 │
 ├── Connection management
 ├── Sequence numbers
 ├── Acknowledgments
 ├── Retransmissions
 ├── Flow control
 └── Congestion control

UDP
 │
 ├── Source port
 ├── Destination port
 ├── Length
 └── Checksum
```

### Important nuance

Low overhead does **not** automatically mean an application will always be faster.

Actual performance depends on:

* Network conditions
* Application design
* Packet size
* Processing overhead
* Congestion
* Latency
* Loss rate
* Protocol implemented above UDP

---

# 3. No Guaranteed Delivery

UDP itself does not provide reliable delivery.

A datagram can potentially be:

```text
Lost
Duplicated
Delayed
Delivered out of order
```

For example:

```text
Sender                       Receiver

Datagram 1 ---------------->
Datagram 2 --------X         ← Lost
Datagram 3 ---------------->

Receiver:
Datagram 1
Datagram 3
```

UDP itself does not automatically say:

> "Datagram 2 was lost, so I will retransmit it."

If retransmission is required, the application or a higher-level protocol must implement it.

---

# 4. No Guaranteed Ordering

Suppose the sender transmits:

```text
Datagram 1
Datagram 2
Datagram 3
```

The network may deliver them as:

```text
Datagram 1
Datagram 3
Datagram 2
```

UDP does not reorder them.

```text
Sent:
1 → 2 → 3

Received:
1 → 3 → 2
```

If the application requires ordering, it must implement an ordering mechanism itself or use a higher-level protocol that provides one.

---

# 5. No Built-In Retransmission

Suppose:

```text
Datagram 1
Datagram 2
Datagram 3
```

are sent.

If Datagram 2 is lost:

```text
Datagram 1 → Receiver
Datagram 2 → X
Datagram 3 → Receiver
```

UDP does not automatically retransmit Datagram 2.

An application could implement:

```text
Sequence Number
      ↓
Acknowledgment
      ↓
Timeout
      ↓
Retransmission
```

if its requirements demand reliability.

This is an important reason why UDP can serve as a building block for higher-level protocols.

---

# 6. Preserves Message Boundaries

This is one of the **most important differences between TCP and UDP**.

TCP provides:

> A reliable ordered **byte stream**

UDP provides:

> Independent **datagrams**

Suppose an application performs:

```text
send(Datagram A)
send(Datagram B)
send(Datagram C)
```

UDP preserves the datagram boundaries at the UDP API/protocol level.

Conceptually:

```text
Application
   │
   ├── Datagram A ──→ UDP
   ├── Datagram B ──→ UDP
   └── Datagram C ──→ UDP
```

The receiver receives datagrams rather than an undifferentiated byte stream.

### TCP vs UDP

```text
TCP:

"Hello"
"World"

        ↓

Byte Stream:

"HelloWorld"
```

Whereas UDP maintains separate datagrams:

```text
UDP:

"Hello"
"World"

        ↓

Datagram 1 = "Hello"
Datagram 2 = "World"
```

### Important nuance

UDP preserves **datagram boundaries**, but that does not mean the network guarantees successful delivery.

A datagram can still be:

```text
Lost
Delayed
Duplicated
Delivered out of order
```

Also, applications should avoid assuming that arbitrarily large UDP payloads will traverse the Internet efficiently; IP fragmentation and path MTU limitations matter.

---

# 7. Uses Port Numbers

UDP uses **source and destination port numbers** to deliver datagrams to the appropriate application endpoint.

For example:

```text
Client
IP   = 192.168.1.10
Port = 50000

        UDP

Server
IP   = 93.x.x.x
Port = 53
```

The destination port `53` is commonly associated with DNS.

Conceptually:

```text
192.168.1.10:50000
        │
        │ UDP
        ↓
93.x.x.x:53
```

The operating system uses the destination port to determine which socket/application should receive the datagram.

---

# Example: UDP Datagram Loss

Suppose an application sends:

```text
Datagram 1
Datagram 2
Datagram 3
```

The network could deliver:

```text
Datagram 1
Datagram 3
```

with Datagram 2 lost.

UDP itself does not automatically perform:

```text
Detect loss
    ↓
Request retransmission
    ↓
Retransmit Datagram 2
```

If the application needs this behavior, it can implement its own reliability mechanism.

For example:

```text
Application
   ↓
Sequence Number
   ↓
ACK
   ↓
Timeout
   ↓
Retransmission
```

At that point, the application is building additional transport-like behavior on top of UDP.

---

# UDP and Error Detection

UDP includes a **checksum** for detecting certain transmission errors.

This is important:

> A UDP checksum helps detect corrupted data; it does not make UDP reliable.

So:

```text
Checksum
   ↓
Detect corruption
```

is different from:

```text
Retransmission
   ↓
Recover lost data
```

UDP does not automatically provide TCP-style recovery for lost or reordered datagrams.

---

# Where Is UDP Useful?

UDP is useful when:

* Low overhead is desirable
* Low latency is important
* The application wants control over reliability
* Individual datagrams are meaningful
* Old data may become useless quickly
* A higher-level protocol will provide additional functionality

Common examples include:

* DNS queries in common configurations
* Real-time audio/video applications
* Online gaming
* Network discovery
* Some telemetry systems
* QUIC

---

# 1. DNS

DNS commonly uses UDP for ordinary queries because DNS requests are often small and benefit from simple request/response communication.

Conceptually:

```text
Client
  │
  │ UDP DNS Query
  ↓
DNS Server
  │
  │ UDP DNS Response
  ↓
Client
```

However, DNS is not exclusively UDP.

DNS can also use TCP in situations such as:

* Certain large responses
* Zone transfers
* Other cases defined by DNS behavior/protocol requirements

Modern DNS can also use encrypted transports such as **DNS-over-TLS (DoT)** and **DNS-over-HTTPS (DoH)**, which changes the underlying transport/application arrangement.

---

# 2. Real-Time Audio/Video

Real-time communication often cares about **timeliness**.

For example, during a live voice call:

```text
Voice Frame 100
Voice Frame 101
Voice Frame 102
Voice Frame 103
```

If Frame 101 is delayed significantly, retransmitting it later may be less useful because the conversation has already moved forward.

The application may prefer:

```text
Use newer data
       ↓
Continue playback
```

rather than:

```text
Stop everything
       ↓
Wait for old packet
       ↓
Resume later
```

This is one reason datagram-based transport can be useful for real-time applications.

---

# 3. Online Gaming

Games frequently exchange rapidly changing state.

For example:

```text
Player position
Player direction
Velocity
Game state
```

Suppose:

```text
Position Update 1
Position Update 2
Position Update 3
Position Update 4
```

If Update 2 is lost, Update 4 may already contain newer information.

Retransmitting the old update may not always be useful.

The game can decide what information is important and how much reliability is necessary.

---

# 4. Network Discovery

Some discovery protocols use UDP because a device may need to send a small message without first establishing a connection.

Conceptually:

```text
Device A
   │
   │ UDP discovery message
   ↓
Local Network
   ↓
Devices listening
```

The lightweight datagram model is useful for this type of communication.

---

# 5. QUIC

One of the most important modern examples is **QUIC**.

QUIC uses UDP as its underlying network transport:

```text
HTTP/3
   ↓
QUIC
   ↓
UDP
   ↓
IP
```

However, QUIC should **not** be thought of as "plain UDP."

QUIC implements substantial transport functionality above UDP, including features such as:

* Reliable delivery
* Stream multiplexing
* Connection management
* Congestion control
* TLS 1.3 integration

Therefore:

```text
UDP
 ↓
Simple datagram transport

QUIC
 ↓
Advanced transport protocol built over UDP
```

This is an important interview distinction.

---

# Application-Controlled Reliability

One of UDP's major advantages is that applications can decide how much reliability they actually need.

For example, an application might use:

```text
Sequence Number
+
Timestamp
+
Selective Retransmission
```

instead of implementing exactly the same behavior as TCP.

Another application might decide:

```text
No retransmission
No ordering
Just send current state
```

This flexibility is useful for specialized protocols.

---

# UDP vs TCP

| Feature             | TCP                                               | UDP                                              |
| ------------------- | ------------------------------------------------- | ------------------------------------------------ |
| Connection          | Connection-oriented                               | Connectionless                                   |
| Reliability         | Built-in                                          | Not built-in                                     |
| Ordering            | Guaranteed byte-stream order                      | Not guaranteed                                   |
| Retransmission      | Built-in                                          | Not built-in                                     |
| Flow control        | Yes                                               | No TCP-style flow control                        |
| Congestion control  | Yes                                               | No TCP-style congestion control                  |
| Data model          | Byte stream                                       | Datagrams                                        |
| Message boundaries  | Not preserved                                     | Preserved                                        |
| Header overhead     | Higher                                            | Lower                                            |
| Handshake           | TCP three-way handshake                           | No TCP-style handshake                           |
| Delivery guarantee  | Reliable byte stream                              | Best-effort datagrams                            |
| Typical uses        | HTTP/1.1, HTTP/2, SSH                             | DNS, real-time applications, QUIC                |
| Application control | Less transport behavior is application-controlled | More behavior can be designed by the application |

---

# TCP vs UDP Data Model

This is worth remembering visually.

### TCP

```text
Application
     ↓
Byte Stream
     ↓
TCP
     ↓
Segments
```

TCP does not preserve application message boundaries.

### UDP

```text
Application
     ↓
Datagram 1
Datagram 2
Datagram 3
     ↓
UDP
     ↓
Datagrams
```

UDP preserves datagram boundaries at the transport API/protocol level.

---

# TCP vs UDP Example

Suppose an application sends:

```text
Message A = "HELLO"
Message B = "WORLD"
```

### TCP

The receiver sees a byte stream:

```text
HELLOWORLD
```

It might read:

```text
HEL
LOWO
RLD
```

The application must define how to reconstruct messages.

### UDP

The receiver gets separate datagrams:

```text
Datagram 1 → "HELLO"
Datagram 2 → "WORLD"
```

But Datagram 2 might be lost:

```text
Datagram 1 → "HELLO"
Datagram 2 → Lost
```

UDP does not automatically recover it.

# Where UDP Fits in the Network Stack

UDP is a **Transport Layer** protocol.

```text
┌───────────────────────────┐
│       Application         │
│ DNS / QUIC / Games / etc. │
├───────────────────────────┤
│           UDP             │ ← Transport Layer
├───────────────────────────┤
│            IP             │ ← Internet Layer
├───────────────────────────┤
│      Ethernet / Wi-Fi     │ ← Link Layer
└───────────────────────────┘
```

For a traditional UDP application:

```text
Application
    ↓
UDP
    ↓
IP
    ↓
Ethernet / Wi-Fi
```

For HTTP/3:

```text
HTTP/3
  ↓
QUIC
  ↓
UDP
  ↓
IP
  ↓
Ethernet / Wi-Fi
```

# Important Interview Point

## Don't say:

> "UDP is always faster than TCP."

This is an oversimplification.

UDP has:

* Less built-in protocol machinery
* No TCP-style handshake
* No TCP-style retransmission
* No TCP-style flow control

But actual application performance depends on:

* Network conditions
* Packet loss
* Latency
* Application design
* Protocol implementation
* Workload
* Packet size
* Congestion
* Reliability requirements

For example, QUIC uses UDP but implements sophisticated transport features above it.

So a better statement is:

> **UDP has lower protocol overhead and provides a simpler datagram transport, but it is not automatically faster in every application or network condition.**

---

# Common Interview Mistakes

### ❌ Mistake 1: Saying UDP is unreliable in every sense

A better statement is:

> UDP does not provide built-in reliable delivery semantics like TCP.

Applications can implement reliability above UDP.

---

### ❌ Mistake 2: Saying UDP has no error detection

UDP has a checksum for detecting certain corruption.

```text
UDP checksum
    ↓
Error detection
```

But:

```text
Error detection ≠ Reliable delivery
```

---

### ❌ Mistake 3: Saying UDP guarantees packet delivery

It does not.

A UDP datagram may be:

```text
Lost
Delayed
Duplicated
Out of order
```

---

### ❌ Mistake 4: Saying UDP has no ports

UDP absolutely uses:

```text
Source Port
Destination Port
```

Ports help the OS deliver datagrams to the appropriate application endpoint.

---

### ❌ Mistake 5: Saying QUIC is UDP

More accurately:

```text
QUIC
 ↓
Uses UDP as its underlying transport
```

QUIC is a higher-level transport protocol built over UDP.

---

### ❌ Mistake 6: Saying UDP always has lower latency

UDP removes TCP's built-in connection/retransmission machinery, but actual latency depends on the complete system.

A badly designed UDP application can still be slow.

---

### ❌ Mistake 7: Saying UDP does not preserve boundaries

It does.

```text
TCP → Byte stream
UDP → Datagram boundaries
```

This is one of the fundamental differences between the two.

# Interview Takeaway

**UDP (User Datagram Protocol)** is a **connectionless transport-layer protocol** that provides lightweight **datagram delivery** without TCP's built-in guarantees of reliability, ordering, or retransmission.

Its key characteristics are:

* **Connectionless**
* **Low overhead**
* **Datagram-based**
* **Preserves message boundaries**
* **Uses source and destination ports**
* **No built-in retransmission**
* **No TCP-style flow control**
* **No TCP-style congestion control**

UDP is useful for applications where low overhead, timely delivery, or application-controlled transport behavior is important, including **DNS, real-time applications, network discovery, and protocols such as QUIC**.

The most important comparison to remember is:

```text
TCP
 ↓
Reliable + Ordered Byte Stream

UDP
 ↓
Lightweight + Connectionless Datagrams
```

And for modern web networking:

```text
HTTP/1.1 / HTTP/2
        ↓
       TCP

HTTP/3
   ↓
  QUIC
   ↓
  UDP
```

So the shortest accurate definition is:

> **UDP is a connectionless transport-layer protocol that provides lightweight, datagram-based communication without built-in guarantees of reliable delivery, ordering, or retransmission.**
