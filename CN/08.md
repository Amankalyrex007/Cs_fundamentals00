# Q8. TCP vs UDP?

**TCP (Transmission Control Protocol)** and **UDP (User Datagram Protocol)** are both **transport-layer protocols** used to provide communication between applications over an IP network.

The major difference is:

> **TCP focuses on reliable, ordered, connection-oriented byte-stream communication, while UDP focuses on lightweight, connectionless datagram communication without built-in delivery and ordering guarantees.**

A simple way to visualize the difference:

```text
                    TCP
Sender                                      Receiver
  │                                            │
  ├── Packet 1 ──────────────────────────────>│
  ├── Packet 2 ──────────────────────────────>│
  ├── Packet 3 ────────X  (lost)              │
  ├── Packet 4 ──────────────────────────────>│
  │                                            │
  │<──────────── Acknowledgments ─────────────│
  │                                            │
  └── Retransmit Packet 3 ──────────────────>│

TCP detects the loss and retransmits the missing data.
The application receives the byte stream in the correct order.
```

With UDP:

```text
                    UDP
Sender                                      Receiver
  │                                            │
  ├── Datagram 1 ────────────────────────────>│
  ├── Datagram 2 ────────────────────────────>│
  ├── Datagram 3 ────────X  (lost)            │
  └── Datagram 4 ────────────────────────────>│

UDP itself does not retransmit Datagram 3.
```

## TCP vs UDP — Key Differences

| Feature                | TCP                                                  | UDP                                                 |
| ---------------------- | ---------------------------------------------------- | --------------------------------------------------- |
| **Connection**         | Connection-oriented                                  | Connectionless                                      |
| **Reliability**        | Reliable delivery                                    | Best-effort delivery                                |
| **Ordering**           | Guarantees ordered byte-stream delivery              | No ordering guarantee                               |
| **Retransmission**     | Yes                                                  | No built-in retransmission                          |
| **Acknowledgments**    | Yes                                                  | No TCP-style acknowledgments                        |
| **Flow control**       | Yes                                                  | No TCP-style flow control                           |
| **Congestion control** | Yes                                                  | No TCP-style congestion control                     |
| **Handshake**          | Three-way handshake                                  | No TCP-style handshake                              |
| **Data type**          | Byte stream                                          | Independent datagrams                               |
| **Message boundaries** | Not preserved                                        | Preserved                                           |
| **Overhead**           | Higher                                               | Lower                                               |
| **Typical use**        | Web, file transfer, email, many database connections | DNS, real-time media, gaming, QUIC                  |
| **Loss handling**      | Built into TCP                                       | Usually handled by application/protocol if required |

> **Important:** “UDP has no reliability” means UDP itself does not provide TCP-like reliable delivery semantics. An application or higher-level protocol can build reliability on top of UDP.

# 1. Connection-Oriented vs Connectionless

### TCP — Connection-Oriented

Before transferring application data, TCP establishes a connection using a **three-way handshake**.

```text
Client                                  Server
  │                                       │
  │──────────── SYN ─────────────────────>│
  │                                       │
  │<────────── SYN + ACK ─────────────────│
  │                                       │
  │──────────── ACK ─────────────────────>│
  │                                       │
  │        Connection established         │
```

After this, application data can be exchanged.

### UDP — Connectionless

UDP does not require a TCP-style connection establishment.

```text
Sender
  │
  ├──────── Datagram 1 ────────> Receiver
  ├──────── Datagram 2 ────────> Receiver
  └──────── Datagram 3 ────────> Receiver
```

The sender can send a datagram without first establishing a connection.

### Example

A DNS client can send a DNS query using UDP:

```text
Client
  │
  │ DNS Query
  │─────────────── UDP ────────────────> DNS Server
  │
  │ DNS Response
  │<────────────── UDP ────────────────
```

There is no TCP-style three-way handshake for this UDP exchange.

# 2. Reliability

### TCP

TCP provides mechanisms to recover from data loss.

It uses:

* Sequence numbers
* Acknowledgments
* Retransmissions
* Timers
* Checksums
* Duplicate detection
* Ordered delivery

For example:

```text
Sender                         Receiver

Packet 1 ────────────────────────> Received
Packet 2 ────────────────────────> Received
Packet 3 ───────────X              Lost
Packet 4 ────────────────────────> Received

             ACKs
              <──────────────────

TCP detects missing data

Packet 3 ────────────────────────> Retransmitted
```

The application ultimately sees the TCP byte stream in the correct order.

### UDP

UDP does not automatically retransmit lost datagrams.

```text
Datagram 1 ─────────────────> Received
Datagram 2 ─────────────────> Received
Datagram 3 ───────X           Lost
Datagram 4 ─────────────────> Received
```

UDP itself does not say:

> “Datagram 3 was lost, so I should resend it.”

If an application requires reliability, it can implement its own mechanism.

For example:

```text
Application
    │
    ├── Sequence Number
    ├── ACK
    ├── Timeout
    └── Retransmission
    │
    ▼
   UDP
```

This is one reason protocols such as **QUIC** can provide reliable transport features while using UDP underneath.

# 3. Ordering

## TCP guarantees ordered byte-stream delivery

Suppose an application sends:

```text
A → B → C → D → E
```

Network conditions may cause segments to arrive at the receiver in a different order.

```text
Network arrival:

B
D
A
C
E
```

TCP uses **sequence numbers** to reconstruct the correct byte stream:

```text
Application receives:

A → B → C → D → E
```

The application does not need to manually reorder TCP data.

---

## UDP does not guarantee ordering

Suppose the sender sends:

```text
Datagram 1
Datagram 2
Datagram 3
Datagram 4
```

The receiver may observe:

```text
Datagram 1
Datagram 3
Datagram 4
Datagram 2
```

or:

```text
Datagram 1
Datagram 3
Datagram 4
```

if Datagram 2 was lost.

If ordering matters, the application must implement the required logic itself.

---

# 4. Retransmission

### TCP

TCP automatically retransmits data when it determines that data was lost.

```text
Packet 1 ───────────────> Receiver
Packet 2 ───────────────> Receiver
Packet 3 ──────X         Lost
Packet 4 ───────────────> Receiver

TCP detects missing data
        ↓
Retransmit Packet 3
        ↓
Packet 3 ───────────────> Receiver
```

The exact loss-detection behavior can involve retransmission timers, duplicate acknowledgments, and other TCP mechanisms.

### UDP

UDP has **no built-in retransmission mechanism**.

```text
Packet 3 ──────X

UDP:
"That datagram was sent; I don't automatically resend it."
```

If retransmission is needed, the application or another protocol layer must provide it.

---

# 5. Acknowledgments

TCP uses acknowledgments to provide feedback about received data.

Conceptually:

```text
Sender                         Receiver

Data ────────────────────────────>
      <──────────────────────── ACK
Data ────────────────────────────>
      <──────────────────────── ACK
```

UDP does not have TCP-style acknowledgments.

```text
Sender                         Receiver

UDP Datagram ────────────────────>
```

The receiver does not automatically send a TCP-style ACK simply because it received a UDP datagram.

However, an application using UDP **can define its own acknowledgment system**.

For example:

```text
Application-level protocol

Sender ───── Data ───────────────> Receiver
Sender <──── ACK ──────────────── Receiver
```

So:

> **UDP does not provide built-in ACKs, but applications can implement their own.**

---

# 6. Flow Control

### TCP

TCP provides **flow control** using mechanisms such as the receiver window.

The purpose is to prevent a fast sender from overwhelming a slower receiver.

```text
Fast Sender
     │
     │ Too much data?
     ▼
Receiver has limited buffer
     │
     ▼
TCP flow control limits sending
```

For example, if the receiver can currently accept only a certain amount of additional data, TCP communicates this through its receive window.

### UDP

UDP does not provide TCP-style flow control.

The application is responsible for deciding how much and how quickly it should send.

> **Flow control protects the receiver.**

---

# 7. Congestion Control

### TCP

TCP includes congestion-control mechanisms designed to respond to network congestion.

Conceptually:

```text
Sender
   │
   ▼
Network
   │
   ├── Low congestion → can increase sending rate
   │
   └── Congestion/loss signals → reduce sending rate
```

TCP uses mechanisms such as:

* Slow start
* Congestion avoidance
* Fast retransmit
* Fast recovery
* Congestion window (`cwnd`)

### UDP

UDP itself does not provide TCP-style congestion control.

An application using UDP may implement its own congestion-control strategy, and higher-level protocols such as **QUIC** do so.

> **Congestion control protects the network.**

### Important distinction

```text
Flow Control
     ↓
Protects the receiver

Congestion Control
     ↓
Responds to network congestion
```

This distinction is frequently asked in interviews.

---

# 8. Data Type: Byte Stream vs Datagram

This is one of the **most important differences** between TCP and UDP.

## TCP → Byte Stream

TCP treats application data as a continuous **ordered byte stream**.

Suppose an application sends:

```text
"HELLO"
"WORLD"
```

TCP does not preserve those application write boundaries.

The receiver might read:

```text
"HELLOWORLD"
```

or:

```text
"HEL"
"LOWO"
"RLD"
```

depending on buffering and how the application reads from the socket.

Therefore:

> **TCP does not preserve application message boundaries.**

If an application needs messages, it must implement framing, such as:

```text
[length][message]
```

or a delimiter-based protocol.

---

## UDP → Independent Datagrams

UDP preserves datagram boundaries.

If the sender sends:

```text
Datagram 1 = "HELLO"
Datagram 2 = "WORLD"
```

the receiver receives those as separate datagrams.

```text
Datagram 1 → "HELLO"
Datagram 2 → "WORLD"
```

If one datagram is lost, UDP does not automatically merge the remaining data into a continuous byte stream.

### Easy memory trick

```text
TCP → Stream
UDP → Datagram
```

# 9. Overhead

TCP has more protocol machinery because it provides:

* Connection establishment
* Sequence numbers
* Acknowledgments
* Retransmissions
* Flow control
* Congestion control
* Connection management

Therefore, TCP generally has **more protocol overhead** than UDP.

UDP has a much smaller transport header and fewer built-in mechanisms.

Simplified view:

```text
TCP
Application
    ↓
TCP
    ├── Sequence numbers
    ├── ACKs
    ├── Window
    ├── Flags
    └── Reliability mechanisms
    ↓
IP
```

Compared with:

```text
UDP
Application
    ↓
UDP
    ├── Source port
    ├── Destination port
    ├── Length
    └── Checksum
    ↓
IP
```

However:

> **Lower protocol overhead does not automatically mean lower application-level latency or higher performance.**

The application requirements and network conditions matter.

# 10. Typical Use Cases

## TCP is commonly used when reliability and ordered delivery matter

Examples:

* Web traffic using HTTP/1.1
* HTTP/2
* File transfer
* Email protocols
* Many database connections
* SSH
* Other applications where losing or reordering bytes would be problematic

Example:

```text
File:
A B C D E F G H

TCP ensures the receiving application gets
the byte stream in the correct order.
```

If a portion is lost, TCP can recover it.

---

## UDP is commonly used when lightweight datagrams and timely delivery matter

Examples:

* DNS
* Real-time audio
* Real-time video
* Online gaming
* Network discovery
* QUIC

For real-time media, an old packet may sometimes be less useful than a newer packet.

For example:

```text
Video frames:

Frame 100
Frame 101
Frame 102
Frame 103
```

If Frame 101 is delayed significantly, waiting for it forever may be worse for an interactive application than continuing with newer data.

The exact behavior depends on the application/protocol.

# TCP Example: File Download

Suppose you download a file:

```text
File
 │
 ├── Block 1
 ├── Block 2
 ├── Block 3
 ├── Block 4
 └── Block 5
```

Imagine Block 3 is lost:

```text
Block 1 ────────────────> ✓
Block 2 ────────────────> ✓
Block 3 ─────X             Lost
Block 4 ────────────────> ✓
Block 5 ────────────────> ✓
```

TCP can detect the missing data and retransmit it:

```text
Block 3 ────────────────> ✓
```

The application can then continue receiving the correct byte stream.

This is useful when **every byte matters**.

---

# UDP Example: Online Game

Consider a multiplayer game sending player-position updates:

```text
Update 1 → Position A
Update 2 → Position B
Update 3 → Position C
Update 4 → Position D
```

Suppose Update 2 is lost:

```text
Update 1 ───────────────> ✓
Update 2 ─────X            Lost
Update 3 ───────────────> ✓
Update 4 ───────────────> ✓
```

A game may prefer receiving the latest position rather than waiting for an old update.

The application can decide how to handle missing or late updates.

> This does **not** mean all games use UDP directly; modern game networking can use UDP-based protocols or other transport designs depending on requirements.

# TCP and UDP Both Use Port Numbers

Both protocols use **port numbers** to identify transport-layer endpoints.

For example:

```text
Client
IP: 192.168.1.10
Port: 53000

        │
        │ TCP
        ▼

Server
IP: 93.184.216.34
Port: 443
```

For UDP:

```text
Client
IP: 192.168.1.10
Port: 53001

        │
        │ UDP
        ▼

DNS Server
Port: 53
```

So:

> **Ports are not exclusive to TCP. Both TCP and UDP use port numbers.**

# Important Modern Example: HTTP/3

A common misconception is:

> “All HTTP uses TCP.”

That is no longer correct.

Common combinations include:

```text
HTTP/1.1 ──> TCP ──> IP
HTTP/2   ──> TCP ──> IP
HTTP/3   ──> QUIC ──> UDP ──> IP
```

**HTTP/3 uses QUIC, and QUIC runs over UDP.**

QUIC provides transport features such as:

* Reliable delivery
* Stream multiplexing
* Congestion control
* Encryption through TLS integration

So UDP can be the underlying transport for a protocol that provides many reliability features above it.

# When Should You Use TCP?

Use TCP when:

* Data must arrive reliably.
* Data must arrive in order.
* Losing data is unacceptable.
* The application benefits from built-in flow control.
* The application benefits from TCP congestion control.
* A continuous byte stream is appropriate.

### Examples

```text
File transfer
     ↓
Every byte matters
     ↓
TCP is commonly appropriate
```

```text
Web application using HTTP/1.1
     ↓
Reliable ordered HTTP data
     ↓
TCP
```

---

# When Should You Use UDP?

Use UDP when:

* You need independent datagrams.
* Lower transport overhead is useful.
* The application wants direct control over reliability/retransmission behavior.
* Some loss or reordering can be tolerated or handled by the application.
* Timeliness is important.

### Examples

```text
Real-time communication
        ↓
Old data may become less useful
        ↓
UDP or a UDP-based protocol can be appropriate
```

Examples include:

* DNS
* Real-time audio/video
* Online gaming
* QUIC

# Common Interview Mistakes

### ❌ Mistake 1: “UDP is always faster than TCP.”

Not necessarily.

Better answer:

> UDP has less built-in protocol overhead, but actual performance depends on network conditions, application behavior, and whether the application needs to implement reliability itself.

---

### ❌ Mistake 2: “UDP has no error detection.”

UDP includes a **checksum** for detecting corruption.

But:

```text
Checksum
   ↓
Detects corruption

Retransmission
   ↓
Recovers lost/corrupted data
```

UDP provides checksum-based error detection but does not provide TCP-style recovery.

---

### ❌ Mistake 3: “TCP sends packets.”

More precise terminology:

* TCP → **segments**
* UDP → **datagrams**
* IP → **packets**
* Ethernet → **frames**

People often use “packet” informally for all of them, but interview answers should use the precise terminology when possible.

---

### ❌ Mistake 4: “UDP has no connection at all.”

UDP is **connectionless** at the transport protocol level, but an application can maintain its own logical session/state.

---

### ❌ Mistake 5: “TCP guarantees that data can never be lost.”

TCP cannot prevent network failures.

Instead, TCP provides mechanisms that allow the receiving application to get a reliable ordered byte stream **when the connection can successfully make progress**.

---

### ❌ Mistake 6: “TCP preserves messages.”

TCP preserves a **byte stream**, not application message boundaries.

```text
Sender:
send("HELLO")
send("WORLD")

Receiver may read:
"HELLOWORLD"

or:
"HEL"
"LOWORLD"
```

Application-level framing is required when message boundaries matter.

---

### ❌ Mistake 7: “UDP is used only when reliability doesn't matter.”

Not necessarily.

Protocols such as **QUIC** use UDP as their underlying transport and implement substantial reliability and congestion-control mechanisms above UDP.


# One-Line Interview Answer

> **TCP provides reliable, ordered, connection-oriented byte-stream communication using mechanisms such as acknowledgments, retransmission, flow control, and congestion control, while UDP provides lightweight, connectionless datagram communication without built-in delivery, ordering, or retransmission guarantees.**

### Interview takeaway

If an interviewer asks **“TCP vs UDP?”**, don't stop at:

> “TCP is reliable and UDP is fast.”

A stronger answer is:

```text
TCP → connection-oriented + reliable + ordered byte stream
      + retransmission + flow control + congestion control

UDP → connectionless + datagram-oriented + lower overhead
      + no built-in reliability/order/retransmission
      + application-controlled behavior
```

The most important conceptual distinction is:

> **TCP provides a reliable byte stream; UDP provides independent datagrams.**
