# Q9. What is the TCP Three-Way Handshake?

The **TCP three-way handshake** is the process TCP uses to **establish a TCP connection** between a client and server before normal application data transfer begins.

It is called a **three-way handshake** because three TCP messages are exchanged:

```text
SYN → SYN + ACK → ACK
```

The handshake allows both endpoints to establish the initial state required for TCP communication.

---

# Why is the TCP Three-Way Handshake Needed?

Before sending normal application data, TCP needs both sides to establish communication state.

The handshake allows both sides to:

* Establish a TCP connection.
* Confirm that both sides can communicate in both directions.
* Synchronize their **initial sequence numbers (ISNs)**.
* Acknowledge the received SYN.
* Prepare for reliable, ordered byte-stream transmission.

A simplified view:

```text
Client                                      Server
  │                                           │
  │──────────── SYN ─────────────────────────>│
  │                                           │
  │<────────── SYN + ACK ────────────────────│
  │                                           │
  │──────────── ACK ─────────────────────────>│
  │                                           │
  │        TCP connection established         │
```

> **Important:** The handshake does not prove that the entire network path is permanently reliable. It establishes TCP connection state and confirms that the endpoints can exchange the required handshake messages.

---

# Three Steps of the TCP Handshake

## Step 1: SYN

The client sends a TCP segment with the **SYN (Synchronize)** flag set.

It essentially says:

> “I want to establish a TCP connection, and here is my initial sequence number.”

For example:

```text
Client → Server

SYN
Seq = x
```

The client enters a state conceptually represented as:

```text
CLOSED
   │
   │ send SYN
   ▼
SYN-SENT
```

### Example

Suppose the client's initial sequence number is:

```text
x = 100
```

The client sends:

```text
Client → Server

SYN
Seq = 100
```

The SYN itself consumes one sequence-number position, which is why the acknowledgment will be:

```text
Ack = 101
```

---

# Step 2: SYN + ACK

The server receives the client's SYN and responds with a segment containing both:

* **SYN** — the server chooses its own initial sequence number.
* **ACK** — the server acknowledges the client's SYN.

For example:

```text
Server → Client

SYN + ACK
Seq = y
Ack = x + 1
```

If:

```text
Client ISN = 100
Server ISN = 500
```

then:

```text
Server → Client

SYN + ACK
Seq = 500
Ack = 101
```

The server's:

```text
Ack = 101
```

means, conceptually:

> “I received your SYN with sequence number 100, and I expect sequence number 101 next.”

At this point, the server has acknowledged the client's connection request and has also communicated its own initial sequence number.

The server enters:

```text
LISTEN
   │
   │ receive SYN
   ▼
SYN-RECEIVED
```

---

# Step 3: ACK

The client receives the server's SYN + ACK and sends an ACK back.

```text
Client → Server

ACK
Ack = y + 1
```

If the server's initial sequence number was:

```text
y = 500
```

then:

```text
Ack = 501
```

So:

```text
Client → Server

ACK
Ack = 501
```

The client can now transition to the established state.

The server receives this ACK and can also consider the connection established.

```text
Client                                  Server
  │                                       │
  │──── SYN, Seq = x ───────────────────>│
  │                                       │
  │<─── SYN+ACK, Seq = y ────────────────│
  │     Ack = x + 1                       │
  │                                       │
  │──── ACK, Ack = y + 1 ───────────────>│
  │                                       │
  │       Connection Established          │
```

---

# Complete Three-Way Handshake Example

Suppose:

```text
Client Initial Sequence Number = 100
Server Initial Sequence Number = 500
```

### 1. Client → Server

```text
SYN
Seq = 100
```

The client is saying:

> “Let's establish a connection. My initial sequence number is 100.”

---

### 2. Server → Client

```text
SYN + ACK
Seq = 500
Ack = 101
```

The server is saying:

> “I received your SYN. My initial sequence number is 500, and I expect your next sequence number to be 101.”

---

### 3. Client → Server

```text
ACK
Ack = 501
```

The client is saying:

> “I received your SYN with sequence number 500, so I expect 501 next.”

Now:

```text
TCP connection established
```

A compact representation:

```text
Client                                  Server
  │                                       │
  │──── SYN, Seq=100 ───────────────────>│
  │                                       │
  │<─── SYN+ACK, Seq=500, Ack=101 ───────│
  │                                       │
  │──── ACK, Ack=501 ───────────────────>│
  │                                       │
  │        Connection Established         │
```

# Why Does SYN Consume One Sequence Number?

This is an important interview detail.

Suppose:

```text
Client sends:

SYN
Seq = 100
```

The next sequence number expected from the client is:

```text
101
```

Therefore the server replies:

```text
ACK = 101
```

Similarly, if the server sends:

```text
SYN
Seq = 500
```

the client acknowledges it with:

```text
ACK = 501
```

So:

```text
SYN at sequence x
        ↓
Consumes one sequence number
        ↓
Next expected sequence = x + 1
```

The same principle applies to a FIN during connection termination.

---

# What Does “Synchronize Sequence Numbers” Mean?

TCP uses sequence numbers to keep track of bytes in the TCP byte stream.

For example:

```text
Application Data

A B C D E F G H
```

TCP assigns sequence-number positions to the bytes.

The initial sequence number gives each side a starting point for its own outgoing byte stream.

Conceptually:

```text
Client → Server
Client sequence space

100 → 101 → 102 → 103 → ...

Server → Client
Server sequence space

500 → 501 → 502 → 503 → ...
```

Notice that TCP communication is **bidirectional**, so each direction has its own sequence-number space.

The handshake establishes the starting points for both directions.

---

# Why Are There Three Steps Instead of Two?

A common interview question is:

> “Why can't TCP establish the connection using only SYN and SYN-ACK?”

Because the third ACK allows the client to explicitly acknowledge the server's SYN.

Consider:

```text
1. Client → Server
   SYN

2. Server → Client
   SYN + ACK

3. Client → Server
   ACK
```

The third message confirms:

```text
Client received:
- Server's SYN
- Server's sequence number
```

This gives both sides confirmation that the necessary handshake information has been received.

It also helps TCP establish synchronized connection state in both directions.

### Simplified reasoning

```text
SYN
↓
"I want to communicate."

SYN + ACK
↓
"I received your request, and I also want to communicate."

ACK
↓
"I received your response."

        ↓
Connection established
```

---

# TCP Connection States During the Handshake

TCP maintains connection states.

A simplified client-side sequence is:

```text
CLOSED
   │
   │ send SYN
   ▼
SYN-SENT
   │
   │ receive SYN+ACK
   │ send ACK
   ▼
ESTABLISHED
```

A simplified server-side sequence is:

```text
LISTEN
   │
   │ receive SYN
   ▼
SYN-RECEIVED
   │
   │ receive final ACK
   ▼
ESTABLISHED
```

So the handshake is not simply three packets with no internal state.

TCP uses the exchange to establish the connection state at both endpoints.

---

# What Happens After the Handshake?

Once the connection reaches the **ESTABLISHED** state, normal application data can be exchanged.

For example:

```text
Client                                  Server
  │                                       │
  │──── SYN ─────────────────────────────>│
  │<─── SYN + ACK ───────────────────────│
  │──── ACK ─────────────────────────────>│
  │                                       │
  │──── HTTP Request ───────────────────>│
  │                                       │
  │<─── HTTP Response ───────────────────│
  │                                       │
```

For a traditional HTTPS connection using TCP, the TCP handshake is followed by the TLS handshake before encrypted HTTP application data is exchanged.

Conceptually:

```text
TCP Three-Way Handshake
        ↓
TCP Connection Established
        ↓
TLS Handshake
        ↓
Encrypted HTTP Communication
```

For HTTP/3, this differs because HTTP/3 uses **QUIC over UDP**, not TCP.

---

# TCP Handshake in a Real Web Request

Suppose you open:

```text
https://example.com
```

If the connection uses TCP, a simplified sequence is:

```text
Browser
   │
   │ TCP SYN
   ▼
Server
   │
   │ TCP SYN + ACK
   ▼
Browser
   │
   │ TCP ACK
   ▼
TCP connection established
   │
   ▼
TLS handshake
   │
   ▼
HTTPS request/response
```

This demonstrates an important point:

> **The TCP three-way handshake establishes the TCP transport connection; it does not itself establish HTTPS encryption.**

TLS is a separate security protocol layered above TCP in traditional HTTPS deployments.

---

# What If a SYN Is Lost?

TCP can retransmit handshake messages when necessary.

For example:

```text
Client                                  Server
  │                                       │
  │──── SYN ───────X                       │
  │                 Lost                   │
  │                                       │
  │──── SYN ─────────────────────────────>│
  │                                       │
  │<─── SYN + ACK ───────────────────────│
  │                                       │
  │──── ACK ─────────────────────────────>│
```

The exact retransmission timing and behavior depend on TCP implementation and configuration, but the key idea is:

> TCP does not assume that a handshake segment successfully arrived simply because it was transmitted.

# TCP Three-Way Handshake vs Data Transfer

Do not confuse the handshake with normal TCP data transfer.

### Handshake

```text
SYN
 ↓
SYN + ACK
 ↓
ACK
```

Purpose:

* Establish connection state
* Synchronize initial sequence numbers
* Acknowledge the connection request

### Data transfer

After establishment:

```text
Data + Sequence Number
        ↓
      ACK
        ↓
More Data
        ↓
      ACK
```

During data transfer, TCP uses sequence numbers, acknowledgments, retransmissions, flow control, and congestion control.

---

# TCP Handshake vs Connection Termination

Don't confuse **connection establishment** with **connection termination**.

## Connection establishment

TCP uses a **three-way handshake**:

```text
SYN
 ↓
SYN + ACK
 ↓
ACK
```

## Connection termination

TCP normally uses a **four-segment FIN/ACK exchange** because TCP is full-duplex and each direction can be closed independently.

Simplified:

```text
Client                                  Server
  │                                       │
  │──────────── FIN ────────────────────>│
  │<──────────── ACK ────────────────────│
  │<──────────── FIN ────────────────────│
  │──────────── ACK ────────────────────>│
  │                                       │
  │       Connection closed               │
```

The exact sequence can vary depending on which side initiates the close and timing of the segments.

### Easy memory trick

```text
Connection Establishment
SYN → SYN-ACK → ACK
       3 steps

Connection Termination
FIN → ACK → FIN → ACK
       commonly 4 segments
```

# Common Interview Mistakes

### ❌ Mistake 1: “The three-way handshake transfers application data.”

Not its primary purpose.

Its main purposes are:

* Establish TCP connection state.
* Synchronize initial sequence numbers.
* Confirm bidirectional communication during setup.

---

### ❌ Mistake 2: “SYN means synchronization of the entire network.”

No.

SYN is a TCP flag used to synchronize the **TCP sequence-number state** and initiate a connection.

---

### ❌ Mistake 3: “The server sends only an ACK in step 2.”

No.

The second message contains:

```text
SYN + ACK
```

The server both:

* Acknowledges the client's SYN.
* Sends its own SYN.

---

### ❌ Mistake 4: “ACK = x.”

If the client sends:

```text
SYN, Seq = x
```

the server normally acknowledges:

```text
Ack = x + 1
```

because the SYN consumes one sequence-number position.

---

### ❌ Mistake 5: “TCP handshake provides encryption.”

The TCP handshake itself does **not** provide encryption.

For HTTPS over TCP:

```text
TCP handshake
      ↓
TLS handshake
      ↓
Encrypted application data
```

---

### ❌ Mistake 6: “TCP always takes exactly three packets to establish a connection.”

The normal establishment sequence is three handshake segments, but real networks can involve retransmissions, delayed packets, loss, and implementation-specific behavior.

# One-Line Interview Answer

> **The TCP three-way handshake is the SYN → SYN-ACK → ACK process used to establish a TCP connection, synchronize the initial sequence numbers of both endpoints, and confirm the required bidirectional communication state before normal data transfer begins.**

### Interview takeaway

Remember the sequence:

```text
Client                         Server

SYN, Seq=x
 ───────────────────────────────>

                  SYN+ACK
                  Seq=y
                  Ack=x+1
 <───────────────────────────────

ACK
Ack=y+1
 ───────────────────────────────>

       ESTABLISHED
```

The most important interview points are:

1. **SYN starts the connection.**
2. **SYN + ACK acknowledges the client's SYN and provides the server's ISN.**
3. **Final ACK acknowledges the server's SYN.**
4. **SYN consumes one sequence-number position.**
5. **TCP establishment uses three handshake segments.**
6. **TCP termination is normally a separate FIN/ACK exchange.**
7. **The TCP handshake itself does not provide encryption.**
