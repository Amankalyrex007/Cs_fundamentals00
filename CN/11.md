# Q11. What Are TCP Flow Control and Congestion Control?

**TCP Flow Control** and **TCP Congestion Control** are two important mechanisms used by TCP to regulate how much data can be sent into the network.

Although both control the sender's transmission rate, they solve **different problems**:

> **Flow Control → protects the receiver from being overwhelmed.**
> **Congestion Control → protects the network from being overwhelmed.**

A simple way to remember:

```text
Flow Control       → "Can the receiver handle this much data?"
Congestion Control → "Can the network handle this much traffic?"
```

---

# 1. TCP Flow Control

**Flow control** ensures that the sender does not send data faster than the receiver can process or buffer it.

The receiver has a limited amount of buffer space for incoming TCP data. If the sender transmits too much data before the receiver can process it, the receiver's buffer could overflow.

To prevent this, TCP uses a **Receive Window (`rwnd`)**.

### Basic idea

```text
Sender                              Receiver
  |                                    |
  | ----------- Data ----------------> |
  |                                    |
  | <--------- rwnd ------------------ |
  |                                    |
```

The receiver tells the sender approximately how much additional unacknowledged data it is currently prepared to accept.

### Example

Suppose a receiver has only **10 KB of available buffer space**.

It may advertise:

```text
rwnd = 10 KB
```

The sender should then avoid having more than approximately 10 KB of outstanding data limited by the advertised receive window.

For example:

```text
Receiver available buffer = 10 KB

Sender
  |
  | ===== 10 KB =====> Receiver
  |
  |       rwnd = 10 KB
```

If the receiver processes some data and frees 5 KB of buffer space, it may advertise a larger window:

```text
Before:
rwnd = 10 KB

After processing data:
rwnd = 15 KB
```

The sender can then increase the amount of data it has outstanding, subject to the congestion window as well.

---

## What If the Receiver's Buffer Becomes Full?

Suppose the receiver cannot process incoming data quickly enough.

Its available buffer might become:

```text
Available buffer = 0 KB
```

The receiver can advertise:

```text
rwnd = 0
```

This is called a **zero window** condition.

Conceptually:

```text
Sender                         Receiver
  |                               |
  | -------- Data -------------> |
  |                               |
  | <-------- rwnd = 0 --------- |
  |                               |
  X  Stop normal data transmission
```

The sender should not continue sending normal application data beyond what the receiver can accept.

TCP has mechanisms such as **window probes** to discover when a zero window has opened again.

### Purpose of Flow Control

```text
Prevent:

Sender  ───────────────→  Receiver
        TOO MUCH DATA
                         ↓
                  Buffer Overflow
```

So:

> **Flow control prevents the sender from overwhelming the receiver's buffer and processing capacity.**

---

# 2. TCP Congestion Control

**Congestion control** deals with a different problem.

The receiver may be perfectly capable of processing data, but the **network itself may not be capable of carrying all the traffic**.

For example:

```text
Sender → Router → Router → Router → Receiver
             ↑
       Network bottleneck
```

If many senders transmit large amounts of traffic through the same routers and links, queues can become full.

This can result in:

* Packet loss
* Increasing delay
* Retransmissions
* Queue buildup
* Reduced throughput

TCP therefore uses a **Congestion Window (`cwnd`)**.

---

## Congestion Window (`cwnd`)

`cwnd` represents the sender's current estimate of how much data can be safely kept in the network without causing excessive congestion.

TCP adjusts `cwnd` dynamically based on network feedback.

For example:

```text
Initially:

cwnd = small
       ↓
Sender sends cautiously
       ↓
ACKs arrive successfully
       ↓
TCP increases sending capacity
       ↓
Network congestion/loss detected
       ↓
TCP reduces sending capacity
```

This allows TCP to adapt to changing network conditions.

---

# Common TCP Congestion-Control Concepts

Important TCP congestion-control mechanisms include:

### 1. Slow Start

TCP initially starts with a relatively small congestion window and increases it rapidly as acknowledgments arrive.

Despite its name, **slow start can actually increase the congestion window quickly**, especially at the beginning.

Conceptually:

```text
Small cwnd
   ↓
Successful ACKs
   ↓
Increase cwnd
   ↓
More data in flight
   ↓
Continue until threshold/congestion signal
```

---

### 2. Congestion Avoidance

After reaching an appropriate threshold, TCP generally increases its sending rate more cautiously.

The goal is to use available network capacity without aggressively causing congestion.

A simplified conceptual view:

```text
Slow Start
    |
    | Rapid increase
    ↓
Congestion Avoidance
    |
    | More cautious increase
    ↓
Congestion detected
    |
    ↓
Reduce sending rate
```

The exact behavior depends on the TCP congestion-control algorithm being used.

---

### 3. Fast Retransmit

TCP can sometimes detect packet loss through **duplicate ACKs** before a retransmission timeout occurs.

For example:

```text
Sender                         Receiver

Segment 1 ------------------>  ACK 2
Segment 2 ------------------>  ACK 3
Segment 3 --------X           (lost)
Segment 4 ------------------>  Duplicate ACK
Segment 5 ------------------>  Duplicate ACK
                              ...
```

Repeated duplicate acknowledgments can indicate that a segment is missing.

TCP may then retransmit the missing segment without waiting for the retransmission timer to expire.

This is called **Fast Retransmit**.

---

### 4. Fast Recovery

After detecting congestion through mechanisms such as duplicate ACKs, some TCP congestion-control algorithms reduce the congestion window and then recover more efficiently rather than returning all the way to the smallest possible sending rate.

The exact behavior depends on the TCP implementation/algorithm.

The important interview concept is:

> **Fast Retransmit helps detect and retransmit suspected lost data quickly, while Fast Recovery helps TCP adjust its sending rate after congestion is detected.**

---

# 3. `rwnd` vs `cwnd`

This is one of the most important distinctions in TCP.

### `rwnd` — Receive Window

`rwnd` represents the amount of data the **receiver is currently prepared to accept**.

It is controlled/advertised by the receiver.

```text
Receiver
   |
   | "I can currently accept this much."
   ↓
  rwnd
```

### `cwnd` — Congestion Window

`cwnd` represents the sender's current estimate of how much data the **network can safely carry**.

It is maintained by the sender's congestion-control algorithm.

```text
Network feedback
      ↓
Sender
      ↓
    cwnd
```

---

# 4. Effective TCP Sending Window

The sender is constrained by **both** receiver capacity and network capacity.

Conceptually:

```text
Effective Sending Window = min(rwnd, cwnd)
```

For example:

```text
rwnd = 100 KB
cwnd = 40 KB

Effective window = min(100, 40)
                 = 40 KB
```

The receiver can accept 100 KB, but TCP currently estimates that only 40 KB should be in flight because of network conditions.

Therefore:

```text
Sender → approximately up to 40 KB outstanding
```

Now consider the opposite:

```text
rwnd = 20 KB
cwnd = 100 KB

Effective window = min(20, 100)
                 = 20 KB
```

The network may be able to handle 100 KB, but the receiver can currently accept only 20 KB.

Therefore:

```text
Receiver capacity becomes the limiting factor.
```

This is why both mechanisms are necessary.

---

# 5. Flow Control vs Congestion Control

| Feature         | Flow Control                                    | Congestion Control                     |
| --------------- | ----------------------------------------------- | -------------------------------------- |
| Protects        | Receiver                                        | Network                                |
| Main problem    | Receiver cannot process/buffer data fast enough | Network is overloaded                  |
| Main mechanism  | Receive Window (`rwnd`)                         | Congestion Window (`cwnd`)             |
| Controlled by   | Receiver advertises capacity                    | Sender estimates network capacity      |
| Main concern    | Receiver buffer                                 | Network bandwidth/queues/congestion    |
| Feedback        | Receiver's advertised window                    | ACKs, packet loss, delay/signals, etc. |
| Example problem | Receiver buffer is filling up                   | Routers/links are becoming congested   |
| Goal            | Avoid overwhelming receiver                     | Avoid overwhelming network             |

# 6. Practical Example

Suppose a server is sending a large file to a client.

```text
Server                              Client
  |                                    |
  | -------- File Data --------------> |
  |                                    |
```

There are **two independent limitations**.

### Situation A: Receiver is slow

The client has limited memory/buffer space.

```text
Client buffer:
[████████████████████] FULL
```

The client advertises a smaller:

```text
rwnd ↓
```

The server must reduce the amount of outstanding data.

This is **flow control**.

---

### Situation B: Network is congested

The client has plenty of buffer space:

```text
rwnd = large
```

But routers between the server and client are experiencing congestion.

```text
Server
  |
  v
Router → Router → Router
          ↑
       Congestion
          ↓
     Packet loss
```

TCP detects signs of congestion and adjusts:

```text
cwnd ↓
```

This is **congestion control**.

---

### Situation C: Both are limiting

Suppose:

```text
rwnd = 50 KB
cwnd = 20 KB
```

Then:

```text
Effective window = min(50, 20)
                 = 20 KB
```

The network is the current bottleneck.

If later:

```text
rwnd = 10 KB
cwnd = 50 KB
```

Then:

```text
Effective window = min(10, 50)
                 = 10 KB
```

Now the receiver is the bottleneck.

# 7. Easy Water-Pipe Analogy

Imagine sending water through a pipe into a container.

```text
Sender              Network Pipe             Receiver
  |                       |                     |
  | ~~~~~~~~~~~~~~~~~~~~~>|~~~~~~~~~~~~~~~~~~~> |
  |                       |                     |
```

### Flow Control

The destination container can hold only a certain amount of water.

```text
Don't send more water than
the destination container can hold.
```

That represents:

```text
Flow Control → Receiver capacity
```

### Congestion Control

The pipe itself has limited capacity.

```text
Don't send more water than
the pipe/network can carry efficiently.
```

That represents:

```text
Congestion Control → Network capacity
```

Therefore:

```text
Flow Control
     ↓
Protects the container

Congestion Control
     ↓
Protects the pipe
```

# 8. Why Are Both Needed?

Consider this situation:

```text
Receiver can handle:
100 Mbps

Network can currently handle:
20 Mbps
```

Even though the receiver is fast enough, sending at 100 Mbps could overload the network.

So congestion control limits transmission.

Now consider:

```text
Receiver can handle:
10 Mbps

Network can handle:
100 Mbps
```

The network has plenty of capacity, but the receiver cannot process data at 100 Mbps.

So flow control limits transmission.

Therefore:

```text
                TCP Sender
                    |
          +---------+---------+
          |                   |
          ↓                   ↓
      rwnd limit          cwnd limit
          |                   |
          ↓                   ↓
      Receiver             Network
      capacity             capacity
          \                   /
           \                 /
            +-------+-------+
                    |
                    ↓
        Effective sending limit
             min(rwnd,cwnd)
```

# 9. Flow Control vs Congestion Control — Interview Scenario

### Interviewer:

> "Suppose the receiver is very slow but the network is completely free. Which mechanism handles this?"

**Answer:**

Flow control.

The receiver advertises a smaller `rwnd`, limiting how much unacknowledged data the sender can have in flight.

---

### Interviewer:

> "Suppose the receiver is fast, but routers in the path are overloaded. Which mechanism handles this?"

**Answer:**

Congestion control.

TCP reduces its effective sending rate by adjusting `cwnd` based on congestion signals.

---

### Interviewer:

> "What happens if `rwnd = 10 KB` and `cwnd = 100 KB`?"

```text
Effective window
= min(10 KB, 100 KB)
= 10 KB
```

So the receiver's capacity is the limiting factor.

---

### Interviewer:

> "What happens if `rwnd = 100 KB` and `cwnd = 10 KB`?"

```text
Effective window
= min(100 KB, 10 KB)
= 10 KB
```

Now network congestion/capacity is the limiting factor.

# 10. Common Mistakes

### ❌ Mistake 1: Flow control and congestion control are the same

They are not.

```text
Flow Control       → Receiver
Congestion Control → Network
```

---

### ❌ Mistake 2: `rwnd` is controlled by the sender

The receiver advertises `rwnd`.

The sender uses that information to limit transmission.

---

### ❌ Mistake 3: `cwnd` is the receiver's capacity

No.

```text
rwnd → receiver's advertised capacity
cwnd → sender's estimate of network capacity
```

---

### ❌ Mistake 4: Congestion control only reacts to packet loss

Packet loss is an important congestion signal, but modern TCP algorithms can also consider other signals depending on the algorithm and environment, such as delay or explicit congestion notification.

So avoid saying:

> "TCP knows congestion only when packets are lost."

---

### ❌ Mistake 5: `rwnd` alone determines how much TCP can send

Not necessarily.

The sender is constrained by both:

```text
rwnd
  +
cwnd
```

Conceptually:

```text
Effective Window = min(rwnd, cwnd)
```

# 12. Memory Trick

Remember:

> **R in `rwnd` → Receiver**

> **C in `cwnd` → Congestion**

So:

```text
rwnd → Receiver Window
cwnd → Congestion Window
```

Or simply:

```text
Flow Control       = "Protect the Receiver"
Congestion Control = "Protect the Network"
```

# Interview Takeaway

**TCP flow control** prevents the sender from overwhelming the **receiver** by using the receiver-advertised **receive window (`rwnd`)**.

**TCP congestion control** prevents the sender from overwhelming the **network** by dynamically managing the **congestion window (`cwnd`)** based on network feedback.

The sender's effective amount of outstanding data is conceptually constrained by:

```text
Effective Sending Window = min(rwnd, cwnd)
```

### One-line interview answer

> **Flow control protects the receiver, while congestion control protects the network; TCP uses `rwnd` for receiver capacity and `cwnd` for estimated network capacity.**
