# Q12. What is HTTP?

**HTTP (HyperText Transfer Protocol)** is an **application-layer protocol** used for communication between clients and servers, especially on the Web.

It defines how a client, such as a browser or mobile application, sends a **request** to a server and how the server returns a **response**.

In simple terms:

```text
Client                          Server
  |                               |
  | -------- Request -----------> |
  |                               |
  | <-------- Response ---------- |
  |                               |
```

For example, when you visit:

```text
https://example.com
```

the browser may request an HTML document from the server. The server can then return HTML, CSS, JavaScript, images, JSON data, or other resources.

> **HTTP defines the communication rules; it does not itself define how the underlying network delivers the packets.**

---

# 1. Basic HTTP Flow

A simplified HTTP communication looks like this:

```text
Browser (Client)                         Web Server
      |                                      |
      | -------- HTTP Request -------------> |
      |                                      |
      | <-------- HTTP Response ------------ |
      |                                      |
```

For example:

```text
Browser
   |
   | GET /products/123
   |
   ↓
Web Server
   |
   | 200 OK
   | {"id":123,"name":"Laptop"}
   |
   ↓
Browser
```

The browser can then use the received data to display a webpage or process an API response.

---

# 2. HTTP Request

An **HTTP request** is a message sent by a client to a server asking the server to perform an operation or provide a resource.

A simplified HTTP request might look like:

```http
GET /users/123 HTTP/1.1
Host: example.com
Accept: application/json
```

Let's break it down.

---

## Request Components

### 1. Method

The **HTTP method** indicates what operation the client is requesting.

Examples:

```text
GET
POST
PUT
PATCH
DELETE
```

For example:

```http
GET /users/123 HTTP/1.1
```

means the client wants to retrieve the resource represented by `/users/123`.

---

### 2. Path / Target Resource

The request identifies the resource being accessed.

Example:

```http
GET /users/123 HTTP/1.1
```

Here:

```text
/users/123
```

is the request target/path.

A full URL might be:

```text
https://example.com/users/123
```

But the exact request-target representation depends on the HTTP communication form and protocol version.

---

### 3. Headers

**Headers** contain additional metadata about the request.

Example:

```http
Host: example.com
Accept: application/json
Authorization: Bearer <token>
Content-Type: application/json
```

Headers can communicate information such as:

* Desired response format
* Content type
* Authentication information
* Caching preferences
* Cookies
* Client capabilities
* Connection/protocol-related information

For example:

```http
Accept: application/json
```

can tell the server that the client prefers a JSON representation.

---

### 4. Body

The **request body** contains data sent by the client when the operation requires it.

For example:

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "name": "Aman",
  "email": "aman@example.com"
}
```

Here the JSON object is the request body.

A body is commonly used with:

* `POST`
* `PUT`
* `PATCH`

However, the presence of a body is not determined simply by the method name; HTTP semantics and the specific request determine whether a body is meaningful.

---

# 3. HTTP Response

After processing the request, the server sends an **HTTP response**.

For example:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "name": "Aman"
}
```

The response tells the client:

1. What happened to the request
2. Additional metadata about the response
3. The actual response data, if any

---

## Response Components

### 1. Status Code

The **status code** indicates the result of the request.

For example:

```text
200 OK
404 Not Found
500 Internal Server Error
```

---

### 2. Headers

Response headers provide metadata about the returned response.

Example:

```http
Content-Type: application/json
Content-Length: 25
Cache-Control: max-age=3600
```

They can describe:

* Response format
* Caching behavior
* Content length
* Cookies
* Security policies
* Other response metadata

---

### 3. Response Body

The **response body** contains the actual data returned by the server.

For example:

```json
{
  "name": "Aman"
}
```

The body could contain:

* HTML
* JSON
* XML
* CSS
* JavaScript
* Images
* Text
* Other media/data

---

# 4. Common HTTP Status Codes

| Code    | Meaning               | Typical Example                              |
| ------- | --------------------- | -------------------------------------------- |
| **200** | OK                    | Successful request                           |
| **201** | Created               | New resource successfully created            |
| **204** | No Content            | Successful request with no response body     |
| **301** | Moved Permanently     | Resource has a new permanent URL             |
| **302** | Found / Redirect      | Temporary redirection                        |
| **400** | Bad Request           | Invalid request                              |
| **401** | Unauthorized          | Authentication is required or failed         |
| **403** | Forbidden             | Server understood request but refuses access |
| **404** | Not Found             | Resource does not exist at that target       |
| **500** | Internal Server Error | Server encountered an unexpected problem     |
| **502** | Bad Gateway           | Gateway/proxy received an invalid response   |
| **503** | Service Unavailable   | Server temporarily unable to handle request  |

A useful classification is:

```text
1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client-side/request-related error
5xx → Server-side error
```

### Important interview nuance

`401` and `403` are often confused.

Conceptually:

```text
401 → Authentication is required/invalid
403 → Request is understood, but access is refused
```

The exact application behavior can depend on the API/server.

# 5. Common HTTP Methods

| Method     | Typical Purpose                          |
| ---------- | ---------------------------------------- |
| **GET**    | Retrieve data                            |
| **POST**   | Submit data / commonly create a resource |
| **PUT**    | Replace a resource representation        |
| **PATCH**  | Partially modify a resource              |
| **DELETE** | Delete a resource                        |

### Example REST-style API

Suppose we have:

```text
/users/123
```

We might have:

```http
GET /users/123
```

→ Retrieve user 123

```http
POST /users
```

→ Submit data to create a new user

```http
PUT /users/123
```

→ Replace/update the representation of user 123

```http
PATCH /users/123
```

→ Partially modify user 123

```http
DELETE /users/123
```

→ Delete user 123

# 6. GET vs POST

A common interview question is:

> What is the difference between GET and POST?

### GET

Generally used to retrieve a representation of a resource.

Example:

```http
GET /products/10
```

A typical GET request does not need a request body.

### POST

Generally used to submit data for processing, often resulting in creation of a resource.

Example:

```http
POST /products
Content-Type: application/json

{
  "name": "Keyboard",
  "price": 1200
}
```

The server may create a new product and return:

```http
HTTP/1.1 201 Created
```

### Important distinction

Do not simply say:

> "GET is for reading and POST is for writing."

That is useful as a beginner shortcut, but HTTP semantics are more precise.

For example, `POST` can be used for operations that don't simply create a database record, while methods such as `PUT` and `PATCH` are commonly used for updates.

---

# 7. HTTP Is Stateless

HTTP is generally described as a **stateless application protocol**.

This means that one HTTP request does not inherently require the server to remember the application state of previous requests.

For example:

```text
Request 1:
GET /products

Request 2:
GET /products/10

Request 3:
GET /cart
```

HTTP itself does not automatically mean:

> "The server remembers everything about Request 1 when processing Request 3."

Applications can maintain state using mechanisms such as:

* Cookies
* Session identifiers
* Authentication tokens
* Databases
* Server-side session storage

For example:

```text
Browser
   |
   | Login
   ↓
Server
   |
   | Set-Cookie: session=abc123
   ↓
Browser
   |
   | Cookie: session=abc123
   ↓
Server
```

The **application** uses the cookie/session information to associate multiple requests with the same user/session.

# 8. HTTP Versions

HTTP has evolved significantly.

## HTTP/1.1

HTTP/1.1 commonly uses **TCP** as its transport.

It supports:

* Persistent connections
* Request/response communication
* Headers
* Chunked transfer encoding
* Various caching mechanisms

A simplified stack:

```text
HTTP/1.1
   ↓
TCP
   ↓
IP
   ↓
Ethernet / Wi-Fi
```

Persistent connections allow multiple HTTP requests/responses to reuse a TCP connection rather than establishing a new TCP connection for every request.

---

# 9. HTTP/2

HTTP/2 introduced a **binary framing layer** and **multiplexing**.

Instead of treating a connection as one simple sequence of HTTP/1.1 messages, HTTP/2 can carry multiple logical streams over a single TCP connection.

Conceptually:

```text
                TCP Connection
                     |
        +------------+------------+
        |            |            |
      Stream 1     Stream 2     Stream 3
        |            |            |
       HTML          CSS          JS
```

This allows multiple requests/responses to progress concurrently over the same connection.

Important HTTP/2 features include:

* Binary framing
* Multiplexing
* Stream-based communication
* Header compression
* More efficient use of a connection

### Important limitation

HTTP/2 still runs over **TCP**.

Therefore, TCP-level packet loss can affect the progress of the connection's streams.

This is one of the issues HTTP/3 and QUIC were designed to address differently.

---

# 10. HTTP/3

HTTP/3 uses **QUIC over UDP** instead of TCP.

```text
HTTP/3
   ↓
QUIC
   ↓
UDP
   ↓
IP
   ↓
Ethernet / Wi-Fi
```

QUIC provides transport functionality such as:

* Reliable delivery
* Encryption integration
* Stream multiplexing
* Connection management

One important benefit is that packet loss affecting one QUIC stream does not necessarily block delivery of data on all other independent streams in the same way TCP-level head-of-line blocking can affect HTTP/2.

Conceptually:

```text
HTTP/2:

Stream A ─┐
Stream B ─┼── TCP ──> packet loss can affect connection-level delivery
Stream C ─┘


HTTP/3:

Stream A ─┐
Stream B ─┼── QUIC ──> independent streams
Stream C ─┘
             ↓
            UDP
```

So:

> **HTTP/3 does not use TCP; it uses HTTP semantics over QUIC, and QUIC runs over UDP.**

---

# 11. HTTP vs HTTPS

A very common interview question is:

> What is the difference between HTTP and HTTPS?

### HTTP

HTTP by itself does not provide confidentiality or cryptographic protection for application data.

Conceptually:

```text
HTTP
 ↓
Transport
 ↓
Network
```

### HTTPS

**HTTPS = HTTP over TLS**

TLS provides important security properties such as:

* Confidentiality
* Integrity protection
* Server authentication through certificates

Conceptually for HTTP/1.1 or HTTP/2:

```text
HTTP
  ↓
TLS
  ↓
TCP
  ↓
IP
```

For HTTP/3:

```text
HTTP
  ↓
QUIC
  ↓
UDP
  ↓
IP
```

TLS is integrated into QUIC rather than being a separate TCP-level layer in the same way.

---

# 12. Why HTTPS Is Needed

Suppose you send:

```text
POST /login

username=aman
password=secret
```

Without encryption, an attacker able to observe the traffic could potentially read sensitive information.

With HTTPS:

```text
Browser
   |
   | ===== Encrypted TLS-protected data =====>
   |
   ↓
Server
```

An observer may see network metadata such as addresses and traffic characteristics, but should not be able to simply read or modify the protected HTTP content.

### TLS Certificates

During TLS setup, the server presents a certificate that helps the client authenticate the server's identity under the Web PKI trust model.

This helps protect against impersonation attacks.

# 13. HTTP Request-Response Example

Suppose a browser wants user information.

### Step 1 — Client sends request

```http
GET /users/123 HTTP/1.1
Host: example.com
Accept: application/json
```

### Step 2 — Server processes request

The server might:

```text
Receive request
      ↓
Check authentication
      ↓
Validate request
      ↓
Check cache/database
      ↓
Retrieve user data
      ↓
Build response
```

### Step 3 — Server responds

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 123,
  "name": "Aman"
}
```

### Step 4 — Client processes response

The browser/application reads the response and uses the data.

```text
Client
  ↓
HTTP Request
  ↓
Server
  ↓
Application logic
  ↓
Database/cache
  ↓
HTTP Response
  ↓
Client
```

# 14. HTTP and DNS Are Different

A common beginner confusion is:

> "Does HTTP find the server?"

Not exactly.

**DNS** is responsible for resolving a domain name to network addressing information.

For example:

```text
example.com
     ↓
    DNS
     ↓
IP address
```

Then HTTP is used to communicate with the server:

```text
Domain
  ↓
DNS resolution
  ↓
IP address
  ↓
TCP/TLS or QUIC
  ↓
HTTP request
  ↓
HTTP response
```

So:

```text
DNS → "Where is the server?"
HTTP → "What resource/operation do I want?"
```

This is a simplified conceptual distinction; real systems involve caching, CDNs, proxies, load balancers, and other components.

# 15. Where HTTP Fits in the Network Stack

HTTP operates at the **Application layer**.

For traditional HTTP/1.1 and HTTP/2:

```text
+-------------------------+
| HTTP                    | Application
+-------------------------+
| TCP                     | Transport
+-------------------------+
| IP                      | Internet/Network
+-------------------------+
| Ethernet / Wi-Fi        | Link
+-------------------------+
```

For HTTP/3:

```text
+-------------------------+
| HTTP/3                  | Application
+-------------------------+
| QUIC                    | Transport functionality
+-------------------------+
| UDP                     | Transport substrate
+-------------------------+
| IP                      | Internet
+-------------------------+
| Ethernet / Wi-Fi        | Link
+-------------------------+
```

# 17. Common Mistakes

### ❌ Mistake 1: HTTP is a transport-layer protocol

Incorrect.

```text
HTTP → Application Layer
TCP/UDP → Transport Layer
```

---

### ❌ Mistake 2: HTTPS is a completely different application protocol

A better description is:

> **HTTPS is HTTP protected by TLS.**

---

### ❌ Mistake 3: HTTP always uses TCP

Not anymore.

```text
HTTP/1.1 → commonly TCP
HTTP/2   → TCP
HTTP/3   → QUIC over UDP
```

---

### ❌ Mistake 4: HTTP provides encryption

HTTP itself does not provide confidentiality.

```text
HTTP  → Application protocol
TLS   → Security/cryptographic protection
```

HTTPS combines HTTP with TLS.

---

### ❌ Mistake 5: HTTP and HTML are the same thing

They are completely different.

```text
HTTP → Communication protocol
HTML → Markup language
```

HTTP can transfer HTML, but HTTP itself is not HTML.

---

### ❌ Mistake 6: Every HTTP response contains HTML

Not true.

HTTP can carry:

```text
HTML
JSON
XML
CSS
JavaScript
Images
Video
Files
Other data
```

For example, an API may return:

```json
{
  "id": 123,
  "name": "Aman"
}
```

# Interview Takeaway

> **HTTP (HyperText Transfer Protocol) is an application-layer request-response protocol used for communication between clients and servers. It defines methods such as GET, POST, PUT, PATCH, and DELETE; uses headers and optional bodies to exchange information; and uses status codes to describe response outcomes. HTTP/1.1 and HTTP/2 commonly run over TCP, while HTTP/3 runs over QUIC over UDP. HTTPS is HTTP protected by TLS, providing confidentiality, integrity protection, and server authentication.**
