# Q14. What Are HTTP Methods?

**HTTP methods** are standardized actions that tell a server what the client wants to do with a resource.

They are also commonly called **HTTP verbs**.

For example, when a browser or API client communicates with a server:

```text
Client
   |
   | HTTP Method + Request
   ↓
Server
   |
   | HTTP Response
   ↓
Client
```

The HTTP method communicates the **intended operation**.

For example:

```text
GET    → "Give me this resource."
POST   → "Process this submitted data."
PUT    → "Replace this resource."
PATCH  → "Modify part of this resource."
DELETE → "Remove this resource."
```

---

# 1. Common HTTP Methods

| Method      | Typical Purpose                          | Example                                  |
| ----------- | ---------------------------------------- | ---------------------------------------- |
| **GET**     | Retrieve data                            | Get user details                         |
| **POST**    | Submit data / commonly create a resource | Create a new user                        |
| **PUT**     | Replace a resource representation        | Replace user profile                     |
| **PATCH**   | Partially modify a resource              | Update only user's email                 |
| **DELETE**  | Delete a resource                        | Delete a user                            |
| **HEAD**    | Get headers without a response body      | Check metadata of a resource             |
| **OPTIONS** | Discover supported communication options | Check supported methods / CORS preflight |

The most frequently used methods in REST-style APIs are:

```text
GET
POST
PUT
PATCH
DELETE
```

---

# 2. GET

The **GET** method is used to **retrieve a resource**.

Example:

```http
GET /users/123
```

The server might return:

```json
{
  "id": 123,
  "name": "Aman"
}
```

The client is asking:

> "Please give me the representation of user 123."

### GET is Safe

GET is intended to be a **safe** HTTP method.

This means that making a GET request is not intended to cause a state change on the server.

For example:

```http
GET /users/123
```

should retrieve the user rather than modify the user's profile.

### Important nuance

"Safe" does **not** mean:

> "The request can never cause any side effect whatsoever."

For example, a server might record logs, metrics, or analytics when a GET request is received.

The HTTP semantic meaning is that the **client did not request a state-changing operation**.

---

# 3. POST

The **POST** method is used to **submit data for processing**.

It is commonly used to create a new resource.

Example:

```http
POST /users
Content-Type: application/json

{
  "name": "Aman",
  "email": "aman@example.com"
}
```

The server may create a new user.

Possible response:

```http
HTTP/1.1 201 Created
```

The server may also return information about the newly created resource.

For example:

```json
{
  "id": 124,
  "name": "Aman",
  "email": "aman@example.com"
}
```

### POST Is Not Limited to Creating Resources

A common shortcut is:

> "POST is always used to create."

That's not completely accurate.

POST is used to **submit data for processing**, and creating a resource is one common use.

For example:

```http
POST /login
POST /payments
POST /search
POST /orders/123/cancel
```

could all use POST depending on the API design.

---

# 4. PUT

The **PUT** method is generally used to **replace the representation of a resource**.

Example:

```http
PUT /users/123
Content-Type: application/json

{
  "name": "Aman",
  "email": "new@example.com"
}
```

Conceptually, the client is saying:

> "Make the resource at `/users/123` have this representation."

---

## PUT vs PATCH

This is a very common interview question.

### PUT

Generally represents **replacement**.

```text
Existing resource:

{
  "name": "Aman",
  "email": "old@example.com",
  "city": "Lucknow"
}
```

A PUT request might provide the desired complete representation:

```json
{
  "name": "Aman",
  "email": "new@example.com",
  "city": "Lucknow"
}
```

### PATCH

Generally represents **partial modification**.

```http
PATCH /users/123

{
  "email": "new@example.com"
}
```

Only the specified change needs to be applied.

So:

```text
PUT   → Replace
PATCH → Partially modify
```

---

## PUT Is Idempotent

PUT is generally **idempotent**.

Suppose:

```http
PUT /users/123

{
  "name": "Aman",
  "email": "new@example.com"
}
```

is sent once.

The resulting resource becomes:

```text
name  = Aman
email = new@example.com
```

If the same request is sent again:

```http
PUT /users/123

{
  "name": "Aman",
  "email": "new@example.com"
}
```

the intended final state remains the same.

Therefore:

```text
PUT × 1 → desired state
PUT × 2 → same desired state
PUT × 10 → same desired state
```

This is the basic idea of **idempotency**.

---

# 5. PATCH

The **PATCH** method is used for a **partial update** of a resource.

Example:

```http
PATCH /users/123
Content-Type: application/json

{
  "email": "new@example.com"
}
```

Only the email field needs to be modified.

Existing resource:

```json
{
  "id": 123,
  "name": "Aman",
  "email": "old@example.com",
  "city": "Lucknow"
}
```

After PATCH:

```json
{
  "id": 123,
  "name": "Aman",
  "email": "new@example.com",
  "city": "Lucknow"
}
```

Notice that:

```text
name → unchanged
city → unchanged
email → changed
```

### PATCH vs PUT

| PUT                                 | PATCH                             |
| ----------------------------------- | --------------------------------- |
| Generally replacement               | Partial modification              |
| Client sends desired representation | Client sends changes/instructions |
| Idempotent by HTTP semantics        | Not necessarily idempotent        |
| Often larger request                | Often smaller request             |

### Important nuance

PATCH is **not automatically non-idempotent**.

A particular PATCH operation can be designed to be idempotent.

For example:

```http
PATCH /users/123

{
  "email": "new@example.com"
}
```

can produce the same final state when repeated.

So the precise statement is:

> **PATCH does not have an inherent requirement to be idempotent; whether a specific PATCH operation is idempotent depends on its semantics.**

---

# 6. DELETE

The **DELETE** method is used to request removal of a resource.

Example:

```http
DELETE /users/123
```

The server may respond:

```http
HTTP/1.1 204 No Content
```

This indicates that the request succeeded and there is no response body.

Conceptually:

```text
Before:

/users/123
     ↓
User exists


DELETE /users/123
     ↓

After:

/users/123
     ↓
User removed
```

### DELETE Is Idempotent

DELETE is generally **idempotent**.

For example:

```text
DELETE /users/123
```

sent once:

```text
User 123 → deleted
```

Sent again:

```text
DELETE /users/123
```

the intended result is still:

```text
User 123 → does not exist
```

The second request might return a different status code, such as `404`, depending on the server, but the intended resource state is still the same.

This is an important distinction:

> **Idempotent does not mean every repeated request returns the exact same response.**

It means the intended effect on the resource state is equivalent.

---

# 7. HEAD

The **HEAD** method is similar to GET, but the server returns **headers without the response body**.

Example:

```http
HEAD /image.jpg
```

The server might return:

```http
HTTP/1.1 200 OK
Content-Type: image/jpeg
Content-Length: 250000
Cache-Control: max-age=3600
```

but does not return the image body.

### Why Use HEAD?

It can be useful when a client wants metadata without downloading the complete resource.

For example:

```text
Client
  |
  | HEAD /large-file.zip
  ↓
Server
  |
  | Headers only
  ↓
Client
```

The client might learn:

* Content type
* Content length
* Cache information
* Last modification information
* Other response metadata

without downloading the entire file.

---

# 8. OPTIONS

The **OPTIONS** method is used to ask about the communication options supported by a resource or server.

Example:

```http
OPTIONS /users
```

The server might respond with information such as:

```http
Allow: GET, POST, OPTIONS
```

This can tell the client which methods are supported for the resource.

---

## OPTIONS and CORS

OPTIONS is also commonly encountered in **CORS (Cross-Origin Resource Sharing)**.

A browser may send an OPTIONS request as a **CORS preflight request** before sending certain cross-origin requests.

Conceptually:

```text
Browser
   |
   | OPTIONS /api/users
   | Origin: https://frontend.example
   | Access-Control-Request-Method: POST
   ↓
Server
   |
   | "POST is allowed from this origin"
   ↓
Browser
   |
   | Actual POST request
   ↓
Server
```

The exact preflight behavior depends on the request and CORS rules.

---

# 9. Safe vs Idempotent

These are extremely common HTTP interview concepts.

They are related, but **not the same thing**.

---

## Safe Methods

A method is **safe** when it is intended not to request a modification of the server's resource state.

Common safe methods include:

```text
GET
HEAD
OPTIONS
```

Think:

```text
Safe → "I'm asking about something, not requesting a state change."
```

---

## Idempotent Methods

A method is **idempotent** if making the same request multiple times has the same **intended effect** as making it once.

Common idempotent methods include:

```text
GET
HEAD
OPTIONS
PUT
DELETE
```

POST is generally **not idempotent**.

---

# 10. Safe vs Idempotent Table

| Method      | Safe? |     Idempotent? | Typical Purpose       |
| ----------- | ----: | --------------: | --------------------- |
| **GET**     |     ✅ |               ✅ | Retrieve              |
| **HEAD**    |     ✅ |               ✅ | Retrieve headers      |
| **OPTIONS** |     ✅ |               ✅ | Discover options      |
| **PUT**     |     ❌ |               ✅ | Replace               |
| **DELETE**  |     ❌ |               ✅ | Delete                |
| **POST**    |     ❌ |     ❌ generally | Submit/create/process |
| **PATCH**   |     ❌ | Not necessarily | Partial modification  |

### Important relationship

```text
Safe methods are also idempotent.
```

But:

```text
Idempotent ≠ Safe
```

For example:

```text
PUT
```

is idempotent but **not safe**, because it can change server state.


```http

```

```text
Purpose → Delete
```

# 12. Why Idempotency Matters

Idempotency becomes particularly important when requests may be **retried**.

Imagine a network timeout occurs after a payment request is sent.

```text
Client
   |
   | POST /payment
   ↓
Server
   |
   | Payment processed
   |
   X---- Network timeout ---- Client
```

The client does not know whether the server processed the request.

If it blindly retries:

```text
POST /payment
```

the operation could potentially be performed twice.

This is one reason APIs performing operations such as payments often use additional mechanisms such as **idempotency keys**.

For example:

```http
POST /payments
Idempotency-Key: abc123
```

The server can use the key to recognize retries of the same logical operation.

### Important distinction

HTTP method semantics alone do not automatically make a business operation safe to retry.

Application-level design may be required.

# 13. Common Interview Confusions

### ❌ "GET is always completely side-effect free."

Better:

> GET is **safe by HTTP semantics**, meaning the client does not request a state-changing operation.

Servers may still perform logging, analytics, caching, etc.

---

### ❌ "POST always creates a resource."

Not necessarily.

POST means submitting a representation/data to a resource for processing.

Creating a resource is one common use.

---

### ❌ "PUT means update."

This is incomplete.

A more precise interview answer is:

> **PUT generally represents replacement of a resource representation.**

---

### ❌ "PATCH is always non-idempotent."

Incorrect.

PATCH is **not required to be idempotent**, but a particular PATCH operation can be designed to be idempotent.

---

### ❌ "DELETE always returns 204."

Not necessarily.

Possible responses include:

```text
200 OK
202 Accepted
204 No Content
404 Not Found
```

depending on the API and situation.

---

### ❌ "Idempotent means the response is always identical."

Incorrect.

Idempotency concerns the **intended effect of repeated requests**, not necessarily identical status codes, headers, timestamps, or response bodies.

---

### ❌ "Safe and idempotent mean the same thing."

They do not.

```text
Safe       → Intended not to modify resource state
Idempotent → Repetition has same intended effect
```



---

# Interview Takeaway

> **HTTP methods indicate the intended operation on a resource. GET retrieves, POST submits data or commonly creates a resource, PUT replaces a resource representation, PATCH partially modifies a resource, and DELETE removes a resource. HEAD retrieves headers without the response body, while OPTIONS is used to discover communication options and is commonly involved in CORS preflight requests.**

### One-line interview answer

> **HTTP methods describe what the client intends to do with a resource: GET retrieves, POST submits, PUT replaces, PATCH partially updates, DELETE removes, HEAD retrieves metadata, and OPTIONS discovers supported communication options.**
