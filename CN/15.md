# Q15. What Are HTTP Status Codes?

**HTTP status codes** are three-digit codes returned by a server in an HTTP response to indicate the **result or status of the client's request**.

For example:

```http
HTTP/1.1 200 OK
```

Here:

* `200` → Status code
* `OK` → Reason phrase describing the status

The first digit of the status code indicates its **broad category**.

---

## 1. HTTP Status Code Categories

| Range   | Category      | Meaning                                                 |
| ------- | ------------- | ------------------------------------------------------- |
| **1xx** | Informational | Request received; processing continues                  |
| **2xx** | Success       | Request was successfully processed                      |
| **3xx** | Redirection   | Further action is needed, often at another URL          |
| **4xx** | Client Error  | Problem with the request or client's current conditions |
| **5xx** | Server Error  | Server failed to fulfill a valid request                |

A simple way to remember them:

```text
1xx → Information
2xx → Success
3xx → Redirection
4xx → Client / Request Problem
5xx → Server Problem
```

---

# 2. 1xx — Informational

**1xx status codes** indicate that the request has been received and processing is continuing.

They are generally **intermediate responses**, rather than the final result of the request.

### Example

```http
100 Continue
```

`100 Continue` tells the client that it can continue sending the request, commonly after sending request headers and waiting for the server's approval to send a request body.

These codes are **less commonly encountered directly** in typical application development.

### Example flow

```text
Client
  |
  | Request headers
  v
Server
  |
  | 100 Continue
  v
Client
  |
  | Request body
  v
Server
```

---

# 3. 2xx — Success

**2xx status codes** indicate that the request was successfully handled.

Common examples include:

| Code               | Meaning                                  | Example                         |
| ------------------ | ---------------------------------------- | ------------------------------- |
| **200 OK**         | Request successful                       | Successful GET request          |
| **201 Created**    | Resource created                         | Successful POST creating a user |
| **202 Accepted**   | Request accepted for processing          | Asynchronous/background job     |
| **204 No Content** | Successful request with no response body | Successful DELETE               |

---

## 200 OK

`200 OK` means the request was successfully processed.

Example:

```http
GET /api/users/123 HTTP/1.1
```

Response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 123,
  "name": "Aman"
}
```

The server successfully found and returned the requested user.

---

## 201 Created

`201 Created` indicates that a new resource was successfully created.

Example:

```http
POST /api/users HTTP/1.1
Content-Type: application/json

{
  "name": "Aman"
}
```

Response:

```http
HTTP/1.1 201 Created
Location: /api/users/123
```

This tells the client that a new user resource was created.

### Typical use

```text
POST /api/users
       |
       v
Server creates user
       |
       v
201 Created
```

---

## 202 Accepted

`202 Accepted` means the server has **accepted the request for processing**, but processing may not have finished yet.

This is useful for asynchronous operations.

For example:

```text
Client
  |
  | POST /generate-report
  v
Server
  |
  | Starts background job
  v
202 Accepted
```

The report might still be generating after the response is returned.

**Important:** `202 Accepted` does not necessarily mean the operation has completed successfully.

---

## 204 No Content

`204 No Content` indicates that the request was successfully processed but there is **no response body**.

Example:

```http
DELETE /api/users/123 HTTP/1.1
```

Response:

```http
HTTP/1.1 204 No Content
```

The server successfully deleted the resource and has nothing else to return.

---

# 4. 3xx — Redirection

**3xx status codes** indicate that the client needs to take additional action to complete the request, often involving another URL or using a cached representation.

Common examples:

| Code                      | Meaning                                   |
| ------------------------- | ----------------------------------------- |
| **301 Moved Permanently** | Resource has a permanent new URL          |
| **302 Found**             | Temporary redirection                     |
| **304 Not Modified**      | Cached representation can still be reused |

---

## 301 Moved Permanently

`301` indicates that a resource has been permanently moved to another URL.

Example:

```text
Browser
   |
   | GET /old-url
   v
Server
   |
   | 301 Moved Permanently
   | Location: /new-url
   v
Browser
   |
   | GET /new-url
   v
Server
```

The browser can follow the new location.

Example:

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-url
```

---

## 302 Found

`302` indicates a temporary redirection.

For example:

```text
/request
   |
   v
302 Found
Location: /temporary-location
```

The client may follow the provided location.

The exact behavior of redirects can depend on the HTTP method, client, and implementation, so `301` and `302` should not simply be thought of as identical except for "permanent vs temporary."

---

## 304 Not Modified

`304 Not Modified` is commonly associated with **HTTP caching**.

It tells the client that its cached representation can still be reused because the resource has not changed according to the cache validation conditions.

Example:

```text
Browser
   |
   | "Do I need a new copy?"
   v
Server
   |
   | 304 Not Modified
   v
Browser uses cached copy
```

This can reduce unnecessary data transfer.

---

# 5. 4xx — Client Errors

**4xx status codes** indicate that the server cannot fulfill the request because of something related to the **request or the client's current situation**.

Common examples:

| Code    | Meaning            | Example                                   |
| ------- | ------------------ | ----------------------------------------- |
| **400** | Bad Request        | Malformed JSON                            |
| **401** | Unauthorized       | Missing/invalid authentication            |
| **403** | Forbidden          | Insufficient permission                   |
| **404** | Not Found          | Invalid user ID                           |
| **405** | Method Not Allowed | DELETE not supported for resource         |
| **409** | Conflict           | Duplicate resource/current-state conflict |
| **429** | Too Many Requests  | Rate limit exceeded                       |

---

## 400 Bad Request

`400` indicates that the server cannot process the request because the request is invalid.

Example:

```http
POST /api/users
Content-Type: application/json

{
  "name": "Aman",
```

The JSON is malformed.

The server may respond:

```http
HTTP/1.1 400 Bad Request
```

Another example could be an invalid query parameter or incorrectly structured request.

---

# 6. 401 Unauthorized

`401` generally indicates that the request lacks valid authentication credentials.

Example:

```http
GET /api/profile
```

Response:

```http
HTTP/1.1 401 Unauthorized
```

Possible reasons:

* Authentication credentials are missing.
* Access token is invalid.
* Access token has expired.

Example:

```text
Client
  |
  | GET /api/profile
  | No valid authentication
  v
Server
  |
  | 401 Unauthorized
  v
Client
```

The client may need to authenticate and try again.

> **Interview point:** Despite its name, `401` is primarily about **authentication**, not permission.

---

# 7. 403 Forbidden

`403` indicates that the server understood the request but **refuses to authorize access**.

Example:

```text
Authenticated User
       |
       | GET /admin/users
       v
Server
       |
       | User is authenticated
       | but lacks required permission
       v
403 Forbidden
```

For example, a normal user might successfully authenticate but still be unable to access an administrator-only endpoint.

---

## 401 vs 403 — Important Interview Distinction

This is one of the most common HTTP interview questions.

| Status  | Main idea                                    | Example                         |
| ------- | -------------------------------------------- | ------------------------------- |
| **401** | Authentication is missing or invalid         | No valid login/token            |
| **403** | Request is understood, but access is refused | Logged-in user lacks permission |

### Easy memory trick

```text
401 → "Who are you?"
403 → "I know who you are, but you can't do this."
```

The exact API behavior can vary, but this is the standard conceptual distinction.

---

# 8. 404 Not Found

`404` indicates that the server could not find a current representation for the requested resource.

Example:

```http
GET /api/users/999999
```

If that user does not exist:

```http
HTTP/1.1 404 Not Found
```

Another common example:

```text
GET /products/abc
        |
        v
Product does not exist
        |
        v
404 Not Found
```

---

# 9. 405 Method Not Allowed

`405` means the HTTP method used is **not supported for the requested resource**.

For example, suppose:

```text
GET /api/users
```

is supported, but:

```text
DELETE /api/users
```

is not allowed.

The server may respond:

```http
HTTP/1.1 405 Method Not Allowed
Allow: GET, POST
```

The `Allow` header can indicate which methods are supported.

### Important distinction

```text
404 → Resource wasn't found
405 → Resource exists, but this HTTP method isn't allowed
```

---

# 10. 409 Conflict

`409 Conflict` indicates that the request conflicts with the **current state of the target resource**.

Example:

```http
POST /api/users
```

Suppose the API requires usernames to be unique and `"aman"` already exists.

The server may respond:

```http
HTTP/1.1 409 Conflict
```

Another example is attempting an operation that conflicts with the current state of a resource.

---

# 11. 429 Too Many Requests

`429` indicates that the client has sent too many requests within a given period.

This is commonly associated with **rate limiting**.

Example:

```text
Client
  |
  | Request 1
  | Request 2
  | Request 3
  | ...
  | Request 1000
  v
Server
  |
  | Rate limit exceeded
  v
429 Too Many Requests
```

A server may also provide a `Retry-After` header to tell the client when it can try again.

---

# 12. 5xx — Server Errors

**5xx status codes** indicate that the server failed to successfully handle an otherwise valid request.

Common examples:

| Code                          | Meaning                                                            |
| ----------------------------- | ------------------------------------------------------------------ |
| **500 Internal Server Error** | Generic server-side failure                                        |
| **502 Bad Gateway**           | Gateway/proxy received an invalid response from an upstream server |
| **503 Service Unavailable**   | Server temporarily unable to handle the request                    |
| **504 Gateway Timeout**       | Gateway/proxy did not receive a timely upstream response           |

---

## 500 Internal Server Error

`500` is a general server-side failure.

Example:

```text
Client
  |
  | GET /api/users
  v
Application Server
  |
  | Unexpected exception
  v
500 Internal Server Error
```

For example, the application might encounter an unexpected programming error or unhandled exception.

---

## 502 Bad Gateway

`502` commonly occurs when a gateway or reverse proxy receives an **invalid response from an upstream server**.

Example:

```text
Client
   |
   v
Load Balancer / Proxy
   |
   v
Application Server
   |
   X Invalid response
   |
   v
Proxy returns 502
```

For example:

```text
Browser
   ↓
Nginx / Load Balancer
   ↓
Application Server
```

If the application server responds incorrectly to the proxy, the proxy may return:

```http
502 Bad Gateway
```

---

## 503 Service Unavailable

`503` indicates that the server is **temporarily unable to handle the request**.

Possible situations:

* Server overload
* Maintenance
* Temporary unavailability
* Service dependency problems

Example:

```text
Client
  |
  | Request
  v
Server
  |
  | Temporarily unavailable
  v
503 Service Unavailable
```

A `Retry-After` header may be included when appropriate.

---

## 504 Gateway Timeout

`504` commonly means that a gateway or proxy **did not receive a timely response from an upstream server**.

Example:

```text
Client
   |
   v
Gateway / Proxy
   |
   | Waiting...
   | Waiting...
   X Timeout
   |
   v
504 Gateway Timeout
```

For example, an API gateway may wait for a backend service, but the backend takes too long to respond.

---

# 13. Complete API Example

Suppose we have this endpoint:

```http

```

Different situations can produce different status codes.

### Case 1 — User exists

```http
HTTP/1.1 200 OK

{
  "id": 123,
  "name": "Aman"
}
```

Meaning:

```text
User found → 200 OK
```

---

### Case 2 — User doesn't exist

```http
HTTP/1.1 404 Not Found
```

Meaning:

```text
User not found → 404
```

---

### Case 3 — Authentication is missing/invalid

```http
HTTP/1.1 401 Unauthorized
```

Meaning:

```text
Authentication problem → 401
```

---

### Case 4 — User is authenticated but lacks permission

```http
HTTP/1.1 403 Forbidden
```

Meaning:

```text
Authorization problem → 403
```

---

### Case 5 — Unexpected server failure

```http
HTTP/1.1 500 Internal Server Error
```

Meaning:

```text
Unexpected server-side failure → 500
```

# 14. Status Code Classes vs Individual Codes

It is important to distinguish between the **category** and the **specific status code**.

For example:

```text
4xx
```

means a broad category of client/request-related errors.

But:

```text
404
```

specifically means:

```text
Not Found
```

Similarly:

```text
5xx
```

means server-side error category, while:

```text
500
502
503
504
```

represent different situations.

---

# 15. Status Codes Are Part of the HTTP Response

A simplified HTTP response looks like:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 42

{
  "message": "Success"
}
```

It contains:

```text
Status Line
    ↓
HTTP/1.1 200 OK

Headers
    ↓
Content-Type: application/json
Content-Length: 42

Body
    ↓
{"message":"Success"}
```

So the status code is one important part of the HTTP response.

---

# 16. Status Codes and REST APIs

Status codes are especially important when designing APIs because they communicate the result of an operation without requiring the client to inspect only the response body.

For example:

```http
POST /api/products
```

Successful creation:

```http
201 Created
```

Invalid request:

```http
400 Bad Request
```

Not authenticated:

```http
401 Unauthorized
```

Not allowed:

```http
403 Forbidden
```

Duplicate/conflicting state:

```http
409 Conflict
```

Rate limited:

```http
429 Too Many Requests
```

Unexpected server failure:

```http
500 Internal Server Error
```

This allows clients to handle responses systematically.

# 17. Common Interview Confusions

### 1. 401 vs 403

```text
401 → Authentication problem
403 → Authorization/access problem
```

Remember:

```text
Authentication = Who are you?
Authorization  = What are you allowed to do?
```

---

### 2. 404 vs 405

```text
404 → Resource not found
405 → Resource found, but HTTP method not allowed
```

---

### 3. 500 vs 502 vs 503 vs 504

```text
500 → Application/server encountered an internal failure

502 → Gateway/proxy got an invalid upstream response

503 → Service is temporarily unavailable

504 → Gateway/proxy timed out waiting for upstream
```

---

### 4. 200 Does Not Mean "Everything About the Application Is Perfect"

`200` means the HTTP request was successfully handled according to the response semantics.

The response body could still contain application-specific information that the client must interpret.

---

### 5. 404 Does Not Always Mean "The Server Is Down"

A `404` usually means the requested resource or route was not found.

A server can be completely healthy while returning:

```http
404 Not Found
```

for a nonexistent resource.

# 19. Memory Trick

A simple way to remember the five categories:

```text
1xx → "Wait / Information"
2xx → "Success"
3xx → "Go somewhere else / use cache"
4xx → "Your request has a problem"
5xx → "Server-side failure"
```

Or simply:

```text
1 = Information
2 = Success
3 = Redirect
4 = Client
5 = Server
```

# 20. Interview Takeaway

> **HTTP status codes are three-digit response codes that communicate the result of an HTTP request. They are grouped into 1xx informational, 2xx success, 3xx redirection, 4xx client/request errors, and 5xx server errors.**

The most important codes to remember are:

```text
200 → OK
201 → Created
204 → No Content

301 → Moved Permanently
302 → Found
304 → Not Modified

400 → Bad Request
401 → Authentication problem
403 → Forbidden / authorization problem
404 → Not Found
405 → Method Not Allowed
409 → Conflict
429 → Too Many Requests

500 → Internal Server Error
502 → Bad Gateway
503 → Service Unavailable
504 → Gateway Timeout
```
