# Q16. What Is HTTP/1.1 vs HTTP/2 at a High Level?

Both **HTTP/1.1** and **HTTP/2** are versions of the **HTTP (HyperText Transfer Protocol)** used for communication between clients and servers.

HTTP/2 was designed primarily to improve **performance, efficiency, and connection utilization**, while preserving the core HTTP semantics such as:

* HTTP methods (`GET`, `POST`, `PUT`, `DELETE`, etc.)
* Status codes (`200`, `404`, `500`, etc.)
* Headers
* Request/response concepts
* URLs and resources

The major difference is **how HTTP messages are transported and organized over the connection**.

---

# 1. Key Differences

| Feature               | HTTP/1.1                                                        | HTTP/2                                                                  |
| --------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Data representation   | Text-based HTTP message syntax                                  | Binary framing                                                          |
| Multiplexing          | ❌ No HTTP/2-style multiplexing                                  | ✅ Multiple streams over one connection                                  |
| Requests in parallel  | Limited by connection behavior                                  | ✅ Multiple concurrent streams                                           |
| Head-of-line blocking | Exists at HTTP/1.1 request/response level                       | Reduced at HTTP layer, but TCP-level blocking remains                   |
| Header compression    | No standardized HTTP/1.1 header compression mechanism           | **HPACK**                                                               |
| Connection usage      | Browsers historically used multiple TCP connections             | Typically fewer TCP connections                                         |
| Server Push           | Not standardized as an HTTP/1.1 feature                         | Originally defined, later deprecated/removed from HTTP/2 specifications |
| Underlying transport  | TCP                                                             | TCP                                                                     |
| Main goal             | Simple and broadly interoperable request/response communication | More efficient use of connections                                       |

### Core idea

```text
HTTP/1.1
→ Multiple HTTP requests/responses
→ Often multiple TCP connections for parallelism

HTTP/2
→ Multiple HTTP streams
→ One TCP connection can carry many streams concurrently
```

---

# 2. HTTP/1.1

HTTP/1.1 represents HTTP communication using the familiar **text-based request/response format**.

For example:

```http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
```

The server might respond:

```http
HTTP/1.1 200 OK
Content-Type: text/html

<html>
    ...
</html>
```

Humans can easily read this representation.

---

## HTTP/1.1 Request Structure

A simplified HTTP/1.1 request contains:

```text
Request Line
     ↓
GET /index.html HTTP/1.1

Headers
     ↓
Host: example.com
Accept: text/html

Optional Body
     ↓
Request data
```

The response similarly contains:

```text
Status Line
     ↓
HTTP/1.1 200 OK

Headers
     ↓
Content-Type: text/html

Body
     ↓
HTML content
```

---

# 3. Persistent Connections in HTTP/1.1

HTTP/1.1 supports **persistent TCP connections**, meaning the same TCP connection can be reused for multiple requests instead of creating a new TCP connection for every request.

Conceptually:

```text
TCP Connection
      |
      +---- Request 1 → Response 1
      |
      +---- Request 2 → Response 2
      |
      +---- Request 3 → Response 3
```

This was an important improvement compared with creating a separate connection for every request.

However, HTTP/1.1 does **not** provide HTTP/2-style multiplexing where independent streams can be freely interleaved over one connection.

---

# 4. HTTP/1.1 and Parallel Requests

Consider a webpage containing:

```text
index.html
style.css
app.js
logo.png
image.jpg
```

The browser may need to request several resources.

Historically, browsers opened **multiple TCP connections** to improve parallelism:

```text
Connection 1 → HTML
Connection 2 → CSS
Connection 3 → JavaScript
Connection 4 → Image
```

This allowed multiple transfers to make progress simultaneously.

However, maintaining multiple TCP connections has costs:

* More connection state
* More TCP overhead
* More TLS/session overhead when HTTPS is used
* More congestion-control state
* Less efficient connection utilization

HTTP/2 was designed to address much of this inefficiency.

---

# 5. HTTP/1.1 Pipelining

HTTP/1.1 also defined **request pipelining**, where multiple requests could be sent without waiting for each response.

Conceptually:

```text
Request 1
Request 2
Request 3
      ↓
Server
      ↓
Response 1
Response 2
Response 3
```

However, pipelining had practical limitations and was not widely adopted by browsers.

One major problem was **head-of-line blocking at the HTTP request/response level**.

If an earlier response was delayed, later responses could be affected.

This is different from HTTP/2's stream multiplexing.

---

# 6. HTTP/2

HTTP/2 changes the way HTTP communication is represented over a connection.

Instead of sending HTTP/1.1-style messages as the primary wire-level representation, HTTP/2 uses **binary framing**.

The application still thinks in terms of:

```text
Request
Response
Headers
Body
```

But HTTP/2 transports these concepts using smaller binary **frames**.

---

# 7. Binary Framing

HTTP/2 breaks communication into binary frames.

Conceptually:

```text
HTTP Request / Response
        ↓
   HTTP/2 Frames
        ↓
+---------+---------+---------+---------+
| Frame 1 | Frame 2 | Frame 3 | Frame 4 |
+---------+---------+---------+---------+
```

These frames contain information associated with different streams.

The binary format is designed for machines to process efficiently and unambiguously.

### Important point

"Binary" does **not** mean HTTP/2 changed the meaning of HTTP.

For example:

```text
GET /users/123
```

is still conceptually a GET request.

HTTP/2 mainly changes the **wire representation and transport organization**, not the fundamental HTTP semantics.

---

# 8. HTTP/2 Streams

A major HTTP/2 feature is the concept of a **stream**.

A stream represents a logical, independent exchange of HTTP messages within an HTTP/2 connection.

For example:

```text
One TCP Connection
        |
        +── Stream 1 → HTML
        |
        +── Stream 3 → CSS
        |
        +── Stream 5 → JavaScript
        |
        +── Stream 7 → Image
```

These streams can share the same TCP connection.

---

# 9. HTTP/2 Multiplexing

HTTP/2 allows frames from multiple streams to be **interleaved** over a single TCP connection.

For example:

```text
One TCP Connection
        |
        v

S1 Frame → S3 Frame → S1 Frame → S5 Frame
     → S3 Frame → S7 Frame → S1 Frame
```

Instead of waiting for an entire response before another stream can send data, frames belonging to different streams can be mixed.

This is called **multiplexing**.

---

## Why Multiplexing Helps

Suppose a webpage needs:

```text
HTML
CSS
JavaScript
Image
```

With HTTP/1.1, browsers historically used multiple TCP connections to obtain better parallelism.

With HTTP/2:

```text
                 One TCP Connection
                        |
        +---------------+---------------+
        |               |               |
        v               v               v
     Stream 1        Stream 3        Stream 5
       HTML            CSS             JS
```

All these streams can make progress through the same connection.

This can reduce the need for multiple TCP connections and improve resource utilization.

---

# 10. HTTP/1.1 vs HTTP/2 Multiplexing

### HTTP/1.1

Conceptually:

```text
Connection
    |
    +── Request → Response
    |
    +── Request → Response
    |
    +── Request → Response
```

Parallelism was often achieved by opening multiple connections.

### HTTP/2

```text
             One TCP Connection
                    |
       +------------+------------+
       |            |            |
       v            v            v
    Stream 1     Stream 3     Stream 5
       |            |            |
       +------ Frames interleaved
```

This is one of the most important differences between HTTP/1.1 and HTTP/2.

---

# 11. HTTP/2 Header Compression

HTTP/2 introduces **HPACK**, a header compression mechanism.

HTTP requests often contain repeated headers such as:

```http
Host: example.com
User-Agent: ...
Accept: application/json
Authorization: Bearer ...
Cookie: session=...
```

When a browser sends many requests to the same server, many header values may be repeated.

For example:

```text
Request 1 → Cookie, Authorization, User-Agent...
Request 2 → Cookie, Authorization, User-Agent...
Request 3 → Cookie, Authorization, User-Agent...
```

Sending all of these repeatedly can waste bandwidth.

HPACK reduces this overhead using techniques including:

* Header compression
* A dynamic table
* A static table
* References to previously seen header information

Conceptually:

```text
HTTP/1.1

Request 1 → Large headers
Request 2 → Large repeated headers
Request 3 → Large repeated headers


HTTP/2

Request 1 → Headers encoded
Request 2 → References/compressed representation
Request 3 → References/compressed representation
```

This can be particularly useful for applications with many requests and large/repeated headers.

---

# 12. Head-of-Line Blocking

This is one of the most important interview concepts when comparing HTTP/1.1 and HTTP/2.

## HTTP/1.1

HTTP/1.1 can suffer from **HTTP-level head-of-line blocking**, especially when requests/responses share a connection and an earlier response delays later work.

Multiple TCP connections were often used to reduce this problem.

---

## HTTP/2

HTTP/2 solves much of the HTTP-layer ordering problem through multiplexed streams.

For example:

```text
One HTTP/2 Connection

Stream 1 → HTML
Stream 3 → CSS
Stream 5 → JavaScript
Stream 7 → Image
```

A slow stream does not inherently require the other HTTP/2 streams to wait at the HTTP layer.

However, there is an important limitation.

---

# 13. The Important TCP Head-of-Line Blocking Problem

HTTP/2 typically runs over **TCP**.

TCP provides an ordered byte stream.

Suppose TCP sends:

```text
Packet 1
Packet 2
Packet 3
Packet 4
Packet 5
```

But packet 2 is lost:

```text
Packet 1 → received
Packet 2 → LOST
Packet 3 → received
Packet 4 → received
Packet 5 → received
```

TCP cannot normally deliver later bytes to the application while maintaining the required byte-stream ordering until the missing data is recovered.

Conceptually:

```text
TCP
 |
 | Packet 1 ✓
 | Packet 2 ✗
 | Packet 3 ✓
 | Packet 4 ✓
 |
 v
Application waits for missing bytes
```

Because HTTP/2 streams share the same TCP connection, this can affect **multiple HTTP/2 streams**.

Therefore:

> **HTTP/2 reduces HTTP-level head-of-line blocking, but it does not eliminate TCP-level head-of-line blocking.**

This distinction is extremely important in interviews.

---

# 14. Why HTTP/3 Was Introduced

HTTP/3 uses **QUIC**, which runs over UDP.

Instead of relying on TCP's single ordered byte stream, QUIC provides multiple independent streams at the transport layer.

Conceptually:

```text
HTTP/2

HTTP/2 Streams
      ↓
     TCP
      ↓
One lost TCP packet can delay
data delivery across the connection


HTTP/3

HTTP/3
  ↓
 QUIC
  ↓
Independent streams
  ↓
UDP
```

If data belonging to one QUIC stream is lost, other streams can continue making progress when their data is available.

This is one of the major architectural differences between HTTP/2 and HTTP/3.

---

# 15. Connection Usage

### HTTP/1.1

Browsers historically used multiple TCP connections:

```text
Browser
   |
   +── TCP 1 → HTML
   |
   +── TCP 2 → CSS
   |
   +── TCP 3 → JavaScript
   |
   +── TCP 4 → Images
```

### HTTP/2

Typically:

```text
Browser
   |
   +──────── One TCP Connection ────────+
                                        |
                             +----------+----------+
                             |          |          |
                          Stream 1   Stream 3   Stream 5
```

This can reduce connection overhead.

However, "HTTP/2 always uses exactly one TCP connection" is too strong. Implementations can use more than one connection in some situations.

---

# 16. Server Push

HTTP/2 originally defined **server push**.

The basic idea was:

```text
Client
   |
   | Request HTML
   v
Server
   |
   | HTML
   | CSS
   | JS
   v
Client
```

The server could proactively send resources it believed the client would need.

However, server push saw limited practical adoption, and it was later **deprecated/removed from HTTP/2's standard evolution**.

Therefore, avoid saying:

> "HTTP/2 always uses server push."

That is incorrect.

---

# 17. Underlying Transport

Both HTTP/1.1 and HTTP/2 commonly run over **TCP**.

```text
HTTP/1.1
   ↓
 TCP
   ↓
 IP
   ↓
 Ethernet / Wi-Fi
```

```text
HTTP/2
   ↓
 TCP
   ↓
 IP
   ↓
 Ethernet / Wi-Fi
```

HTTP/3 changes this:

```text
HTTP/3
   ↓
 QUIC
   ↓
 UDP
   ↓
 IP
   ↓
 Ethernet / Wi-Fi
```

# 18. Practical Website Example

Suppose you open:

```text
https://example.com
```

The page requires:

```text
index.html
style.css
app.js
logo.png
```

### HTTP/1.1-style approach

Conceptually, the browser may use several TCP connections:

```text
TCP Connection 1 → HTML
TCP Connection 2 → CSS
TCP Connection 3 → JavaScript
TCP Connection 4 → Image
```

This provides parallelism but requires multiple connections.

### HTTP/2 approach

The browser can use one TCP connection:

```text
             One TCP Connection
                     |
       +-------------+-------------+
       |             |             |
       v             v             v
   Stream 1      Stream 3      Stream 5
    HTML           CSS            JS
       |
       +------ Stream 7 → Image
```

Frames from these streams can be interleaved.

# 20. Important Terminology

Do not confuse these terms:

| Term               | Meaning                                         |
| ------------------ | ----------------------------------------------- |
| **HTTP message**   | Request or response at HTTP semantics level     |
| **Frame**          | HTTP/2 binary unit of transmission              |
| **Stream**         | Logical bidirectional sequence within HTTP/2    |
| **TCP segment**    | Transport-layer unit used by TCP                |
| **TCP connection** | Reliable ordered byte-stream connection         |
| **Multiplexing**   | Multiple logical streams sharing one connection |

A useful conceptual hierarchy is:

```text
HTTP/2
  |
  +── Stream 1
  |      ├── Frames
  |      └── Frames
  |
  +── Stream 3
  |      ├── Frames
  |      └── Frames
  |
  +── Stream 5
         ├── Frames
         └── Frames
```

# 21. HTTP/1.1 vs HTTP/2 — Interview Comparison

| Feature             | HTTP/1.1                                          | HTTP/2                                 |
| ------------------- | ------------------------------------------------- | -------------------------------------- |
| HTTP representation | Text-oriented message syntax                      | Binary framing                         |
| Multiplexing        | ❌                                                 | ✅                                      |
| Streams             | No HTTP/2-style streams                           | ✅                                      |
| Header compression  | No standardized equivalent to HPACK               | ✅ HPACK                                |
| Parallelism         | Often multiple TCP connections                    | Multiple streams over connection       |
| TCP connections     | Often multiple historically                       | Typically fewer                        |
| HTTP-level HOL      | More significant                                  | Greatly reduced                        |
| TCP-level HOL       | Possible                                          | **Still possible**                     |
| Transport           | TCP                                               | TCP                                    |
| Server Push         | Not standardized                                  | Originally supported, later deprecated |
| Main goal           | Simple, persistent request/response communication | Efficient multiplexed communication    |

# 22. Common Interview Mistakes

### Mistake 1: "HTTP/2 eliminates head-of-line blocking."

❌ Not completely correct.

Correct:

> HTTP/2 reduces HTTP-layer head-of-line blocking through multiplexing, but TCP-level head-of-line blocking can still affect the connection.

---

### Mistake 2: "HTTP/2 uses UDP."

❌ Incorrect.

HTTP/2 normally uses:

```text
HTTP/2 → TCP
```

HTTP/3 uses:

```text
HTTP/3 → QUIC → UDP
```

---

### Mistake 3: "HTTP/2 changed HTTP methods."

❌ Not the main purpose.

HTTP/2 preserves the core HTTP semantics.

You can still use:

```text
GET
POST
PUT
PATCH
DELETE
```

The major changes are in **framing, multiplexing, header compression, and connection efficiency**.

---

### Mistake 4: "HTTP/1.1 cannot keep a connection alive."

❌ Incorrect.

HTTP/1.1 supports **persistent connections**.

The important distinction is that persistent connection ≠ HTTP/2 multiplexing.

---

### Mistake 5: "HTTP/2 always uses exactly one TCP connection."

❌ Too absolute.

HTTP/2 generally reduces the need for multiple connections, but implementations may establish multiple connections for various reasons.

---

### Mistake 6: "Binary framing means HTTP/2 is no longer HTTP."

❌ Incorrect.

HTTP semantics remain. The wire representation and transport organization are different.

# 24. Memory Trick

Remember:

```text
HTTP/1.1 → Multiple connections for parallelism
HTTP/2   → Multiple streams on one TCP connection
HTTP/3   → Multiple streams through QUIC over UDP
```

Or:

```text
1.1 → Connections
2   → Multiplexing
3   → QUIC
```

---

# 25. Interview Takeaway

> **HTTP/1.1 uses text-oriented HTTP messages and persistent TCP connections, while HTTP/2 introduces binary framing, multiplexing, and HPACK header compression so multiple HTTP streams can share a TCP connection efficiently. HTTP/2 reduces HTTP-level head-of-line blocking, but because it normally runs over TCP, packet loss can still cause connection-level head-of-line blocking. HTTP/3 addresses this using QUIC over UDP.**

### ⭐ Common Follow-up: HTTP/2 vs HTTP/3

```text
HTTP/2
   ↓
Binary framing + multiplexing
   ↓
TCP
   ↓
TCP-level HOL blocking can remain


HTTP/3
   ↓
Multiplexed HTTP streams
   ↓
QUIC
   ↓
UDP
   ↓
No TCP connection-level HOL blocking
```

The key progression is:

**HTTP/1.1 → persistent connections**

**HTTP/2 → multiplexed streams + HPACK**

**HTTP/3 → QUIC + independent streams**
