# Q17. What Is HTTP/3 and How Does It Differ Conceptually?

**HTTP/3** is a version of HTTP that uses **QUIC** as its transport protocol instead of TCP.

The biggest conceptual change is not the HTTP request/response model itself, but **the transport underneath HTTP**.

The progression can be remembered as:

```text
HTTP/1.1
   ↓
HTTP over TCP


HTTP/2
   ↓
HTTP over TCP
   ↓
Multiplexed HTTP streams


HTTP/3
   ↓
HTTP over QUIC
   ↓
QUIC over UDP
```

So:

```text
HTTP/1.1 → HTTP over TCP

HTTP/2   → HTTP over TCP with multiplexed streams

HTTP/3   → HTTP over QUIC over UDP
```

---

# 1. High-Level Architecture

## HTTP/1.1

```text
HTTP
 ↓
TCP
 ↓
IP
 ↓
Ethernet / Wi-Fi
```

HTTP/1.1 uses TCP's reliable, ordered byte-stream transport.

---

## HTTP/2

```text
HTTP
 ↓
HTTP/2 Streams
 ↓
TCP
 ↓
IP
 ↓
Ethernet / Wi-Fi
```

HTTP/2 introduces multiplexed streams, but those streams ultimately share a single TCP connection.

---

## HTTP/3

```text
HTTP
 ↓
HTTP/3
 ↓
QUIC
 ↓
UDP
 ↓
IP
 ↓
Ethernet / Wi-Fi
```

HTTP/3 uses QUIC instead of TCP.

QUIC itself provides many of the transport capabilities that applications traditionally obtained from TCP, while also providing features designed for modern Internet communication.

---

# 2. Why Was HTTP/3 Introduced?

HTTP/2 solved an important HTTP-level performance problem by allowing **multiple streams over one TCP connection**.

For example:

```text
HTTP/2

Stream A ─┐
Stream B ─┼──→ One TCP connection
Stream C ─┘
```

This means HTML, CSS, JavaScript, images, and other resources can be transferred concurrently using different HTTP/2 streams.

However, there is an important limitation:

> **TCP is a single ordered byte stream.**

TCP must deliver bytes in order.

---

# 3. The TCP Head-of-Line Blocking Problem

Suppose an HTTP/2 connection contains:

```text
Stream A → HTML
Stream B → CSS
Stream C → JavaScript
```

All three streams share one TCP connection:

```text
Stream A ─┐
Stream B ─┼──→ TCP Connection
Stream C ─┘
```

Now suppose a TCP segment carrying some data is lost:

```text
TCP Segment 1 → Received
TCP Segment 2 → LOST
TCP Segment 3 → Received
TCP Segment 4 → Received
```

TCP cannot simply deliver the later bytes to the application while pretending the missing bytes do not exist.

It must recover the missing data and preserve the ordered byte-stream abstraction.

Conceptually:

```text
TCP
 |
 +── Segment 1 ✓
 |
 +── Segment 2 ✗
 |
 +── Segment 3 ✓
 |
 +── Segment 4 ✓
 |
 v
Waiting for missing bytes
```

Because HTTP/2 streams share that TCP connection, a loss affecting one part of the connection can delay delivery of data associated with other streams.

This is called **connection-level head-of-line (HOL) blocking**.

---

# 4. How HTTP/3 Changes This

HTTP/3 uses **QUIC**, which provides independent streams within a QUIC connection.

Conceptually:

```text
QUIC Connection
│
├── Stream A → HTML
├── Stream B → CSS
└── Stream C → JavaScript
```

Suppose data belonging to Stream A is lost:

```text
QUIC Connection
│
├── Stream A → LOST DATA → waits for recovery
├── Stream B → can continue
└── Stream C → can continue
```

The loss affecting Stream A does not inherently require Stream B and Stream C to stop delivering their independently available data.

Therefore:

> **HTTP/3 avoids TCP's connection-level head-of-line blocking by using QUIC's independent streams instead of TCP's single ordered byte stream.**

This is one of the most important conceptual differences between HTTP/2 and HTTP/3.

---

# 5. Major Features of HTTP/3

## 1. QUIC Instead of TCP

HTTP/3 uses **QUIC** as its transport protocol.

QUIC runs over UDP:

```text
HTTP/3
   ↓
QUIC
   ↓
UDP
   ↓
IP
```

However, QUIC provides many transport features that are not provided by plain UDP.

These include:

* Reliable delivery
* Congestion control
* Flow control
* Stream multiplexing
* Connection management
* Secure connection establishment

Therefore:

> **HTTP/3 using UDP does not mean HTTP/3 is inherently unreliable.**

The reliability comes from **QUIC**, not from UDP.

---

# 6. QUIC vs UDP

This is an extremely common interview confusion.

A simplified view is:

```text
HTTP/3
   ↓
QUIC
   ↓
UDP
   ↓
IP
```

UDP itself provides a lightweight datagram transport.

UDP does **not** provide TCP-style:

* Reliable delivery
* Ordered byte-stream delivery
* Retransmission
* Congestion control

QUIC builds additional transport functionality above UDP.

Conceptually:

```text
UDP
 ↓
Basic datagram delivery
 ↓
QUIC adds:
   • Reliability
   • Congestion control
   • Flow control
   • Multiplexed streams
   • Secure connection establishment
 ↓
HTTP/3
```

So saying:

> "HTTP/3 is unreliable because it uses UDP"

is incorrect.

A better statement is:

> **HTTP/3 uses QUIC over UDP, and QUIC provides reliable, secure, multiplexed transport semantics to HTTP/3.**

---

# 7. Reduced Head-of-Line Blocking

HTTP/3's independent QUIC streams reduce a major limitation of HTTP/2 over TCP.

### HTTP/2

```text
Stream A ─┐
Stream B ─┼──→ TCP
Stream C ─┘
            |
            ↓
     One ordered byte stream
            |
            ↓
TCP packet loss can delay
data delivery across streams
```

### HTTP/3

```text
Stream A ─┐
Stream B ─┼──→ QUIC
Stream C ─┘
            |
            ↓
      Independent streams
```

If Stream A experiences packet loss:

```text
Stream A → affected
Stream B → can continue
Stream C → can continue
```

This does not mean HTTP/3 makes packet loss irrelevant.

The affected stream still has to recover its lost data.

The important difference is that **other independent streams are not inherently blocked by the loss**.

---

# 8. TLS 1.3 Integration

Another major feature of QUIC is its integration with **TLS 1.3**.

Traditional HTTPS over TCP can be conceptualized as:

```text
HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
```

With HTTP/3:

```text
HTTP/3
 ↓
QUIC
 ↓
UDP
 ↓
IP
```

QUIC incorporates TLS 1.3 into its connection establishment.

This means encryption and authentication are an integral part of establishing a QUIC connection.

---

# 9. What Does TLS Provide?

TLS provides important security properties such as:

### Confidentiality

Data is encrypted so unauthorized observers cannot simply read the HTTP content.

### Integrity

Attackers should not be able to silently modify protected data without detection.

### Authentication

The TLS certificate and trust system help authenticate the server endpoint.

Conceptually:

```text
HTTP/3
   ↓
QUIC + TLS 1.3
   ↓
Encrypted communication
   ↓
UDP
```

---

# 10. Why TLS 1.3 Matters for HTTP/3

QUIC does not treat security as an optional extra layer that can simply be added later.

TLS 1.3 is closely integrated into QUIC's connection establishment.

This helps QUIC combine:

```text
Transport establishment
       +
Security establishment
       +
Stream setup
```

into an efficient connection-establishment design.

### Important interview point

Do not say:

> "HTTP/3 doesn't use TLS because it uses UDP."

Incorrect.

HTTP/3 normally uses **QUIC with TLS 1.3**.

---

# 11. Connection Migration

QUIC supports **connection migration**, which is particularly useful for mobile devices.

Consider a smartphone moving between networks:

```text
Wi-Fi
  ↓
Mobile Network
```

A traditional TCP connection is associated with the TCP connection's network endpoints.

If the device's network path changes significantly, the TCP connection may need to be recreated.

QUIC uses connection identifiers and has mechanisms that allow a connection to survive certain network-path/address changes.

Conceptually:

```text
Before:

Phone
  |
  | Wi-Fi
  v
Server
  |
  | QUIC Connection


Network changes


After:

Phone
  |
  | Mobile Network
  v
Server
  |
  | Same logical QUIC connection
```

This can reduce disruption during network changes.

### Important nuance

Connection migration does **not** mean every network change is guaranteed to preserve a connection.

It depends on:

* QUIC connection state
* Connection identifiers
* Network conditions
* NAT/firewall behavior
* Endpoint implementation
* Whether the old/new paths can be validated

So the accurate statement is:

> **QUIC supports connection migration, allowing a connection to survive certain network-path changes.**

# 12. HTTP/2 vs HTTP/3

| Feature                      | HTTP/2                                    | HTTP/3                                               |
| ---------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| HTTP version                 | HTTP/2                                    | HTTP/3                                               |
| Transport                    | TCP                                       | QUIC                                                 |
| Underlying network transport | TCP → IP                                  | UDP → IP                                             |
| Multiplexing                 | Yes                                       | Yes                                                  |
| Streams                      | HTTP/2 streams                            | QUIC streams                                         |
| Header compression           | **HPACK**                                 | **QPACK**                                            |
| TCP-level HOL blocking       | Possible                                  | Avoided because QUIC is not TCP                      |
| TLS                          | Commonly TLS 1.2/1.3                      | TLS 1.3 integrated with QUIC                         |
| Connection migration         | TCP does not provide QUIC-style migration | Supported by QUIC                                    |
| Transport reliability        | TCP                                       | QUIC                                                 |
| Congestion control           | TCP                                       | QUIC                                                 |
| Flow control                 | TCP                                       | QUIC                                                 |
| Main conceptual improvement  | Multiplex HTTP streams over TCP           | Multiplex streams without TCP's connection-level HOL |

# 13. HPACK vs QPACK

This is another useful interview detail.

### HTTP/2

Uses:

```text
HPACK
```

for HTTP header compression.

### HTTP/3

Uses:

```text
QPACK
```

for HTTP header compression.

Why was a different mechanism needed?

Because HTTP/3 uses QUIC's independently multiplexed streams rather than TCP's ordered byte stream.

QPACK is designed to work effectively with QUIC's stream model while avoiding problematic blocking behavior caused by header compression dependencies.

So remember:

```text
HTTP/2 → HPACK
HTTP/3 → QPACK
```

# 15. Easy Mental Model

Think of HTTP versions as improving the communication pipeline.

## HTTP/1.1 — Basic lanes

```text
One connection
      ↓
Request → Response
Request → Response
Request → Response
```

Browsers historically created multiple connections to achieve more parallelism.

---

## HTTP/2 — Multiple lanes over TCP

```text
              One TCP Connection
                     |
       +-------------+-------------+
       |             |             |
       v             v             v
   Stream A      Stream B      Stream C
       |             |             |
       +------ Multiplexed ------+
```

Multiple streams can share one connection.

But:

```text
TCP
 ↓
One ordered byte stream
 ↓
Loss can cause connection-level blocking
```

---

## HTTP/3 — Independent QUIC streams

```text
              One QUIC Connection
                     |
       +-------------+-------------+
       |             |             |
       v             v             v
   Stream A      Stream B      Stream C
       |             |             |
       +---- Independent streams--+
```

If Stream A loses data:

```text
Stream A → waits for recovery

Stream B → can continue

Stream C → can continue
```

# 18. Important Interview Point

Do **not** say:

> ❌ "HTTP/3 uses UDP, so it is unreliable."

That is incorrect.

The correct layering is:

```text
HTTP/3
   ↓
QUIC
   ↓
UDP
```

UDP provides the underlying datagram transport.

QUIC adds:

```text
• Reliable delivery
• Congestion control
• Flow control
• Stream multiplexing
• Connection management
• TLS 1.3 security
```

Therefore:

> **HTTP/3 uses UDP underneath, but HTTP/3 communication is carried over QUIC, which provides the transport features required by HTTP/3.**

# 19. Common Interview Mistakes

### Mistake 1: "HTTP/3 is HTTP over UDP."

This is incomplete.

Better:

```text
HTTP/3
   ↓
QUIC
   ↓
UDP
```

HTTP/3 does **not** directly depend on plain UDP for all its transport semantics.

---

### Mistake 2: "QUIC is just UDP."

Incorrect.

UDP is a basic datagram transport.

QUIC is a much richer transport protocol built over UDP.

---

### Mistake 3: "HTTP/3 doesn't provide reliability."

Incorrect.

QUIC provides reliable delivery mechanisms for the streams that require them.

---

### Mistake 4: "HTTP/2 has no multiplexing."

Incorrect.

HTTP/2 introduced **multiplexed streams**.

The limitation is that all those streams share a TCP connection.

---

### Mistake 5: "HTTP/3 eliminates all head-of-line blocking."

Too broad.

More accurately:

> HTTP/3 avoids **TCP's connection-level head-of-line blocking** by using QUIC's independently multiplexed streams.

An individual QUIC stream can still be affected by loss of its own data.

---

### Mistake 6: "HTTP/3 doesn't use TLS."

Incorrect.

QUIC incorporates **TLS 1.3** into its connection establishment.

---

### Mistake 7: "Connection migration means the connection can never break."

Incorrect.

QUIC supports migration across certain network-path/address changes, but network conditions, endpoint behavior, NATs, firewalls, and path validation can still cause a connection to fail.

# 22. Interview Takeaway

> **HTTP/3 is HTTP running over QUIC rather than TCP. Its biggest conceptual change is replacing TCP's single ordered byte-stream transport with QUIC's independently multiplexed streams. QUIC runs over UDP but provides transport features such as reliable delivery, congestion control, flow control, stream multiplexing, TLS 1.3 security, and connection migration. Because QUIC does not use TCP's single ordered byte stream, packet loss on one stream does not inherently block delivery on other streams.**

### ⭐ One-Line Interview Answer

**HTTP/3 = HTTP over QUIC over UDP, where QUIC provides secure, reliable, multiplexed transport without TCP's connection-level head-of-line blocking.**
