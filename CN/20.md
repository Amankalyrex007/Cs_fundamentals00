# Q20. What is DNS?

**DNS (Domain Name System)** is a distributed naming system that translates **human-readable domain names** into network information, most commonly **IP addresses**, so clients can locate servers and services over an IP network.

For example:

```text
www.example.com
       |
       | DNS lookup
       v
93.184.216.34
```

Instead of remembering an IP address such as:

```text
93.184.216.34
```

users can simply remember:

```text
www.example.com
```

DNS is therefore often described as the **directory service of the Internet**.

---

# 1. Why Is DNS Needed?

Humans prefer meaningful names:

```text
google.com
github.com
amazon.com
example.com
```

Networks communicate using IP addresses such as:

```text
142.250.x.x
```

or IPv6 addresses such as:

```text
2001:db8::1
```

DNS provides the mapping between these names and network information.

Conceptually:

```text
Human
  |
  | "I want example.com"
  v
DNS
  |
  | "Its address is 93.184.216.34"
  v
IP Network
```

Without DNS, users would often have to remember IP addresses directly.

---

# 2. DNS Is More Than "Domain → IP"

A common beginner definition is:

> DNS converts domain names into IP addresses.

This is useful, but incomplete.

DNS is actually a **general distributed naming system** that stores different types of records.

For example:

```text
Domain
  |
  +── A      → IPv4 address
  +── AAAA   → IPv6 address
  +── MX     → Mail server
  +── CNAME  → Alias
  +── NS     → Authoritative name server
  +── TXT    → Text/policy information
  +── PTR    → Reverse DNS
```

Therefore, DNS can provide information about **how a name should be resolved or which service is associated with that name**, not just an IP address.

---

# 3. How DNS Resolution Works

Suppose you enter:

```text
https://www.example.com
```

A simplified DNS resolution process is:

```text
Browser
   |
   v
DNS Cache
   |
   v
Recursive DNS Resolver
   |
   v
Root DNS Server
   |
   v
.com TLD Server
   |
   v
Authoritative DNS Server
   |
   v
IP Address
```

The resolver eventually obtains the required DNS record and returns the result to the client.

For example:

```text
Client:
"What is the IP of www.example.com?"

        |
        v

Recursive Resolver
        |
        v
      Root
        |
        v
     .com TLD
        |
        v
Authoritative DNS Server
        |
        v
"93.184.216.34"

        |
        v

Client
93.184.216.34
```

However, this is a **simplified flow**.

In practice, caching often allows the resolver to answer without contacting every level of the hierarchy.

---

# 4. Important DNS Components

The DNS system contains several important components.

---

## 4.1 Recursive DNS Resolver

A **recursive resolver** performs DNS lookups on behalf of the client.

The client generally asks the resolver:

```text
"What is the address of www.example.com?"
```

The resolver does the work of obtaining the answer.

Examples include:

* ISP-operated resolvers
* Enterprise/network resolvers
* Public DNS resolvers

Conceptually:

```text
Client
   |
   | DNS query
   v
Recursive Resolver
   |
   | performs lookup if needed
   v
DNS hierarchy
```

The resolver also maintains a **cache**.

---

# 5. Root DNS Servers

At the top of the public DNS hierarchy are the **root DNS servers/root server system**.

They generally do not provide the final IP address for every domain.

Instead, they provide information about where to find the appropriate **Top-Level Domain (TLD) name servers**.

For example, for:

```text
www.example.com
```

the root system can direct the resolver toward the:

```text
.com
```

TLD name servers.

Conceptually:

```text
Root
 |
 +---- .com
 +---- .org
 +---- .in
 +---- .net
 ...
```

---

# 6. TLD Servers

**TLD** stands for:

> **Top-Level Domain**

Examples include:

```text
.com
.org
.net
.in
.edu
```

A TLD name server is responsible for information about domains under that TLD.

For example:

```text
example.com
```

belongs under:

```text
.com
```

The `.com` TLD infrastructure can direct the resolver toward the **authoritative name servers** responsible for `example.com`.

Important distinction:

```text
Root
  ↓
Which TLD?
  ↓
TLD server
  ↓
Which authoritative server?
  ↓
Authoritative DNS server
```

---

# 7. Authoritative DNS Server

An **authoritative DNS server** holds the DNS information for a particular domain/zone and provides authoritative answers for that data.

For example, it may contain:

```text
example.com    A       93.184.216.34
example.com    AAAA    2001:db8::1
```

If the resolver asks:

```text
"What is the A record for example.com?"
```

the authoritative server can provide the configured answer.

Conceptually:

```text
example.com
      |
      v
Authoritative DNS
      |
      +---- A     → IPv4
      +---- AAAA  → IPv6
      +---- MX    → Mail servers
      +---- TXT   → Text/policy data
```

---

# 8. Complete DNS Resolution Example

Suppose a user enters:

```text
https://www.example.com
```

The browser needs the IP address associated with the hostname.

A simplified process is:

```text
1. Browser checks its DNS cache
              ↓
2. Operating system may check its cache
              ↓
3. DNS query goes to recursive resolver
              ↓
4. Resolver checks its cache
              ↓
5. If needed, resolver asks root
              ↓
6. Root points toward .com TLD
              ↓
7. .com TLD points toward authoritative server
              ↓
8. Authoritative server returns DNS record
              ↓
9. Resolver caches the answer
              ↓
10. Resolver returns the answer to client
```

The browser can then use the resulting address to establish the appropriate network connection.

---

# 9. DNS Caching

DNS would be inefficient if every request required a complete traversal of:

```text
Root
  ↓
TLD
  ↓
Authoritative server
```

Therefore, DNS uses extensive caching.

Caching may occur at multiple levels:

```text
Browser
   ↓
Operating System
   ↓
Local Network / Router / Resolver
   ↓
Recursive DNS Resolver
```

For example:

```text
First lookup:

Client → Resolver → Root → TLD → Authoritative
                         ↓
                      Answer

Later lookup:

Client → Resolver
            ↓
          Cache
            ↓
          Answer
```

This can significantly reduce DNS latency and traffic.

---

# 10. DNS TTL

DNS records have a **TTL (Time To Live)** value that influences how long a response may be cached.

For example:

```text
example.com
A
93.184.216.34
TTL = 3600
```

A TTL of 3600 seconds means a caching resolver can generally retain that DNS data for up to approximately:

```text
3600 seconds
= 60 minutes
= 1 hour
```

before it needs to refresh it.

Conceptually:

```text
DNS record
    |
    | TTL = 3600
    v
Cache
    |
    | Valid while TTL remains
    v
Reuse answer
```

A shorter TTL can allow changes to propagate through caches sooner, while a longer TTL can reduce DNS lookup traffic.

---

# 11. Common DNS Record Types

DNS supports many record types.

| Record    | Purpose                                                                          |
| --------- | -------------------------------------------------------------------------------- |
| **A**     | Maps a name to an IPv4 address                                                   |
| **AAAA**  | Maps a name to an IPv6 address                                                   |
| **CNAME** | Alias from one domain name to another name                                       |
| **MX**    | Specifies mail servers                                                           |
| **NS**    | Specifies authoritative name servers                                             |
| **TXT**   | Stores text information, often used for verification and email-security policies |
| **PTR**   | Used for reverse DNS lookups                                                     |

---

# 12. A Record

An **A record** maps a hostname to an IPv4 address.

Example:

```text
example.com    A    93.184.216.34
```

Conceptually:

```text
example.com
     |
     | A
     v
93.184.216.34
```

Remember:

```text
A → IPv4
```

---

# 13. AAAA Record

An **AAAA record** maps a hostname to an IPv6 address.

Example:

```text
example.com    AAAA    2001:db8::1
```

Conceptually:

```text
example.com
     |
     | AAAA
     v
2001:db8::1
```

Remember:

```text
AAAA → IPv6
```

A domain can have both:

```text
A     → IPv4
AAAA  → IPv6
```

allowing clients with IPv4 or IPv6 connectivity to use the appropriate address.

---

# 14. CNAME Record

A **CNAME** creates an alias from one DNS name to another DNS name.

For example:

```text
www.example.com
       |
       | CNAME
       v
example.com
```

The target is another **domain name**, not directly an IP address.

Conceptually:

```text
www.example.com
       |
       v
example.com
       |
       v
A / AAAA record
       |
       v
IP address
```

This distinction is important in interviews:

```text
A / AAAA
→ name → IP

CNAME
→ name → another name
```

---

# 15. MX Record

**MX** stands for:

> **Mail Exchange**

MX records specify which mail servers handle email for a domain.

Example conceptually:

```text
example.com
      |
      | MX
      v
mail.example.com
      |
      v
A / AAAA
      |
      v
IP address
```

When mail is sent to:

```text
user@example.com
```

mail infrastructure can use DNS MX records to determine where the message should be delivered.

---

# 16. NS Record

**NS** stands for:

> **Name Server**

An NS record identifies the authoritative name servers for a DNS zone/domain.

Conceptually:

```text
example.com
     |
     | NS
     v
ns1.example-dns.com
ns2.example-dns.com
```

These servers can provide authoritative DNS information for the domain.

---

# 17. TXT Record

A **TXT record** stores text information associated with a DNS name.

It is commonly used for:

* Domain verification
* Email-security policies
* SPF-related configurations
* Other service-specific verification/policy data

For example, a service may ask a domain owner to add a TXT record to prove ownership.

---

# 18. PTR Record and Reverse DNS

A **PTR record** is commonly used for **reverse DNS**.

Normal DNS:

```text
Domain
   ↓
IP
```

Reverse DNS:

```text
IP
   ↓
Domain
```

For example:

```text
93.184.216.34
       |
       | PTR lookup
       v
example.com
```

So remember:

```text
Forward DNS
→ Name to address

Reverse DNS
→ Address to name
```

---

# 19. DNS and HTTP

Suppose you enter:

```text
https://example.com
```

DNS usually happens before the client can establish the connection to the server using the resolved address.

A simplified sequence is:

```text
Domain name
     |
     v
DNS resolution
     |
     v
IP address
     |
     v
Connection establishment
     |
     +--------------------------+
     |                          |
     v                          v
TCP + TLS                    QUIC
     |                          |
     | HTTP/1.1 or HTTP/2       | HTTP/3
     |                          |
     +-------------+------------+
                   |
                   v
              HTTP Request
                   |
                   v
                 Server
```

For traditional HTTPS:

```text
DNS
 ↓
TCP connection
 ↓
TLS
 ↓
HTTP
```

For HTTP/3:

```text
DNS
 ↓
QUIC
 ↓
HTTP/3
```

QUIC runs over UDP and integrates TLS into its connection establishment.

---

# 20. DNS Does Not Download the Website

This is an important interview distinction.

DNS's job is to resolve names into DNS information.

It does **not** download the HTML page.

For example:

```text
DNS:
example.com
     ↓
93.184.216.34
```

Then HTTP takes over:

```text
93.184.216.34
     ↓
HTTPS connection
     ↓
GET / HTTP/...
     ↓
HTML response
```

So:

```text
DNS → "Where?"
HTTP → "Give me the resource."
```

---

# 21. DNS Uses UDP and TCP

A common beginner statement is:

> "DNS always uses UDP."

That is incorrect.

Traditional DNS commonly uses:

```text
UDP port 53
```

but DNS can also use:

```text
TCP port 53
```

TCP can be used in situations such as:

* Responses that require TCP
* Zone transfers
* Certain DNS operational scenarios

Modern DNS can also be transported using encrypted protocols such as:

* **DoT** — DNS over TLS
* **DoH** — DNS over HTTPS

Therefore, the exact DNS transport depends on the DNS mechanism being used.

---

# 22. DNS Query vs DNS Response

A DNS exchange generally consists of a query and a response.

Conceptually:

```text
Client / Stub Resolver
        |
        | "A www.example.com?"
        v
Recursive Resolver
        |
        | DNS Response
        v
Client
```

The response can contain:

* Requested record
* TTL
* Other DNS information
* Error/status information

---

# 23. What Happens If DNS Fails?

Suppose the destination server is actually running:

```text
Server
  |
  v
Working
```

but DNS cannot resolve:

```text
example.com
```

to an address.

The client may not know which IP address to connect to.

Therefore:

```text
DNS failure
     ↓
Hostname cannot be resolved
     ↓
Intended destination address unavailable
     ↓
Connection using that hostname generally cannot proceed
```

This does **not necessarily mean the server itself is down**.

The server might be perfectly healthy while the DNS infrastructure or DNS configuration has a problem.

---

# 24. DNS Failure Example

Imagine:

```text
example.com
     |
     X
DNS resolution fails
```

Even if:

```text
93.184.216.34
     |
     v
Server is running
```

the user may still see an error because the client cannot determine the destination address from the hostname.

If the user already knows the IP and the server accepts connections by that address, direct access might behave differently, depending on the server and application configuration.

---

# 25. DNS Error Examples

DNS can fail for different reasons.

For example:

```text
NXDOMAIN
```

generally indicates that the queried domain name does not exist according to the responding DNS system.

Other failures can involve:

* DNS timeout
* Misconfigured records
* Unavailable resolver
* Authoritative DNS problems
* Network connectivity issues
* Expired/incorrect DNS configuration

So "DNS failed" does not describe only one specific problem.

---

# 26. DNS Hierarchy

A useful way to visualize DNS is as a hierarchy:

```text
                         Root
                          |
             +------------+------------+
             |            |            |
            .com         .org         .in
             |
          example
             |
        example.com
             |
       www.example.com
```

More precisely, DNS is a hierarchy of **names and zones**, with different servers responsible for different parts of that hierarchy.

This distributed architecture allows DNS to scale globally rather than relying on one central database.

---

# 27. Why Is DNS Distributed?

Imagine one global DNS server handling every hostname lookup.

That would create:

```text
Huge traffic
     +
Single point of failure
     +
Poor scalability
     +
High latency
```

Instead, DNS distributes responsibility:

```text
Root
 ↓
TLD
 ↓
Authoritative servers
 ↓
Caching resolvers
```

Combined with caching, this allows DNS to serve a huge number of queries.

---

# 28. DNS Caching Example

Suppose thousands of users request:

```text
www.example.com
```

Without caching:

```text
User 1 → DNS hierarchy
User 2 → DNS hierarchy
User 3 → DNS hierarchy
...
User 10000 → DNS hierarchy
```

With caching:

```text
First query
User → Resolver → Authoritative DNS
                    ↓
                  Answer
                    ↓
                 Cache


Later queries
User → Resolver → Cache → Answer
```

This reduces both latency and DNS infrastructure load.

# 29. DNS in the Complete Website Flow

Suppose you enter:

```text
https://www.example.com/products
```

A simplified flow is:

```text
1. Browser parses URL
          ↓
2. Browser/OS checks DNS-related caches
          ↓
3. Resolver obtains IP address
          ↓
4. Client establishes appropriate transport connection
          ↓
5. TLS is established for HTTPS
          ↓
6. HTTP request is sent
          ↓
7. Server processes request
          ↓
8. HTTP response is returned
          ↓
9. Browser renders the response
```

DNS is therefore one important part of the complete web-request process, not the entire process.

# 30. Important DNS Interview Distinctions

### DNS vs HTTP

```text
DNS
→ Resolves names / obtains DNS records

HTTP
→ Transfers web resources
```

### DNS vs IP

```text
DNS
→ Naming system

IP
→ Network-layer addressing and packet forwarding
```

### DNS vs DHCP

```text
DNS
→ Name resolution

DHCP
→ Network configuration/address assignment
```

These protocols solve different problems.

# 31. Common Interview Mistakes

### Mistake 1: "DNS converts every domain directly into an IP."

❌ Incomplete.

DNS supports many record types such as:

```text
A
AAAA
CNAME
MX
NS
TXT
PTR
```

---

### Mistake 2: "DNS always queries root → TLD → authoritative."

❌ Not every time.

Caching can allow the resolver to answer immediately.

```text
Cache hit
→ No full hierarchy traversal required
```

---

### Mistake 3: "DNS always uses UDP."

❌ Incorrect.

DNS can use both UDP and TCP, and modern DNS mechanisms can use TLS or HTTPS transports.

---

### Mistake 4: "DNS downloads the website."

❌ Incorrect.

```text
DNS
→ Finds DNS information

HTTP/HTTPS
→ Retrieves web resources
```

---

### Mistake 5: "DNS failure means the server is down."

❌ Incorrect.

DNS infrastructure may fail while the actual destination server remains operational.

---

### Mistake 6: "DNS is one centralized server."

❌ Incorrect.

DNS is a **distributed hierarchical system** involving resolvers, root infrastructure, TLD servers, authoritative servers, and caches.

---

### Mistake 7: "CNAME stores an IP address."

❌ Incorrect.

```text
A
→ Name → IPv4

AAAA
→ Name → IPv6

CNAME
→ Name → another name
```

# 34. Interview Takeaway

> **DNS (Domain Name System) is a distributed hierarchical naming system that resolves domain names into DNS information such as IP addresses. A client typically uses a recursive resolver, which may consult cached data or query the DNS hierarchy involving root, TLD, and authoritative servers. DNS supports records such as A, AAAA, CNAME, MX, NS, TXT, and PTR, and caching with TTL improves performance and reduces DNS traffic.**

### ⭐ One-Line Interview Answer

**DNS is a distributed naming system that translates human-readable domain names into network information such as IPv4/IPv6 addresses, using recursive resolvers, hierarchical DNS servers, authoritative records, and caching.**
