# Q21. How Does DNS Resolution Work?

**DNS resolution** is the process of finding the DNS information—most commonly an **IP address**—associated with a domain name.

For example:

```text
www.example.com
       |
       | DNS Resolution
       v
93.184.216.34
```

The goal is to allow applications and humans to use **human-readable names**, while the underlying network uses **IP addresses** to locate network destinations.

A browser does not normally connect to:

```text
www.example.com
```

at the IP layer.

It first needs DNS resolution to obtain an appropriate address, such as:

```text
93.184.216.34
```

or an IPv6 address.

---

# 1. High-Level DNS Resolution Flow

Suppose you enter:

```text
https://www.example.com
```

A simplified DNS resolution process is:

```text
Browser
   |
   v
OS / Local DNS Cache
   |
   v
Recursive DNS Resolver
   |
   v
Root DNS Server
   |
   v
TLD DNS Server (.com)
   |
   v
Authoritative DNS Server
   |
   v
IP Address
```

However, this is a **simplified flow**.

In real systems, caching can eliminate several of these steps.

For example:

```text
Cache Hit:

Client
  |
  v
Recursive Resolver
  |
  v
Cached Answer
  |
  v
Client
```

So the resolver does not necessarily contact the root and TLD servers for every request.

---

# 2. Step-by-Step DNS Resolution

Let's understand the process using:

```text
https://www.example.com
```

The browser needs to determine the address associated with:

```text
www.example.com
```

---

# Step 1: Check Local Caches

Before contacting a DNS server, the client may already have a cached answer.

Possible cache locations include:

```text
Browser
   ↓
Operating System
   ↓
Local Network / Router
   ↓
Recursive DNS Resolver
```

If a valid cached answer exists, the lookup can finish without performing the complete DNS hierarchy traversal.

For example:

```text
Browser
   |
   | "Do I already know www.example.com?"
   |
   +---- YES ----> Use cached address
   |
   +---- NO -----> Continue DNS resolution
```

This is important because DNS caching significantly reduces lookup latency.

---

# Step 2: Query the Recursive DNS Resolver

If the client does not have a usable local answer, it typically sends a DNS query to a **recursive DNS resolver**.

For example:

```text
Client → Recursive Resolver

"What is the IP address of
 www.example.com?"
```

The recursive resolver performs the remaining lookup work on behalf of the client.

Conceptually:

```text
Client
  |
  | DNS query
  v
Recursive Resolver
  |
  | performs lookup if necessary
  v
DNS hierarchy
```

The client generally does not need to individually contact the root, TLD, and authoritative servers.

---

# Step 3: Resolver Checks Its Own Cache

The recursive resolver will normally check whether it already has a valid cached answer.

For example:

```text
Resolver Cache:

www.example.com
        |
        v
93.184.216.34
TTL remaining
```

If the cached record is still valid:

```text
Client
  |
  v
Recursive Resolver
  |
  v
Cache Hit
  |
  v
93.184.216.34
```

The resolver can immediately return the answer.

This is one of the most important optimizations in DNS.

---

# Step 4: Query the Root DNS Server

If the recursive resolver does not have the required information cached, it can query the DNS hierarchy.

The first major level is the **root DNS system**.

For:

```text
www.example.com
```

the root system can help identify where the `.com` TLD infrastructure is located.

The root server does **not normally return**:

```text
93.184.216.34
```

Instead, it provides a referral toward the appropriate TLD servers.

Conceptually:

```text
Resolver
   |
   | "Where should I look for .com?"
   v
Root
   |
   | ".com TLD servers are here"
   v
Resolver
```

---

# Step 5: Query the TLD Server

The resolver now contacts an appropriate **TLD (Top-Level Domain)** server.

For:

```text
www.example.com
```

the TLD is:

```text
.com
```

The resolver asks approximately:

```text
"Where are the authoritative
 name servers for example.com?"
```

The `.com` TLD infrastructure provides information that directs the resolver toward the authoritative name servers for:

```text
example.com
```

Conceptually:

```text
Recursive Resolver
       |
       v
     .com
       |
       | "Authoritative servers
       |  for example.com are..."
       v
Authoritative DNS
```

---

# Step 6: Query the Authoritative DNS Server

The resolver now contacts the authoritative DNS server responsible for the relevant DNS zone.

It asks something like:

```text
"What is the address of
 www.example.com?"
```

The authoritative server returns the appropriate DNS record.

For example:

```text
www.example.com
        |
        | A
        v
93.184.216.34
```

Or the domain may have an IPv6 record:

```text
www.example.com
        |
        | AAAA
        v
2001:db8::1
```

So:

```text
A
→ IPv4 address

AAAA
→ IPv6 address
```

---

# Step 7: Resolver Caches the Answer

After receiving the authoritative response, the recursive resolver can cache the result according to the record's **TTL (Time To Live)**.

For example:

```text
www.example.com
A
93.184.216.34
TTL = 3600 seconds
```

The resolver can generally use that cached information for the permitted TTL period.

Conceptually:

```text
Authoritative DNS
       |
       | Answer + TTL
       v
Recursive Resolver
       |
       | Store in cache
       v
Future queries
```

This means the next client asking for the same record may not require another root/TLD/authoritative lookup.

---

# Step 8: Resolver Returns the Answer to the Client

The recursive resolver sends the result back to the client.

For example:

```text
DNS:

www.example.com
        ↓
93.184.216.34
```

The client can now use the address to establish the appropriate network connection.

---

# Step 9: Client Uses the IP Address

DNS resolution is only one part of the complete network communication process.

After obtaining the IP address, the client can establish the appropriate transport/application connection.

For traditional HTTP over TCP:

```text
DNS
 ↓
IP address
 ↓
TCP connection
 ↓
TLS
 ↓
HTTP/1.1 or HTTP/2
```

For HTTP/3:

```text
DNS
 ↓
IP address
 ↓
QUIC
 ↓
HTTP/3
```

Therefore:

```text
DNS ≠ HTTP
```

DNS helps the client determine **where to connect**; HTTP is then used to exchange web resources.

# 4. Recursive Resolver vs Authoritative Server

This is a **very common interview question**.

| Recursive Resolver                         | Authoritative DNS Server                                                      |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| Finds the answer on behalf of the client   | Holds authoritative DNS data for its zone                                     |
| Can query other DNS servers                | Provides authoritative answers for its zone                                   |
| Usually maintains a cache                  | Source of authoritative DNS records                                           |
| Receives client queries                    | Answers queries for domains/zones it serves                                   |
| May contact root/TLD/authoritative servers | Normally does not need to search the hierarchy for its own authoritative data |

### Simple mental model

```text
Recursive Resolver
→ "I will find the answer for you."


Authoritative Server
→ "I am responsible for this DNS data."
```

---

# 5. Recursive vs Iterative Behavior

There is an important technical distinction.

A client typically makes a **recursive request** to its recursive resolver:

```text
Client
  |
  | "Find the answer for me."
  v
Recursive Resolver
```

The resolver may then perform a sequence of **iterative queries/referrals** through the DNS hierarchy.

Conceptually:

```text
Resolver
   |
   | Query
   v
Root
   |
   | Referral
   v
Resolver
   |
   | Query
   v
TLD
   |
   | Referral
   v
Resolver
   |
   | Query
   v
Authoritative
   |
   | Answer
   v
Resolver
```

This is a useful distinction:

```text
Recursive
→ Resolver does the work on behalf of client.

Iterative/referral process
→ Resolver follows the DNS hierarchy step by step.
```

# 6. DNS Resolution Example

Suppose the user requests:

```text
www.example.com
```

The recursive resolver does not know the answer.

### Step 1 — Root

```text
Resolver
   |
   v
Root
   |
   | ".com is handled by these TLD servers"
   v
Resolver
```

### Step 2 — TLD

```text
Resolver
   |
   v
.com TLD
   |
   | "example.com is handled by these
   |  authoritative name servers"
   v
Resolver
```

### Step 3 — Authoritative

```text
Resolver
   |
   v
Authoritative Server
   |
   | "www.example.com = 93.184.216.34"
   v
Resolver
```

### Step 4 — Client

```text
Resolver
   |
   | 93.184.216.34
   v
Client
```

### Step 5 — Connection

```text
Client
   |
   v
93.184.216.34
   |
   v
TCP/TLS or QUIC
   |
   v
HTTP
```

# 7. DNS Caching at Multiple Levels

DNS caching can occur at multiple places.

```text
Browser
   ↓
Operating System
   ↓
Local Network / Router
   ↓
Recursive Resolver
   ↓
Authoritative DNS
```

For example, suppose the browser already has:

```text
www.example.com
       ↓
93.184.216.34
```

in its cache.

Then:

```text
Browser
   |
   | Cache Hit
   v
93.184.216.34
```

No DNS network query may be required at all.

If the browser misses but the OS cache has the answer:

```text
Browser
   ↓
OS Cache
   ↓
Answer
```

If both miss:

```text
Browser
   ↓
OS
   ↓
Recursive Resolver
```

The resolver may then have its own cache.

---

# 8. Why DNS Caching Is Important

Without caching, a large number of DNS queries would repeatedly travel through the hierarchy.

For example:

```text
Without effective caching:

Client
 ↓
Resolver
 ↓
Root
 ↓
TLD
 ↓
Authoritative
```

With caching:

```text
Client
 ↓
Resolver
 ↓
Cache
 ↓
Answer
```

Caching reduces:

* Lookup latency
* DNS traffic
* Load on DNS servers
* Repeated queries across the DNS hierarchy

---

# 9. TTL — Time To Live

DNS records contain a TTL that influences how long cached information can be reused.

For example:

```text
www.example.com
A
93.184.216.34
TTL = 300
```

means the record may generally be cached for:

```text
300 seconds
= 5 minutes
```

Another example:

```text
TTL = 3600
```

means:

```text
3600 seconds
= 1 hour
```

Conceptually:

```text
Authoritative DNS
       |
       | Answer + TTL
       v
Recursive Resolver
       |
       | Cache
       v
Reuse until TTL expires
```

Once the cached information is no longer valid, the resolver may need to obtain fresh information.

---

# 10. A Record vs AAAA Record During Resolution

A DNS lookup may involve different address record types.

### IPv4

```text
www.example.com
       |
       | A
       v
93.184.216.34
```

### IPv6

```text
www.example.com
       |
       | AAAA
       v
2001:db8::1
```

A domain can have both:

```text
www.example.com
       |
       +── A     → IPv4 address
       |
       +── AAAA  → IPv6 address
```

The client's network configuration and resolver/application behavior determine which address is ultimately used.

---

# 11. DNS Does Not Always Follow Root → TLD → Authoritative

This is one of the most important details.

You should **not** say:

> "Every DNS request always goes through root, then TLD, then authoritative server."

That is incorrect.

Caching can eliminate many of these steps.

For example:

```text
First lookup:

Resolver
 ↓
Root
 ↓
TLD
 ↓
Authoritative
 ↓
Cache


Later lookup:

Resolver
 ↓
Cache
 ↓
Answer
```

The resolver may also cache information about:

* TLD name servers
* Authoritative name servers
* DNS records

Therefore, the exact number of DNS queries varies.

---

# 12. DNS Resolution and Connection Establishment

DNS resolution itself does **not** establish the HTTP connection.

These are separate stages.

For traditional HTTPS:

```text
1. DNS resolution
       ↓
2. IP address
       ↓
3. TCP three-way handshake
       ↓
4. TLS handshake
       ↓
5. HTTP request
```

For HTTP/3:

```text
1. DNS resolution
       ↓
2. IP address
       ↓
3. QUIC connection establishment
       ↓
4. HTTP/3 request
```

This distinction is useful when explaining:

> "What happens when you enter a URL?"

---

# 13. What Happens If DNS Resolution Fails?

Suppose:

```text
www.example.com
```

cannot be resolved.

The client may receive a DNS error or timeout.

Conceptually:

```text
Client
   |
   | www.example.com
   v
Resolver
   |
   X
DNS resolution fails
```

The client may then be unable to establish the intended connection using that hostname.

However, this does **not necessarily mean the destination server is down**.

For example:

```text
DNS problem
     ≠
Server problem
```

The server could be completely operational while its DNS records or the DNS infrastructure are unavailable.

---

# 14. Example: Server Works but DNS Fails

Suppose:

```text
Server:
93.184.216.34
```

is running normally.

But:

```text
www.example.com
       ↓
DNS failure
```

Then:

```text
Browser
   |
   | www.example.com
   v
DNS
   |
   X
Unable to resolve
```

The browser may fail before it can establish the intended connection.

This is why troubleshooting should distinguish:

```text
DNS resolution problem
vs
Network connectivity problem
vs
Transport connection problem
vs
TLS problem
vs
Application/HTTP problem
```

---

# 15. Useful DNS Troubleshooting Model

When a hostname does not work, think in layers:

```text
1. Can the hostname resolve?
        ↓
2. What IP address was returned?
        ↓
3. Can the client reach that IP?
        ↓
4. Can TCP/QUIC establish a connection?
        ↓
5. Can TLS succeed?
        ↓
6. Does HTTP return the expected response?
```

For example:

```text
DNS works
  ↓
IP reachable
  ↓
TCP works
  ↓
TLS fails
```

This is a very different problem from:

```text
DNS fails
  ↓
No usable destination address
```

---

# 16. DNS Resolution and Ports

DNS resolution generally gives you an address, but the application still needs to know **which service/port** to connect to.

For example:

```text
DNS:
example.com
    ↓
93.184.216.34
```

Then an HTTPS client may connect using the conventional HTTPS port:

```text
93.184.216.34:443
```

For HTTP:

```text
93.184.216.34:80
```

The important distinction is:

```text
DNS
→ Where?

Port
→ Which service?
```

# 17. DNS and URL Parsing

Consider:

```text
https://www.example.com/products?id=10
```

The browser identifies:

```text
Scheme:
https

Hostname:
www.example.com

Path:
/products

Query:
id=10
```

DNS is primarily concerned with the **hostname**:

```text
www.example.com
```

The path and query are not sent to DNS as part of the normal hostname lookup.

So:

```text
https://www.example.com/products?id=10
          |
          v
        DNS
          |
          v
www.example.com
```

Then HTTP uses:

```text
/products?id=10
```

when constructing the web request.

# 18. Common Interview Mistakes

### Mistake 1: "The browser always asks the root server."

❌ Not necessarily.

Browser, OS, local resolver, and recursive resolver caches may already contain the required information.

---

### Mistake 2: "The client directly contacts the root, TLD, and authoritative servers."

❌ Usually not.

Typically:

```text
Client
   ↓
Recursive Resolver
   ↓
DNS hierarchy
```

The recursive resolver performs the lookup work.

---

### Mistake 3: "Root server gives the final IP address."

❌ Usually incorrect.

The root provides information/referrals about TLD infrastructure.

```text
Root
 ↓
TLD information

TLD
 ↓
Authoritative-server information

Authoritative
 ↓
Actual DNS record
```

---

### Mistake 4: "TLD server gives the final IP."

❌ Not normally.

The TLD server generally directs the resolver toward the authoritative servers for the requested domain.

---

### Mistake 5: "DNS resolution and HTTP are the same thing."

❌ Incorrect.

```text
DNS
→ Resolve name

HTTP
→ Exchange application data
```

---

### Mistake 6: "DNS always returns one IP."

❌ Not necessarily.

A domain may have:

* Multiple A records
* Multiple AAAA records
* CNAME chains
* Other DNS record types

The resolver/client may therefore receive multiple pieces of DNS information.

---

### Mistake 7: "DNS always uses UDP."

❌ Incorrect.

DNS can use UDP, TCP, and modern encrypted transports such as DNS over TLS or DNS over HTTPS.

---

### Mistake 8: "DNS failure means Internet is completely down."

❌ Not necessarily.

The network may work while DNS resolution is failing.

# 20. Memory Trick

Remember:

```text
C → R → T → A
```

Where:

```text
C = Cache
R = Root
T = TLD
A = Authoritative
```

But remember that **Root → TLD → Authoritative is conditional** because caching can skip levels.

A more accurate mental model is:

```text
Local Cache
     ↓
Recursive Resolver
     ↓
Cache Hit? ── Yes → Return Answer
     |
     No
     ↓
Root
     ↓
TLD
     ↓
Authoritative
     ↓
Cache
     ↓
Client
```

---

# 21. Interview Takeaway

> **DNS resolution is the process of obtaining DNS information, commonly an IP address, for a domain name. A client typically checks local caches first and then queries a recursive resolver. If the resolver does not have a cached answer, it can follow the DNS hierarchy through root and TLD servers to the authoritative server, obtain the required A or AAAA record, cache the result according to its TTL, and return the answer to the client.**

### One-Line Interview Answer

**DNS resolution starts with local/recursive caches; if the answer is not cached, a recursive resolver can query the root, TLD, and authoritative DNS servers, obtain the required record, cache it according to TTL, and return the result to the client.**
