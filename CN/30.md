# Q30. What Happens When a TCP Connection Fails?

A **TCP connection failure** occurs when TCP can no longer establish or maintain reliable communication between two endpoints.

What happens depends on **when the failure occurs and what caused it**. TCP is designed to detect communication problems using mechanisms such as **ACKs, sequence numbers, retransmissions, duplicate ACKs, and timers**.

Depending on the situation, TCP may:

* Retransmit lost data
* Retry connection establishment
* Reduce its sending rate when congestion is detected
* Wait for a response
* Gracefully close the connection
* Abruptly reset the connection
* Eventually report an error to the application

---

## 1. Connection Fails During the TCP Handshake

Before data can be exchanged, TCP normally performs the **three-way handshake**.

```text
Client                    Server
  |                         |
  | -------- SYN ---------> |
  | <------ SYN-ACK --------|
  | -------- ACK ---------> |
  |                         |
  |       Connected         |
```

After this exchange, the TCP connection enters the **ESTABLISHED** state.

### What if the server or network does not respond?

For example:

```text
Client                    Server
  |                         |
  | -------- SYN ---------> |
  |                         X
  |                         |
  | <---- No response ------|
  |                         |
  |        Timeout          |
  | -------- SYN ---------> |
  |                         |
```

The client does not immediately assume that the connection has failed.

Instead, TCP waits for a response. If the expected response does not arrive, the SYN may be **retransmitted**.

If repeated attempts fail, the connection attempt eventually gives up.

The application may then receive an error such as:

```text
Connection timed out
```

### Possible reasons

* Server is unreachable
* Network path is broken
* Firewall silently drops packets
* Server is overloaded or unavailable
* Routing problem
* Incorrect destination address
* Network interface failure

### Important point

A **timeout does not necessarily mean that the server is down**.

A firewall that silently drops the SYN, for example, can produce a timeout even when the server itself is running.

# 2. Connection Is Established, but a Packet Is Lost

Suppose the TCP connection has already been established.

TCP uses:

* Sequence numbers
* Acknowledgements (ACKs)
* Retransmission timers

to detect missing data.

For example:

```text
Client                         Server
  |                             |
  | ---- Data (Seq 100) ------> |
  |                             |
  | <--------- ACK 110 ---------|
  |                             |
```

Suppose the data segment is lost:

```text
Client                         Server
  |                             |
  | ---- Data (Seq 100) ------> X
  |                             |
  |       No ACK arrives        |
  |                             |
```

TCP detects the missing data using mechanisms such as:

### A. Retransmission Timeout (RTO)

If the sender waits too long for the expected acknowledgement, it retransmits the data.

```text
Client                         Server
  | ---- Data ----------------> X
  |                             |
  |        RTO expires          |
  |                             |
  | ---- Retransmit ----------> |
  | <--------- ACK ------------ |
```

### B. Duplicate ACKs / Fast Retransmit

Suppose later data reaches the receiver while an earlier segment is missing.

The receiver may repeatedly acknowledge the last contiguous data it received.

Conceptually:

```text
Client                         Server
  | ---- Seq 100 ------------> X
  | ---- Seq 110 ------------> |
  | <------ ACK 100 ----------- |
  | ---- Seq 120 ------------> |
  | <------ ACK 100 ----------- |
  | ---- Seq 130 ------------> |
  | <------ ACK 100 ----------- |
```

Repeated duplicate ACKs can provide an early indication that a segment is missing, allowing TCP to perform **fast retransmit** rather than waiting for the retransmission timer.

### Result

The application usually does **not** need to know that an individual TCP segment was lost.

TCP attempts to recover the loss transparently.

# 3. Connection Is Suddenly Broken

Suppose a TCP connection is active:

```text
Client                         Server
  |                             |
  | <====== TCP connection ===> |
  |                             |
```

Now imagine the network path suddenly disappears.

For example:

```text
Client ---- Router ---- X ---- Server
                         ^
                    Link failure
```

TCP may continue attempting to transmit data and wait for acknowledgements.

If acknowledgements do not arrive, TCP may retransmit data.

If the failure continues for long enough, TCP eventually concludes that communication is no longer viable and reports the failure to the application.

Conceptually:

```text
Data
 ↓
No ACK
 ↓
Retransmission
 ↓
Still no ACK
 ↓
More waiting/retransmission
 ↓
Failure detected
 ↓
Connection reported as failed
```

The application may observe errors such as:

* `Connection timed out`
* `Connection reset`
* `Broken pipe`

The exact error and wording depend on the **operating system, socket state, and exact failure condition**.

---

## Example: Network Cable/Wi-Fi Failure

Imagine downloading a large file:

```text
Browser
   ↓
TCP socket
   ↓
Wi-Fi
   ↓
Router
   ↓
Internet
   ↓
Server
```

If the Wi-Fi connection disappears:

```text
Browser
   ↓
TCP socket
   ↓
Wi-Fi ❌
```

TCP may not instantly know that the physical link has disappeared.

It may initially behave as though packets are simply being lost.

After retransmissions and timeout-related mechanisms fail to recover communication, TCP eventually reports the connection failure.

# 4. Server Explicitly Closes or Resets the Connection

A server can terminate a TCP connection in different ways.

## Graceful termination using FIN

A normal TCP close uses **FIN**.

For example:

```text
Client                         Server
  |                             |
  | <--------- FIN ------------ |
  |                             |
  | --------- ACK ------------> |
  |                             |
```

A complete TCP connection close is full-duplex, so both directions may close independently.

Conceptually:

```text
Client                         Server
  |                             |
  | <--------- FIN ------------ |
  | --------- ACK ------------> |
  |                             |
  | --------- FIN ------------> |
  | <--------- ACK ------------ |
  |                             |
```

The exact exchange can vary because ACKs and FINs can sometimes be combined.

### FIN means:

> "I have finished sending data in this direction."

It is therefore associated with **graceful connection termination**.

---

# 5. Abrupt Connection Termination Using RST

TCP can also terminate a connection abruptly using **RST (Reset)**.

For example:

```text
Client                         Server
  |                             |
  | -------- Data ------------> |
  |                             |
  | <--------- RST ------------ |
  |                             |
  |       Connection reset      |
```

RST essentially tells the other endpoint that the connection should be **immediately reset rather than gracefully closed**.

The application may receive an error corresponding to:

```text
Connection reset
```

---

# 6. Example: Nothing Is Listening on the Destination Port

Consider:

```text
Client
192.168.1.10:50000
       |
       | TCP SYN
       ↓
Server
192.168.1.20:8080
```

If the server is reachable but **no application is listening on TCP port 8080**, the host may respond with a TCP RST.

```text
Client                         Server
  |                             |
  | -------- SYN -------------> |
  |                             |
  | <--------- RST ------------ |
  |                             |
```

The client may then report:

```text
Connection refused
```

This is different from a timeout.

### Important distinction

```text
No response
    ↓
Possible timeout

RST received
    ↓
Connection reset / refused
```

The exact user-visible error depends on the state and operating system.

# 7. What Happens When TCP Problems Occur?

TCP has several mechanisms for dealing with communication problems.

| Mechanism              | Purpose                                                    |
| ---------------------- | ---------------------------------------------------------- |
| **ACKs**               | Confirm receipt of data                                    |
| **Sequence numbers**   | Track data and identify missing/duplicate data             |
| **Retransmission**     | Resend data that appears to be lost                        |
| **Timers**             | Detect lack of expected responses                          |
| **Flow control**       | Prevent overwhelming the receiver                          |
| **Congestion control** | Reduce sending pressure when the network appears congested |
| **FIN**                | Gracefully close a connection                              |
| **RST**                | Abruptly reset a connection                                |

---

## 8. Sequence Numbers Help Detect Missing Data

Suppose the sender sends:

```text
Seq 100
Seq 110
Seq 120
Seq 130
```

If `Seq 110` is lost:

```text
Seq 100  ✓
Seq 110  ❌
Seq 120  ✓
Seq 130  ✓
```

The receiver cannot treat the stream as fully contiguous.

TCP's sequence-number and acknowledgement mechanisms allow the sender and receiver to detect that some data is missing and recover it.

This is one of the fundamental reasons TCP can provide **reliable ordered byte-stream delivery** even though IP itself is a best-effort network protocol.

# 9. TCP Failure Does Not Always Mean "Server Is Down"

This is one of the most important interview points.

A TCP connection failure can occur at many different points.

```text
Client
   ↓
DNS problem
   ↓
Network/routing problem
   ↓
Firewall filtering
   ↓
Server unreachable
   ↓
Destination port unavailable
   ↓
Server application failure
   ↓
TCP connection failure
```

For example, suppose a user enters:

```text
https://example.com
```

The problem could occur during:

```text
DNS resolution
      ↓
TCP connection
      ↓
TLS handshake
      ↓
HTTP request
      ↓
Application processing
```

A failure at one stage does not necessarily imply failure at another stage.

# 10. Timeout vs Connection Refused vs Connection Reset

This is a common interview follow-up.

| Situation              | Typical behavior                                | Common interpretation                                                                                    |
| ---------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Timeout**            | No expected response arrives                    | Packet may be dropped, host/path unreachable, firewall may silently filter                               |
| **Connection refused** | TCP RST is returned during connection attempt   | Host is reachable but nothing is accepting the connection on that port, or the stack actively rejects it |
| **Connection reset**   | RST terminates an existing/attempted connection | Connection was abruptly rejected or terminated                                                           |
| **Successful close**   | FIN/ACK exchange                                | Graceful TCP termination                                                                                 |

### Conceptual comparison

```text
TIMEOUT
Client ─── SYN ───> Server
Client <── nothing
        ↓
      timeout
```

```text
REFUSED
Client ─── SYN ───> Server
Client <── RST ──── Server
        ↓
 connection refused
```

```text
RESET
Client <════ Active TCP connection ════> Server
                    ↓
                   RST
                    ↓
             connection reset
```

The exact error exposed to an application depends on the OS and socket state.

# 11. TCP Failure vs Congestion

Not every packet loss means that the connection has completely failed.

Packet loss can happen because of:

* Temporary congestion
* Wireless interference
* Queue overflow
* Routing problems
* Link failure
* Server/network failure

TCP may initially treat loss as something that can be recovered from.

For example:

```text
Packet loss
    ↓
TCP detects loss
    ↓
Retransmit
    ↓
Continue communication
```

If the problem persists:

```text
Repeated loss
    ↓
Repeated retransmission
    ↓
No successful acknowledgements
    ↓
Connection eventually fails
```

TCP's **congestion control** may also reduce the sending rate when loss or other congestion signals suggest that the network is overloaded.

### Important distinction

**Packet loss ≠ immediate TCP connection failure.**

TCP is specifically designed to tolerate and recover from some amount of packet loss.

# 12. Flow Control vs Congestion Control During Problems

These two mechanisms are sometimes confused.

### Flow Control

Protects the **receiver**.

```text
Sender ───────────────> Receiver
              ↓
       Receiver buffer
```

If the receiver cannot accept more data, TCP's receive-window mechanism can limit how much unacknowledged data the sender is allowed to have outstanding.

### Congestion Control

Protects the **network**.

```text
Sender
  ↓
Network
  ↓
Router queues / links
  ↓
Receiver
```

If the network appears congested, TCP adjusts its sending behavior.

So:

```text
Flow control      → Protect receiver
Congestion control → Protect network
```

# 13. TCP Does Not Detect Every Failure Instantly

Another important interview nuance is that TCP does not necessarily know immediately that the remote machine has disappeared.

Consider:

```text
Client                         Server
  |                             |
  | <==== Established ========> |
  |                             |
  |                         Server crashes
  |                             X
```

If there is no traffic, the client may not immediately discover the failure.

Detection can depend on:

* Whether data is being transmitted
* Retransmission timers
* TCP keepalive configuration
* Application-level heartbeats
* OS-specific timeout behavior
* Network conditions

This is why an application can sometimes appear to hold a TCP connection even though the remote endpoint is no longer functioning.

# 14. TCP Failure Handling — Complete Picture

A simplified flow is:

```text
             TCP Communication
                    |
                    v
          Is connection established?
             /               \
           No                 Yes
           |                   |
      Send SYN              Send data
           |                   |
     Response received?     ACK received?
       /        \             /       \
     Yes         No          Yes       No
      |           |           |         |
  Continue    Retransmit   Continue   Detect loss
                  |                    |
             Retry limit/RTO       Retransmit
                  |                    |
             Connection fail       Recovered?
                                      /   \
                                    Yes    No
                                     |      |
                                  Continue  Eventually fail
```

This is a simplified conceptual diagram; actual TCP behavior includes more state, timers, congestion-control algorithms, and implementation-specific details.

# 15. Real-World Example: Opening a Website

Suppose you open:

```text
https://example.com
```

A simplified sequence is:

```text
1. DNS resolution
       ↓
2. TCP connection
       ↓
3. TLS handshake
       ↓
4. HTTP request
       ↓
5. HTTP response
```

Now consider different failures.

### DNS failure

```text
DNS lookup fails
      ↓
No server IP obtained
      ↓
TCP connection cannot begin normally
```

### TCP handshake timeout

```text
SYN
 ↓
No SYN-ACK
 ↓
Retransmission
 ↓
Timeout
```

### TCP connection reset

```text
TCP connection
      ↓
RST
      ↓
Application receives connection-reset error
```

### Packet loss after connection establishment

```text
Data
 ↓
Lost
 ↓
TCP retransmission
 ↓
ACK
 ↓
Communication continues
```

Therefore, "the website is not opening" does not by itself tell us which layer failed.

# 16. Common Mistakes

### ❌ Mistake 1: "Any packet loss means TCP connection fails."

Not necessarily.

TCP can retransmit lost data and continue the connection.

---

### ❌ Mistake 2: "TCP immediately knows when the server crashes."

Not always.

If there is no traffic, detection may take time and can depend on keepalive or application-level mechanisms.

---

### ❌ Mistake 3: "Timeout means the server is down."

Not necessarily.

A timeout can also be caused by:

* Firewall filtering
* Routing problems
* Packet loss
* Network failure
* Incorrect addressing
* Intermediate device problems

---

### ❌ Mistake 4: "Connection refused means the server is unreachable."

Usually the opposite: a refusal commonly means the destination was reachable enough to return a rejection such as RST, often because no service is listening on the requested port.

---

### ❌ Mistake 5: "RST is the same as FIN."

They are different.

```text
FIN → graceful termination
RST → abrupt reset
```

---

### ❌ Mistake 6: "TCP guarantees the connection will never fail."

TCP provides mechanisms for **reliable transport**, but it cannot repair a permanently broken network path or make an unavailable endpoint available.

```text
TCP connection failure
        |
        +--> During handshake
        |       ↓
        |   SYN retransmission
        |       ↓
        |   Timeout / connection error
        |
        +--> Packet loss
        |       ↓
        |   ACK/sequence detection
        |       ↓
        |   Retransmission
        |
        +--> Network disappears
        |       ↓
        |   Retransmissions / waiting
        |       ↓
        |   Eventually connection failure
        |
        +--> Server closes normally
        |       ↓
        |      FIN
        |
        +--> Server resets abruptly
                ↓
               RST
```

### Memory Trick

> **TCP first tries to recover; if recovery fails, it eventually reports the failure.**

### Interview Takeaway

> When a TCP connection encounters a problem, TCP uses sequence numbers, ACKs, retransmissions, duplicate ACKs, and timers to detect and recover from lost communication. If the problem is temporary, the connection may continue after retransmission. If communication cannot be restored, TCP eventually terminates or resets the connection and the application receives an appropriate error. A TCP failure does not automatically mean that the server is down; the cause may be DNS, routing, firewall filtering, packet loss, an unavailable port, or an actual server/network failure.
