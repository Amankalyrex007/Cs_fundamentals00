# Q31. How Would You Debug an API That Works Locally but Not From Another Machine?

This is a very common real-world networking and backend debugging problem.

For example:

```text
Same machine:

curl http://localhost:8000
        ↓
       Works ✓


Another machine:

curl http://192.168.1.10:8000
        ↓
       Fails ✗
```

The important thing is **not to immediately assume that the API code is broken**.

The failure could be anywhere between the client and the application:

```text
Client
  ↓
DNS
  ↓
Network / Routing
  ↓
Firewall / Security Group
  ↓
TCP Port
  ↓
Server Process
  ↓
HTTP
  ↓
API Application
  ↓
Authentication / CORS / Configuration
```

Therefore, I would debug it **from the bottom of the stack upward**, starting with basic connectivity and gradually moving toward application-level behavior.

---

# 1. Confirm the API Is Actually Listening Externally

One of the most common causes is that the API is bound only to:

```text
127.0.0.1
```

For example:

```text
127.0.0.1:8000
```

`127.0.0.1` is the **loopback address**.

It means:

> Accept connections through the local machine's loopback interface.

Therefore:

```text
Same machine
localhost → API
        ✓
```

but:

```text
Another machine
Client → Network → Server:8000
                    ✗
```

because the server is not listening on the network-facing interface.

---

## Binding to an External Interface

For development servers, you will often see:

```text
0.0.0.0:8000
```

This generally means:

> Listen on all available IPv4 interfaces.

For example:

```text
Server
 ├── 127.0.0.1:8000
 │      └── local access
 │
 └── 0.0.0.0:8000
        └── listens on available IPv4 interfaces
```

Then verify what the operating system is actually listening on.

### Linux

```bash
ss -lntp
```

You might see:

```text
LISTEN 0 128 127.0.0.1:8000
```

which suggests localhost-only binding.

Or:

```text
LISTEN 0 128 0.0.0.0:8000
```

which means the process is listening on all IPv4 interfaces.

### Windows

```powershell
netstat -ano
```

You can then identify the process using the PID.

### Important nuance

`0.0.0.0` is generally a **listen/bind address**, not an address that a client should use to connect.

A client would normally connect to the server's actual reachable IP, such as:

```text
192.168.1.10:8000
```

---

# 2. Test Locally Using the Machine's Actual IP

Suppose the server has:

```text
192.168.1.10
```

Do not test only:

```text
http://localhost:8000
```

Also test:

```text
http://192.168.1.10:8000
```

For example:

```bash
curl http://localhost:8000
```

and:

```bash
curl http://192.168.1.10:8000
```

### Why is this useful?

It separates two situations.

### Case A

```text
localhost:8000          → works
192.168.1.10:8000       → fails
```

This strongly suggests a problem with:

* Binding
* Network interface
* Host firewall
* Server configuration

### Case B

```text
localhost:8000          → works
192.168.1.10:8000       → works
```

but:

```text
Client machine → 192.168.1.10:8000 → fails
```

Now the API itself is more likely to be functioning, so investigate:

* Network connectivity
* Routing
* Firewall
* Security groups
* ACLs
* Port accessibility

---

# 3. Check Whether the TCP Port Is Reachable

Once the server is confirmed to be listening, test whether the **client can establish TCP connectivity** to the port.

Suppose:

```text
Server IP = 192.168.1.10
Port      = 8000
```

From the client machine:

### Linux/macOS

```bash
nc -vz 192.168.1.10 8000
```

or:

```bash
telnet 192.168.1.10 8000
```

### Windows PowerShell

```powershell
Test-NetConnection 192.168.1.10 -Port 8000
```

This gives an important distinction.

### Port reachable

```text
Client
  |
  | TCP connection ✓
  ↓
Server:8000
```

Then investigate:

* HTTP
* TLS
* Authentication
* Application routing
* Request data
* CORS

### Port unreachable

```text
Client
  |
  | TCP connection ✗
  ↓
Server:8000
```

Investigate:

* Listening address
* Firewall
* Security group
* Routing
* Network ACL
* Server availability

### Key principle

> First determine whether TCP connectivity exists. Do not debug HTTP application code before knowing whether the client can reach the TCP endpoint.

---

# 4. Check the Firewall

The server's firewall may allow local traffic but block connections from other machines.

For example:

```text
localhost → API
     ✓

other machine → API
     ✗
```

Check the relevant firewall/security controls.

### On the server

Possible mechanisms include:

```text
Windows Firewall
iptables
nftables
firewalld
```

### In cloud environments

Also check:

```text
Security Groups
Network ACLs
Cloud firewall rules
Load balancer rules
```

### Corporate networks

There may also be:

```text
Corporate firewall
VPN policies
Network segmentation
Proxy rules
```

Make sure the required TCP port is allowed from the **appropriate source network**, rather than simply opening it to everyone.

For example:

```text
Client subnet
192.168.1.0/24
        |
        | TCP 8000
        ↓
Server
192.168.1.10
```

The firewall should permit the required traffic according to the environment's security policy.

---

# 5. Check Network Connectivity and Routing

Verify that the client can communicate with the server.

For example:

```bash
ping 192.168.1.10
```

You can also inspect the network path.

### Linux/macOS

```bash
traceroute 192.168.1.10
```

### Windows

```powershell
tracert 192.168.1.10
```

This can help identify routing/path problems.

However, there is an important interview point:

> **Ping failure does not prove that the API is unreachable.**

Why?

Because `ping` uses **ICMP**, while the API may use **TCP**.

A firewall could block:

```text
ICMP ✗
```

while allowing:

```text
TCP 8000 ✓
```

So:

```text
ping fails
```

does not automatically mean:

```text
API unreachable
```

The actual TCP port test is more relevant to an API.

---

# 6. Check DNS

Suppose the client uses:

```text
https://api.example.com
```

instead of:

```text
http://192.168.1.10:8000
```

Verify that the hostname resolves to the expected address.

### Linux/macOS

```bash
dig api.example.com
```

### Windows

```powershell
nslookup api.example.com
```

A common problem is that DNS behaves differently depending on the network.

For example:

```text
Inside office network:

api.example.com
       ↓
192.168.1.10


Outside network:

api.example.com
       ↓
203.0.113.50
```

The API may work from one network but fail from another because the hostname resolves differently.

### Important distinction

DNS answers:

> "Which address should I try?"

It does **not** establish the TCP connection or guarantee that the API is reachable.

---

# 7. Check HTTP-Level Behavior

If TCP connectivity works, move up to the HTTP layer.

For example:

```bash
curl -v http://192.168.1.10:8000/api/users
```

The `-v` option is useful because it shows connection and HTTP details.

Look at:

* TCP connection result
* HTTP status code
* Response headers
* Request path
* Redirects
* TLS errors
* Authentication
* Request body
* Proxy behavior

For example:

```text
HTTP/1.1 200 OK
```

means the request reached an HTTP server and received a successful response.

Whereas:

```text
HTTP/1.1 401 Unauthorized
```

indicates the request reached the application/server but authentication is required or invalid.

And:

```text
HTTP/1.1 404 Not Found
```

means an HTTP server responded, but the requested resource/path was not found.

This is very different from:

```text
Connection timed out
```

because the latter may indicate that an HTTP response was never reached.

---

# 8. For HTTPS, Check TLS and Certificates

If the API is:

```text
https://api.example.com
```

then TCP connectivity alone is not sufficient.

The sequence is conceptually:

```text
Client
  ↓
TCP connection
  ↓
TLS handshake
  ↓
HTTP request
  ↓
API response
```

A failure can therefore occur during TLS.

Check for:

* Expired certificate
* Certificate issued for a different hostname
* Untrusted CA
* Missing intermediate certificate
* Incorrect server certificate
* TLS configuration
* SNI/hostname mismatch
* Proxy interception
* Incorrect hostname

For example:

```text
https://api.example.com
```

may fail certificate validation if the server presents a certificate that does not cover:

```text
api.example.com
```

### Important point

The TCP port being reachable does **not** mean HTTPS is working.

You can have:

```text
TCP ✓
TLS ✗
HTTP never reached
```

---

# 9. Check Server Logs

Server logs are one of the most valuable debugging tools.

Make a request from the remote machine while watching the API logs.

There are two major possibilities.

## Case A: No request appears in the logs

```text
Client
  ↓
DNS / Network / Firewall / Proxy / TCP
  ↓
API
```

If the request never reaches the application, investigate the layers **before the application**.

Possible causes:

* DNS
* Routing
* Firewall
* Security group
* Port
* Proxy
* Load balancer
* Listening address

---

## Case B: Request appears in the logs

```text
Client
  ↓
Network ✓
  ↓
TCP ✓
  ↓
HTTP ✓
  ↓
Application receives request
```

Now the problem is more likely to be:

* Authentication
* Authorization
* CORS
* Application routing
* Environment configuration
* Request validation
* Database dependency
* API logic
* IP allowlist

This gives a powerful debugging rule:

> **No application log entry usually means the problem is before the application. An application log entry means the request has reached at least the application layer.**

---

# 10. Check Application Configuration

Even when the network is working, the API may behave differently depending on the client or environment.

Check:

### CORS

For browser-based clients:

```text
Browser
   ↓
API
```

The browser may block the response because of the API's **CORS policy**.

Important:

> CORS is primarily a browser-enforced security mechanism.

Therefore:

```text
curl → API
   ✓
```

while:

```text
Browser → API
   ✗ CORS error
```

can happen.

A successful `curl` request does **not** prove that a browser-based frontend will be allowed to make the same cross-origin request.

---

### Authentication / Authorization

Check:

* API keys
* JWT tokens
* Cookies
* OAuth configuration
* Authorization headers
* User permissions
* IP-based access policies

For example:

```text
Machine A → API → 200 OK
Machine B → API → 401 Unauthorized
```

may be caused by different credentials or authentication configuration rather than networking.

---

### Other configuration

Check:

* Allowed hosts
* Allowed origins
* Environment variables
* API base URL
* IP allowlists
* Proxy configuration
* Rate limits
* Feature flags
* Environment-specific configuration

---

# 11. If the API Is Running in Docker

Docker introduces another common networking issue.

Suppose the application listens inside the container on:

```text
8000
```

You may need to publish the port:

```bash
docker run -p 8000:8000 my-api
```

Conceptually:

```text
Client
   |
   v
Host:8000
   |
   v
Docker container:8000
   |
   v
API
```

Without appropriate port publishing, the service may be reachable only inside the Docker networking environment or host, depending on the configuration.

Check:

```bash
docker ps
```

and:

```bash
docker logs <container>
```

Also verify that the application **inside the container** is not listening only on:

```text
127.0.0.1:8000
```

Inside a container, binding to localhost can prevent access through the container's network interface.

For many server applications, you would instead bind to an appropriate interface such as:

```text
0.0.0.0:8000
```

inside the container.

---

# 12. Check Reverse Proxy / Load Balancer Configuration

In real deployments, the API may not be directly exposed.

The architecture could be:

```text
Client
   ↓
DNS
   ↓
Load Balancer / Reverse Proxy
   ↓
Web Server
   ↓
API
   ↓
Database
```

For example:

```text
https://api.example.com
          ↓
      Nginx
          ↓
    localhost:8000
          ↓
        API
```

In this situation, the application may be working correctly while the reverse proxy is misconfigured.

Check:

* Proxy upstream address
* Proxy port
* TLS termination
* Host header handling
* Routing rules
* Load balancer health checks
* Security groups
* Backend target health

---

# 13. Practical Debugging Flow

I would debug it from the **bottom of the stack upward**.

```text
1. Is the API process running?
            ↓
2. Is it listening on the expected port?
            ↓
3. Is it listening on the correct interface?
            ↓
4. Can the server access its own IP:port?
            ↓
5. Can the client resolve the hostname?
            ↓
6. Can the client reach the server IP:port?
            ↓
7. Is a firewall/security group blocking traffic?
            ↓
8. Does TCP connect successfully?
            ↓
9. Does TLS succeed, if HTTPS is used?
            ↓
10. Does curl receive an HTTP response?
            ↓
11. Do server logs show the request?
            ↓
12. Check CORS/auth/application configuration
```

This approach avoids randomly changing application code.

---

# 14. A More Precise Layer-by-Layer Diagnosis

A useful way to think about the problem is:

```text
Layer / Area             Test
------------------------------------------------
Process                  Is API process running?
Listening                ss / netstat
Interface binding        127.0.0.1 vs 0.0.0.0
DNS                      nslookup / dig
Network                  ping / route / traceroute
TCP                      nc / Test-NetConnection
Firewall                 Firewall/security-group rules
TLS                      curl -v / certificate checks
HTTP                     curl -v
Application              API/server logs
Browser                  CORS / browser DevTools
Container                docker ps / docker logs
Proxy/LB                 Proxy and health-check configuration
```

The key is to move upward only after the lower layer is working.

# 15. Interview Example

Suppose the following happens:

```text
On server:

curl localhost:8000
        ↓
      works ✓

curl 192.168.1.10:8000
        ↓
      works ✓


From client:

curl 192.168.1.10:8000
        ↓
      fails ✗
```

I would **not immediately debug the API code**.

I would first investigate:

1. Whether the client can reach `192.168.1.10`
2. Whether TCP port `8000` is reachable
3. Firewall rules
4. Network routing
5. Security groups/ACLs
6. Whether a proxy or network policy is interfering

Because the API has already demonstrated that it works through the server's own network interface.

---

# 16. Another Interview Scenario

Suppose:

```text
Client
  ↓
curl http://192.168.1.10:8000/api/users
  ↓
HTTP 401
```

This is different.

An HTTP `401` means the request reached an HTTP server that responded with an authentication-related status.

Therefore, I would investigate:

```text
Authentication
Authorization
API keys
JWT
Cookies
Headers
```

rather than starting with routing.

Similarly:

```text
Connection timeout
```

suggests investigating connectivity before application authentication.

---

# 17. Another Useful Diagnostic: Compare localhost, IP, and hostname

A very effective sequence is:

```text
Test 1:
curl http://localhost:8000
```

Then:

```text
Test 2:
curl http://192.168.1.10:8000
```

Then from another machine:

```text
Test 3:
curl http://192.168.1.10:8000
```

Then:

```text
Test 4:
curl http://api.example.com
```

This progressively tests:

```text
localhost
   ↓
server network interface
   ↓
remote TCP connectivity
   ↓
DNS + complete endpoint
```

The first test that fails gives you a strong clue about where to investigate.

# 18. Common Mistakes

### ❌ Mistake 1: "It works on localhost, so the API is fine."

Not necessarily.

`localhost` only proves that the local path to the service works.

The network-facing path may still be broken.

---

### ❌ Mistake 2: "Change the API code first."

Usually not the best first step.

First determine whether the request even reaches the application.

---

### ❌ Mistake 3: "Use `0.0.0.0` as the client destination."

`0.0.0.0` is commonly used as a **server bind/listen address**.

Clients should normally connect to a specific reachable address such as:

```text
192.168.1.10
```

or:

```text
api.example.com
```

---

### ❌ Mistake 4: "Ping works, therefore the API must work."

Not necessarily.

Ping tests ICMP, while the API may use TCP.

You still need to test the actual TCP port.

---

### ❌ Mistake 5: "Ping fails, therefore the server is unreachable."

Also not necessarily.

ICMP may be blocked while TCP traffic is allowed.

---

### ❌ Mistake 6: "CORS is a server/network connectivity problem."

CORS is primarily enforced by browsers.

A command-line client such as `curl` may successfully access an API even though browser JavaScript is blocked by CORS policy.

---

### ❌ Mistake 7: "Port 8000 is open, so the API is working."

An open TCP port only proves that something is accepting TCP connections there.

The application may still return:

```text
404
401
403
500
```

or fail during TLS/application processing.

# Interview Takeaway

> When an API works locally but not from another machine, first determine **where the request stops**. Verify that the API process is running and listening on the correct interface and port, then test connectivity using the server's actual IP and the client's TCP connection tools. Check routing, firewalls, security groups, DNS, TLS, and HTTP behavior. Finally, inspect server logs and application-specific configuration such as CORS, authentication, allowed hosts, and environment variables.
>
> The most important principle is: **do not start by debugging application code until you know that the request is actually reaching the application.**

### Common Follow-Up

**How would you distinguish a DNS problem from a firewall problem from an application problem?**

A useful first distinction is:

```text
DNS problem
    ↓
Hostname does not resolve to the expected address

Firewall / network problem
    ↓
Correct address, but TCP connection cannot be established

Application problem
    ↓
TCP/HTTP request reaches the server,
but the application returns an error or unexpected response
```

That layer-by-layer distinction is one of the most useful practical networking debugging skills.
