# Q32. What Is a Proxy?

A **proxy server** is an intermediary that receives a network request from a client and forwards that request to another server **on behalf of the client**.

Without a proxy, communication is usually:

```text
Client ─────────────────────→ Server
Client ←───────────────────── Server
```

With a proxy:

```text
Client ─────→ Proxy ─────→ Server
Client ←───── Proxy ←───── Server
```

The proxy sits between the client and destination server and can potentially:

* Inspect traffic
* Modify requests or responses
* Filter traffic
* Cache content
* Enforce access-control policies
* Route traffic
* Perform authentication
* Apply rate limits
* Terminate TLS
* Hide or abstract the identity/topology of the other side

The exact capabilities depend on the **type of proxy and its configuration**.

---

# 1. Simple Example

Suppose an application wants to access:

```text
https://api.example.com
```

Without a proxy:

```text
Application
     |
     | HTTPS request
     ↓
api.example.com
```

With a proxy:

```text
Application
     |
     | Request
     ↓
Proxy Server
     |
     | Forwarded request
     ↓
api.example.com
```

The proxy receives the request and makes a request toward the destination server.

The response follows the reverse path:

```text
api.example.com
     |
     | Response
     ↓
Proxy Server
     |
     | Response
     ↓
Application
```

---

# 2. What Can a Proxy Do?

A proxy is not necessarily just a simple packet forwarder.

Depending on its role, it can perform additional functions.

### Inspection

A proxy may inspect request metadata or, depending on where TLS is terminated and the configuration, application-layer traffic.

For example:

```text
Request
   ↓
Proxy
   ↓
Check URL / headers / policy
   ↓
Allow or reject
```

### Modification

A proxy can add, remove, or modify headers.

For example:

```text
Client Request
      ↓
   Proxy
      ↓
Add forwarding metadata
      ↓
Server
```

### Filtering

A corporate proxy might block access to certain destinations.

```text
Employee
   ↓
Proxy
   ↓
Policy check
   ├── Allowed → Internet
   └── Blocked → Request denied
```

### Caching

A proxy can cache responses.

```text
Client
   ↓
Proxy
   ↓
Cache hit?
  /    \
Yes     No
 |       |
Response  Server
         |
         ↓
       Proxy
         |
       Cache
```

If the requested content is already cached and still valid, the proxy may serve it without contacting the destination server.

---

# 3. Forward Proxy

A **forward proxy** sits between clients and external servers.

```text
Client
   |
   ↓
Forward Proxy
   |
   ↓
Internet Server
```

The important idea is:

> The proxy represents the **client side**.

The client is generally configured to use the proxy.

For example:

```text
Company Laptop
      |
      ↓
Corporate Forward Proxy
      |
      ↓
Internet
```

---

## Common Uses of a Forward Proxy

### 1. Corporate Internet Access

A company may require employee machines to access the Internet through a central proxy.

```text
Employee Laptop
       ↓
Corporate Proxy
       ↓
Internet
```

This allows the organization to apply centralized policies.

---

### 2. Content Filtering

The proxy can block certain destinations or categories.

```text
Client
  ↓
Proxy
  ↓
Policy check
  ↓
Allowed / Blocked
```

---

### 3. Access Control

The proxy can determine which users or machines are allowed to access particular destinations.

---

### 4. Caching

Frequently requested resources may be cached to reduce external traffic.

---

### 5. Outbound Traffic Control

Organizations can use proxies to control or monitor outbound traffic according to their network policies.

---

# 4. Reverse Proxy

A **reverse proxy** sits in front of one or more backend servers.

```text
                ┌─────────────┐
                │  Server A   │
                └─────────────┘
                       ↑
                       |
Client → Reverse Proxy ├──→ Server B
                       |
                       ↓
                ┌─────────────┐
                │  Server C   │
                └─────────────┘
```

The important idea is:

> A reverse proxy represents the **server side**.

The client generally communicates with the reverse proxy rather than directly with the backend servers.

For example:

```text
Client
   |
   | https://api.example.com
   ↓
Reverse Proxy
   |
   +------→ API Server 1
   |
   +------→ API Server 2
   |
   +------→ API Server 3
```

The client may not know which backend server ultimately handled the request.

---

# 5. Common Uses of a Reverse Proxy

## 1. Load Balancing

Suppose three backend servers exist:

```text
             Reverse Proxy
             /     |     \
            ↓      ↓      ↓
        Server A Server B Server C
```

The reverse proxy can distribute incoming requests across the servers.

For example:

```text
Request 1 → Server A
Request 2 → Server B
Request 3 → Server C
Request 4 → Server A
```

The exact load-balancing algorithm depends on the configuration.

---

## 2. TLS Termination

A reverse proxy can terminate TLS at the edge.

Conceptually:

```text
Client
  |
  | HTTPS
  ↓
Reverse Proxy
  |
  | HTTP or HTTPS
  ↓
Backend
```

The proxy handles the TLS connection with the client.

The connection from the proxy to the backend can then use HTTP or HTTPS depending on the architecture and security requirements.

### Important

TLS termination does **not automatically mean** that the internal network is trusted or that encryption between proxy and backend is unnecessary.

In security-sensitive environments, HTTPS may still be used between the proxy and backend.

---

## 3. Request Routing

A reverse proxy can route different paths to different backend services.

For example:

```text
/api/users
      ↓
User Service

/api/orders
      ↓
Order Service

/api/payments
      ↓
Payment Service
```

Conceptually:

```text
                    Reverse Proxy
                    /     |      \
                   /      |       \
             User API  Order API  Payment API
```

This is common in microservice architectures.

---

## 4. Authentication and Access Control

The reverse proxy can enforce certain access policies before forwarding requests.

For example:

```text
Client
  ↓
Reverse Proxy
  ↓
Authentication check
  ├── Failed → Reject
  └── Passed → Backend
```

---

## 5. Rate Limiting

A reverse proxy can limit how frequently clients send requests.

For example:

```text
Client
  ↓
Reverse Proxy
  ↓
Rate limit check
  ├── Within limit → Backend
  └── Too many → 429 Too Many Requests
```

This can help protect backend services from excessive traffic.

---

## 6. Hiding Backend Topology

The client might know only:

```text
api.example.com
```

while the actual architecture is:

```text
api.example.com
       ↓
Reverse Proxy
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
API-1 API-2 API-3
```

The backend server addresses do not normally need to be exposed directly to clients.

This provides **architectural abstraction**, although a reverse proxy should not be treated as a complete security boundary by itself.

---

# 6. Proxy Headers and Original Client Information

A reverse proxy may forward information about the original client.

For example:

```text
Client
IP: 192.168.1.20
      |
      ↓
Reverse Proxy
      |
      ↓
Backend
```

The backend may see the proxy as its immediate network peer.

To preserve client information, deployments commonly use headers such as:

```text
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host
```

For example:

```text
X-Forwarded-For: 192.168.1.20
```

There is also the standardized `Forwarded` header.

### Important security point

Applications should not blindly trust forwarding headers from arbitrary clients.

The infrastructure should establish which proxies are trusted to set or preserve those headers.

Otherwise, a client might attempt to spoof its apparent IP address.

# 7. Forward Proxy vs Reverse Proxy

| Feature                         | Forward Proxy                  | Reverse Proxy                  |
| ------------------------------- | ------------------------------ | ------------------------------ |
| Sits in front of                | Clients                        | Servers                        |
| Represents                      | Client side                    | Server side                    |
| Main direction                  | Outbound client traffic        | Incoming server traffic        |
| Client usually knows it exists? | Usually yes                    | Often no                       |
| Typical users                   | Employees/devices/applications | Websites/APIs/backend services |
| Common use                      | Internet access/control        | Load balancing/routing         |
| Caching                         | Yes                            | Yes                            |
| Filtering                       | Common                         | Common                         |
| TLS termination                 | Possible                       | Very common                    |
| Load balancing                  | Not the primary purpose        | Common                         |
| Example                         | Corporate proxy                | Nginx/HAProxy in front of APIs |

### Memory Trick

```text
Forward Proxy
      ↓
Forward client's request outward

Reverse Proxy
      ↓
Reverse proxy protects/represents servers
```

# 8. Real-World Reverse Proxy Example

Suppose a company has:

```text
api.example.com
```

The public architecture might be:

```text
                     Internet
                         |
                         ↓
                 api.example.com
                         |
                         ↓
                 Reverse Proxy
                  /     |      \
                 /      |       \
                ↓       ↓        ↓
             API-1    API-2    API-3
```

A client sends:

```http
GET /users HTTP/1.1
Host: api.example.com
```

The reverse proxy can:

1. Accept the client connection
2. Terminate TLS
3. Check access policy
4. Apply rate limiting
5. Select a backend
6. Forward the request
7. Receive the backend response
8. Return the response to the client

The client only needs to know the public endpoint.

# 9. Proxy vs VPN

A **proxy and a VPN are not necessarily the same thing**.

A proxy typically handles traffic for specific applications or protocols that are configured to use the proxy.

Conceptually:

```text
Application
     ↓
Proxy
     ↓
Destination
```

A VPN generally creates a **network-level tunnel/interface** through which broader system traffic can be routed.

Conceptually:

```text
Applications
     ↓
Operating System
     ↓
VPN Interface / Tunnel
     ↓
VPN Gateway
     ↓
Network
```

The exact behavior depends on:

* VPN technology
* Routing configuration
* Split tunneling
* Application configuration
* Proxy configuration
* Operating-system settings

Therefore:

> **Proxy ≠ VPN**

although both can act as intermediaries for network traffic.

# 10. Proxy vs NAT

Another common interview confusion is:

> "Is a proxy the same as NAT?"

No.

### NAT

NAT primarily translates network addresses, and commonly transport ports, as traffic passes between networks.

```text
Private Client
192.168.1.10
      ↓
NAT
      ↓
Public IP
203.0.113.5
```

### Proxy

A proxy is an intermediary that typically operates at a higher/application-aware level and **receives and forwards requests**.

```text
Client
  ↓
Proxy
  ↓
Server
```

A proxy can understand application concepts such as:

```text
HTTP method
URL
Host header
HTTP headers
Cookies
```

depending on the proxy type.

NAT does not inherently perform those application-level functions.

---

# 11. Proxy vs Router

A router primarily forwards IP packets between networks.

```text
Network A
   ↓
Router
   ↓
Network B
```

A proxy generally acts as an intermediary for requests/connections:

```text
Client
   ↓
Proxy
   ↓
Server
```

The distinction is important:

```text
Router → primarily packet forwarding at Layer 3

Proxy → intermediary communication, often application-aware
```

Modern network devices can combine multiple functions, so the physical device alone does not determine the exact role.

# 12. Forward Proxy Request Flow

A simplified forward-proxy flow looks like:

```text
Client
   |
   | Request
   ↓
Forward Proxy
   |
   | New/forwarded request
   ↓
Internet Server
   |
   | Response
   ↓
Forward Proxy
   |
   | Response
   ↓
Client
```

The proxy may apply policies before forwarding the request.

```text
Request
   ↓
Proxy
   ↓
Policy
   ├── Allow → Destination
   └── Deny  → Error/Blocked
```

# 13. Reverse Proxy Request Flow

A reverse proxy flow looks like:

```text
Client
   |
   | Request
   ↓
Reverse Proxy
   |
   | Routing / authentication /
   | rate limiting / load balancing
   ↓
Backend Server
   |
   | Response
   ↓
Reverse Proxy
   |
   ↓
Client
```

This architecture is extremely common for production web applications and APIs.

# 15. Common Mistakes

### ❌ Mistake 1: "A proxy and reverse proxy are completely different technologies."

They use the same broad concept: an intermediary.

The main difference is **which side they represent**.

```text
Forward Proxy → represents clients

Reverse Proxy → represents servers
```

---

### ❌ Mistake 2: "A reverse proxy is just a load balancer."

Not exactly.

Load balancing is **one common function** of a reverse proxy.

A reverse proxy can also perform:

* TLS termination
* Routing
* Authentication
* Rate limiting
* Caching
* Header manipulation
* Access control

---

### ❌ Mistake 3: "A proxy always hides the client's IP."

Not necessarily.

A proxy may forward client information using headers such as:

```text
X-Forwarded-For
```

and the destination may be able to identify the original client depending on the architecture.

---

### ❌ Mistake 4: "A proxy automatically encrypts traffic."

Not necessarily.

A proxy can participate in TLS, terminate TLS, or forward encrypted connections depending on its configuration.

A proxy should not automatically be considered an encryption mechanism.

---

### ❌ Mistake 5: "VPN and proxy are the same."

They operate at different conceptual levels and can affect traffic differently.

```text
Proxy → often application-specific

VPN → generally network-level tunnel/routing
```

---

### ❌ Mistake 6: "Reverse proxy means the backend is automatically secure."

No.

A reverse proxy can improve architecture and enforce controls, but backend security still requires:

* Authentication
* Authorization
* Network controls
* Secure configuration
* Input validation
* Proper access policies

# Interview Takeaway

> A proxy is an intermediary that receives and forwards network requests between a client and another server. A **forward proxy** sits in front of clients and commonly controls outbound traffic, while a **reverse proxy** sits in front of servers and commonly provides routing, load balancing, TLS termination, caching, authentication, rate limiting, and access control. A proxy is different from NAT, a router, and a VPN because these technologies perform different functions and operate at different conceptual levels.
