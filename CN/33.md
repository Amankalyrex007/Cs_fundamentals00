# Q33. What Is a Reverse Proxy?

A **reverse proxy** is a server or service that sits in front of one or more backend servers and receives client requests **on behalf of those backend servers**.

Instead of the client communicating directly with a backend:

```text id="p5g0jr"
Client ─────────────────→ Backend Server
```

the architecture becomes:

```text id="jv2k3e"
                    ┌──→ Backend Server 1
                    │
Client ─→ Reverse Proxy ─→ Backend Server 2
                    │
                    └──→ Backend Server 3
```

The client typically knows the **reverse proxy's public address**, not the internal addresses of the backend servers.

For example:

```text id="t7nq5x"
Client
   |
   | https://api.example.com
   ↓
Reverse Proxy
   |
   ├──→ API Server 1
   ├──→ API Server 2
   └──→ API Server 3
```

The reverse proxy acts as an intermediary between the public clients and the backend infrastructure.

---

# 1. How Does a Reverse Proxy Work?

Suppose a company has:

```text id="y2jv8h"
api.example.com
       |
       ↓
Reverse Proxy
       |
       ├──→ API-1
       ├──→ API-2
       └──→ API-3
```

A client sends:

```http id="zq4g7j"
GET /users HTTP/1.1
Host: api.example.com
```

The request first reaches the reverse proxy.

The reverse proxy can then:

1. Receive the client connection
2. Inspect the request
3. Apply security/access policies
4. Determine the appropriate backend
5. Forward the request
6. Receive the backend response
7. Return the response to the client

Conceptually:

```text id="w5j9pm"
Client
  |
  | GET /users
  ↓
Reverse Proxy
  |
  | Select backend
  ↓
API-2
  |
  | Response
  ↓
Reverse Proxy
  |
  | Response
  ↓
Client
```

The client does not normally need to know that `API-2` handled the request.

---

# 2. Why Is a Reverse Proxy Used?

Reverse proxies are commonly used because they allow an organization to put a **single controlled entry point** in front of multiple backend services.

Major use cases include:

1. Load balancing
2. TLS termination
3. Security and access control
4. Request routing
5. Caching
6. Rate limiting
7. Authentication
8. Backend topology abstraction

Let's examine the major ones.

---

# 3. Load Balancing

One of the most common uses of a reverse proxy is **load balancing**.

Suppose there are three backend servers:

```text id="k0y3p8"
                  Reverse Proxy
                  /     |     \
                 ↓      ↓      ↓
             Server 1 Server 2 Server 3
```

Instead of sending every request to one server:

```text id="6msk5r"
100 requests
     |
     ↓
Server 1
```

the reverse proxy can distribute requests:

```text id="1qj3m6"
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1
Request 5 → Server 2
...
```

The exact distribution depends on the configured load-balancing algorithm.

Common strategies include:

* Round robin
* Least connections
* Weighted distribution
* Hash-based routing

This helps prevent one backend server from receiving all incoming traffic.

---

# 4. TLS Termination

A reverse proxy can handle HTTPS connections from clients.

For example:

```text id="z0g9tq"
Client
  |
  | HTTPS
  ↓
Reverse Proxy
  |
  | HTTP or HTTPS
  ↓
Backend
```

The reverse proxy performs the TLS handshake with the client and can decrypt the HTTP traffic before forwarding it to the backend.

This is called **TLS termination**.

---

## Why is TLS termination useful?

Suppose there are 50 backend servers.

Without centralized TLS termination, certificate configuration may need to be managed across many services.

With a reverse proxy:

```text id="9h0x44"
                 TLS Certificate
                       ↓
Client ───────→ Reverse Proxy
                       |
                       ├──→ Backend 1
                       ├──→ Backend 2
                       └──→ Backend 3
```

Certificate management can be centralized at the edge.

### Important security nuance

The connection from the reverse proxy to the backend does not automatically need to be plain HTTP.

For sensitive environments, HTTPS can also be used internally:

```text id="7b4j7m"
Client
  |
 HTTPS
  ↓
Reverse Proxy
  |
 HTTPS
  ↓
Backend
```

So:

> TLS termination at the reverse proxy does not automatically mean that backend traffic should be unencrypted.

The appropriate architecture depends on the security requirements.

---

# 5. Security and Access Control

A reverse proxy can provide a controlled entry point to backend services.

For example:

```text id="l1p6sl"
Internet
    |
    ↓
Reverse Proxy  ← Public
    |
    ↓
Backend Servers ← Private
```

The backend servers can remain on a private network and may not be directly reachable from the public Internet.

The reverse proxy can enforce policies such as:

* Authentication
* Authorization checks
* IP allowlists
* Rate limits
* Request filtering
* Access-control rules
* Header validation

For example:

```text id="1v6qkk"
Client
  ↓
Reverse Proxy
  ↓
Authentication
  ├── Failed → Reject
  └── Passed → Backend
```

This provides a useful security control point.

### Important clarification

A reverse proxy is **not automatically a complete security solution**.

Backend services still need appropriate:

* Authentication
* Authorization
* Input validation
* Network controls
* Secure configuration
* Application security

---

# 6. Request Routing

A reverse proxy can route requests to different backend services based on information such as:

* Hostname
* URL path
* Headers
* Other configured rules

For example:

```text id="g45wjy"
             Reverse Proxy
                  |
        ┌─────────┼──────────┐
        ↓         ↓          ↓
     /api/*   /images/*   /payments/*
        ↓         ↓          ↓
    API Service Image      Payment
               Service     Service
```

For example:

```text id="n7sq3p"
/api/users
      ↓
User API

/api/orders
      ↓
Order API

/images/logo.png
      ↓
Image Service

/payments
      ↓
Payment Service
```

This is particularly useful in **microservice architectures**.

---

# 7. Host-Based Routing

A reverse proxy can also route based on hostname.

For example:

```text id="iyz6ca"
api.example.com
      ↓
API servers


admin.example.com
      ↓
Admin servers


static.example.com
      ↓
Static-content servers
```

Conceptually:

```text id="dy0az3"
                     Reverse Proxy
                    /       |       \
                   ↓        ↓        ↓
             API Service Admin     Static
                         Service    Service
```

This allows multiple services to share the same public infrastructure.

---

# 8. Caching

A reverse proxy can cache frequently requested responses.

Without caching:

```text id="dsv3u5"
Client
  ↓
Reverse Proxy
  ↓
Backend
  ↓
Response
```

Every request may reach the backend.

With caching:

```text id="9z1n3g"
Client
  ↓
Reverse Proxy
  ↓
Cache hit?
 /       \
Yes       No
 |         |
Response  Backend
           |
           ↓
         Response
           |
           ↓
          Cache
```

If the response is cacheable and still valid, the reverse proxy may serve it without contacting the backend.

This can:

* Reduce backend load
* Reduce latency
* Reduce network traffic
* Improve scalability

Caching behavior depends on HTTP cache semantics and proxy configuration.

---

# 9. Rate Limiting

A reverse proxy can also control how many requests a client sends.

For example:

```text id="h78n9c"
Client
  ↓
Reverse Proxy
  ↓
Rate limit check
  ├── Within limit → Backend
  └── Exceeded → 429 Too Many Requests
```

For example, an API might configure a policy such as:

```text id="m3n0za"
100 requests/minute/client
```

If the client exceeds the configured limit, the reverse proxy can reject or delay additional requests.

This helps protect backend services from excessive traffic.

---

# 10. Hiding Backend Topology

Suppose the internal architecture is:

```text id="9sp9lh"
api.example.com
       ↓
Reverse Proxy
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
API-1 API-2 API-3
```

The public client only needs to know:

```text id="px7dws"
api.example.com
```

It does not normally need to know:

```text id="iy4x8f"
10.0.1.10
10.0.1.11
10.0.1.12
```

This provides **topology abstraction**.

It also makes backend infrastructure easier to change.

For example, you could replace:

```text id="kbyv1m"
API-1 + API-2 + API-3
```

with:

```text id="x3b4g6"
API-4 + API-5 + API-6 + API-7
```

without requiring clients to change the public API endpoint.

---

# 11. Reverse Proxy and Client IP Information

Because the reverse proxy receives the client connection first, the backend may see the reverse proxy as its immediate network peer.

For example:

```text id="m9i3zt"
Client
IP: 192.168.1.20
       |
       ↓
Reverse Proxy
       |
       ↓
Backend
```

The backend's TCP peer may be the reverse proxy rather than the original client.

To preserve original client information, reverse proxies commonly use headers such as:

```text id="1z0q6x"
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host
```

There is also the standardized `Forwarded` header.

For example:

```http id="6o2xvb"
X-Forwarded-For: 192.168.1.20
```

This allows the backend application to know the original client IP **when the proxy infrastructure is configured to provide it**.

### Important security point

The backend should not blindly trust these headers from arbitrary clients.

Only trusted proxy infrastructure should normally be allowed to establish these values.

# 12. Reverse Proxy Architecture in a Real Application

A typical production API might look like:

```text id="1ajf8k"
                         Internet
                            |
                            ↓
                    DNS / Public IP
                            |
                            ↓
                  Reverse Proxy / LB
                            |
                ┌───────────┼───────────┐
                ↓           ↓           ↓
             API-1        API-2        API-3
                |           |           |
                └───────────┼───────────┘
                            ↓

```

The reverse proxy becomes the public entry point.

It can handle:

```text id="b4zvxy"
TLS
Routing
Load balancing
Rate limiting
Authentication
Caching
Access control
```

while backend servers focus primarily on application processing.

# 13. Reverse Proxy vs Forward Proxy

A reverse proxy and forward proxy both act as intermediaries, but they represent different sides of communication.

| Feature                         | Forward Proxy             | Reverse Proxy              |
| ------------------------------- | ------------------------- | -------------------------- |
| Represents                      | Client                    | Server/backend             |
| Sits in front of                | Clients                   | Servers                    |
| Main direction                  | Outbound traffic          | Incoming traffic           |
| Client usually knows it exists? | Usually yes               | Often no                   |
| Typical use                     | Corporate Internet access | Load balancing/API routing |
| Common users                    | Employees/applications    | Websites/APIs/services     |
| Backend hidden?                 | Not the main purpose      | Commonly yes               |
| Load balancing                  | Not primary purpose       | Common                     |
| TLS termination                 | Possible                  | Very common                |

### Simple memory trick

```text id="q4cv8x"
Forward Proxy
     ↓
Client → Proxy → Internet

Reverse Proxy
     ↓
Internet → Proxy → Backend
```

Or:

> **Forward proxy represents clients. Reverse proxy represents servers.**

# 14. Reverse Proxy vs Load Balancer

This is a common interview follow-up.

A **load balancer** distributes traffic across multiple backend servers.

A **reverse proxy** is a broader intermediary that can perform many functions, including load balancing.

Therefore:

```text id="xk7h4w"
Reverse Proxy
    |
    +── Load balancing
    +── TLS termination
    +── Routing
    +── Caching
    +── Authentication
    +── Rate limiting
    +── Access control
```

A load balancer can therefore be implemented as or combined with a reverse proxy, but the concepts are not identical.

For example:

```text id="3c5k0z"
Client
   ↓
Reverse Proxy
   ↓
Load Balancing
   ↓
Backend 1 / Backend 2 / Backend 3
```

The exact capabilities depend on the software or cloud service being used.

# 16. Common Mistakes

### ❌ Mistake 1: "A reverse proxy is only used for load balancing."

No.

Load balancing is only one common use.

A reverse proxy can also provide:

* TLS termination
* Routing
* Caching
* Authentication
* Rate limiting
* Access control
* Header manipulation

---

### ❌ Mistake 2: "Reverse proxy and forward proxy are the same thing."

Both are intermediaries, but they represent different sides.

```text id="25ov1a"
Forward Proxy → represents client

Reverse Proxy → represents server
```

---

### ❌ Mistake 3: "TLS termination means backend traffic is always insecure."

Not necessarily.

The reverse proxy can communicate with the backend using HTTPS as well:

```text id="t6bqjb"
Client
  ↓ HTTPS
Reverse Proxy
  ↓ HTTPS
Backend
```

---

### ❌ Mistake 4: "The reverse proxy automatically secures the backend."

Not automatically.

Backend security still requires proper:

* Authentication
* Authorization
* Network controls
* Application security
* Configuration

---

### ❌ Mistake 5: "The backend always sees the original client's IP."

Not directly at the TCP layer.

The backend may see the reverse proxy as its immediate peer.

Original client information may be forwarded through trusted proxy headers such as `X-Forwarded-For` or `Forwarded`.

---

### ❌ Mistake 6: "A reverse proxy and API gateway are always exactly the same."

Not necessarily.

An API gateway is typically a more specialized gateway for APIs and may provide features such as:

* Authentication
* API policies
* Rate limiting
* Request transformation
* Service routing

A reverse proxy can provide some or many of these capabilities, but the terms describe different architectural concepts.

# Interview Takeaway

> A **reverse proxy** is an intermediary placed in front of one or more backend servers. It accepts client requests and forwards them to an appropriate backend, then returns the backend response to the client. It is commonly used for **load balancing, TLS termination, routing, caching, rate limiting, authentication, and access control**, while also hiding the internal backend topology from clients.
>
> The key distinction is: **a forward proxy represents clients, while a reverse proxy represents servers.**
>
> A reverse proxy is also broader than a load balancer: **load balancing is one of the functions a reverse proxy can perform**, while reverse proxies can additionally handle TLS, routing, caching, authentication, and other policies.
