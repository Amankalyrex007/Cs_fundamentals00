# Q34. What Is a Load Balancer?

A **load balancer** is a system that distributes incoming network traffic or requests across multiple backend servers instead of sending all traffic to a single server.

The basic goal is to prevent one backend from becoming an unnecessary bottleneck and to improve:

* Scalability
* Availability
* Traffic distribution
* Resource utilization
* Maintenance flexibility

---

# 1. Basic Idea

Without a load balancer:

```text id="x6jv4m"
              ┌──→ Server
              │
Clients ──────┘
```

All clients communicate with the same server.

As traffic increases:

```text id="m0v6l9"
Clients
   |
   ↓
Single Server
   |
   ↓
Overloaded
```

This can create a bottleneck or single point of failure.

With a load balancer:

```text id="qj9q5n"
                    ┌──→ Server 1
                    │
Clients ──→ Load ───┼──→ Server 2
           Balancer │
                    ├──→ Server 3
                    │
                    └──→ Server 4
```

The load balancer decides which backend should handle each incoming connection or request.

---

# 2. Why Do We Need a Load Balancer?

Suppose an API initially runs on one server:

```text id="8xq1me"
             ┌──────────┐
Clients ───→ │ API S1   │
             └──────────┘
```

As traffic grows:

```text id="xq2xv6"
10 requests/sec
      ↓
100 requests/sec
      ↓
1,000 requests/sec
      ↓
Server becomes overloaded
```

Instead of continuously relying on one increasingly powerful machine, we can add multiple instances:

```text id="9d0jz3"
             ┌──→ API-1
             │
Clients → LB ├──→ API-2
             │
             └──→ API-3
```

Now traffic can be distributed across multiple servers.

This is a common horizontal-scaling architecture.

---

# 3. How Does a Load Balancer Work?

Suppose four API servers are available:

```text id="v6c5xe"
                    Load Balancer
                         |
             ┌───────────┼───────────┐
             ↓           ↓           ↓
            S1          S2          S3          S4
```

A client sends a request:

```text id="j0v4g8"
Client
   |
   | Request
   ↓
Load Balancer
```

The load balancer examines the configured information and selects an appropriate backend.

For example:

```text id="9t9z6f"
Request 1 → S1
Request 2 → S2
Request 3 → S3
Request 4 → S4
Request 5 → S1
```

The exact behavior depends on the load-balancing algorithm.

---

# 4. Common Load-Balancing Algorithms

## 4.1 Round Robin

The load balancer distributes requests sequentially.

For four servers:

```text id="5l4zqm"
Request 1 → S1
Request 2 → S2
Request 3 → S3
Request 4 → S4
Request 5 → S1
Request 6 → S2
```

Conceptually:

```text id="b2b5qx"
S1 → S2 → S3 → S4 → S1 → S2 → ...
```

### Advantage

Simple and easy to implement.

### Limitation

It assumes the servers can handle roughly similar workloads.

If S1 is much more powerful than S2, treating them equally may not be ideal.

---

# 5. Weighted Round Robin

In **Weighted Round Robin**, servers receive different amounts of traffic based on assigned weights.

For example:

```text id="7r9f1v"
S1 → Weight 4
S2 → Weight 2
S3 → Weight 1
```

A simplified distribution might look like:

```text id="q3s2i4"
S1 → S1 → S1 → S1
S2 → S2
S3
```

The idea is:

> More capable servers can receive more traffic.

This is useful when backend servers have different capacities.

---

# 6. Least Connections

The load balancer sends new connections toward a server with fewer active connections.

Suppose:

```text id="q6y3i5"
S1 → 100 active connections
S2 →  40 active connections
S3 →  20 active connections
```

A new connection may be sent to:

```text id="9j0q8a"
S3
```

because it currently has the fewest active connections.

This can be useful when connections have significantly different lifetimes or resource costs.

---

# 7. IP Hash

With **IP Hash**, information derived from the client IP can be used to select a backend consistently.

Conceptually:

```text id="g3x8a5"
Hash(client IP)
       ↓
Backend selection
```

For example:

```text id="p2q7l8"
Client A → S1
Client B → S3
Client C → S2
```

The goal can be to keep a client consistently associated with a particular backend.

However, this is not a guarantee of application-level session persistence in every architecture, and behavior depends on the algorithm and configuration.

---

# 8. Health Checks

One of the most important features of a load balancer is **backend health checking**.

Suppose:

```text id="2x5w4n"
Load Balancer
   |
   ├── Health check → Server 1 ✓
   ├── Health check → Server 2 ✓
   ├── Health check → Server 3 ✗
   └── Health check → Server 4 ✓
```

If Server 3 repeatedly fails its configured health checks, the load balancer can mark it as unhealthy.

Then:

```text id="v1s0yj"
Before:

LB → S1
LB → S2
LB → S3
LB → S4
```

becomes conceptually:

```text id="n8d2xq"
After S3 fails:

LB → S1
LB → S2
LB -X→ S3
LB → S4
```

New traffic is directed toward healthy backends.

### Important nuance

The exact behavior depends on the implementation.

A health check might test:

* TCP connection
* HTTP endpoint
* HTTPS endpoint
* Application-specific health endpoint

For example:

```http id="0g4z4w"
GET /health
```

might return:

```text id="y2j4k6"
200 OK
```

indicating that the service is healthy according to that check.

---

# 9. Why Use a Load Balancer?

## 9.1 Scalability

A load balancer allows additional backend instances to be added.

Before:

```text id="q5h8r9"
LB
 |
 ├── S1
 └── S2
```

After:

```text id="p9q4r2"
LB
 |
 ├── S1
 ├── S2
 ├── S3
 └── S4
```

This supports **horizontal scaling**.

Instead of making one server infinitely larger, you can add more servers.

---

# 10. Availability

Suppose:

```text id="t6v3k1"
LB
 |
 ├── S1 ✓
 ├── S2 ✓
 └── S3 ✗
```

If S3 fails its health checks, new requests can be sent to S1 and S2.

Therefore, one backend failure does not necessarily make the entire service unavailable.

### Important nuance

A load balancer does not automatically make an application highly available.

The overall system also needs appropriate:

* Backend redundancy
* Database availability
* Network redundancy
* Health checks
* Deployment strategy
* Failure handling

---

# 11. Traffic Distribution

Without load balancing:

```text id="e4b7i8"
1000 requests
       |
       ↓
      S1
```

With multiple servers:

```text id="n4v6z1"
1000 requests
       |
       ↓
      LB
    / | \
   ↓  ↓  ↓
 S1  S2  S3
```

Traffic can be distributed according to the chosen algorithm and current backend state.

This improves overall resource utilization when the workload and architecture are suitable.

---

# 12. Maintenance

A load balancer can help with maintenance.

Suppose:

```text id="j8x1cz"
LB
 |
 ├── S1 ✓
 ├── S2 ✓
 └── S3 ✓
```

You want to update S2.

You can conceptually remove it from rotation:

```text id="c5z7na"
LB
 |
 ├── S1 ✓
 ├── S2  ← maintenance
 └── S3 ✓
```

New traffic goes to S1 and S3.

After the update:

```text id="0z2p7x"
LB
 |
 ├── S1 ✓
 ├── S2 ✓
 └── S3 ✓
```

S2 can be returned to service.

This supports deployment and maintenance strategies such as **rolling updates**, assuming the application architecture supports them.

# 13. Layer 4 vs Layer 7 Load Balancing

Load balancers can operate at different layers.

The two important categories are:

* **Layer 4 (L4)**
* **Layer 7 (L7)**

---

## Layer 4 Load Balancer

An L4 load balancer operates primarily using transport/network connection information.

It can make decisions based on information such as:

* Source IP
* Destination IP
* TCP/UDP
* Source port
* Destination port
* Connection state

Conceptually:

```text id="1u8y0b"
Client
  |
  | TCP :443
  ↓
L4 Load Balancer
  |
  ├──→ Server 1
  ├──→ Server 2
  └──→ Server 3
```

It generally does not need to understand the HTTP URL or application-level headers.

---

# 14. Layer 7 Load Balancer

An L7 load balancer understands application-layer protocols such as HTTP.

Therefore, it can make decisions based on:

* Hostname
* URL path
* HTTP headers
* Cookies
* HTTP method
* Other application-layer information

For example:

```text id="0cx4qv"
/api/*

       ↓
API servers
```

while:

```text id="z2c1mv"
/images/*

       ↓
Image servers
```

and:

```text id="7s9y0h"
/payments/*

       ↓
Payment service
```

This requires understanding HTTP, so it is typically an **L7 routing decision**.

---

# 15. L4 vs L7 Comparison

| Feature                         | L4 Load Balancer             | L7 Load Balancer                           |
| ------------------------------- | ---------------------------- | ------------------------------------------ |
| Main layer                      | Transport                    | Application                                |
| Typical protocols               | TCP/UDP                      | HTTP/HTTPS and other application protocols |
| Understands HTTP path?          | No                           | Yes                                        |
| Understands HTTP headers?       | No                           | Yes                                        |
| Can route `/api/*` differently? | Not based on HTTP path       | Yes                                        |
| Can inspect cookies?            | Generally no                 | Yes                                        |
| Connection-oriented decisions   | Yes                          | Yes, plus application context              |
| Typical use                     | TCP/UDP traffic distribution | Web/API routing                            |

### Memory Trick

> **L4 sees connections. L7 understands application requests.**

---

# 16. Example: L7 API Routing

Suppose:

```text id="0w7g4q"
api.example.com
       |
       ↓
L7 Load Balancer
       |
       ├── /users    → User Service
       ├── /orders   → Order Service
       └── /payments → Payment Service
```

A request:

```http id="5n6p3w"
GET /orders/123
Host: api.example.com
```

can be routed to the order service because the load balancer understands the HTTP request.

An L4 load balancer generally cannot make that decision from the URL path because the URL is application-layer information.

---

# 17. Load Balancer vs Reverse Proxy

These concepts **overlap**, but they are not identical.

A **reverse proxy** is an intermediary that receives requests on behalf of backend servers.

It can perform functions such as:

* TLS termination
* Routing
* Caching
* Authentication
* Access control
* Rate limiting
* Load balancing

A **load balancer** specifically focuses on distributing traffic or connections across multiple backend instances.

Therefore:

```text id="b4g7w0"
Reverse Proxy
     |
     +── TLS termination
     +── Routing
     +── Caching
     +── Authentication
     +── Rate limiting
     +── Load balancing
```

A load balancer can therefore be implemented as or combined with a reverse proxy.

---

# 18. One System Can Perform Both Roles

For example:

```text id="3t4j9v"
                         Reverse Proxy /
Client ─────────────→    Load Balancer
                              |
                    ┌─────────┼─────────┐
                    ↓         ↓         ↓
                  API-1     API-2     API-3
```

The same component might:

1. Accept the client connection
2. Terminate TLS
3. Inspect the HTTP request
4. Apply access policies
5. Select a backend
6. Forward the request
7. Return the response

This is common in modern infrastructure.

For example, **Nginx** can be configured to perform both reverse-proxy and load-balancing functions.

# 19. Session Persistence / Sticky Sessions

Some applications maintain session state locally on a particular backend.

For example:

```text id="k9r0v3"
Client A
   ↓
Load Balancer
   ↓
Server 1
   ↓
Session stored locally
```

If the next request goes to Server 2:

```text id="0x3z7v"
Client A
   ↓
Load Balancer
   ↓
Server 2
   ↓
Session missing
```

the application may behave incorrectly if the session is not shared elsewhere.

Some load balancers support **session persistence**, commonly called sticky sessions.

Conceptually:

```text id="y3n7k8"
Client A → Server 1
Client A → Server 1
Client A → Server 1
```

However, a more scalable architecture often stores shared session/state information in a shared data store or uses stateless application design where appropriate.

Examples include:

```text id="6q9m2x"
Redis
Database
Distributed session store
Signed/stateless tokens
```

This is an important architectural consideration when introducing load balancing.

---

# 20. Health Checks vs Application Health

A backend passing a health check does not necessarily mean every application feature is working perfectly.

For example:

```text id="5h1x3a"
GET /health
       ↓
200 OK
```

does not necessarily prove:

```text id="6b3v2z"
Database queries ✓
Payment service ✓
External API ✓
All business logic ✓
```

A well-designed health-check strategy distinguishes between:

* **Liveness** — is the process alive?
* **Readiness** — is it ready to receive traffic?
* Deeper dependency health, when appropriate

This helps prevent traffic from being sent to an instance that is alive but not ready to serve requests.

# 21. Common Mistakes

### ❌ Mistake 1: "A load balancer is just a router."

Not exactly.

A router primarily forwards IP packets between networks.

A load balancer distributes connections or requests across backend instances according to configured policies.

---

### ❌ Mistake 2: "Every load balancer is Layer 7."

No.

Load balancing can happen at:

```text id="d0m7b2"
L4 → TCP/UDP connection-level information

L7 → HTTP/application-level information
```

---

### ❌ Mistake 3: "Load balancing automatically guarantees high availability."

Not by itself.

You still need:

* Multiple healthy backends
* Reliable health checks
* Redundant infrastructure
* Appropriate data-layer architecture
* Proper deployment strategies

---

### ❌ Mistake 4: "Round robin always gives equal real-world load."

Not necessarily.

Requests can have different processing costs.

For example:

```text id="z2k1cs"
Request A → 2 ms
Request B → 5 seconds
```

Two servers receiving the same number of requests may have very different workloads.

This is why other algorithms may be more appropriate for some workloads.

---

### ❌ Mistake 5: "The load balancer always sends a client to the same server."

Not necessarily.

Unless session persistence or another consistent-selection mechanism is configured, consecutive requests may reach different backends.

---

### ❌ Mistake 6: "Health check success means the application is completely healthy."

Not necessarily.

A health check tests whatever condition the configured health endpoint or mechanism checks.

A shallow health check may only prove that the process is alive.

# Interview Takeaway

> A **load balancer** distributes incoming connections or requests across multiple backend servers to improve scalability, availability, and resource utilization. It can use algorithms such as **Round Robin, Weighted Round Robin, Least Connections, and IP Hash**, and commonly performs health checks so that new traffic is not sent to unhealthy backends.
>
> Load balancing can operate at **Layer 4**, using transport/network connection information, or **Layer 7**, where the system can understand application-level information such as HTTP hostnames, paths, headers, and cookies.
>
> A load balancer and reverse proxy can overlap: a reverse proxy can perform load balancing, while also providing features such as TLS termination, caching, routing, authentication, and rate limiting.
