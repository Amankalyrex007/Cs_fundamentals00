# Q35. What Is a CDN?

A **CDN (Content Delivery Network)** is a geographically distributed network of servers, commonly called **edge servers** or **edge locations**, that delivers content to users from a location closer to them.

The main goals of a CDN are to:

* Reduce network latency
* Improve content delivery performance
* Reduce load on the origin server
* Handle large amounts of traffic
* Improve availability and resilience
* Provide additional edge security capabilities

---

# 1. Basic Idea

Without a CDN, users in different geographic locations may all request content from the same origin server.

```text
                         ┌──→ User A
                         │
Origin Server ───────────┼──→ User B
                         │
                         └──→ User C
```

For example, suppose the origin server is located in the US.

A user in India may have to communicate across a long network path:

```text
User in India
      |
      | Long network path
      ↓
   Internet
      |
      ↓
Origin Server in US
```

This can increase latency.

With a CDN, content can be replicated or cached at edge locations closer to users:

```text
                       ┌──→ User A
                       │
Origin ──→ CDN ────────┼──→ User B
                       │
                       └──→ User C
                    Edge Servers
```

Conceptually:

```text
User in India
      |
      ↓
CDN Edge in/near India
      |
      ↓
Cached Content
```

The content may therefore travel a much shorter network path.

---

# 2. Origin Server vs Edge Server

Two important terms are:

### Origin Server

The **origin** is the authoritative backend from which the CDN obtains content when it does not already have a usable cached copy.

For example:

```text
Origin
 ├── Application servers
 ├── Databases
 ├── Object storage
 └── Static content
```

### Edge Server

An **edge server** is a CDN server located closer to users and responsible for serving content from the CDN's distributed infrastructure.

```text
                 CDN
                  |
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Edge A      Edge B      Edge C
```

Users are generally directed toward an appropriate edge location according to the CDN's routing and configuration.

---

# 3. How Does a CDN Work?

Suppose a user requests an image:

```http
GET /images/product.jpg
```

The request reaches the CDN.

Conceptually:

```text
User
 ↓
CDN Edge
 ↓
Is content cached?
```

There are two main possibilities:

* **Cache hit**
* **Cache miss**

---

# 4. CDN Cache Hit

If the requested content is already available and usable in the edge cache:

```text
User
 ↓
CDN Edge
 ↓
Cached content
 ↓
User
```

The CDN can return the content without contacting the origin server.

For example:

```text
User requests:
GET /images/product.jpg

CDN Edge:
" I already have product.jpg "

        ↓

Return cached file
```

This reduces:

* Latency
* Origin requests
* Origin bandwidth consumption
* Backend workload

---

# 5. CDN Cache Miss

Suppose the requested object is not present in the edge cache.

The flow can be:

```text
User
 ↓
CDN Edge
 ↓
Origin Server
 ↓
CDN Edge
 ↓
Cache content
 ↓
User
```

For example:

```text
1. User requests product.jpg
2. CDN edge does not have it
3. CDN requests it from origin
4. Origin returns the image
5. CDN stores/cache the image according to its rules
6. CDN returns the image to the user
```

A future request may then become:

```text
User
 ↓
CDN Edge
 ↓
Cached image
```

instead of repeatedly contacting the origin.

---

# 6. Cache Hit vs Cache Miss

| Situation         | What happens                                                         |
| ----------------- | -------------------------------------------------------------------- |
| Cache hit         | CDN serves cached content                                            |
| Cache miss        | CDN obtains content from origin or another configured source         |
| Cacheable content | Can generally be stored according to cache policy                    |
| Stale content     | CDN may revalidate, refresh, or serve according to configured policy |

A high cache-hit ratio is often desirable for content that can safely be cached.

---

# 7. What Can a CDN Deliver?

CDNs commonly deliver:

* Images
* CSS files
* JavaScript files
* Videos
* Fonts
* Software downloads
* Static web pages

Depending on the CDN and configuration, they can also accelerate some:

* API responses
* Dynamic content
* Personalized content
* Streaming workloads

However, dynamic or personalized content often requires more careful caching rules.

---

# 8. Example: Static Website

Suppose a website contains:

```text
index.html
style.css
app.js
logo.png
product.jpg
font.woff2
```

These resources may be suitable for CDN delivery.

A user requests:

```text
https://example.com/product.jpg
```

Instead of:

```text
User
 ↓
Origin
 ↓
product.jpg
```

the request may become:

```text
User
 ↓
Nearest/appropriate CDN Edge
 ↓
product.jpg
```

if the object is already cached there.

---

# 9. Why Does a CDN Reduce Latency?

Suppose the origin server is far away from the user.

Without CDN:

```text
User
 |
 |-----------------------------|
 |     Long network path       |
 |-----------------------------|
 |
Origin
```

With CDN:

```text
User
 |
 |--- Shorter path ---|
 |
CDN Edge
```

The physical distance is not the only factor determining latency, but reducing the network path and serving content from a nearby edge can significantly improve delivery performance.

### Important clarification

A CDN does **not** magically increase the speed of the user's Internet connection.

It primarily reduces the distance and work required to retrieve content from the origin for content that can be effectively served at the edge.

---

# 10. CDN Caching

Caching is one of the most important CDN features.

Suppose:

```text
100,000 users
      |
      ↓
CDN Edge
```

If the same image is requested repeatedly:

```text
product.jpg
```

the CDN may cache it.

Instead of:

```text
100,000 requests
       ↓
Origin
```

many requests can become:

```text
100,000 requests
       ↓
CDN
       ↓
Origin receives far fewer requests
```

This can dramatically reduce origin load.

---

# 11. Cache-Control and TTL

Caching is controlled by policies and HTTP caching mechanisms.

For example, a response may contain:

```http
Cache-Control: public, max-age=3600
```

This indicates that the response can be cached according to the specified policy for the given freshness period.

A related concept is **TTL (Time To Live)**.

Conceptually:

```text
Object cached
     ↓
Fresh for configured period
     ↓
TTL expires
     ↓
CDN may revalidate/fetch a newer version
```

The exact caching behavior depends on CDN configuration and HTTP cache headers.

---

# 12. What Happens When Content Becomes Stale?

Suppose the CDN has:

```text
product.jpg → old version
```

but the origin now contains:

```text
product.jpg → new version
```

The CDN needs a mechanism to determine whether its cached object is still usable.

Possible approaches include:

* Waiting for the cache freshness period to expire
* Revalidating with the origin
* Purging/invalidation
* Updating cache rules
* Versioning the resource URL

For example:

```text
/product-v1.jpg
/product-v2.jpg
```

Changing the URL is a common strategy for static assets because the new URL represents a different cache key.

---

# 13. CDN Cache Invalidation

Suppose a company updates:

```text
logo.png
```

but users are still receiving the old cached version.

The CDN can often support **cache invalidation/purging**.

Conceptually:

```text
Origin
  |
  | New logo
  ↓
CDN caches
  |
  | Purge old object
  ↓
New requests fetch updated content
```

This is important when content changes before its normal cache lifetime expires.

---

# 14. Benefits of a CDN

| Benefit                 | Explanation                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| **Lower latency**       | Content can be served from an edge location closer to the user                              |
| **Reduced origin load** | Cached content does not always need to reach the origin                                     |
| **Scalability**         | Distributed infrastructure can handle large request volumes                                 |
| **Availability**        | Multiple edge locations can provide resilience                                              |
| **Security**            | Many CDNs provide features such as DDoS protection, WAF, TLS termination, and rate limiting |

---

# 15. Reduced Origin Load

Consider a popular image:

```text
product.jpg
```

Without CDN:

```text
Users ───────────────→ Origin
Users ───────────────→ Origin
Users ───────────────→ Origin
Users ───────────────→ Origin
```

With CDN caching:

```text
Users
  |
  ↓
CDN Edge
  |
  └──→ Origin only when needed
```

The origin can therefore spend more resources handling requests that actually require backend processing.

---

# 16. Scalability

Suppose a website suddenly becomes popular.

Without edge caching:

```text
Millions of users
        |
        ↓
Origin
```

The origin may become a bottleneck.

With a CDN:

```text
                     ┌── Edge 1
                     │
Millions of users ───┼── Edge 2
                     │
                     ├── Edge 3
                     │
                     └── Edge 4
                            |
                            ↓
                         Origin
```

Much of the traffic can be handled at distributed edge locations.

This does not eliminate the need to scale the origin for dynamic traffic, but it can significantly reduce the amount of traffic reaching it.

---

# 17. CDN and Security

Modern CDN providers often provide additional security capabilities, such as:

* DDoS protection
* Web Application Firewall (WAF)
* TLS termination
* Rate limiting
* Bot management
* Access-control features

A typical architecture might look like:

```text
Internet
   |
   ↓
CDN / Edge
   |
   ├── DDoS protection
   ├── WAF
   ├── TLS
   ├── Rate limiting
   └── Caching
   |
   ↓
Origin / Backend
```

### Important clarification

A CDN is not automatically a complete security solution.

The actual protection depends on:

* Provider
* Configuration
* Security rules
* Application architecture
* Origin protection

---

# 18. CDN Request Routing

A CDN may have many edge locations:

```text
              CDN
       ┌──────┼──────┐
       ↓      ↓      ↓
    Edge A  Edge B  Edge C
```

When a user makes a request, the CDN's infrastructure can direct the request to an appropriate edge location.

The exact mechanism depends on the CDN provider and architecture and may involve DNS, anycast, routing, and other techniques.

The high-level idea is:

```text
User
 ↓
Appropriate CDN Edge
 ↓
Cached content
```

rather than:

```text
User
 ↓
Distant origin
```

---

# 19. CDN vs Load Balancer

CDNs and load balancers solve related but different problems.

| CDN                                         | Load Balancer                                       |
| ------------------------------------------- | --------------------------------------------------- |
| Distributes content geographically          | Distributes traffic among backend servers           |
| Often caches content                        | Usually forwards connections/requests               |
| Focuses on edge delivery                    | Focuses on backend traffic distribution             |
| Reduces latency for cacheable content       | Improves backend scalability and availability       |
| Can serve content without contacting origin | Usually selects a backend for the request           |
| Often globally distributed                  | Often positioned in front of a service/backend pool |

### Simple memory trick

> **CDN = Where should content be served from?**

> **Load Balancer = Which backend should handle this traffic?**

---

# 20. CDN and Load Balancer Can Work Together

A modern architecture can use both:

```text
User
  |
  ↓
CDN / Edge
  |
  ↓
Load Balancer
  |
  ├──────────┬──────────┐
  ↓          ↓          ↓
 API-1      API-2      API-3
```

For a cacheable image:

```text
User
 ↓
CDN
 ↓
Cache HIT
 ↓
Image returned
```

The request may never reach the load balancer or origin.

For a dynamic API request:

```text
User
 ↓
CDN
 ↓
Cache MISS / dynamic request
 ↓
Load Balancer
 ↓
API-1 / API-2 / API-3
```

This is why the two technologies can complement each other.

---

# 21. CDN vs Reverse Proxy

A CDN can be thought of as a distributed edge infrastructure that often performs reverse-proxy-like functions.

However, a CDN is primarily designed around **distributed content delivery and edge caching**, while a reverse proxy is a broader intermediary pattern that may run at a single location or within a private infrastructure.

For example:

```text
CDN:
User → Edge → Origin

Reverse Proxy:
User → Reverse Proxy → Backend

Combined:
User → CDN Edge → Reverse Proxy/LB → Backend
```

---

# 22. Important: CDN Does Not Automatically Make Every Request Faster

This is a very important interview point.

A CDN is especially useful when content can be effectively cached or served at the edge.

For example:

```text
logo.png
style.css
app.js
video segment
```

can often benefit significantly from CDN caching.

But consider:

```http
GET /account/balance
```

The response may be personalized for one user.

Caching it incorrectly could expose one user's data to another user.

Therefore, such content requires careful caching policies and may need to be fetched from the origin.

Conceptually:

```text
Static content:
User → CDN → Cache HIT ✓

Dynamic/personalized content:
User → CDN → Origin/API
```

# 23. CDN Example: Video Streaming

Suppose a popular video is requested by millions of users.

Without a CDN:

```text
Millions of users
        |
        ↓
Origin
```

The origin must handle enormous amounts of traffic.

With a CDN:

```text
                     ┌── User
                     ↓
                   Edge A

Origin → CDN ────────┼── Edge B → Users
                     │
                     └── Edge C → Users
```

Video content can be cached and served from distributed edge locations.

This is particularly useful for large static objects and repeated content delivery.

# 24. Common Mistakes

### ❌ Mistake 1: "CDN is just a faster server."

No.

A CDN is a **distributed network of edge infrastructure** designed to deliver content closer to users.

---

### ❌ Mistake 2: "CDN always caches everything."

No.

Caching depends on:

* HTTP headers
* CDN configuration
* Cache rules
* Content type
* Request characteristics
* Personalization requirements

---

### ❌ Mistake 3: "CDN means the origin server is no longer needed."

Usually not.

The origin often remains the authoritative source for content that is not cached or cannot be served entirely from the edge.

---

### ❌ Mistake 4: "CDN is the same as a load balancer."

No.

```text
CDN
→ Distributed edge delivery/cache

Load Balancer
→ Backend traffic distribution
```

They can work together.

---

### ❌ Mistake 5: "Every CDN request goes to the origin first."

No.

That would defeat one of the major purposes of caching.

A cache hit can be served directly from the edge:

```text
User
 ↓
CDN
 ↓
Cache HIT
 ↓
User
```

---

### ❌ Mistake 6: "CDN always reduces latency."

Not necessarily.

A cache miss, poorly placed edge, uncached dynamic request, or other network conditions may prevent a CDN from providing a latency improvement.

# Interview Takeaway

> A **CDN (Content Delivery Network)** is a geographically distributed network of edge servers that delivers content closer to users. It can cache content at edge locations so that repeated requests can be served without contacting the origin server, reducing latency and origin load while improving scalability and availability.
>
> A CDN commonly handles static assets such as images, CSS, JavaScript, fonts, videos, and software downloads, while some dynamic or API content can also be handled depending on the caching and application configuration.
>
> The two key CDN scenarios are **cache hit** and **cache miss**. On a cache hit, the edge serves the content directly. On a cache miss, the CDN may retrieve the content from the origin, cache it according to its rules, and return it to the user.
>
> A CDN and a **load balancer** are complementary: the CDN focuses on **geographically distributed edge delivery**, while the load balancer focuses on **distributing traffic among backend servers**.
