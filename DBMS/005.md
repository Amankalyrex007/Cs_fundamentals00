# Q5. What are Primary and Foreign Keys?

## Answer

**Primary key** and **foreign key** are important concepts in relational databases. They are used to:

* Uniquely identify records.
* Establish relationships between tables.
* Maintain referential integrity.
* Improve data consistency and support efficient querying.

The simplest way to remember them is:

```text
Primary Key → Identifies a row

Foreign Key → Connects tables
```

---

# 1. Primary Key

A **primary key** is a column or combination of columns that **uniquely identifies each row in a table**.

For example:

| student_id | name  | course |
| ---------: | ----- | ------ |
|        101 | Rahul | B.Tech |
|        102 | Priya | BCA    |
|        103 | Amit  | B.Tech |

Here, `student_id` can be the primary key because every student has a unique ID.

```sql
CREATE TABLE Students (
    student_id INT PRIMARY KEY,
    name VARCHAR(100),
    course VARCHAR(50)
);
```

The database will enforce the primary-key constraint.

Therefore:

* Every `student_id` must be **unique**.
* A primary-key value **cannot be NULL**.
* A table has **one primary-key constraint**.
* That primary key can consist of **one column or multiple columns**.

---

# Primary Key Example

Suppose we try to insert:

```sql
INSERT INTO Students
VALUES (101, 'Rahul', 'B.Tech');
```

This is valid if `101` doesn't already exist.

But trying:

```sql
INSERT INTO Students
VALUES (101, 'Aman', 'BCA');
```

would violate the primary-key constraint because `101` is already being used.

Conceptually:

```text
Students
+------------+--------+
| student_id | name   |
+------------+--------+
| 101        | Rahul  |
| 102        | Priya  |
| 103        | Amit   |
+------------+--------+

student_id
    ↓
Must uniquely identify each row
```

---

# Important Point: Primary Key and NULL

A primary key cannot contain `NULL`.

Why?

Because the purpose of a primary key is to provide a reliable identity for every row.

```text
Primary Key
     ↓
Unique
     +
Not NULL
     ↓
Identifies a row
```

In SQL, the database enforces this as part of the primary-key constraint.

---

# Composite Primary Key

A primary key does not have to consist of only one column.

A **composite primary key** uses multiple columns together to uniquely identify a row.

For example, consider an `Enrollments` table:

| student_id | course_id | semester |
| ---------: | --------: | -------- |
|        101 |       501 | 1        |
|        101 |       502 | 1        |
|        102 |       501 | 1        |

Suppose the combination of `student_id` and `course_id` must be unique.

We can define:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    PRIMARY KEY (student_id, course_id)
);
```

Here:

```text
student_id + course_id
          ↓
   Composite Primary Key
```

Neither column necessarily has to be unique individually.

For example:

```text
student_id = 101
```

can appear multiple times, and:

```text
course_id = 501
```

can also appear multiple times.

But their **combination** must be unique.

---

# 2. Foreign Key

A **foreign key** is a column or combination of columns in one table that references a **candidate key—commonly a primary key—in another table**, establishing a relationship between the tables.

For example:

### Students

| student_id | name  |
| ---------: | ----- |
|        101 | Rahul |
|        102 | Priya |

### Orders

| order_id | student_id | amount |
| -------: | ---------: | -----: |
|      501 |        101 |    500 |
|      502 |        102 |    800 |

Here:

```text
Students.student_id
        ↑
        │
        │ referenced by
        │
Orders.student_id
```

The `student_id` in `Orders` is a **foreign key** referencing `Students.student_id`.

---

# Defining a Foreign Key

We can define it using:

```sql
CREATE TABLE Orders (
    order_id INT PRIMARY KEY,
    student_id INT,
    amount DECIMAL(10, 2),

    FOREIGN KEY (student_id)
        REFERENCES Students(student_id)
);
```

Now the database can enforce the relationship between the two tables.

---

# Referential Integrity

The foreign key helps enforce **referential integrity**.

For example, suppose the `Students` table contains:

```text
101 → Rahul
102 → Priya
```

Then this order is valid:

```text
order_id = 501
student_id = 101
```

because student `101` exists.

But this would normally violate the foreign-key constraint:

```text
order_id = 503
student_id = 999
```

if student `999` does not exist in the referenced table.

Conceptually:

```text
Students
+-------------+
| student_id  |
+-------------+
| 101         |
| 102         |
+-------------+
       ↑
       |
       | Foreign Key
       |
Orders
+-------------+
| student_id  |
+-------------+
| 101         | ✓
| 102         | ✓
| 999         | ✗
+-------------+
```

This prevents an order from referencing a nonexistent student, subject to the database's configured constraint behavior.

---

# Primary Key vs Foreign Key

| Primary Key                            | Foreign Key                                       |
| -------------------------------------- | ------------------------------------------------- |
| Uniquely identifies a row in its table | References a key in another table                 |
| Must be unique                         | Does not necessarily have to be unique            |
| Cannot contain `NULL`                  | Can contain `NULL` if the column permits it       |
| Identifies the row/entity              | Establishes a relationship                        |
| One primary-key constraint per table   | A table can have multiple foreign-key constraints |
| Can contain one or multiple columns    | Can also contain one or multiple columns          |

### Easy Diagram

```text
        Students
        +---------+
        |   PK    |
        |student_id|
        +----+----+
             |
             | referenced by
             ↓
        Orders
        +---------+
        |   FK    |
        |student_id|
        +---------+
```

# Why Isn't a Foreign Key Necessarily Unique?

This is an important interview question.

Suppose:

```text
Students
student_id
-----------
101
102
```

A student can place multiple orders:

```text
Orders
order_id | student_id
---------+-----------
501      | 101
502      | 101
503      | 101
504      | 102
```

Here, `Orders.student_id` contains:

```text
101
101
101
102
```

It is **not unique**.

That is perfectly valid because multiple orders can belong to the same student.

This represents a **one-to-many relationship**:

```text
One Student
     |
     +---- Order 1
     |
     +---- Order 2
     |
     +---- Order 3
```

# Real-World Analogy

Think about a college system.

### Students

```text
Students
----------------
student_id ← Primary Key
name
course
```

### Courses

```text
Courses
----------------
course_id ← Primary Key
course_name
```

### Enrollments

```text
Enrollments
----------------
student_id ← Foreign Key
course_id  ← Foreign Key
```

The foreign keys connect enrollment records to the corresponding students and courses.

```text
Students
   |
   | student_id
   ↓
Enrollments
   ↑
   | course_id
   |

```

This is a common many-to-many relationship design.

---

# Many-to-Many Relationship Example

Suppose:

```text
Student 101 → B.Tech
Student 101 → DBMS
Student 102 → DBMS
```

A student can enroll in multiple courses, and a course can have multiple students.

We can represent this using a junction/associative table:

```text
Students
+-------------+
| student_id  |
+-------------+
      |
      | 1
      |
      | N
      ↓
Enrollments
+-------------+-----------+
| student_id  | course_id |
+-------------+-----------+
      ↑             |
      | N           | N
      |             |
      +-------------+
            |
            ↓
         Courses
```

The foreign keys in `Enrollments` connect the two entities.

Example:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    PRIMARY KEY (student_id, course_id),

    FOREIGN KEY (student_id)
        REFERENCES Students(student_id),

    FOREIGN KEY (course_id)
        REFERENCES Courses(course_id)
);
```

This demonstrates how **primary keys and foreign keys work together to model relationships**.

---

# Foreign Key and NULL

A foreign key can often contain `NULL`, provided the column is not defined as `NOT NULL`.

For example:

```sql
CREATE TABLE Orders (
    order_id INT PRIMARY KEY,
    customer_id INT NULL,

    FOREIGN KEY (customer_id)
        REFERENCES Customers(customer_id)
);
```

A `NULL` foreign key generally means that there is currently **no referenced value** for that row.

For example:

```text
order_id | customer_id
---------+------------
501      | 101
502      | NULL
```

However, whether `NULL` is appropriate depends on the application's rules.

If every order must belong to a customer, we can enforce that:

```sql
customer_id INT NOT NULL
```

along with the foreign key.

---

# Foreign Key Actions

When a referenced row is updated or deleted, the database can be configured with actions such as:

```text
ON DELETE CASCADE
ON DELETE SET NULL
ON DELETE RESTRICT
ON UPDATE CASCADE
```

For example:

```sql
FOREIGN KEY (customer_id)
REFERENCES Customers(customer_id)
ON DELETE CASCADE;
```

With `CASCADE`, deleting a customer can cause related child rows to be deleted as well, according to the database's foreign-key behavior.

This should be chosen carefully because cascading deletes can remove multiple related records.

---

# Primary Key vs Unique Key

Another common interview confusion is:

> "Is a primary key the same as a UNIQUE constraint?"

They are related but not exactly the same.

A table can have:

```text
One primary-key constraint
+
Multiple UNIQUE constraints
```

For example:

```sql
CREATE TABLE Users (
    user_id INT PRIMARY KEY,
    email VARCHAR(150) UNIQUE,
    username VARCHAR(100) UNIQUE
);
```

Here:

```text
user_id  → Primary Key
email    → UNIQUE
username → UNIQUE
```

The primary key is the table's main identifier, while unique constraints enforce uniqueness on other candidate attributes.

---

# Candidate Key and Primary Key

A **candidate key** is a minimal set of attributes that can uniquely identify a row.

A table can have multiple candidate keys, but one is selected as the **primary key**.

For example:

```text
Users
-------------------------
user_id
email
username
name
```

Suppose both:

```text
user_id
email
```

can uniquely identify a user.

Then:

```text
Candidate Keys
    ├── user_id
    └── email

Chosen Primary Key
    └── user_id
```

This is why a foreign key can technically reference a **candidate key**, although in basic DBMS discussions it is most commonly described as referencing a primary key.

---

# Why Are Keys Important?

Keys help with:

### 1. Unique Identification

Primary keys uniquely identify records.

```text
student_id → 101
```

---

### 2. Relationships Between Tables

Foreign keys connect related tables.

```text
Students
   ↓
Orders
```

---

### 3. Referential Integrity

Foreign keys prevent invalid references when the constraint is enforced.

```text
Order → Existing Student ✓
Order → Nonexistent Student ✗
```

---

### 4. Data Consistency

Keys help maintain reliable relationships between records.

---

### 5. Efficient Querying and Joins

Keys provide the logical connection needed for joins.

For example:

```sql
SELECT Students.name, Orders.amount
FROM Students
JOIN Orders
    ON Students.student_id = Orders.student_id;
```

The relationship between:

```text
Students.student_id
```

and:

```text
Orders.student_id
```

provides the logical basis for this join.

# Common Mistakes

### Mistake 1: Foreign key must be unique

Incorrect.

A foreign key can contain duplicate values.

```text
student_id
-----------
101
101
101
102
```

This is valid when multiple child records reference the same parent.

---

### Mistake 2: Foreign key cannot be NULL

Not always true.

A foreign-key column **can contain `NULL`** unless a `NOT NULL` constraint or other rule prevents it.

---

### Mistake 3: A table can have multiple primary keys

More precisely:

> A table can have **one primary-key constraint**, but that primary key may consist of multiple columns.

For example:

```sql
PRIMARY KEY (student_id, course_id)
```

is one **composite primary key**.

---

### Mistake 4: Primary key always means one column

Not necessarily.

```text
Primary Key
     ↓
One column OR multiple columns
```

Multiple columns together form a composite primary key.

---

### Mistake 5: Foreign key only establishes a logical relationship

A foreign key can also **enforce referential integrity** when the corresponding constraint is enabled and enforced by the DBMS.

# Interview Takeaway

A strong interview answer would be:

> **A primary key is a column or combination of columns that uniquely identifies each row in a table. It cannot contain NULL values, and a table has one primary-key constraint. A foreign key is a column or combination of columns that references a candidate key—commonly a primary key—in another table. It establishes relationships between tables and helps maintain referential integrity.**

### One-Line Definitions

```text
Primary Key
→ Uniquely identifies a row in its own table.

Foreign Key
→ References a key in another table and establishes a relationship.
```
