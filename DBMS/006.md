# Q6. What is a Candidate Key?

## Answer

A **candidate key** is a **minimal set of one or more attributes that can uniquely identify each row in a table**.

The two most important properties are:

```text
Candidate Key
     ↓
Uniqueness
     +
Minimality
```

A table can have **multiple candidate keys**, but only **one candidate key is selected as the primary key**.

---

# Simple Example

Suppose we have a `Students` table:

| student_id | email                                         | name  | course |
| ---------: | --------------------------------------------- | ----- | ------ |
|        101 | [rahul@example.com](mailto:rahul@example.com) | Rahul | B.Tech |
|        102 | [priya@example.com](mailto:priya@example.com) | Priya | BCA    |
|        103 | [amit@example.com](mailto:amit@example.com)   | Amit  | B.Tech |

Here, both:

```text
student_id
email
```

can uniquely identify a student, assuming both are guaranteed to be unique.

Therefore:

```text
student_id → Candidate Key
email      → Candidate Key
```

We might choose:

```text
student_id → Primary Key
```

while:

```text
email → Another Candidate Key
```

The other candidate key is often referred to as an **alternate key** and may be enforced using a `UNIQUE` constraint.

---

# Why Is It Called a "Candidate" Key?

It is called a **candidate key** because it is a key that is **eligible to become the primary key**.

Suppose we have:

```text
student_id
email
```

Both can uniquely identify a student.

Therefore:

```text
Candidate Keys
      |
      +---- student_id
      |
      +---- email
```

We then choose one:

```text
Candidate Keys
      |
      +---- student_id ──→ Primary Key
      |
      +---- email ───────→ Alternate Key
```

So:

> **Primary key = the candidate key selected as the table's main identifier.**

---

# Why "Minimal"?

The word **minimal** is extremely important.

A candidate key must contain **no unnecessary attributes**.

Suppose:

```text
(student_id, email)
```

uniquely identifies a student.

But:

```text
student_id
```

by itself already uniquely identifies the student.

Therefore:

```text
(student_id, email)
```

is **not** a candidate key.

Why?

Because it is not minimal.

```text
{student_id, email}
        ↓
Can uniquely identify a row
        ↓
But student_id alone is enough
        ↓
Not minimal
        ↓
Not a candidate key
```

---

# Candidate Key Example

Consider:

| student_id | email                                         | name  |
| ---------: | --------------------------------------------- | ----- |
|        101 | [rahul@example.com](mailto:rahul@example.com) | Rahul |
|        102 | [priya@example.com](mailto:priya@example.com) | Priya |
|        103 | [amit@example.com](mailto:amit@example.com)   | Amit  |

Assume both `student_id` and `email` are unique.

Then:

```text
{student_id} → Candidate Key
{email}      → Candidate Key
```

But:

```text
{student_id, email}
```

is **not** a candidate key because `student_id` alone is sufficient.

However, it is still a **super key**.

---

# Candidate Key vs Primary Key

| Candidate Key                                        | Primary Key                                     |
| ---------------------------------------------------- | ----------------------------------------------- |
| Any minimal key capable of uniquely identifying rows | The candidate key chosen as the main identifier |
| A table can have multiple candidate keys             | A table has one primary-key constraint          |
| Not every candidate key becomes the primary key      | Selected from candidate keys                    |
| Other candidate keys are often called alternate keys | Main key used for identification                |
| Must be unique and minimal                           | Must be unique and non-NULL                     |

### Example

```text
Candidate Keys
      |
      +---- student_id
      |
      +---- email
      |
      ↓
Choose one
      ↓
Primary Key
      |
      └---- student_id
```

---

# SQL Example

We can represent this design using SQL:

```sql
CREATE TABLE Students (
    student_id INT PRIMARY KEY,
    email VARCHAR(100) UNIQUE,
    name VARCHAR(100)
);
```

Here:

```text
student_id → Primary Key
email      → Another candidate key / alternate key
name       → Not a candidate key
```

Assuming the business rule guarantees that every student's email is unique, `email` can serve as a candidate key.

The `UNIQUE` constraint helps enforce that uniqueness in the database.

---

# Important Nuance About UNIQUE

A common interview simplification is:

> "A UNIQUE column is always a candidate key."

That is not strictly correct.

A candidate key must be:

1. **Unique**
2. **Minimal**
3. **Able to identify each row**

A `UNIQUE` constraint is a database mechanism for enforcing uniqueness, but whether an attribute is conceptually a candidate key depends on the **data model and business rules**.

For example, a system might technically enforce uniqueness on an attribute that is not intended to identify an entity.

So:

```text
UNIQUE constraint ≠ automatically a candidate key
```

The database design determines whether the attribute is actually a candidate identifier.

# Candidate Key vs Super Key

This is a **very common DBMS interview question**.

### Super Key

A **super key** is any set of attributes that uniquely identifies a row.

### Candidate Key

A **candidate key** is a **minimal super key**.

Therefore:

```text
Candidate Key ⊂ Super Key
```

More precisely:

> **Every candidate key is a super key, but not every super key is a candidate key.**

---

# Example: Super Key vs Candidate Key

Consider:

```text
Students
+-------------+---------------------+--------+
| student_id  | email               | name   |
+-------------+---------------------+--------+
| 101         | rahul@example.com   | Rahul  |
| 102         | priya@example.com   | Priya  |
| 103         | amit@example.com    | Amit   |
+-------------+---------------------+--------+
```

Assume:

```text
student_id → Unique
email      → Unique
```

Then:

```text
{student_id}
        ↓
Candidate Key

{email}
        ↓
Candidate Key
```

But:

```text
{student_id, name}
```

also uniquely identifies a student because `student_id` alone is enough.

Therefore:

```text
{student_id, name}
        ↓
Super Key
        ↓
Not Candidate Key
```

because it is not minimal.

Similarly:

```text
{student_id, email}
        ↓
Super Key
        ↓
Not Candidate Key
```

because either attribute alone may already be sufficient.

# Composite Candidate Key

A candidate key can consist of **multiple attributes**.

For example, consider an `Enrollments` table:

| student_id | course_id | semester |
| ---------: | --------: | -------: |
|        101 |       501 |        1 |
|        101 |       502 |        1 |
|        102 |       501 |        1 |

Suppose neither `student_id` nor `course_id` alone uniquely identifies an enrollment.

But:

```text
(student_id, course_id)
```

uniquely identifies one enrollment.

Then:

```text
{student_id, course_id}
        ↓
Composite Candidate Key
```

It is a candidate key because:

* The combination is unique.
* Removing either attribute would make it insufficient.

It could then be selected as the primary key:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    PRIMARY KEY (student_id, course_id)
);
```

This is an important point:

> **A candidate key can contain one attribute or multiple attributes.**

---

# Example of Minimality with a Composite Key

Suppose:

```text
(student_id, course_id)
```

uniquely identifies an enrollment.

Then:

```text
student_id
```

alone is not unique because one student can enroll in multiple courses.

Likewise:

```text
course_id
```

alone is not unique because many students can enroll in the same course.

Therefore:

```text
student_id + course_id
```

is necessary.

```text
student_id     → Not sufficient
course_id      → Not sufficient
student_id +
course_id      → Sufficient and minimal
```

Therefore it can be a **candidate key**.

---

# Candidate Key vs Super Key vs Primary Key

This comparison is useful for interviews:

| Concept           | Meaning                                              |
| ----------------- | ---------------------------------------------------- |
| **Super Key**     | Any set of attributes that uniquely identifies a row |
| **Candidate Key** | Minimal super key                                    |
| **Primary Key**   | Candidate key selected as the main identifier        |
| **Alternate Key** | Candidate key not selected as the primary key        |

Example:

```text
Super Keys:
{student_id}
{email}
{student_id, name}
{student_id, email}
{email, name}
...

Candidate Keys:
{student_id}
{email}

Primary Key:
{student_id}

Alternate Key:
{email}
```

The exact list of super keys depends on which attribute combinations are guaranteed to uniquely identify rows.

# Real-World Example

Consider a `Users` table:

| user_id | email                                 | username | name  |
| ------: | ------------------------------------- | -------- | ----- |
|       1 | [a@example.com](mailto:a@example.com) | aman01   | Aman  |
|       2 | [b@example.com](mailto:b@example.com) | rahul02  | Rahul |
|       3 | [c@example.com](mailto:c@example.com) | priya03  | Priya |

Suppose the system guarantees that:

```text
user_id → unique
email → unique
username → unique
```

Then potentially:

```text
Candidate Keys
├── user_id
├── email
└── username
```

The database designer may choose:

```text
user_id → Primary Key
```

while:

```text
email
username
```

remain alternate candidate keys.

SQL could be:

```sql
CREATE TABLE Users (
    user_id INT PRIMARY KEY,
    email VARCHAR(150) UNIQUE,
    username VARCHAR(100) UNIQUE,
    name VARCHAR(100)
);
```

# Why Are Candidate Keys Important?

Candidate keys help database designers identify the attributes that can uniquely identify an entity.

They are important for:

### 1. Identifying Records

They provide possible unique identifiers.

### 2. Choosing a Primary Key

The primary key is selected from candidate keys.

### 3. Maintaining Data Integrity

Candidate attributes should remain unique according to the data model.

### 4. Database Design

Identifying candidate keys helps determine relationships, functional dependencies, and normalization.

### 5. Avoiding Redundant Identifiers

The concept of minimality helps ensure that unnecessary attributes are not included in a key.

# Common Mistakes

### Mistake 1: "Candidate key is any unique column"

Not necessarily.

A candidate key can contain:

```text
One attribute
OR
Multiple attributes
```

And it must be **minimal**.

---

### Mistake 2: "Every super key is a candidate key"

Incorrect.

```text
Candidate Key = Minimal Super Key
```

A super key containing unnecessary attributes is not a candidate key.

---

### Mistake 3: "There can be only one candidate key"

Incorrect.

A table can have multiple candidate keys.

Example:

```text
student_id → Candidate Key
email      → Candidate Key
```

---

### Mistake 4: "Every candidate key becomes a primary key"

Incorrect.

Only **one candidate key is selected as the primary key**.

The others can be considered **alternate keys**.

---

### Mistake 5: "Candidate key must always be one column"

Incorrect.

A candidate key can be composite:

```text
(student_id, course_id)
```

# Interview Takeaway

A strong interview answer would be:

> **A candidate key is a minimal set of one or more attributes that can uniquely identify each row in a table. A table can have multiple candidate keys, and one of them is selected as the primary key. The remaining candidate keys are often called alternate keys. A candidate key is a minimal super key, meaning it contains no unnecessary attributes.**

### One-Line Definition

> **Candidate Key = A minimal set of attributes that uniquely identifies a row.**
