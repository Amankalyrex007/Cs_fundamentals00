# Q7. What is a Composite Key?

## Answer

A **composite key** is a key made up of **two or more columns together** that uniquely identify a row in a table.

A single column may not be unique, but the **combination of multiple columns** is unique.

```text
Column A ──┐
           ├──→ Composite Key
Column B ──┘
```

The important point is:

> **The combination of columns must uniquely identify the row.**

The individual columns do **not** necessarily have to be unique.

---

# Example

Consider a student enrollment table:

| student_id | course_id | semester |
| ---------: | --------- | -------: |
|        101 | C01       |     2026 |
|        101 | C02       |     2026 |
|        102 | C01       |     2026 |
|        102 | C02       |     2026 |

Here:

```text
student_id
```

alone is **not unique** because a student can enroll in multiple courses.

For example:

```text
101 → C01
101 → C02
```

Similarly:

```text
course_id
```

alone is **not unique** because many students can take the same course.

For example:

```text
C01 → Student 101
C01 → Student 102
```

But:

```text
(student_id, course_id)
```

together can uniquely identify an enrollment.

```text
(101, C01)
(101, C02)
(102, C01)
(102, C02)
```

Each combination is different.

Therefore:

```text
(student_id, course_id)
        ↓
Composite Key
```

---

# Creating a Composite Primary Key

We can define it using SQL:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,
    semester INT,

    PRIMARY KEY (student_id, course_id)
);
```

Now:

```text
student_id + course_id
        ↓
Composite Primary Key
```

The database will not allow two rows with the same combination.

For example, this is valid:

```sql
INSERT INTO Enrollments
VALUES (101, 'C01', 2026);

INSERT INTO Enrollments
VALUES (101, 'C02', 2026);
```

But this would violate the primary-key constraint:

```sql
INSERT INTO Enrollments
VALUES (101, 'C01', 2026);
```

because:

```text
(101, C01)
```

already exists.

---

# Why Use a Composite Key?

A composite key is useful when **no single attribute is sufficient to uniquely identify a row**, but a combination of attributes is.

A very common example is a **many-to-many relationship**.

For example:

```text
Students                    Courses
   |                           |
   |                           |
   +-------- Enrollments ------+
```

A student can enroll in many courses:

```text
Student 101 → C01
Student 101 → C02
Student 101 → C03
```

And a course can have many students:

```text
C01 → Student 101
C01 → Student 102
C01 → Student 103
```

Therefore, the `Enrollments` table acts as a **junction/associative table**.

```text
Students
   |
   | student_id
   ↓
Enrollments
   ↑
   | course_id
   |
Courses
```

The combination:

```text
(student_id, course_id)
```

identifies each student-course relationship.

---

# Many-to-Many Relationship Example

Suppose we have:

### Students

| student_id | name  |
| ---------: | ----- |
|        101 | Rahul |
|        102 | Priya |

### Courses

| course_id | course_name       |
| --------- | ----------------- |
| C01       | DBMS              |
| C02       | Operating Systems |

### Enrollments

| student_id | course_id |
| ---------: | --------- |
|        101 | C01       |
|        101 | C02       |
|        102 | C01       |

This means:

```text
Rahul → DBMS
Rahul → Operating Systems
Priya → DBMS
```

The combination:

```text
(student_id, course_id)
```

ensures that the same student cannot be enrolled in the same course twice, assuming that is the intended business rule.

# Composite Key vs Single-Column Key

| Single-Column Key                          | Composite Key                                 |
| ------------------------------------------ | --------------------------------------------- |
| Uses one column                            | Uses two or more columns                      |
| Example: `student_id`                      | Example: `(student_id, course_id)`            |
| One attribute is sufficient for uniqueness | Combination provides uniqueness               |
| Usually simpler to reference               | May require multiple columns when referencing |
| Common for entity tables                   | Common in junction/associative tables         |

### Example

Single-column key:

```text
Students
   |
student_id
   ↓
Primary Key
```

Composite key:

```text
Enrollments
   |
   +── student_id
   |
   +── course_id
   ↓
Composite Primary Key
```

---

# Composite Key Does NOT Mean Every Column Is Unique

This is one of the most important points.

Consider:

| student_id | course_id |
| ---------: | --------- |
|        101 | C01       |
|        101 | C02       |
|        102 | C01       |

Here:

```text
student_id = 101
```

appears more than once.

And:

```text
course_id = C01
```

also appears more than once.

That is completely valid.

What must be unique is:

```text
(student_id, course_id)
```

So:

```text
student_id → Not individually unique
course_id  → Not individually unique

(student_id, course_id)
             ↓
          Unique
```

Therefore:

> **A composite key requires uniqueness of the combination, not necessarily of each individual column.**

---

# Composite Key vs Composite Index

Do not confuse these two concepts.

### Composite Key

A **composite key** consists of multiple columns that participate in uniquely identifying records and can enforce a key constraint.

Example:

```sql
PRIMARY KEY (student_id, course_id)
```

### Composite Index

A **composite index** is an index built on multiple columns, primarily to improve query performance.

Example:

```sql
CREATE INDEX idx_student_course
ON Enrollments(student_id, course_id);
```

This creates a **composite index**, not a primary key.

The two concepts solve different problems:

```text
Composite Key
      ↓
Data identification / integrity

Composite Index
      ↓
Query performance
```

A composite index can also be declared `UNIQUE`, in which case it enforces uniqueness, but it is still conceptually different from a primary-key constraint.

---

# Composite Primary Key vs Composite Foreign Key

A composite key can also be referenced by a **composite foreign key**.

Suppose:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    PRIMARY KEY (student_id, course_id)
);
```

Another table can reference both columns together:

```sql
CREATE TABLE Attendance (
    student_id INT,
    course_id INT,
    attendance_date DATE,
    present BOOLEAN,

    FOREIGN KEY (student_id, course_id)
        REFERENCES Enrollments(student_id, course_id)
);
```

Here:

```text
(student_id, course_id)
        ↓
Composite Primary Key
        ↑
        |
Composite Foreign Key
```

The referencing columns must correspond to the referenced key as required by the database system.

---

# Composite Key and Minimality

A useful connection to the previous topic—**candidate keys**—is that a composite candidate key must also be **minimal**.

Suppose:

```text
(student_id, course_id)
```

uniquely identifies an enrollment.

If neither column alone is sufficient:

```text
student_id     → Not unique
course_id      → Not unique
```

then:

```text
(student_id, course_id)
```

can be a candidate key.

But suppose:

```text
student_id
```

alone were already unique.

Then:

```text
(student_id, course_id)
```

would be unnecessary as a candidate key because it is not minimal.

So:

```text
Composite Candidate Key
        ↓
Multiple columns
        +
Unique combination
        +
Minimal
```

This is an important distinction between a **composite key** and simply having multiple columns in a unique constraint.

---

# Composite Key vs UNIQUE Constraint

A composite `UNIQUE` constraint can also enforce uniqueness across multiple columns:

```sql
CREATE TABLE Enrollments (
    enrollment_id INT PRIMARY KEY,
    student_id INT,
    course_id INT,

    UNIQUE (student_id, course_id)
);
```

Here:

```text
enrollment_id
     ↓
Primary Key

(student_id, course_id)
     ↓
Composite UNIQUE constraint
```

The pair cannot be duplicated.

This design is different from:

```sql
PRIMARY KEY (student_id, course_id)
```

where the combination itself is the primary identifier.

# Another Real-World Example: Product Orders

Consider an order-items table:

| order_id | product_id | quantity |
| -------: | ---------: | -------: |
|     1001 |        P01 |        2 |
|     1001 |        P02 |        1 |
|     1002 |        P01 |        3 |

Here:

```text
order_id
```

is not unique because one order can contain multiple products.

Similarly:

```text
product_id
```

is not unique because the same product can appear in multiple orders.

But:

```text
(order_id, product_id)
```

can uniquely identify a particular product within an order.

For example:

```text
(1001, P01)
(1001, P02)
(1002, P01)
```

Therefore, a composite key can be appropriate for an order-items relationship when the business rule says a product appears at most once per order.

# Advantages of Composite Keys

### 1. Naturally Represents Relationships

They work particularly well for junction tables.

### 2. Enforces Business Rules

They can prevent duplicate combinations.

For example:

```text
Same student + same course
        ↓
Cannot be inserted twice
```

### 3. No Artificial Identifier Required

Sometimes the combination itself is a natural identifier, so an additional `id` column may not be necessary.

### 4. Useful for Many-to-Many Relationships

They are very common in associative tables such as:

```text
Student ↔ Course
User ↔ Role
Order ↔ Product
Employee ↔ Project
```

---

# Potential Drawbacks

Composite keys are not always the simplest choice.

### 1. More Columns to Reference

A foreign key referencing a composite key may need multiple columns:

```sql
FOREIGN KEY (student_id, course_id)
```

instead of:

```sql
FOREIGN KEY (enrollment_id)
```

### 2. Larger Foreign Keys

If several tables reference the composite key, the key columns may be repeated in those tables.

### 3. More Complex Joins

Queries and relationships may need multiple columns in join conditions:

```sql
SELECT *
FROM Attendance a
JOIN Enrollments e
  ON a.student_id = e.student_id
 AND a.course_id = e.course_id;
```

Therefore, database designers sometimes use a **surrogate key** such as `enrollment_id` while retaining a `UNIQUE(student_id, course_id)` constraint.

---

# Natural Composite Key vs Surrogate Key

There are two common designs for the `Enrollments` table.

### Design 1: Composite Primary Key

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    PRIMARY KEY (student_id, course_id)
);
```

Here:

```text
(student_id, course_id)
        ↓
Primary Key
```

### Design 2: Surrogate Primary Key

```sql
CREATE TABLE Enrollments (
    enrollment_id INT PRIMARY KEY,
    student_id INT,
    course_id INT,

    UNIQUE (student_id, course_id)
);
```

Here:

```text
enrollment_id
     ↓
Primary Key

(student_id, course_id)
     ↓
Unique relationship
```

Both designs can be valid. The appropriate choice depends on the database design, application requirements, and how the relationship needs to be referenced.

# Common Mistakes

### Mistake 1: "Each column in a composite key must be unique"

Incorrect.

```text
student_id → May repeat
course_id  → May repeat
```

Only the **combination** must satisfy the key's uniqueness requirement.

---

### Mistake 2: "Composite key means composite index"

Incorrect.

```text
Composite Key
→ Data identification / integrity

Composite Index
→ Query performance
```

They are related concepts but are not the same thing.

---

### Mistake 3: "Composite key always has exactly two columns"

Incorrect.

A composite key can contain:

```text
2 columns
3 columns
4 columns
...
```

The defining characteristic is that it contains **more than one attribute**.

---

### Mistake 4: "Composite keys are only used as primary keys"

Not necessarily.

A composite key can refer to a multi-column candidate/unique key, and a database can have composite foreign keys as well.

However, in common interview discussions, "composite key" is frequently used to describe a **composite primary key**.

---

### Mistake 5: "A composite key is always better than a single-column key"

Not necessarily.

Composite keys are useful when the combination naturally identifies the record, but they can make references and queries more complex.

The choice depends on the data model.

---

# Interview Takeaway

A strong interview answer would be:

> **A composite key is a key consisting of two or more columns whose combination uniquely identifies a row in a table. The individual columns do not necessarily need to be unique. Composite keys are especially common in junction or associative tables that represent many-to-many relationships, such as a student enrollment table where `(student_id, course_id)` identifies each enrollment.**

### One-Line Definition

> **Composite Key = Multiple columns whose combination uniquely identifies a row.**
