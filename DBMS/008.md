# Q8. What are Constraints?

## Answer

**Constraints** are rules enforced by a database on **columns or tables** to maintain **data accuracy, consistency, and integrity**.

They prevent invalid or unwanted data from being stored in the database.

In simple terms:

```text
Application
     ↓
Sends Data
     ↓
Database
     ↓
Constraints Check the Data
     ↓
Valid → Store
Invalid → Reject
```

For example, if a student's age must be at least 18, the database can enforce:

```sql
CHECK (age >= 18)
```

Even if an application accidentally tries to insert:

```text
age = 15
```

the database can reject the row.

---

# Common Types of Constraints

| Constraint      | Purpose                                               | Example             |
| --------------- | ----------------------------------------------------- | ------------------- |
| **PRIMARY KEY** | Uniquely identifies each row                          | `student_id`        |
| **FOREIGN KEY** | Maintains relationships between tables                | `course_id`         |
| **NOT NULL**    | Prevents missing (`NULL`) values                      | `name`              |
| **UNIQUE**      | Prevents duplicate values according to the constraint | `email`             |
| **CHECK**       | Ensures a condition is satisfied                      | `age >= 18`         |
| **DEFAULT**     | Provides a value when none is supplied                | `status = 'Active'` |

These constraints help the database enforce important rules about the data.

---

# Example

Consider the following `Students` table:

```sql
CREATE TABLE Students (
    student_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE,
    age INT CHECK (age >= 18),
    status VARCHAR(20) DEFAULT 'Active'
);
```

Let's understand each constraint.

---

# 1. PRIMARY KEY

```sql
student_id INT PRIMARY KEY
```

A primary key uniquely identifies each row.

For example:

| student_id | name  |
| ---------: | ----- |
|        101 | Rahul |
|        102 | Priya |
|        103 | Amit  |

Here:

```text
student_id
     ↓
Unique identifier
```

The primary key cannot contain `NULL` values, and a table has one primary-key constraint, although that constraint can contain multiple columns as a **composite primary key**.

For example:

```sql
PRIMARY KEY (student_id, course_id)
```

---

# 2. NOT NULL

```sql
name VARCHAR(100) NOT NULL
```

This means the column cannot contain `NULL`.

For example, this is invalid:

```sql
INSERT INTO Students (student_id, name)
VALUES (101, NULL);
```

The database rejects the value because:

```text
name → NOT NULL
```

A `NOT NULL` constraint is useful when a value is required for every row.

---

# 3. UNIQUE

```sql
email VARCHAR(150) UNIQUE
```

A `UNIQUE` constraint prevents duplicate values according to the constraint.

For example:

```text
rahul@example.com
priya@example.com
```

are different values.

But if the database already contains:

```text
rahul@example.com
```

and another row attempts to use the same value, the database can reject it.

For example:

```sql
INSERT INTO Students
VALUES (104, 'Aman', 'rahul@example.com', 20, 'Active');
```

would violate the uniqueness requirement if that email already exists.

### Important distinction

`UNIQUE` and `PRIMARY KEY` are related but not identical.

```text
PRIMARY KEY
→ Main row identifier

UNIQUE
→ Enforces uniqueness on another column or combination
```

A table can have multiple `UNIQUE` constraints but only one primary-key constraint.

---

# 4. CHECK

```sql
age INT CHECK (age >= 18)
```

The `CHECK` constraint ensures that a specified condition is satisfied.

For example:

```sql
INSERT INTO Students
VALUES (105, 'Ravi', 'ravi@example.com', 16, 'Active');
```

The database can reject this because:

```text
age = 16
16 >= 18 → FALSE
```

Therefore:

```text
CHECK (age >= 18)
        ↓
Condition must be satisfied
```

Other examples include:

```sql
CHECK (salary >= 0)
```

```sql
CHECK (quantity > 0)
```

```sql
CHECK (marks BETWEEN 0 AND 100)
```

The exact behavior and limitations of `CHECK` expressions can vary somewhat between database systems.

---

# 5. DEFAULT

```sql
status VARCHAR(20) DEFAULT 'Active'
```

A `DEFAULT` provides a value when an insert does not supply a value for that column.

For example:

```sql
INSERT INTO Students (
    student_id,
    name,
    email,
    age
)
VALUES (
    101,
    'Rahul',
    'rahul@example.com',
    20
);
```

No `status` was supplied.

The database can therefore use:

```text
status = 'Active'
```

because of:

```sql
DEFAULT 'Active'
```

### Important point

A `DEFAULT` is not the same as `NOT NULL`.

For example:

```sql
status VARCHAR(20) DEFAULT 'Active'
```

provides a value when the column is omitted from the insert, but it does not by itself mean that the column can never contain `NULL`.

If the column must always contain a value, use:

```sql
status VARCHAR(20) NOT NULL DEFAULT 'Active'
```

---

# 6. FOREIGN KEY

A foreign key maintains a relationship between tables.

For example:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    FOREIGN KEY (student_id)
        REFERENCES Students(student_id)
);
```

Here:

```text
Enrollments.student_id
          ↓
References
          ↓
Students.student_id
```

This ensures that values in the foreign-key column satisfy the database's **referential-integrity rules**.

For example, if there is no student with:

```text
student_id = 999
```

then inserting:

```sql
INSERT INTO Enrollments (student_id, course_id)
VALUES (999, 'C01');
```

can be rejected because the referenced student does not exist.

The exact behavior for deletion or updating of referenced rows depends on the configured referential actions, such as:

```sql
ON DELETE CASCADE
ON DELETE SET NULL
ON DELETE RESTRICT
```

---

# Referential Integrity

A foreign key is closely related to **referential integrity**.

Suppose we have:

```text
Students
+------------+--------+
| student_id | name   |
+------------+--------+
| 101        | Rahul  |
| 102        | Priya  |
+------------+--------+

Enrollments
+------------+-----------+
| student_id | course_id |
+------------+-----------+
| 101        | C01       |
| 102        | C02       |
+------------+-----------+
```

The `Enrollments.student_id` values refer to students in the `Students` table.

This prevents relationships from pointing to non-existent parent rows, subject to the foreign-key rules.

---

# Multiple Constraints Can Apply to One Column

A column can have more than one constraint.

For example:

```sql
status VARCHAR(20)
    NOT NULL
    DEFAULT 'Active'
    CHECK (status IN ('Active', 'Inactive'));
```

Here `status` has three constraints:

```text
NOT NULL
   +
DEFAULT
   +
CHECK
```

This provides stronger data integrity.

---

# Composite Constraints

Constraints do not always have to apply to a single column.

For example, suppose an enrollment should not contain the same student-course combination twice:

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,

    UNIQUE (student_id, course_id)
);
```

Here the uniqueness rule applies to the **combination**:

```text
(student_id, course_id)
```

not to each column individually.

For example:

```text
101, C01 → Valid
101, C02 → Valid
102, C01 → Valid
101, C01 → Duplicate
```

This is common in many-to-many relationship tables.

---

# Named Constraints

Constraints can also be given explicit names.

For example:

```sql
CREATE TABLE Students (
    student_id INT,
    age INT,

    CONSTRAINT pk_students
        PRIMARY KEY (student_id),

    CONSTRAINT chk_student_age
        CHECK (age >= 18)
);
```

Here:

```text
pk_students
     ↓
Primary key constraint

chk_student_age
     ↓
CHECK constraint
```

Naming constraints can make database maintenance and error handling easier, especially in larger systems.

---

# Why Are Constraints Important?

Without constraints, an application could accidentally store data such as:

```text
student_id = NULL
email = same@email.com
age = -10
```

or create invalid relationships such as:

```text
Enrollment
student_id = 999
```

when student `999` does not exist.

Constraints allow the **database itself** to enforce important rules instead of relying entirely on application code.

This provides:

### 1. Data Integrity

Keeps stored data valid according to defined rules.

### 2. Data Consistency

Prevents contradictory or duplicate data where rules prohibit it.

### 3. Error Prevention

Rejects invalid data at the database level.

### 4. Referential Integrity

Ensures valid relationships between related tables.

### 5. Reliable Database Design

Makes important business and structural rules explicit.

---

# Constraints vs Validation

They are related but **not identical**.

### Application Validation

Validation can happen in application code:

```python
if age < 18:
    raise ValueError("Invalid age")
```

The application checks the value before sending it to the database.

### Database Constraint

The database can enforce the same rule:

```sql
CHECK (age >= 18)
```

The important difference is **where the rule is enforced**.

```text
Application Validation
        ↓
Application Code
        ↓
Database

Database Constraint
        ↓
Database Engine
        ↓
Stored Data
```

---

# Why Database-Level Enforcement Matters

Imagine a system where data can be inserted through:

```text
Web Application
       |
Mobile Application
       |
Admin Dashboard
       |
Background Job
       |
External Service
       |
       ↓
    Database
```

If the rule exists only in one application's code, another application might accidentally bypass it.

For example:

```text
Web App
   ↓
Checks age >= 18
   ↓
Database
```

But:

```text
Admin Tool
   ↓
Doesn't perform the check
   ↓
Database
```

A database-level constraint provides a final integrity boundary:

```text
Any Application
       ↓
    Database
       ↓
  Constraints
       ↓
Valid Data
```

Therefore:

> For important data-integrity rules, database constraints provide protection even when data comes from multiple applications or clients.

# Constraints and NULL

Understanding `NULL` is important in DBMS interviews.

`NULL` generally means **unknown, missing, or not applicable**, depending on the context.

It is not the same as:

```text
0
```

or:

```text
''
```

For example:

```sql
name VARCHAR(100) NOT NULL
```

does not allow `NULL`.

However, a nullable column may contain `NULL` unless another rule prevents it.

Also remember:

```sql
WHERE email = NULL
```

is not the correct way to test for `NULL`.

Use:

```sql
WHERE email IS NULL
```

or:

```sql
WHERE email IS NOT NULL
```

# Constraint Summary

| Constraint    | Main Purpose                                          | Example                            |
| ------------- | ----------------------------------------------------- | ---------------------------------- |
| `PRIMARY KEY` | Identifies each row uniquely                          | `student_id`                       |
| `FOREIGN KEY` | Maintains table relationships                         | `student_id → Students.student_id` |
| `NOT NULL`    | Prevents `NULL` values                                | `name`                             |
| `UNIQUE`      | Prevents duplicate values according to the constraint | `email`                            |
| `CHECK`       | Enforces a condition                                  | `age >= 18`                        |
| `DEFAULT`     | Supplies a value when one isn't provided              | `'Active'`                         |

A useful memory trick is:

```text
PRIMARY KEY → Who is this row?
FOREIGN KEY → Which row does this relate to?
NOT NULL    → Must a value exist?
UNIQUE      → Can this value repeat?
CHECK       → Is this value valid?
DEFAULT     → What value should be used if omitted?
```

# Common Mistakes

### Mistake 1: "Constraints are only application validation"

Incorrect.

Constraints can be enforced directly by the database.

```text
Application validation
        +
Database constraints
```

can work together, but database constraints provide database-level protection.

---

### Mistake 2: "UNIQUE and PRIMARY KEY are exactly the same"

Incorrect.

A primary key is the table's selected main identifier.

A table can have multiple `UNIQUE` constraints.

```text
PRIMARY KEY → Main identifier
UNIQUE      → Additional uniqueness rule
```

---

### Mistake 3: "DEFAULT means NOT NULL"

Incorrect.

```sql
status VARCHAR(20) DEFAULT 'Active'
```

does not automatically mean the column can never contain `NULL`.

If required:

```sql
status VARCHAR(20)
    NOT NULL
    DEFAULT 'Active'
```

---

### Mistake 4: "FOREIGN KEY values must always be unique"

Incorrect.

Foreign-key values commonly repeat.

For example:

```text
student_id
----------
101
101
101
102
102
```

can be perfectly valid because one student can have multiple enrollments.

---

### Mistake 5: "CHECK only works for numbers"

Incorrect.

`CHECK` can enforce many kinds of conditions supported by the database system.

For example:

```sql
CHECK (status IN ('Active', 'Inactive'))
```

---

### Mistake 6: "Constraints only apply to columns"

Not always.

Some constraints can apply to **multiple columns**, such as:

```sql
UNIQUE (student_id, course_id)
```

or:

```sql
PRIMARY KEY (student_id, course_id)
```

# Interview Takeaway

A strong interview answer would be:

> **Constraints are rules enforced by a database to ensure that stored data satisfies specific integrity, consistency, and validity requirements. Common constraints include PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, CHECK, and DEFAULT. They allow the database itself to protect important data-integrity rules rather than relying entirely on application code.**

### One-Line Definition

> **Constraints = Database-enforced rules that maintain data integrity and consistency.**

