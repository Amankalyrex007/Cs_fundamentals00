# Q9. What is Normalization?

## Answer

**Normalization** is the process of organizing data in a relational database to:

* Reduce **data redundancy**
* Avoid **data anomalies**
* Improve **data integrity**
* Make relationships between data clearer
* Improve the maintainability of the database

The basic idea is to divide large or poorly structured tables into **smaller, logically related tables** and connect them using keys.

In simple terms:

```text
Large / Repetitive Table
          ↓
   Identify dependencies
          ↓
    Split logically
          ↓
 Smaller Related Tables
          ↓
       Use Keys
          ↓
   Better Data Integrity
```

Normalization is primarily a **database design technique**. It is not simply about creating more tables.

---

# Simple Example

Suppose we store student and course information in one table:

| student_id | student_name | course_id | course_name | instructor |
| ---------: | ------------ | --------- | ----------- | ---------- |
|        101 | Rahul        | C01       | DBMS        | Sharma     |
|        102 | Priya        | C01       | DBMS        | Sharma     |
|        103 | Amit         | C02       | Python      | Verma      |

Here, information about the `DBMS` course is repeated for every student enrolled in it.

For example:

```text
C01 → DBMS → Sharma
C01 → DBMS → Sharma
```

This is **data redundancy**.

If 1,000 students are enrolled in DBMS, the same course information may be stored 1,000 times.

---

# Problems with the Unnormalized Design

Suppose we have:

```text
Students + Courses
        ↓
One Large Table
```

The table contains both:

```text
Student information
        +
Course information
```

This can create several problems:

```text
Redundancy
    ↓
Update Anomaly
Insert Anomaly
Delete Anomaly
    ↓
Data Integrity Problems
```

Normalization addresses these problems by separating data according to its logical dependencies.

---

# Normalized Design

Instead, we can separate the information into three tables.

## Students

| student_id | student_name |
| ---------: | ------------ |
|        101 | Rahul        |
|        102 | Priya        |
|        103 | Amit         |

## Courses

| course_id | course_name | instructor |
| --------- | ----------- | ---------- |
| C01       | DBMS        | Sharma     |
| C02       | Python      | Verma      |

## Enrollments

| student_id | course_id |
| ---------: | --------- |
|        101 | C01       |
|        102 | C01       |
|        103 | C02       |

Now:

```text
Students
   │
   │ student_id
   ↓
Enrollments
   ↑
   │ course_id
   │
Courses
```

The tables are connected using keys.

For example:

```text
Students.student_id
        ↓
Enrollments.student_id
```

and:

```text
Courses.course_id
        ↓
Enrollments.course_id
```

The `Enrollments` table represents the relationship between students and courses.

---

# Why Do We Normalize?

Normalization primarily helps prevent **data anomalies**.

The three classic anomalies are:

1. **Update anomaly**
2. **Insert anomaly**
3. **Delete anomaly**

Let's understand each one.

---

# 1. Update Anomaly

Suppose the instructor `Sharma` changes their name to `Dr. Sharma`.

In the original table:

| student_id | student_name | course_id | course_name | instructor |
| ---------: | ------------ | --------- | ----------- | ---------- |
|        101 | Rahul        | C01       | DBMS        | Sharma     |
|        102 | Priya        | C01       | DBMS        | Sharma     |
|        103 | Amit         | C02       | Python      | Verma      |

The instructor name is repeated.

Therefore, we may need to update:

```text
Row 1 → Sharma → Dr. Sharma
Row 2 → Sharma → Dr. Sharma
...
Row 1000 → Sharma → Dr. Sharma
```

If even one row is missed, the database becomes inconsistent.

For example:

```text
C01 → Sharma
C01 → Dr. Sharma
```

Now the same course appears to have two different instructor names.

### With normalization

The course information is stored once:

| course_id | course_name | instructor |
| --------- | ----------- | ---------- |
| C01       | DBMS        | Sharma     |
| C02       | Python      | Verma      |

Now we only update one row:

```text
C01 → Sharma → Dr. Sharma
```

This significantly reduces the chance of inconsistent duplicate data.

---

# 2. Insert Anomaly

Suppose a new course is introduced:

```text
C03 → Operating Systems
```

but no student has enrolled yet.

In the original combined table, we may not have a natural place to store the course because the table expects student information along with course information.

We might be forced to insert unnecessary or `NULL` student-related values.

This is an **insert anomaly**.

### With normalization

We can simply insert the course:

```text
Courses

C03 | Operating Systems | Kumar
```

There is no need for a student enrollment.

The relationship is stored separately in `Enrollments`.

Therefore:

```text
Course exists
      ↓
No enrollment required
```

---

# 3. Delete Anomaly

Suppose:

```text
Amit
```

is the only student enrolled in:

```text
C02 → Python
```

If we delete Amit's row from the original table:

```text
student_id = 103
```

we may accidentally lose the only stored information about:

```text
C02 → Python → Verma
```

This is a **delete anomaly**.

The student information and course information are tied together unnecessarily.

### With normalization

We have:

```text
Students
Courses
Enrollments
```

If Amit's enrollment is removed:

```text
DELETE FROM Enrollments
WHERE student_id = 103
  AND course_id = 'C02';
```

the `Python` course can still remain in the `Courses` table.

Therefore:

```text
Delete Enrollment
        ↓
Course still exists
```

This prevents the accidental loss of independent course information.

---

# Normal Forms

Normalization is commonly discussed using **normal forms**.

The commonly discussed normal forms include:

```text
1NF
 ↓
2NF
 ↓
3NF
 ↓
BCNF
```

Each level addresses particular types of dependency and redundancy problems.

For most placement and interview preparation, a strong understanding of **1NF, 2NF, 3NF, and the basic idea of BCNF** is important.

---

# 1NF — First Normal Form

A table is in **First Normal Form (1NF)** when each column contains **atomic/single values**, rather than repeating groups or lists.

In simple terms:

> **One cell should represent one value, not a list of values.**

## Bad Example

| student_id | name  | courses            |
| ---------: | ----- | ------------------ |
|        101 | Rahul | DBMS, Python, Java |

The `courses` column contains multiple values in one cell:

```text
DBMS, Python, Java
```

This makes querying and maintaining individual courses more difficult.

---

## Better Structure

We can represent each student-course relationship separately:

| student_id | name  | course |
| ---------: | ----- | ------ |
|        101 | Rahul | DBMS   |
|        101 | Rahul | Python |
|        101 | Rahul | Java   |

Now each cell contains a single value.

```text
One Cell
   ↓
One Atomic Value
```

This satisfies the basic atomic-value requirement of 1NF.

### Important Interview Point

1NF is not simply:

> "There can never be a comma in a string."

Atomicity depends on how the data is modeled and used.

For example, a person's full name being stored as one string is not automatically a 1NF violation.

The key issue is whether a single attribute value is being used to store multiple logically separate values that should be represented separately.

---

# 2NF — Second Normal Form

A table is in **2NF** when:

1. It is already in **1NF**.
2. Every non-key attribute depends on the **whole candidate key**, not just part of a composite key.

This mainly matters when a table has a **composite candidate key**.

---

# Example of Partial Dependency

Consider:

| student_id | course_id | student_name | course_name |
| ---------: | --------- | ------------ | ----------- |
|        101 | C01       | Rahul        | DBMS        |
|        101 | C02       | Rahul        | Python      |
|        102 | C01       | Priya        | DBMS        |

Suppose the candidate key is:

```text
(student_id, course_id)
```

Now look at:

```text
student_name
```

`student_name` depends only on:

```text
student_id
```

It does not depend on the complete key:

```text
(student_id, course_id)
```

This is called a **partial dependency**.

Similarly:

```text
course_name
```

depends only on:

```text
course_id
```

Therefore, the table contains dependencies on only part of the composite key.

---

# Removing Partial Dependency

We can separate the data:

### Students

| student_id | student_name |
| ---------: | ------------ |
|        101 | Rahul        |
|        102 | Priya        |

### Courses

| course_id | course_name |
| --------- | ----------- |
| C01       | DBMS        |
| C02       | Python      |

### Enrollments

| student_id | course_id |
| ---------: | --------- |
|        101 | C01       |
|        101 | C02       |
|        102 | C01       |

Now:

```text
student_name
     ↓
student_id

course_name
     ↓
course_id
```

and:

```text
student_id + course_id
        ↓
Enrollment
```

This removes the partial dependencies.

---

# Easy Way to Remember 2NF

For a composite key:

```text
(student_id, course_id)
```

every non-key attribute should depend on:

```text
student_id + course_id
```

not only:

```text
student_id
```

or only:

```text
course_id
```

Therefore:

```text
2NF
 ↓
No partial dependency
```

### Important Nuance

If a table has a **single-column candidate key**, partial dependency on part of that key cannot occur.

Therefore, once a table is in 1NF, it is effectively in 2NF with respect to a single-attribute candidate key.

---

# 3NF — Third Normal Form

A table is in **3NF** when:

1. It is already in **2NF**.
2. Non-key attributes do not depend on other non-key attributes in a way that creates a **transitive dependency**.

A common simplified interview definition is:

> **Non-key attributes should depend on the key, the whole key, and nothing but the key.**

The phrase is useful for interviews, but the formal definition of 3NF is expressed in terms of functional dependencies and candidate keys.

---

# Example of Transitive Dependency

Suppose we have:

| student_id | student_name | department_id | department_name  |
| ---------: | ------------ | ------------- | ---------------- |
|        101 | Rahul        | D01           | Computer Science |
|        102 | Priya        | D01           | Computer Science |
|        103 | Amit         | D02           | Mathematics      |

We can describe the dependencies as:

```text
student_id
    ↓
department_id
    ↓
department_name
```

That means:

```text
student_id → department_id
department_id → department_name
```

Therefore:

```text
student_id → department_name
```

indirectly.

This is a **transitive dependency**.

The department name does not directly describe the student. It describes the department.

---

# Removing the Transitive Dependency

We can separate the department information.

### Students

| student_id | student_name | department_id |
| ---------: | ------------ | ------------- |
|        101 | Rahul        | D01           |
|        102 | Priya        | D01           |
|        103 | Amit         | D02           |

### Departments

| department_id | department_name  |
| ------------- | ---------------- |
| D01           | Computer Science |
| D02           | Mathematics      |

Now:

```text
Students
   |
   | department_id
   ↓
Departments
```

The department name is stored in the appropriate table.

Therefore:

```text
Students
→ Student information

Departments
→ Department information
```

This reduces redundancy and helps prevent update anomalies.

---

# Easy Way to Remember 3NF

```text
Student
   ↓
Department ID
   ↓
Department Name
```

The goal is to avoid storing:

```text
Department Name
```

in the `Students` table when it is really determined by:

```text
Department ID
```

So:

```text
3NF
 ↓
No problematic transitive dependency
```

---

# BCNF

**BCNF** stands for:

> **Boyce-Codd Normal Form**

BCNF is a **stronger form of 3NF**.

It handles certain functional-dependency situations that can satisfy 3NF but still allow redundancy or anomalies.

The formal idea is:

> For every non-trivial functional dependency `X → Y`, `X` should be a super key.

In simplified interview language:

```text
BCNF
 ↓
Every determinant must be a candidate key
```

You generally do not need to solve complex BCNF decomposition problems unless the interview specifically focuses on advanced database theory.

For most placement interviews:

```text
1NF → Atomic values
2NF → No partial dependency
3NF → No problematic transitive dependency
BCNF → Stronger version of 3NF
```

is an important foundation.

---

# Functional Dependency and Normalization

Understanding **functional dependency** makes normalization easier.

Suppose:

```text
student_id → student_name
```

This means:

> If we know `student_id`, we can determine the corresponding `student_name`.

Similarly:

```text
course_id → course_name
```

means:

> If we know `course_id`, we can determine the corresponding `course_name`.

For the enrollment relationship:

```text
(student_id, course_id) → enrollment information
```

The dependencies help us determine how tables should be structured.

---

# Normalization Example from Start to Finish

Suppose we initially have:

| student_id | student_name | course_id | course_name | instructor |
| ---------: | ------------ | --------- | ----------- | ---------- |
|        101 | Rahul        | C01       | DBMS        | Sharma     |
|        101 | Rahul        | C02       | Python      | Verma      |
|        102 | Priya        | C01       | DBMS        | Sharma     |

There is repeated information.

We can identify dependencies:

```text
student_id → student_name

course_id → course_name, instructor

(student_id, course_id)
        ↓
Enrollment relationship
```

Therefore, we can create:

### Students

```text
student_id → student_name
```

### Courses

```text
course_id → course_name, instructor
```

### Enrollments

```text
(student_id, course_id)
```

The final design becomes:

```text
             Students
                 |
                 | student_id
                 ↓
          +--------------+
          | Enrollments  |
          +--------------+
                 ↑
                 | course_id
                 |
              Courses
```

This is the core idea behind normalization.

---

# Normalization vs Denormalization

Normalization and denormalization are different database design strategies.

| Normalization                                   | Denormalization                                         |
| ----------------------------------------------- | ------------------------------------------------------- |
| Reduces redundancy                              | Intentionally introduces some redundancy                |
| Improves data integrity                         | Can improve read performance in some workloads          |
| Usually creates more logically separated tables | May combine or duplicate data                           |
| May require more joins                          | Can reduce joins                                        |
| Common in transactional systems                 | Often considered for read-heavy or analytical workloads |

---

# What Is Denormalization?

**Denormalization** is the deliberate introduction of some redundancy into a database to satisfy performance, reporting, or application requirements.

For example, instead of repeatedly joining:

```text
Orders
   +
Customers
```

a system might intentionally store:

```text
order_id
customer_id
customer_name
order_amount
```

in a read-optimized structure.

This may make some queries faster or simpler, but it introduces duplicated data.

Therefore:

```text
Denormalization
      ↓
More redundancy
      +
Potentially fewer joins
      ↓
Potential performance benefits
      +
More consistency-management responsibility
```

Denormalization should generally be a **deliberate design decision**, not the default solution to every performance problem.

---

# Normalization Is Not "More Is Always Better"

An important real-world point is:

> **Normalization is not about making the database "as normalized as possible" in every situation.**

Highly normalized schemas can require more joins.

For example:

```text
Orders
   ↓
Customers
   ↓
Addresses
   ↓
Countries
```

A reporting query may need several joins.

Depending on workload, data volume, latency requirements, and architecture, a system may deliberately denormalize selected data.

Therefore, real database design involves balancing:

```text
Data Integrity
       +
Redundancy
       +
Query Performance
       +
Maintainability
```

---

# Normalization in OLTP vs Analytical Systems

Normalization is particularly common in **OLTP (Online Transaction Processing)** systems where correctness, consistency, and frequent inserts/updates are important.

For example:

```text
Banking
E-commerce transactions
Student management
Order processing
```

Analytical systems may use more denormalized structures because large read-heavy queries can benefit from fewer joins.

For example:

```text
Data Warehouses
Reporting Systems
Business Intelligence
Analytics
```

However, this is a general tendency, not an absolute rule.

---

# Advantages of Normalization

### 1. Reduces Data Redundancy

Repeated information is stored in fewer places.

### 2. Prevents Update Anomalies

Changes can be made in the appropriate location.

### 3. Prevents Insert Anomalies

Independent entities can be inserted without requiring unrelated data.

### 4. Prevents Delete Anomalies

Deleting one relationship does not necessarily delete unrelated information.

### 5. Improves Data Integrity

Data is organized according to logical relationships and dependencies.

### 6. Improves Maintainability

Changes to an entity's information are easier to manage.

### 7. Makes Relationships Explicit

Keys clearly represent relationships between entities.

---

# Potential Disadvantages

Normalization also has trade-offs.

### 1. More Tables

A normalized database may contain many related tables.

### 2. More JOINs

Retrieving complete information may require multiple joins.

For example:

```sql
SELECT
    s.student_name,
    c.course_name
FROM Students s
JOIN Enrollments e
    ON s.student_id = e.student_id
JOIN Courses c
    ON e.course_id = c.course_id;
```

### 3. Query Complexity

Some reporting queries can become more complex.

### 4. Performance Trade-offs

In certain workloads, repeated joins can become expensive, which may motivate carefully chosen denormalization or other optimization techniques.

---

# Normal Forms — Quick Comparison

| Normal Form | Main Idea                                                        |
| ----------- | ---------------------------------------------------------------- |
| **1NF**     | Atomic values; no repeating groups/lists in a single attribute   |
| **2NF**     | 1NF + no partial dependency on part of a composite candidate key |
| **3NF**     | 2NF + no problematic transitive dependency of non-key attributes |
| **BCNF**    | Stronger dependency rule; every determinant must be a super key  |

A useful memory trick:

```text
1NF → Atomic
2NF → Whole Key
3NF → Nothing But Key
BCNF → Every Determinant Is a Candidate-Key-Level Identifier
```

# Common Interview Example

Suppose you have:

```text
StudentCourse
------------------------------------------------
student_id
student_name
course_id
course_name
instructor
```

and the candidate key is:

```text
(student_id, course_id)
```

Then:

```text
student_id → student_name
course_id  → course_name, instructor
```

There are partial dependencies because:

```text
student_name
     ↓
student_id only

course_name
     ↓
course_id only
```

So the table should be decomposed into:

```text
Students
--------
student_id
student_name

Courses
-------
course_id
course_name
instructor

Enrollments
-----------
student_id
course_id
```

This is the classic normalization pattern for a student-course many-to-many relationship.

# Common Mistakes

### Mistake 1: "Normalization means splitting every table"

Incorrect.

The goal is not to create as many tables as possible.

The goal is to organize data based on **dependencies and relationships** while reducing unnecessary redundancy and anomalies.

---

### Mistake 2: "Normalization always improves performance"

Not necessarily.

Normalization can improve consistency and reduce redundancy, but it can also require more joins.

Performance depends on workload, indexes, query patterns, data volume, and database design.

---

### Mistake 3: "1NF means there can never be multiple words in a column"

Incorrect.

1NF is about representing an attribute as an atomic value according to the database's data model.

A string such as:

```text
Rahul Sharma
```

can still be one atomic name value.

The problem is storing multiple logically separate values in one attribute when they should be represented separately.

---

### Mistake 4: "2NF applies only to every table"

The important issue is **partial dependency on part of a composite candidate key**.

If the relevant candidate key contains only one attribute, there is no smaller subset of that key to create a partial dependency.

---

### Mistake 5: "3NF means there can be no relationships between tables"

Incorrect.

3NF is about **functional dependencies within the schema**, not about eliminating relationships.

Foreign keys and relationships are fundamental to normalized relational designs.

---

### Mistake 6: "Normalization eliminates all redundancy"

Not necessarily.

Normalization aims to reduce **unnecessary redundancy caused by poor dependency structure**.

Some controlled redundancy can exist, and real systems may deliberately denormalize.

---

### Mistake 7: "Denormalization is bad database design"

Not necessarily.

Denormalization can be a deliberate optimization when its trade-offs are understood and consistency is managed appropriately.

---

# Interview Takeaway

A strong interview answer would be:

> **Normalization is the process of organizing relational data into well-structured tables to reduce unnecessary data redundancy and prevent insertion, update, and deletion anomalies while maintaining data integrity. It involves decomposing tables based on dependencies and connecting the resulting tables using keys. The commonly discussed normal forms are 1NF, 2NF, 3NF, and BCNF.**

### One-Line Definition

> **Normalization = Organizing relational data to reduce redundancy and prevent data anomalies while maintaining integrity.**

