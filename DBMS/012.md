12.When might denormalization be useful?
Denormalization is the deliberate introduction of some redundancy into a database to improve read/query performance, usually after normalization has already been considered.

Why use denormalization?

Normalization reduces redundancy and improves data integrity, but it can sometimes require many joins to retrieve information. Denormalization can reduce those joins and make frequent queries faster or simpler.

Common situations where denormalization is useful
Read-heavy applications
When data is read much more frequently than it is updated.
Example: product catalogs, dashboards, reporting systems.
Reducing expensive joins
If a query repeatedly joins several large tables, storing some related data together can reduce query complexity and potentially improve latency.
Analytics and reporting
Data warehouses often use denormalized structures such as star schemas to make analytical queries efficient.
Caching frequently accessed data
Frequently needed derived or related values can be stored directly.

Example:

Orders
--------------------------------
order_id | customer_id | customer_name

Instead of joining Orders with Customers every time to display the customer's name.

Precomputing expensive calculations
A frequently requested aggregate can be stored rather than calculated repeatedly.

Example:

product_id | review_count | average_rating

instead of calculating these values from all reviews for every request.

Trade-off

The main trade-off is:

Normalization	Denormalization
Less redundant data	More redundant data
Better consistency	More synchronization responsibility
More joins may be required	Fewer joins
Usually easier updates	Potentially faster reads
Good for transactional workloads	Useful for read-heavy/analytical workloads
Important interview point

Denormalization does not mean normalization is bad. A common approach is:

Normalize first for data integrity, then selectively denormalize when measured performance or workload requirements justify it.

The cost is that duplicated data must remain consistent when the original data changes.

Example: In an e-commerce system, storing customer_name directly in an order/reporting table can avoid repeated joins for a read-heavy dashboard, but the system must decide how that copied value is maintained.

Interview takeaway:
Denormalization is useful when reducing joins or precomputing frequently accessed data can improve performance, especially in read-heavy and analytical workloads, while accepting the additional storage and consistency complexity.
