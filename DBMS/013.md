# Q13. What Is a Transaction?

## Answer

A **transaction** is a sequence of one or more database operations that are treated as **one logical unit of work**.

The key idea is:

> **A transaction should either complete successfully as a whole, or its changes should be rolled back so the database does not remain in an inconsistent state.**

---

# Example: Bank Transfer

Suppose we transfer **₹1,000** from Account A to Account B.

Two operations are required:

```text
1. Deduct ₹1,000 from Account A
2. Add ₹1,000 to Account B
```

Both operations should belong to the **same transaction**.

Before:

```text
A = ₹10,000
B = ₹5,000
```

Transaction:

```text
A = A - ₹1,000
B = B + ₹1,000
```

After successful completion:

```text
A = ₹9,000
B = ₹6,000
```

But suppose step 1 succeeds and step 2 fails:

```text
A = ₹9,000
B = ₹5,000   ❌
```

This would be incorrect because ₹1,000 has effectively disappeared.

The transaction should therefore perform:

```text
ROLLBACK
   ↓
Return to previous state
```

Result:

```text
A = ₹10,000
B = ₹5,000
```

This is the core purpose of transactions.

---

# ACID Properties

Transactions are commonly explained using **ACID**:

| Property        | Meaning                                                                 |
| --------------- | ----------------------------------------------------------------------- |
| **Atomicity**   | All operations succeed, or none are applied                             |
| **Consistency** | The transaction preserves database rules and constraints                |
| **Isolation**   | Concurrent transactions should not improperly interfere with each other |
| **Durability**  | Once committed, changes survive failures such as a crash                |

### Easy Memory Trick

```text
A → Atomicity   → All or Nothing
C → Consistency → Valid State
I → Isolation   → Transactions don't improperly interfere
D → Durability  → Committed data survives failures
```

# COMMIT vs ROLLBACK

A transaction can be controlled using commands such as:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE account_id = 2;

COMMIT;
```

### COMMIT

```text
COMMIT
   ↓
Confirm transaction
   ↓
Save its changes
```

After a successful commit, the transaction's changes are considered committed and are expected to survive normal system failures according to the database's durability mechanisms.

### ROLLBACK

```text
ROLLBACK
   ↓
Undo uncommitted changes
   ↓
Return to previous transaction state
```

If something goes wrong before the transaction is committed, the application can roll back the transaction.

---

# Why Are Transactions Important?

Transactions are especially important when **partial updates would be incorrect**.

Common examples include:

* **Bank transfers**
* **Order creation and payment processing**
* **Inventory updates**
* **Ticket/seat booking**
* **Updating multiple related tables**

For example, creating an order might involve:

```text
Create Order
     ↓
Add Order Items
     ↓
Reduce Inventory
     ↓
Record Payment
```

If one critical operation fails, the application may need to roll back the appropriate changes rather than leaving a partially completed operation.

# Transaction Flow

```text
        BEGIN
          ↓
    Database Operations
          ↓
      ┌───┴───┐
      ↓       ↓
   Success   Failure
      ↓       ↓
   COMMIT   ROLLBACK
      ↓       ↓
   Changes   Undo
   Saved    Changes
```

# Important Interview Point

A transaction is **not necessarily only one SQL statement**.

It can contain multiple related operations that must be treated as one logical unit.

For example:

```text
Transaction
   ├── UPDATE Account A
   ├── UPDATE Account B
   └── COMMIT
```

The purpose is to maintain reliable database behavior when multiple operations belong to the same logical task.

---

# Common Mistakes

### Mistake 1: "A transaction means one SQL query"

Incorrect.

A transaction can contain multiple SQL statements.

### Mistake 2: "COMMIT and ROLLBACK are the same"

Incorrect.

```text
COMMIT   → Confirm/save transaction changes
ROLLBACK → Undo uncommitted transaction changes
```

### Mistake 3: "Transactions are only useful for banking"

Incorrect.

They are useful whenever multiple operations must behave reliably as one logical unit.

### Mistake 4: "Atomicity means the database is always correct"

Not exactly.

Atomicity means the transaction's operations are treated as an **all-or-nothing unit**. Consistency refers to preserving defined database rules and constraints.

---

# Interview Takeaway

A strong interview answer would be:

> **A transaction is a logical unit of database work whose operations are handled together. If the transaction succeeds, its changes are committed; if it fails, its uncommitted changes can be rolled back. Transactions provide reliable behavior through the ACID properties: Atomicity, Consistency, Isolation, and Durability.**

### One-Line Definition

> **Transaction = A logical unit of database operations that succeeds as a whole or can be rolled back to avoid an incorrect partial state.**
