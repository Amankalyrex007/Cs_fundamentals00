14.Explain ACID properties.
ACID is a set of properties that makes database transactions reliable and predictable, especially when multiple operations must be treated as one unit.

ACID stands for:

A — Atomicity
C — Consistency
I — Isolation
D — Durability

1. Atomicity

Atomicity means a transaction is all-or-nothing.

Either all operations in the transaction succeed, or none of them are applied.

Example: Bank transfer

A → deduct ₹1,000
B → add ₹1,000

If adding ₹1,000 to B fails after deducting it from A, the deduction from A is rolled back.

COMMIT   → save all changes
ROLLBACK → undo the transaction

Why? Prevents partial transactions.

2. Consistency

Consistency means a transaction takes the database from one valid state to another valid state, while respecting defined rules, constraints, and relationships.

For example, suppose:

Account balance >= 0

is a database/business constraint.

A transaction should not leave the database violating that rule.

Consistency can involve:

Primary-key constraints
Foreign-key constraints
NOT NULL
UNIQUE
CHECK constraints
Application/business rules

Why? Prevents invalid database states.

3. Isolation

Isolation means concurrent transactions should not improperly interfere with each other.

Imagine two users trying to modify the same account at nearly the same time. The database uses transaction isolation mechanisms to control what one transaction can see from another and how concurrent changes interact.

Without proper isolation, problems such as these can occur:

Dirty read — reading uncommitted data
Non-repeatable read — reading the same row twice and getting different committed values
Phantom read — repeating a query and seeing a different set of rows

Databases provide different isolation levels that trade off consistency/isolation against concurrency and performance.

Why? Makes concurrent transactions behave predictably.

4. Durability

Durability means that once a transaction is successfully committed, its changes should survive subsequent failures, such as a database/server crash.

For example:

COMMIT
   ↓
Server crashes
   ↓
Database restarts
   ↓
Committed changes are still present

Databases typically achieve this through mechanisms such as transaction logs and recovery procedures.

Why? Prevents committed data from being lost after a failure.

Quick comparison
Property	Core idea	Prevents
Atomicity	All or nothing	Partial transactions
Consistency	Valid state → valid state	Invalid database states
Isolation	Concurrent transactions don't improperly interfere	Concurrency anomalies
Durability	Committed changes survive failures	Loss of committed data
Easy way to remember

Think of a bank transfer:

Atomicity: Both debit and credit happen, or neither happens.
Consistency: Account/database rules remain valid.
Isolation: Simultaneous transfers don't incorrectly interfere.
Durability: After successful commit, the transfer isn't lost after a crash.

Interview takeaway

ACID properties ensure that database transactions are reliable: Atomicity provides all-or-nothing execution, Consistency preserves valid states, Isolation controls concurrent transaction interactions, and Durability ensures committed changes survive failures.
