15.What are transaction isolation levels?
Transaction isolation levels define how much one transaction is isolated from the changes made by other concurrent transactions.

They control the trade-off between:

Data consistency
Concurrency
Performance

The standard SQL isolation levels are:

Isolation level	Dirty read	Non-repeatable read	Phantom read
Read Uncommitted	Possible	Possible	Possible
Read Committed	Prevented	Possible	Possible
Repeatable Read	Prevented	Prevented	DBMS-dependent / traditionally possible
Serializable	Prevented	Prevented	Prevented
1. Read Uncommitted

The transaction may read data that another transaction has not committed yet.

Example:

Transaction A:
balance = ₹5,000 → changes it to ₹4,000
                     ↓
Transaction B reads ₹4,000
                     ↓
Transaction A rolls back

Transaction B read a value that never became permanent. This is called a dirty read.

Advantage: High concurrency and potentially good performance.
Disadvantage: Very weak isolation.

2. Read Committed

A transaction can only read committed data.

Therefore, dirty reads are prevented.

However, another transaction can commit a change between two reads:

Transaction A reads: ₹5,000

Transaction B changes: ₹5,000 → ₹4,000 and commits

Transaction A reads again: ₹4,000

The same query/row can produce different results within the same transaction. This is a non-repeatable read.

Advantage: Common practical default in many relational databases.
Trade-off: Some concurrency anomalies can still occur.

3. Repeatable Read

Once a transaction reads a row, repeated reads of that row should return a consistent result within the transaction.

It prevents:

Dirty reads
Non-repeatable reads

However, the exact behavior around phantom reads depends on the database's implementation. Modern databases may use MVCC or other mechanisms that provide stronger behavior than the basic SQL definition suggests.

A phantom read occurs when repeating a query returns a different set of rows because another transaction inserted or deleted matching rows.

4. Serializable

Serializable provides the strongest standard isolation level.

The goal is that concurrent transactions produce results equivalent to some serial execution of those transactions.

Conceptually:

Transaction A
      ↓
Transaction B

rather than allowing problematic interleavings.

It prevents:

Dirty reads
Non-repeatable reads
Phantom reads

Trade-off: Stronger isolation can reduce concurrency and increase waiting, contention, or retries depending on the database implementation.

Isolation vs performance

A useful way to think about the levels is:

Read Uncommitted
       ↓
Read Committed
       ↓
Repeatable Read
       ↓
Serializable

As isolation generally becomes stronger, the database imposes more restrictions on concurrent operations, which can increase contention or reduce concurrency.

But don't say "Serializable is always slow"—actual performance depends on the database engine, workload, indexes, transaction duration, and implementation.

Interview takeaway

Transaction isolation levels define how concurrent transactions interact and what changes one transaction can observe from others. The standard levels are Read Uncommitted, Read Committed, Repeatable Read, and Serializable, with different trade-offs between consistency and concurrency.
