# Q15. What are Transaction Isolation Levels?

**Transaction isolation levels** define how much one transaction is isolated from changes made by other **concurrent transactions**.

They control the trade-off between:

* **Data consistency**
* **Concurrency**
* **Performance**

The SQL standard defines four main isolation levels:

| Isolation Level      | Dirty Read | Non-Repeatable Read | Phantom Read                            |
| -------------------- | ---------- | ------------------- | --------------------------------------- |
| **Read Uncommitted** | Possible   | Possible            | Possible                                |
| **Read Committed**   | Prevented  | Possible            | Possible                                |
| **Repeatable Read**  | Prevented  | Prevented           | DBMS-dependent / traditionally possible |
| **Serializable**     | Prevented  | Prevented           | Prevented                               |

> **Important:** Exact behavior can vary by database engine and implementation, especially for `REPEATABLE READ`.

---

## 1. Read Uncommitted

**Read Uncommitted** is the weakest standard isolation level.

A transaction may read data that another transaction has **not committed yet**.

### Example

Suppose an account has ₹5,000.

```text
Transaction A:
₹5,000 → ₹4,000
       ↓
Transaction B reads ₹4,000
       ↓
Transaction A ROLLBACK
       ↓
Actual balance = ₹5,000
```

Transaction B read a value that was later rolled back.

This is called a **Dirty Read**.

### Advantages

* High concurrency
* Potentially good performance
* Less waiting between transactions

### Disadvantage

* Very weak isolation
* Transaction may observe temporary/uncommitted data

---

## 2. Read Committed

In **Read Committed**, a transaction can read only **committed data**.

Therefore:

> **Dirty reads are prevented.**

### Example

```text
Transaction A reads: ₹5,000

Transaction B:
₹5,000 → ₹4,000
COMMIT

Transaction A reads again: ₹4,000
```

Transaction A sees different values for the same row during its transaction.

This is called a **Non-Repeatable Read**.

### Advantages

* Prevents dirty reads
* Good balance between consistency and concurrency
* Common practical default in many relational databases

### Trade-off

Other transactions can still commit changes while the current transaction is running.

Therefore:

```text
Dirty Read       → Prevented
Non-Repeatable   → Possible
Phantom Read     → Possible
```

---

## 3. Repeatable Read

**Repeatable Read** provides stronger isolation.

Once a transaction reads a row, repeated reads of that row should return a **consistent result** within that transaction.

It prevents:

* **Dirty Reads**
* **Non-Repeatable Reads**

### Example

```text
Transaction A reads:
Account balance = ₹5,000

Transaction B:
Changes balance → ₹4,000
COMMIT

Transaction A reads the same row again
→ Its view of that row remains consistent
```

The exact behavior depends on the database engine and its implementation.

Modern databases may use **MVCC (Multi-Version Concurrency Control)** or other mechanisms that provide behavior stronger than the simplified SQL definition.

### What about Phantom Reads?

A **phantom read** occurs when repeating a query returns a different **set of rows** because another transaction inserted, deleted, or otherwise changed rows matching the query.

For example:

```sql
SELECT * FROM Orders
WHERE amount > 10000;
```

First execution:

```text
101
102
```

Another transaction inserts order `103` with amount `15000`.

Second execution:

```text
101
102
103
```

The newly appearing row is a **phantom row**.

Whether `REPEATABLE READ` prevents this depends on the database implementation.

---

## 4. Serializable

**Serializable** is the strongest standard isolation level.

Its goal is to make concurrent transactions produce results equivalent to **some serial execution** of those transactions.

Conceptually:

```text
Transaction A
      ↓
Transaction B
```

rather than allowing problematic concurrent interleavings.

It prevents:

* **Dirty Reads**
* **Non-Repeatable Reads**
* **Phantom Reads**

### Example

Suppose two transactions simultaneously try to modify the same limited inventory.

A serializable implementation ensures the final result behaves as if the transactions had been processed in a valid serial order.

### Trade-off

Stronger isolation can result in:

* More waiting
* Higher contention
* Reduced concurrency
* Transaction retries or serialization failures, depending on the DBMS

So, **Serializable is not automatically "slow."** Actual performance depends on:

* Database engine
* Workload
* Indexes
* Transaction duration
* Locking/MVCC implementation
* Number of concurrent transactions

# Isolation Levels at a Glance

```text
                 Stronger Isolation
                       ↑
Read Uncommitted
       ↓
Read Committed
       ↓
Repeatable Read
       ↓
Serializable
```

Generally, as isolation becomes stronger, the database places more restrictions on concurrent operations.

This can improve consistency but may increase contention or reduce concurrency.

---

# Common Concurrency Problems

| Problem                 | Meaning                                                        |
| ----------------------- | -------------------------------------------------------------- |
| **Dirty Read**          | Reading data that another transaction has not committed        |
| **Non-Repeatable Read** | Reading the same row twice and getting different values        |
| **Phantom Read**        | Repeating a query and getting a different set of matching rows |

### Easy Example

```text
Dirty Read
→ "I read your uncommitted change."

Non-Repeatable Read
→ "I read the same row twice, but its value changed."

Phantom Read
→ "I ran the same query twice, but new matching rows appeared/disappeared."
```

# Isolation Level Comparison

| Level                | Dirty Read  | Non-Repeatable Read | Phantom Read   | General Trade-off            |
| -------------------- | ----------- | ------------------- | -------------- | ---------------------------- |
| **Read Uncommitted** | ✅ Possible  | ✅ Possible          | ✅ Possible     | Highest concurrency          |
| **Read Committed**   | ❌ Prevented | ✅ Possible          | ✅ Possible     | Balanced                     |
| **Repeatable Read**  | ❌ Prevented | ❌ Prevented         | DBMS-dependent | Stronger consistency         |
| **Serializable**     | ❌ Prevented | ❌ Prevented         | ❌ Prevented    | Strongest standard isolation |

> **Interview nuance:** Avoid memorizing the table as an absolute statement for every database. Real DBMS implementations can differ, especially in how `REPEATABLE READ` handles phantoms and how MVCC/locking is implemented.

# Isolation vs Performance

A useful mental model is:

```text
Read Uncommitted
       ↓
Read Committed
       ↓
Repeatable Read
       ↓
Serializable
```

As isolation generally becomes stronger:

```text
Consistency ↑
Concurrency ↓ / may decrease
Contention  ↑ / may increase
```

But this is a **general trade-off**, not a guarantee that every stronger level will always perform worse.

For example, a well-indexed workload using an efficient MVCC implementation may behave differently from a heavily locked workload.

# Real-World Example: Ticket Booking

Suppose only **one seat** is available.

Two users try to book it simultaneously.

```text
User A → Book Seat A1
User B → Book Seat A1
```

If concurrent transactions are not properly isolated, both transactions might incorrectly observe the seat as available.

A suitable isolation strategy helps the database coordinate these operations so that the final result remains consistent.

This is why transaction isolation matters in:

* Banking
* Ticket booking
* Inventory management
* E-commerce orders
* Seat reservations
* Payment systems

# Important Interview Point

Isolation levels do **not** mean that transactions simply run one after another.

Instead, they define **what effects concurrent transactions can observe from one another**.

The four standard levels are:

```text
Read Uncommitted
Read Committed
Repeatable Read
Serializable
```

The key idea is:

> **Higher isolation generally provides stronger guarantees about concurrent data visibility, but may reduce concurrency or increase contention.**

# Common Mistakes

### ❌ Mistake 1: "Read Committed prevents all concurrency problems."

No.

It prevents **dirty reads**, but non-repeatable and phantom reads can still occur.

### ❌ Mistake 2: "Repeatable Read always prevents phantom reads."

Not necessarily.

Its exact behavior depends on the database implementation.

### ❌ Mistake 3: "Serializable means transactions literally execute one at a time."

Not necessarily.

It means their outcome should be equivalent to some **serial execution**.

### ❌ Mistake 4: "Serializable is always slow."

Incorrect.

Performance depends on the DBMS, workload, indexes, transaction duration, concurrency, and implementation.

### ❌ Mistake 5: "Isolation is the same as atomicity."

They are different ACID properties.

* **Atomicity** → transaction succeeds completely or rolls back.
* **Isolation** → concurrent transactions should not improperly interfere with one another.

---

# Interview Takeaway

> **Transaction isolation levels define how concurrent transactions interact and what changes one transaction can observe from other transactions. The standard levels are Read Uncommitted, Read Committed, Repeatable Read, and Serializable, providing progressively stronger isolation with different trade-offs between consistency, concurrency, and performance.**

### One-Line Definition

> **Isolation levels control the visibility and interaction of concurrent transactions in a database.**
