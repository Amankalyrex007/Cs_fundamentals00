# Q16. What are Dirty Reads, Non-Repeatable Reads, and Phantom Reads?

**Dirty reads, non-repeatable reads, and phantom reads** are **concurrency anomalies** that can occur when multiple transactions execute at the same time.

They describe different ways in which one transaction can observe changes made by another concurrent transaction.

---

## 1. Dirty Read

A **dirty read** occurs when one transaction reads data that another transaction has changed but **not yet committed**.

### Example

Suppose an account initially has ₹5,000.

```text
Transaction A:
Balance = ₹5,000
UPDATE → ₹4,000
         ↓
      Not committed

Transaction B:
Reads balance → ₹4,000

Transaction A:
ROLLBACK

Actual balance → ₹5,000
```

Transaction B read ₹4,000 even though that value was never committed.

Therefore:

> **Dirty read = reading uncommitted data.**

### Problem

Transaction B may make decisions based on data that can later disappear because Transaction A may **ROLLBACK**.

### Prevented By

* `READ COMMITTED`
* `REPEATABLE READ`
* `SERIALIZABLE`

---

## 2. Non-Repeatable Read

A **non-repeatable read** occurs when a transaction reads the **same row twice** but gets different values because another transaction modified and committed that row between the two reads.

### Example

```text
Transaction A:
Reads balance → ₹5,000

Transaction B:
Changes balance → ₹4,000
COMMIT

Transaction A:
Reads balance again → ₹4,000
```

Transaction A read the same row twice but obtained different values.

Therefore:

> **Non-repeatable read = same row, different value.**

### Problem

The row's committed value changed while Transaction A was still executing.

### Prevented By

* `REPEATABLE READ`
* `SERIALIZABLE`

> Exact behavior can depend on the database engine and its isolation implementation.

---

## 3. Phantom Read

A **phantom read** occurs when a transaction executes the **same query twice** but gets a different **set of rows** because another transaction inserted, deleted, or otherwise changed rows matching the query between the two executions.

### Example

Transaction A executes:

```sql
SELECT *
FROM employees
WHERE salary > 50000;
```

Result:

```text
10 employees
```

Meanwhile, Transaction B inserts another employee:

```text
salary = ₹60,000
```

and commits.

Transaction A executes the same query again:

```sql
SELECT *
FROM employees
WHERE salary > 50000;
```

Now the result contains:

```text
11 employees
```

The additional row is a **phantom row**.

Therefore:

> **Phantom read = same query, different set of matching rows.**

### Problem

The result set changed between two executions of the same query.

### Prevented By

* `SERIALIZABLE`
* `REPEATABLE READ` behavior can depend on the database implementation.

---

# Dirty vs Non-Repeatable vs Phantom

| Anomaly                 | What Changes?                | Simple Example                                      |
| ----------------------- | ---------------------------- | --------------------------------------------------- |
| **Dirty Read**          | Uncommitted value is read    | A changes → B reads → A rolls back                  |
| **Non-Repeatable Read** | Same row's value changes     | A reads ₹5k → B commits ₹4k → A reads ₹4k           |
| **Phantom Read**        | Set of matching rows changes | A gets 10 rows → B inserts matching row → A gets 11 |

# Visual Comparison

```text
Dirty Read
──────────
A: UPDATE → ₹4,000 (uncommitted)
B: READ   → ₹4,000
A: ROLLBACK
             ↓
       B read temporary data


Non-Repeatable Read
───────────────────
A: READ → ₹5,000
B: UPDATE → ₹4,000
B: COMMIT
A: READ → ₹4,000
             ↓
       Same row, different value


Phantom Read
────────────
A: SELECT → 10 rows
B: INSERT matching row
B: COMMIT
A: SELECT → 11 rows
             ↓
       Different result set
```

  ↓

Phantom
  ↓

> **Non-repeatable → same row, different value**

# Real-World Example

Consider an e-commerce system.

### Dirty Read

An order's payment status temporarily changes to:

```text
PAID
```

but the transaction later rolls back.

Another transaction that read `PAID` before the rollback performed a **dirty read**.

### Non-Repeatable Read

A transaction reads:

```text
Stock = 20
```

Another transaction sells some items and commits:

```text
Stock = 15
```

The first transaction reads the same product again and gets `15`.

That is a **non-repeatable read**.

### Phantom Read

A transaction searches:

```sql
SELECT *
FROM Products
WHERE price < 1000;
```

It initially finds 50 products.

Another transaction inserts a new product priced at ₹800 and commits.

The first transaction runs the same query again and finds 51 products.

That is a **phantom read**.

# Relationship with Isolation Levels

These anomalies are closely related to transaction isolation levels:

| Isolation Level      | Dirty Read | Non-Repeatable Read | Phantom Read   |
| -------------------- | ---------- | ------------------- | -------------- |
| **Read Uncommitted** | Possible   | Possible            | Possible       |
| **Read Committed**   | Prevented  | Possible            | Possible       |
| **Repeatable Read**  | Prevented  | Prevented           | DBMS-dependent |
| **Serializable**     | Prevented  | Prevented           | Prevented      |

> **Important:** This is the standard conceptual model. Actual behavior can vary between database systems, particularly for `REPEATABLE READ`, because databases may use different locking or MVCC implementations.

# Common Confusion

### Dirty Read vs Non-Repeatable Read

```text
Dirty Read
→ Value was never committed.

Non-Repeatable Read
→ Value was committed, but changed between reads.
```

### Non-Repeatable Read vs Phantom Read

```text
Non-Repeatable Read
→ Same row, different value.

Phantom Read
→ Same query, different set of rows.
```

This distinction is very important in database interviews.

---

# Interview Takeaway

> **Dirty reads concern uncommitted data, non-repeatable reads concern changes to an already-read row, and phantom reads concern changes to the set of rows matching a query.**

### One-Line Definitions

* **Dirty Read:** Reading another transaction's uncommitted changes.
* **Non-Repeatable Read:** Reading the same row twice and getting different values.
* **Phantom Read:** Repeating a query and getting a different set of matching rows.
