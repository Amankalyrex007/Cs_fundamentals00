# Q17. What is a Deadlock in a Database?

A **deadlock** occurs when two or more transactions are **waiting for each other to release resources or locks**, so none of them can proceed.

In simple words:

> **Each transaction is waiting for something held by another transaction, creating a circular wait.**

---

## Example

Suppose a database contains two rows:

```text
Row A
Row B
```

Two transactions access them in different orders:

```text
Transaction 1              Transaction 2
---------------            ---------------
Locks A                    Locks B
   ↓                          ↓
Requests B                 Requests A
   ↓                          ↓
Waits for T2               Waits for T1
```

Now:

```text
T1 cannot continue
    ↓
Waiting for T2 to release B

T2 cannot continue
    ↓
Waiting for T1 to release A
```

This creates a **circular wait**.

Therefore:

```text
T1 → waits for T2
T2 → waits for T1
```

Neither transaction can proceed normally.

This is a **deadlock**.

---

# Real-World Analogy

Imagine two people:

```text
Person A
  ↓
Has Key 1
Needs Key 2

Person B
  ↓
Has Key 2
Needs Key 1
```

Person A waits for Person B.

Person B waits for Person A.

```text
A → needs B
↑         ↓
└─────────┘
```

Neither can proceed.

This is similar to a database deadlock.

---

# Why Do Deadlocks Happen?

Common causes include:

### 1. Transactions acquire locks in different orders

For example:

```text
Transaction 1:
Lock A → Lock B

Transaction 2:
Lock B → Lock A
```

This is one of the most common deadlock patterns.

---

### 2. Transactions hold locks for too long

A transaction that performs many operations while keeping locks can increase the time other transactions must wait.

For example:

```text
BEGIN
   ↓
Lock A
   ↓
Long processing
   ↓
Lock B
   ↓
COMMIT
```

The longer locks are held, the greater the opportunity for contention and deadlocks.

---

### 3. High concurrency

When many transactions access the same resources simultaneously, the probability of lock conflicts can increase.

---

### 4. Large or inefficient database operations

Poorly optimized queries may scan or lock more rows than necessary and hold locks for longer.

Examples include:

* Missing or ineffective indexes
* Large transactions
* Unnecessarily broad updates
* Long-running transactions

---

### 5. Isolation and locking behavior

Different database engines and isolation levels use different locking/MVCC strategies.

Certain combinations of:

* Queries
* Locking behavior
* Isolation levels
* Transaction ordering

can create deadlock situations.

---

# How Are Deadlocks Handled?

Databases commonly use **deadlock detection**.

The database can represent waiting relationships conceptually as:

```text
T1 → waiting for resource held by T2
T2 → waiting for resource held by T3
T3 → waiting for resource held by T1
```

The cycle indicates a deadlock.

Once a deadlock is detected, the database typically:

```text
1. Detects the circular wait
          ↓
2. Chooses a transaction as the victim
          ↓
3. Rolls that transaction back
          ↓
4. Releases its locks
          ↓
5. Allows the remaining transaction(s) to proceed
```

The exact victim-selection policy depends on the database system.

---

# Application Retry

After a transaction is rolled back because of a deadlock, the application may retry the operation.

A typical strategy is:

```text
Transaction fails
      ↓
Check whether failure was a deadlock
      ↓
Wait briefly (backoff)
      ↓
Retry
      ↓
Stop after a bounded number of attempts
```

A retry should generally use **bounded retries and backoff** rather than retrying indefinitely.

# Example: Bank Accounts

Suppose two transactions transfer money between accounts.

### Transaction 1

```text
Transfer A → B

Lock Account A
Lock Account B
Update A
Update B
```

### Transaction 2

```text
Transfer B → A

Lock Account B
Lock Account A
Update B
Update A
```

If both transactions acquire their first lock before requesting the second:

```text
T1 → holds A → needs B
T2 → holds B → needs A
```

A deadlock can occur.

---

# How Can Deadlocks Be Reduced?

Deadlocks cannot always be completely eliminated, but applications and database designs can reduce their likelihood.

### 1. Acquire locks in a consistent order

For example, always lock accounts by increasing ID:

```text
Account 10 → Account 20
```

instead of sometimes:

```text
10 → 20
```

and sometimes:

```text
20 → 10
```

This helps prevent circular wait patterns.

### 2. Keep transactions short

Do only the required work inside the transaction.

```text
BEGIN
   ↓
Required DB operations
   ↓
COMMIT
```

Avoid unnecessary processing while locks are held.

### 3. Optimize queries

Proper indexes and efficient queries can reduce the number of rows locked or the time locks are held.

### 4. Handle deadlock errors correctly

Applications should recognize deadlock-related failures and retry when the operation is safe to retry.

---

# Deadlock vs Normal Blocking

These concepts are related but different.

### Normal Blocking

```text
T1 holds A
T2 waits for A

T1 finishes
↓
T1 releases A
↓
T2 continues
```

There is no circular dependency.

### Deadlock

```text
T1 holds A → waits for B
T2 holds B → waits for A
```

Both transactions are waiting for each other.

> **Blocking can resolve naturally; a deadlock requires intervention such as rollback of one transaction.**

---

# Important Interview Point

A deadlock does **not** mean that the database has permanently stopped working.

The database detects the circular dependency and typically rolls back one transaction to break the cycle.

The application may then retry the failed transaction if appropriate.

---

# Common Mistakes

### ❌ Mistake 1: "Any waiting transaction is a deadlock."

No.

Waiting is normal when another transaction temporarily holds a lock.

A deadlock requires a **cycle of dependencies**.

### ❌ Mistake 2: "Deadlock means both transactions are rolled back."

Usually, the database chooses one or more transactions as victims to break the cycle. It does not necessarily roll back every transaction involved.

### ❌ Mistake 3: "Deadlocks happen only with two transactions."

No.

Three or more transactions can also form a circular wait:

```text
T1 → waits for T2
T2 → waits for T3
T3 → waits for T1
```

### ❌ Mistake 4: "A deadlock can always be prevented completely."

Not necessarily.

Good transaction design can reduce the likelihood, but applications should still be prepared to handle deadlock errors.

---

# Interview Takeaway

> **A database deadlock occurs when transactions form a circular wait for resources held by one another. The database detects the cycle and typically rolls back one transaction to break the deadlock, after which the application may retry the failed transaction.**

### One-Line Definition

> **Deadlock = two or more transactions waiting for each other in a cycle, so none can proceed.**
