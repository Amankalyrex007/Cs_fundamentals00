# Q18. How Can Database Deadlocks Be Prevented or Handled?

A **deadlock** occurs when two or more transactions are waiting for each other to release locks, so none of them can proceed.

### Example

Suppose there are two rows, `A` and `B`.

```text
Transaction 1                  Transaction 2
---------------                ---------------
Locks A                        Locks B
     ↓                              ↓
Tries to lock B                Tries to lock A
     ↓                              ↓
Waits for T2                   Waits for T1
```

Now:

```text
T1 → waiting for T2
T2 → waiting for T1
```

This circular wait creates a **deadlock**.

---

# How Can Deadlocks Be Prevented?

Deadlocks cannot always be completely eliminated, but good database and application design can **greatly reduce their likelihood**.

---

## 1. Access Resources in a Consistent Order

This is one of the most effective application-level strategies.

For example, always lock accounts in increasing `account_id` order.

### Safe pattern

```text
Transaction 1: A → B
Transaction 2: A → B
```

Instead of:

```text
Transaction 1: A → B
Transaction 2: B → A
```

When transactions acquire resources in a consistent order, circular waiting becomes much less likely.

### Example

Suppose:

```text
Account A → ID 101
Account B → ID 205
```

Always lock:

```text
101 → 205
```

regardless of which account is the sender.

---

## 2. Keep Transactions Short

Avoid holding locks longer than necessary.

### Bad

```text
BEGIN

Perform database operations
Perform unrelated processing
Call external API
Wait for API response
Perform more processing

COMMIT
```

The transaction may keep locks while waiting for an external service.

### Prefer

```text
BEGIN

Perform required database operations

COMMIT

Perform unrelated work
```

Shorter transactions generally mean:

* Locks are held for less time
* Less contention
* Lower chance of deadlocks

> **Important:** Avoid placing slow external API calls or unnecessary application processing inside a database transaction unless there is a specific reason to do so.

---

## 3. Access Only the Required Rows

Use appropriate queries and indexes so the database does not need to scan or lock more data than necessary.

For example:

```sql
UPDATE Accounts
SET balance = balance - 1000
WHERE account_id = 101;
```

An appropriate index on `account_id` can help the database locate the required row efficiently.

However:

> Exact locking behavior depends on the **database engine, query plan, indexes, and isolation level**.

An index does not automatically mean that a query will lock exactly one row in every situation.

---

## 4. Avoid Unnecessary Locking

Use an isolation level that provides the application's required correctness guarantees rather than automatically choosing the strongest possible isolation.

For example:

```text
Lower isolation
      ↓
More concurrency / potentially less contention

Higher isolation
      ↓
Stronger consistency guarantees
      ↓
Potentially more contention
```

The correct choice depends on the workload and database implementation.

> **Do not choose an isolation level solely to avoid deadlocks.** Correctness requirements come first.

---

# How Can Deadlocks Be Handled?

Even well-designed systems can encounter deadlocks.

Therefore, applications should also have a **recovery strategy**.

---

## 1. Let the Database Detect the Deadlock

Many relational databases have built-in **deadlock detection**.

When a deadlock is detected, the database typically:

```text
Detects circular wait
        ↓
Chooses a transaction as the victim
        ↓
Rolls that transaction back
        ↓
Releases its locks
        ↓
Allows other transaction(s) to proceed
```

The exact victim-selection policy depends on the database system.

Therefore, applications should be prepared for a transaction to fail because of a deadlock.

---

## 2. Retry the Transaction

A common production strategy is to retry a transaction that failed specifically because of a deadlock.

```text
Start Transaction
       ↓
Execute Operations
       ↓
    Deadlock?
     ↙     ↘
   No       Yes
   ↓         ↓
 Commit    Rollback
             ↓
        Wait / Backoff
             ↓
           Retry
```

Use:

* **Bounded retry count**
* **Backoff**
* Often some **jitter** to avoid many transactions retrying simultaneously

For example:

```text
Attempt 1 → Deadlock
    ↓
Short backoff
    ↓
Attempt 2 → Deadlock
    ↓
Longer backoff
    ↓
Attempt 3 → Success
```

Do not retry indefinitely.

---

## 3. Make Retried Operations Safe

If a transaction can be retried, the operation should be designed so that repeating it does not accidentally produce duplicate or incorrect effects.

This is where **idempotent design** can be useful.

Techniques may include:

* Unique constraints
* Idempotency keys
* Carefully designed update logic
* Application-level request identifiers

### Example

For a payment request, an idempotency key can help ensure that retrying the same request does not create two separate payment effects.

```text
Request ID: PAY-1001

First attempt → Deadlock
Second attempt → Retry

Database recognizes PAY-1001
→ Avoid duplicate processing
```

> Idempotency does not prevent deadlocks; it helps make **retries safe**.

---

# Prevention vs Handling

| Technique                       | Purpose                                |
| ------------------------------- | -------------------------------------- |
| **Consistent lock ordering**    | Prevent circular waiting               |
| **Short transactions**          | Reduce lock duration                   |
| **Appropriate indexes**         | Reduce unnecessary work and contention |
| **Appropriate isolation level** | Balance correctness and concurrency    |
| **Deadlock detection**          | Detect unavoidable deadlocks           |
| **Rollback victim transaction** | Break the deadlock                     |
| **Bounded retry + backoff**     | Recover automatically                  |
| **Idempotent operations**       | Make retries safer                     |

# Interview Example: Bank Transfer

Suppose two users transfer money:

```text
Transfer 1:
Account A → Account B

Transfer 2:
Account B → Account A
```

If each transaction locks its source account first:

```text
Transfer 1:
Lock A
   ↓
Wait for B

Transfer 2:
Lock B
   ↓
Wait for A
```

A deadlock can occur.

### Safer Strategy

Always acquire locks in a deterministic order, such as the smaller account ID first.

For example:

```text
A = 101
B = 205

Always lock:
101 → 205
```

Regardless of the transfer direction:

```text
A → B
B → A

Both:
101 → 205
```

This removes the inconsistent lock ordering that could create the circular wait.

# Important Interview Point

Deadlock handling has **two sides**:

```text
Prevention
   ↓
Reduce the chance of deadlocks

Handling
   ↓
Recover when a deadlock still occurs
```

A robust production system generally needs **both**.

---

# Common Mistakes

### ❌ Mistake 1: "Deadlocks can always be prevented."

Not necessarily.

Good design can reduce their likelihood, but applications should still handle deadlock failures.

### ❌ Mistake 2: "Any blocked transaction is a deadlock."

No.

A transaction may simply be waiting for another transaction to release a lock.

A deadlock requires a **circular dependency**.

### ❌ Mistake 3: "Just use the strongest isolation level."

Not necessarily.

Higher isolation can provide stronger guarantees but may increase contention. Choose isolation based on correctness requirements and workload.

### ❌ Mistake 4: "Indexes completely prevent deadlocks."

No.

Indexes can reduce unnecessary scanning and contention, but deadlocks can still occur.

### ❌ Mistake 5: "Retry forever."

Incorrect.

Use a **bounded retry count** with appropriate backoff, and make sure retrying the operation is safe.

# Interview Takeaway

> **Deadlocks occur when transactions wait for each other in a circular dependency. They can be reduced using consistent resource ordering, short transactions, appropriate indexing, and suitable isolation. Unavoidable deadlocks are handled through database detection and rollback, followed by bounded application-level retries with backoff when safe.**

### One-Line Definition

> **Prevent deadlocks through good transaction design; handle unavoidable deadlocks through detection, rollback, and safe retry.**
