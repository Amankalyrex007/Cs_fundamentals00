17.How can database deadlocks be prevented or handled?
A deadlock occurs when two or more transactions are waiting for each other to release locks, so none of them can proceed.

Example

Suppose there are two rows, A and B.

Transaction 1                  Transaction 2
-------------                  -------------
Locks A                        Locks B
     ↓                              ↓
Tries to lock B                Tries to lock A
     ↓                              ↓
Waits for T2                   Waits for T1

Neither transaction can continue:

T1 → waiting for T2
T2 → waiting for T1

This is a deadlock.

How can deadlocks be prevented?
1. Access resources in a consistent order

This is one of the most effective application-level strategies.

For example, always lock accounts in increasing account_id order:

Transaction 1: A → B
Transaction 2: A → B

Instead of:

Transaction 1: A → B
Transaction 2: B → A

A consistent ordering reduces the possibility of circular waiting.

2. Keep transactions short

Do not hold locks longer than necessary.

Bad:
BEGIN
    Perform many unrelated operations
    Call external API
    Perform more processing
COMMIT

Prefer:

BEGIN
    Perform required database operations
COMMIT

Then perform unrelated work

Shorter transactions generally mean locks are held for less time.

3. Access only the required rows

Use appropriate queries and indexes so the database doesn't need to lock or scan more data than necessary.

For example, make sure frequently used lookup conditions can use suitable indexes.

However, the exact locking behavior depends on the database engine and isolation level.

4. Avoid unnecessary locking

Use the lowest isolation level that correctly satisfies the application's requirements, rather than automatically choosing the strongest level.

Stronger isolation can increase locking/contention depending on the database's implementation.

How can deadlocks be handled?
1. Let the database detect the deadlock

Many relational databases have deadlock detection.

When a deadlock is detected, the database typically chooses one transaction as a victim, rolls it back, and allows the other transaction to proceed.

The application should therefore be prepared for a transaction to fail because of a deadlock.

2. Retry the transaction

A common production strategy is:

Start transaction
      ↓
Execute operations
      ↓
Deadlock?
   ↙       ↘
 No        Yes
 ↓          ↓
Commit    Rollback
            ↓
          Retry

Use a bounded retry count and usually some backoff/jitter, rather than retrying indefinitely.

The transaction should be designed so that retrying it is safe.

3. Keep transactions idempotent where possible

If an operation may be retried, structure it so that executing it again does not accidentally produce duplicate or incorrect effects.

For example, use appropriate unique constraints, idempotency keys, or carefully designed update logic when applicable.

Prevention vs handling
Technique	Purpose
Consistent lock ordering	Prevent circular waiting
Short transactions	Reduce lock duration
Appropriate indexes	Reduce unnecessary work/locking
Appropriate isolation level	Balance correctness and contention
Deadlock detection	Detect unavoidable deadlocks
Rollback victim transaction	Break the deadlock
Bounded retry + backoff	Recover automatically
Interview example

Suppose two users transfer money between accounts:

Transfer 1: Account A → Account B
Transfer 2: Account B → Account A

If each transaction locks its source account first, they can end up waiting for each other's destination account.

A safer strategy is to always acquire locks in a deterministic order, such as the smaller account ID first.

Interview takeaway

Deadlocks occur when transactions wait for each other in a cycle. Prevent them by using consistent resource/lock ordering, short transactions, appropriate indexing and isolation. Handle unavoidable deadlocks through database detection, rollback, and bounded application-level retries with backoff.
