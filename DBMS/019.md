# Q19. What is an Index?

A **database index** is a data structure that helps the database find rows **more efficiently** without scanning the entire table.

Think of it like the **index of a book**:

> Instead of reading every page to find a topic, you use the index to locate the relevant pages directly.

---

# Example

Suppose we have a `Users` table:

```text
+----+--------+-------------------+
| id | name   | email             |
+----+--------+-------------------+
| 1  | Aaman  | aaman@example.com  |
| 2  | Rahul  | rahul@example.com  |
| 3  | Priya  | priya@example.com  |
| .. | ..     | ..                |
+----+--------+-------------------+
```

Suppose we run:

```sql
SELECT *
FROM users
WHERE email = 'aaman@example.com';
```

## Without a Suitable Index

The database may need to examine many rows:

```text
Row 1 → Check email
Row 2 → Check email
Row 3 → Check email
...
Row N → Check email
```

This is commonly called a **table scan**.

For a large table, this can be expensive.

## With an Index

We can create an index:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Conceptually:

```text
Query
  ↓
Index on email
  ↓
Locate matching entry
  ↓
Find corresponding row
```

The database can use the index to locate matching rows much more efficiently.

> Whether an index is actually used depends on the query, table size, data distribution, statistics, indexes available, and the database optimizer.

---

# How Does an Index Work?

A common index implementation is a **B-tree / B+ tree**, although databases support other index structures and specialized index types.

Conceptually:

```text
                    Index
                  /       \
               A - M      N - Z
              /    \      /    \
            ...    ...   ...    ...
```

The index stores organized information that allows the database to navigate toward relevant rows instead of examining every row.

For example:

```text
Email Index

aaman@example.com  → Row 1
priya@example.com  → Row 3
rahul@example.com  → Row 2
...
```

The database can search the index and then locate the corresponding table row.

---

# Why Are Indexes Useful?

Indexes can improve performance for queries involving:

* `WHERE`
* `JOIN`
* `ORDER BY`
* Range conditions such as `>`, `<`, `BETWEEN`
* Uniqueness checks

For example:

```sql
SELECT *
FROM Orders
WHERE customer_id = 101;
```

An index on `customer_id` may make this lookup much more efficient.

Similarly:

```sql
SELECT *
FROM Orders
WHERE order_date >= '2026-01-01'
ORDER BY order_date;
```

An appropriate index on `order_date` may help with both filtering and ordering.

---

# Advantages of Indexes

### 1. Faster SELECT Queries

Indexes can significantly improve lookup performance for suitable queries.

### 2. Faster Searches

Queries filtering on indexed columns can avoid scanning the entire table in many cases.

### 3. Can Improve JOIN Performance

For example:

```sql
SELECT *
FROM Orders o
JOIN Customers c
  ON o.customer_id = c.customer_id;
```

Indexes on appropriate join columns can help the database execute such joins efficiently.

### 4. Can Help `ORDER BY` and Range Queries

For example:

```sql
SELECT *
FROM Products
WHERE price BETWEEN 500 AND 1000
ORDER BY price;
```

An appropriate index on `price` may help the database process this query efficiently.

### 5. Can Enforce Uniqueness

A **unique index** can enforce that indexed values are unique.

For example:

```sql
CREATE UNIQUE INDEX idx_users_email
ON users(email);
```

This can prevent duplicate email values, subject to the database's handling of `NULL`.

---

# Disadvantages of Indexes

Indexes are **not free**.

### 1. Additional Storage

Indexes require disk and memory resources.

### 2. Slower INSERT Operations

When a new row is inserted, relevant indexes may also need to be updated.

```text
INSERT row
   ↓
Update table
   ↓
Update indexes
```

### 3. Slower UPDATE Operations

If an indexed column changes, the corresponding index entries may need to be updated.

### 4. Slower DELETE Operations

Deleting a row may also require removing its entries from relevant indexes.

### 5. Maintenance Overhead

Too many indexes increase:

* Storage requirements
* Write overhead
* Maintenance work
* Optimization complexity

Therefore:

> **Creating an index on every column is usually not a good strategy.**

---

# Primary Key and Indexes

A **primary key** is commonly backed by an index, but the exact implementation depends on the database system.

For example:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(255)
);
```

The database typically creates or uses an index to efficiently enforce the primary key's uniqueness requirement.

So:

```text
PRIMARY KEY
     ↓
Uniqueness + identification
     ↓
Usually supported by an index
```

However:

> **A primary key and an index are not the same concept.**

A primary key is a **data-integrity/key constraint**, while an index is primarily a **data-access structure**.

---

# Composite Index

An index can contain **multiple columns**.

For example:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

This is called a **composite index** or **multi-column index**.

It can be useful for queries such as:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
ORDER BY order_date;
```

The index is organized using:

```text
(customer_id, order_date)
```

---

# Column Order Matters

The order of columns in a composite index is important.

These two indexes are not equivalent for every query:

```sql
CREATE INDEX idx1
ON orders(customer_id, order_date);
```

and:

```sql
CREATE INDEX idx2
ON orders(order_date, customer_id);
```

For example, an index on:

```text
(customer_id, order_date)
```

is particularly useful for queries that constrain or organize data beginning with `customer_id`.

This is related to the **leftmost-prefix principle** used by many B-tree-based systems.

For example:

```text
(customer_id, order_date)
      ↑
First indexed column
```

The database can often use the index effectively for:

```sql
WHERE customer_id = 101
```

or:

```sql
WHERE customer_id = 101
ORDER BY order_date;
```

But the same index may be less useful for a query that only filters on:

```sql
WHERE order_date = '2026-10-01'
```

depending on the database and query plan.

# Index Example: E-Commerce

Suppose we have:

```text
Orders
+----------+-------------+------------+--------+
| order_id | customer_id | order_date | amount |
+----------+-------------+------------+--------+
| 101      | 5           | 2026-09-01 | 1200   |
| 102      | 8           | 2026-09-03 | 2500   |
| 103      | 5           | 2026-09-05 | 1800   |
| 104      | 12          | 2026-09-07 | 900    |
+----------+-------------+------------+--------+
```

Suppose the application frequently asks:

```sql
SELECT *
FROM Orders
WHERE customer_id = 5
ORDER BY order_date;
```

A composite index can be created:

```sql
CREATE INDEX idx_orders_customer_date
ON Orders(customer_id, order_date);
```

Conceptually:

```text
Index
  ↓
customer_id = 5
  ↓
Orders for customer 5
  ↓
Already organized by order_date
```

This can reduce the work required for the query.

# Index vs Full Table Scan

### Full Table Scan

```text
Query
  ↓
Check Row 1
  ↓
Check Row 2
  ↓
Check Row 3
  ↓
...
  ↓
Check Row N
```

### Index-Based Access

```text
Query
  ↓
Search Index
  ↓
Locate relevant entries
  ↓
Fetch matching rows
```

The second approach can be much more efficient for selective queries on large tables.

However, the optimizer may still choose a table scan when it estimates that scanning is cheaper—for example, when a query returns a large portion of the table.

---

# Indexes and Write Performance

A useful way to remember the trade-off is:

```text
More / Better Indexes
        ↓
Potentially faster reads
        ↓
But
        ↓
More storage
        +
More work during INSERT/UPDATE/DELETE
```

Therefore, database indexing is a **read-performance vs write/maintenance trade-off**.

---

# Common Mistakes

### ❌ Mistake 1: "Indexes always make queries faster."

Not necessarily.

The database optimizer may decide that an index is not useful for a particular query.

### ❌ Mistake 2: "Create an index on every column."

Usually a bad strategy.

Indexes consume storage and add write/maintenance overhead.

### ❌ Mistake 3: "Primary key and index are the same thing."

No.

A primary key is a **constraint/key**, while an index is a **data structure used for efficient access**. A primary key is commonly supported by an index.

### ❌ Mistake 4: "Indexes only help SELECT."

Indexes can also help with:

* Joins
* Sorting
* Range searches
* Uniqueness enforcement

But they can increase the cost of writes.

### ❌ Mistake 5: "Column order doesn't matter in a composite index."

Incorrect.

For:

```text
(customer_id, order_date)
```

the order can significantly affect which queries can use the index efficiently.

---

# Important Interview Point

An index does **not** store a separate copy of the entire table in the same form as the table itself.

It stores an organized structure containing indexed values and enough information to locate the corresponding rows.

Also remember:

> **An index improves data access, but every index has a storage and write-maintenance cost.**

```text
Without Index
```


# Interview Takeaway

> **An index is a database data structure that improves query performance by allowing the database to locate relevant rows more efficiently than a full table scan. The trade-off is additional storage and overhead during INSERT, UPDATE, and DELETE operations.**

### One-Line Definition

> **Index = a data structure that speeds up suitable data access by organizing lookup information, at the cost of storage and write-maintenance overhead.**
