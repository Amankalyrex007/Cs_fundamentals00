# Q20. How Does an Index Improve Query Performance?

An **index improves query performance** by allowing the database to locate matching rows more efficiently instead of scanning every row in the table.

The basic idea is:

```text
Without Index → Scan many rows
With Index    → Search index → Locate required rows
```

---

# Without an Index

Suppose we have **10 million users**:

```sql
SELECT *
FROM users
WHERE email = 'aaman@example.com';
```

If there is no suitable index, the database may perform a **full table scan**:

```text
Row 1 → Check email
Row 2 → Check email
Row 3 → Check email
...
Row 10,000,000 → Check email
```

The database may need to examine a very large number of rows before finding the match.

Conceptually:

```text
Query
  ↓
Full Table Scan
  ↓
Row 1
Row 2
Row 3
...
Row N
```

This can be expensive for large tables.

---

# With an Index

Create an index:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Now the database can search the index structure first.

Conceptually:

```text
             Query
               ↓
        Index on email
               ↓
      aaman@example.com
               ↓
         Row location
               ↓
         Required row
```

Instead of checking every user, the database can navigate the index to find the relevant entry.

---

# How Much Faster Can It Be?

For a typical **B-tree-style index**, searching the index is roughly **O(log N)** for the index traversal, compared with **O(N)** work for scanning N rows.

```text
Full Table Scan
      O(N)
       ↓
Check many rows

B-tree Index Search
      O(log N)
       ↓
Navigate the index
```

For example, with millions of rows, a well-designed index can dramatically reduce the amount of data that needs to be examined.

> **Important:** `O(log N)` describes the index traversal, not necessarily the total query cost. Actual performance depends on the database engine, index type, data distribution, query selectivity, table layout, caching, and the execution plan chosen by the optimizer.

---

# What Happens Internally?

When a query is executed, the database conceptually performs the following steps:

```text
1. Receive the SQL query
          ↓
2. Examine available indexes
          ↓
3. Consider possible execution plans
          ↓
4. Estimate their costs
          ↓
5. Choose an execution plan
          ↓
6. Traverse the index if beneficial
          ↓
7. Locate matching row(s)
          ↓
8. Retrieve required data
```

The database optimizer is responsible for deciding whether using an index is actually beneficial.

---

# Example: Equality Search

Suppose:

```sql
SELECT *
FROM users
WHERE email = 'aaman@example.com';
```

With:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

The database can conceptually perform:

```text
email index
     ↓
aaman@example.com
     ↓
Row location
     ↓
users row
```

Instead of:

```text
users table
     ↓
Row 1
Row 2
Row 3
...
Row 10,000,000
```

This is especially useful when `email` is highly selective—for example, when one email normally identifies one user.

---

# Example: Range Query

Indexes can also help with **range queries**.

For example:

```sql
SELECT *
FROM orders
WHERE order_date >= '2026-01-01';
```

An appropriate index:

```sql
CREATE INDEX idx_orders_date
ON orders(order_date);
```

can help the database locate the relevant portion of the index:

```text
Index on order_date

2025-12-28
2025-12-29
2025-12-30
2025-12-31
──────────────
2026-01-01  ← Start
2026-01-02
2026-01-03
...
```

A B-tree-style index can efficiently navigate to the starting point and then scan the relevant range.

---

# Why Are Indexes Useful for Different Operations?

Indexes can improve several types of queries when the index matches the query pattern.

### `WHERE`

```sql
SELECT *
FROM Users
WHERE email = 'aaman@example.com';
```

### `JOIN`

```sql
SELECT *
FROM Orders o
JOIN Customers c
  ON o.customer_id = c.customer_id;
```

An index on an appropriate join column can help locate matching rows efficiently.

### `ORDER BY`

```sql
SELECT *
FROM Orders
ORDER BY order_date;
```

An appropriate index may help with ordering, depending on the query and database engine.

### `GROUP BY`

```sql
SELECT customer_id, COUNT(*)
FROM Orders
GROUP BY customer_id;
```

An appropriate index may sometimes help the database process grouping more efficiently.

> The presence of an index does **not** guarantee that it will be used. The optimizer chooses the plan it estimates to be cheapest.

---

# Important Concept: Selectivity

An index is often most useful when a query retrieves a relatively **small portion of the table**.

Suppose there are 10 million users.

### Highly selective

```sql
WHERE email = 'aaman@example.com'
```

Perhaps only one row matches.

An index can be very useful.

### Low selectivity

```sql
WHERE gender = 'Male'
```

Suppose 5 million rows match.

In that case, using the index may require retrieving a huge number of rows, and a full/sequential scan may be cheaper.

Therefore:

> **More selective queries often benefit more from indexes, but the optimizer makes the final decision.**

# Index vs Full Table Scan

## Without Index

```text
Query
  ↓
Full Table Scan
  ↓
Row 1
Row 2
Row 3
Row 4
...
Row N
```

Potential work:

```text
O(N)
```

## With Suitable B-tree Index

```text
Query
  ↓
Index
  ↓
Navigate to matching key
  ↓
Find row location(s)
  ↓
Retrieve rows
```

Index traversal:

```text
O(log N)
```

But remember:

> The total query cost can be more complicated than simply comparing `O(log N)` with `O(N)`.

---

# Important Trade-Off

Indexes improve read performance, but they have costs.

```text
             Index
               │
       ┌───────┴───────┐
       ↓               ↓
 Faster Reads      Additional Cost
                       ↓
              ┌────────┴────────┐
              ↓                 ↓
          Storage        Write Maintenance
                              ↓
                       INSERT/UPDATE/DELETE
```

### Benefits

* Faster suitable searches
* Faster lookups
* Potentially faster joins
* Can help sorting and range queries

### Costs

* Additional storage
* Index maintenance
* More work during `INSERT`
* More work during `UPDATE`
* More work during `DELETE`

---

# Why Doesn't Every Query Use an Index?

An index is **not automatically faster**.

Suppose a query returns 90% of a table:

```sql
SELECT *
FROM users
WHERE country = 'India';
```

If most rows match, the database may determine that scanning the table sequentially is cheaper than:

```text
Search index
     ↓
Find millions of entries
     ↓
Fetch millions of rows
```

In such a situation:

```text
Full Table Scan
      ↓
May be cheaper
```

The database optimizer makes this decision based on estimated costs.

---

# Real-World Example

Consider an e-commerce website with **50 million orders**.

The application frequently executes:

```sql
SELECT *
FROM orders
WHERE customer_id = 101;
```

Without an index:

```text
50 million orders
       ↓
Scan many rows
       ↓
Find customer 101's orders
```

With:

```sql
CREATE INDEX idx_orders_customer
ON orders(customer_id);
```

the database can use the index to locate entries associated with customer `101` much more efficiently.

Conceptually:

```text
50 million orders
       ↓
Customer Index
       ↓
customer_id = 101
       ↓
Matching row locations
       ↓
Customer 101's orders
```

This is particularly useful when a customer represents only a small fraction of the total orders.

---

# Composite Index Example

Suppose the application frequently runs:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
ORDER BY order_date;
```

A composite index may be useful:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

Conceptually:

```text
(customer_id, order_date)
          ↓
      Customer 101
          ↓
   Orders by date
```

The column order matters.

```text
(customer_id, order_date)
```

is not equivalent to:

```text
(order_date, customer_id)
```

for all query patterns.

---

# Important Interview Point

An index does not mean that the database automatically reads only one row.

Instead:

> **An index provides an efficient path to locate relevant data.**

The database may still need to retrieve:

* One row
* Several rows
* Thousands of rows
* Or a large portion of the table

depending on the query.

---

# Common Mistakes

### ❌ Mistake 1: "Indexes always make queries faster."

No.

The optimizer may choose a table scan when it is cheaper.

### ❌ Mistake 2: "Index search is always O(log N) for the entire query."

Not exactly.

`O(log N)` is a useful approximation for B-tree index traversal. Total query cost also includes locating and retrieving the actual rows.

### ❌ Mistake 3: "Indexes eliminate table scans."

No.

Some queries are better served by a full/sequential scan.

### ❌ Mistake 4: "Indexes are free."

No.

They require storage and add write-maintenance overhead.

### ❌ Mistake 5: "Every indexed column should be used by every query."

No.

An index is useful only when it matches a query's access pattern and is cost-effective for that workload.

# Interview Takeaway

> **An index improves query performance by providing an efficient path to locate matching rows, reducing the amount of data the database needs to scan. However, indexes consume storage and add write/maintenance overhead, so they should be created according to actual query patterns and workload.**

### One-Line Definition

> **Index = an efficient lookup structure that can reduce the amount of data examined for suitable queries, at the cost of additional storage and write-maintenance overhead.**
