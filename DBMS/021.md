# Q21. What Are the Disadvantages of Indexes?

Indexes can significantly improve **read/query performance**, but they also introduce **storage, write, and maintenance costs**.

The key trade-off is:

```text
Indexes
   ↓
Faster reads
   +
Higher storage + write + maintenance cost
```

---

## 1. Additional Storage

Indexes require extra disk space because the database stores indexed values along with information needed to locate the corresponding rows.

For large tables with multiple indexes, this storage can become significant.

```text
Users Table
     +
Index on email
     +
Index on username
     +
Index on created_at
     ↓
More disk space
```

Therefore, indexes are not free from a storage perspective.

---

## 2. Slower INSERT Operations

When a new row is inserted, the database may need to update every relevant index.

```text
INSERT row
    ↓
Update table
    ↓
Update Index 1
Update Index 2
Update Index 3
```

For example, if `users` has indexes on `email`, `username`, and `phone`:

```sql
INSERT INTO users (name, email, username, phone)
VALUES ('Rahul', 'rahul@example.com', 'rahul01', '9876543210');
```

The table is updated, but the relevant indexes must also be updated.

So, **more indexes can increase INSERT cost**.

---

## 3. Slower UPDATE Operations

If an indexed column changes, the corresponding index must also be updated.

For example:

```sql
UPDATE users
SET email = 'new@example.com'
WHERE id = 101;
```

If `email` has an index, the database may need to:

```text
Find old index entry
        ↓
Remove/update old entry
        ↓
Add new index entry
```

Updates to non-indexed columns may avoid this particular index-maintenance cost, although the database still has to update the table row.

---

## 4. Slower DELETE Operations

Deleting a row also requires removing its entries from relevant indexes.

For example:

```sql
DELETE FROM users
WHERE id = 101;
```

Conceptually:

```text
Delete row from table
        ↓
Remove corresponding index entries
```

Therefore:

> **Indexes can speed up reads but increase the cost of writes.**

This is especially important in applications with very frequent `INSERT`, `UPDATE`, or `DELETE` operations.

---

## 5. Maintenance Overhead

Indexes need to be maintained as data changes.

Depending on the database system and index type, this can consume additional:

* CPU
* I/O
* Memory
* Storage
* Maintenance resources

Large or heavily modified indexes may also require database-specific maintenance operations.

Therefore, an index should be considered an ongoing resource cost, not just a one-time optimization.

---

## 6. Too Many Indexes Can Hurt Performance

Creating an index on every column is generally a bad strategy.

For example:

```text
Users
 ├── Index on name
 ├── Index on email
 ├── Index on age
 ├── Index on city
 ├── Index on phone
 └── ...
```

Every additional index can increase:

```text
Storage requirements
Write overhead
Maintenance cost
Query-planning complexity
```

For example, if a table receives thousands of inserts per second, maintaining many indexes can become expensive.

Indexes should therefore be created based on **actual query patterns and workload**, not simply because a column exists.

---

## 7. An Index May Not Always Be Used

Having an index does **not** guarantee that the database will use it.

The query optimizer estimates the cost of different execution plans.

For example:

```sql
SELECT *
FROM users
WHERE gender = 'Male';
```

Suppose:

```text
Total rows = 10,000,000
Male rows  = 5,000,000
```

An index on `gender` may not provide enough benefit because a very large portion of the table matches the condition.

The optimizer may decide that a sequential table scan is cheaper.

```text
Query
  ↓
Optimizer
  ↓
Is index cheaper?
  ├── Yes → Use index
  └── No  → Use table scan
```

Therefore:

> **Having an index does not guarantee that a query will use it or become faster.**

---

## Index Disadvantages — Quick Summary

| Disadvantage          | Effect                                   |
| --------------------- | ---------------------------------------- |
| **Extra storage**     | Requires additional disk space           |
| **INSERT overhead**   | Indexes must be updated                  |
| **UPDATE overhead**   | Indexed values may require index updates |
| **DELETE overhead**   | Index entries must be removed            |
| **Maintenance cost**  | Requires additional database resources   |
| **Too many indexes**  | Can increase overall workload            |
| **Not always useful** | Optimizer may choose a table scan        |

---

## Read Performance vs Write Cost

The main trade-off can be visualized as:

```text
                 INDEX
                   │
        ┌──────────┴──────────┐
        ↓                     ↓
   Faster Reads          Higher Write Cost
        │                     │
     SELECT              INSERT
     JOIN                UPDATE
     ORDER BY             DELETE
     Range Queries       Maintenance
```

For a read-heavy application:

```text
Many SELECTs
Few writes
     ↓
Indexes can be very useful
```

For a write-heavy application:

```text
Many INSERT/UPDATE/DELETE
     ↓
Too many indexes can become expensive
```

The correct index strategy therefore depends on the application's workload.

---

## Important Interview Point

The biggest disadvantage of indexes is the **read-performance vs write-cost trade-off**.

Indexes can make queries faster, but they:

* consume additional storage,
* increase `INSERT` cost,
* increase `UPDATE` cost,
* increase `DELETE` cost,
* require ongoing maintenance, and
* may not even be used for every query.

Therefore, indexes should be created **selectively based on real query patterns and workload**.

---

## Common Mistakes

### ❌ Mistake 1: "More indexes always mean better performance."

Not necessarily.

Too many indexes can significantly increase write and maintenance costs.

### ❌ Mistake 2: "Every query will use an index."

False.

The optimizer may choose a table scan when it estimates that it will be cheaper.

### ❌ Mistake 3: "Indexes only consume storage."

False.

They can also increase CPU, I/O, memory, and write-maintenance costs.

### ❌ Mistake 4: "Every column should be indexed."

False.

Indexes should be designed around actual query patterns and workload.

---

## Interview Takeaway

> **Indexes improve read performance, but they consume storage and add overhead to INSERT, UPDATE, DELETE, and maintenance operations. Therefore, indexes should be created selectively according to actual workload and query patterns.**

### One-Line Definition

> **The main disadvantage of an index is that it trades additional storage and write/maintenance cost for potentially faster read performance.**

**Easy Memory Trick:**

```text
Index = Faster Reads
        +
        More Storage
        +
        More Write Cost
```
