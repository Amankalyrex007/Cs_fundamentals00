# Q22. Clustered vs Non-Clustered Index?

A **clustered index** determines how a table's rows are physically organized/stored around the index key, whereas a **non-clustered index** is a separate index structure containing indexed keys and references to the corresponding table rows.

> **Important:** The exact implementation and terminology vary between database systems. Therefore, clustered and non-clustered indexes should not be treated as identical concepts across every DBMS.

---

## 1. Clustered Index

A **clustered index** organizes the table's data around the index key.

Conceptually:

```text
Clustered Index on employee_id

1 → Row 1
2 → Row 2
3 → Row 3
4 → Row 4
...
```

The table's data rows are organized according to the clustered structure.

Because the table's rows themselves are organized around this structure, a table can generally have **only one clustered organization**.

### Useful for

Clustered organization is particularly useful when queries frequently:

* perform range searches,
* filter/order by the clustered key,
* access nearby key values sequentially.

For example:

```sql
SELECT *
FROM employees
WHERE employee_id BETWEEN 100 AND 200;
```

If the table is organized around `employee_id`, rows in that range can often be accessed efficiently.

---

## 2. Non-Clustered Index

A **non-clustered index** is a separate data structure from the table's main data.

Conceptually:

```text
Non-Clustered Index
        ↓
    email key
        ↓
   Row locator
        ↓
  Actual table row
```

For example:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

The index allows the database to find rows using `email` without requiring the table itself to be organized around `email`.

A table can generally have **multiple non-clustered indexes**.

For example:

```text
Users Table
   │
   ├── Index on email
   ├── Index on phone
   ├── Index on username
   └── Index on created_at
```

---

# Clustered vs Non-Clustered Index

| Feature                | Clustered                                    | Non-Clustered                      |
| ---------------------- | -------------------------------------------- | ---------------------------------- |
| **Data organization**  | Table data is organized around the index key | Separate structure from table data |
| **Number per table**   | Generally one                                | Generally multiple                 |
| **Additional storage** | Depends on implementation                    | Requires additional index storage  |
| **Range queries**      | Often efficient for the clustered key        | Can also be efficient              |
| **Data and index**     | Closely tied                                 | Separate structures                |
| **Typical use**        | Primary/range access pattern                 | Additional search patterns         |

> **Note:** These are general characteristics, not universal rules. Exact behavior depends on the DBMS.

# Example

Suppose we have:

```text
Users

+----+--------+-------------------+
| id | name   | email             |
+----+--------+-------------------+
| 1  | Aaman  | aaman@example.com  |
| 2  | Rahul  | rahul@example.com  |
| 3  | Priya  | priya@example.com  |
+----+--------+-------------------+
```

Suppose the table is organized around `id`, while we also create a non-clustered index on `email`.

### Table organization

```text
1 → Aaman
2 → Rahul
3 → Priya
```

### Non-clustered index

```text
aaman@example.com → row for id 1
priya@example.com → row for id 3
rahul@example.com → row for id 2
```

Now consider:

```sql
SELECT *
FROM users
WHERE email = 'aaman@example.com';
```

The database can use the `email` index to locate the corresponding row efficiently.

Conceptually:

```text
Query
  ↓
email index
  ↓
aaman@example.com
  ↓
row locator
  ↓
User row (id = 1)
```

---

# Why Can a Table Generally Have Only One Clustered Organization?

A table's rows can only have one primary physical organization at a time.

For example, suppose the table is organized around:

```text
employee_id
```

You cannot simultaneously organize the same table's rows physically around:

```text
employee_id
```

and:

```text
email
```

as two independent clustered organizations.

However, you can create several separate non-clustered indexes:

```text
Table organization → employee_id

Additional indexes:
    email
    phone
    department_id
    joining_date
```

This is why a table generally has **one clustered organization but multiple non-clustered indexes**.

---

# Range Query Example

Suppose employee IDs are organized in clustered order:

```text
100
101
102
103
104
105
106
...
```

A query such as:

```sql
SELECT *
FROM employees
WHERE employee_id BETWEEN 100 AND 105;
```

can efficiently access a contiguous range of nearby key values.

This is one reason clustered organization can be useful for **range-based access**.

A non-clustered index can also support range queries, but the database may need additional row lookups depending on the index and query.

---

# Important Interview Nuance

Do **not** memorize:

> ❌ Clustered = faster
> ❌ Non-clustered = slower

That is too simplistic.

Actual performance depends on factors such as:

* Query pattern
* Index key
* Selectivity
* Data distribution
* Covering indexes
* Database engine
* Execution plan
* Whether additional row lookups are required

The optimizer chooses the access method based on the estimated cost.

---

# DBMS-Specific Behavior

The terminology and implementation can differ between database systems.

For example, **SQL Server** has a well-defined clustered-index model where a clustered index determines the organization of the table's data.

**PostgreSQL**, however, does not have a continuously maintained clustered-index model in the same sense.

PostgreSQL provides a `CLUSTER` operation that can physically reorganize a table based on an index, but that ordering is **not automatically maintained** as rows are subsequently modified.

Therefore:

> Always consider the specific DBMS when discussing clustered indexes.

## Common Interview Mistakes

### ❌ Mistake 1: "A clustered index is always faster."

Not necessarily. Performance depends on the query, data distribution, optimizer, and execution plan.

### ❌ Mistake 2: "A table can have many clustered indexes."

Generally, no. A table can have only one clustered physical organization.

### ❌ Mistake 3: "Non-clustered indexes contain the complete table."

Usually, they contain indexed values and information needed to locate the corresponding rows, although some indexes can include additional columns and become covering indexes for particular queries.

### ❌ Mistake 4: "Clustered indexes work the same way in every DBMS."

False. The implementation and terminology vary across database systems.

---

## Interview Takeaway

> **A clustered index organizes a table's data around its key, while a non-clustered index is a separate structure that helps locate the corresponding table rows. A table generally has one clustered organization but can have multiple non-clustered indexes.**

### One-Line Memory Trick

```text
Clustered     → Data organized around the key
Non-Clustered → Separate index → Row locator → Data
```
