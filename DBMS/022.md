22.Clustered vs non-clustered index?
A clustered index determines how the table's rows are physically organized/stored according to the index key, whereas a non-clustered index is a separate index structure that contains indexed keys and references to the corresponding table rows.

The exact implementation and terminology can vary between database systems, so the distinction should not be treated as identical across all DBMSs.

1. Clustered index

A clustered index organizes the table's data around the index key.

Conceptually:

Clustered index on employee_id

1 → Row 1
2 → Row 2
3 → Row 3
4 → Row 4
...

The data rows are stored in the order/structure defined by the clustered index.

Because the table's rows themselves are organized around this structure, a table can generally have only one clustered organization.

Useful for:

Range queries
Queries frequently ordered/filtering by the clustered key
Sequential access to nearby key values
2. Non-clustered index

A non-clustered index is a separate data structure from the table's main data.

Conceptually:

Non-clustered index
       ↓
   email key
       ↓
 Row locator
       ↓
Actual table row

For example:

CREATE INDEX idx_users_email
ON users(email);

The index allows the database to find rows using email without requiring the table itself to be organized by email.

A table can generally have multiple non-clustered indexes.

Key differences
Feature	Clustered	Non-clustered
Data organization	Table data organized around the index key	Separate structure from table data
Number per table	Generally one	Generally multiple
Additional storage	Depends on implementation	Requires additional index storage
Range queries	Often efficient for the clustered key	Can also be efficient
Data and index	Closely tied	Separate structures
Typical use	Primary/range access pattern	Additional search patterns
Example

Suppose:

Users
--------------------------------
id | name  | email
1  | Aaman | aaman@example.com
2  | Rahul | rahul@example.com
3  | Priya | priya@example.com

You might have the table organized around id, while also having a non-clustered index on email:

Table organization:
1 → Aaman
2 → Rahul
3 → Priya

Non-clustered index:
aaman@example.com → row for id 1
priya@example.com → row for id 3
rahul@example.com → row for id 2

Then:

SELECT *
FROM users
WHERE email = 'aaman@example.com';

can use the email index to locate the corresponding row efficiently.

Important interview nuance

Don't memorize "clustered = faster, non-clustered = slower." That is too simplistic.

Performance depends on:

Query pattern
Index key
Selectivity
Data distribution
Covering indexes
Database engine
Execution plan

Also, some databases use terminology differently. For example, PostgreSQL does not have a continuously maintained clustered-index model in the same sense as SQL Server; its CLUSTER operation physically reorganizes a table based on an index but does not maintain that ordering automatically.

Interview takeaway

A clustered index organizes the table's data around its key, while a non-clustered index is a separate structure that points to the corresponding table rows. A table generally has one clustered organization but can have multiple non-clustered indexes.
