# Q23. What Is a Composite Index?

A **composite index** is an index created on **two or more columns** of a table.

It is useful when queries frequently **filter, sort, or join using a combination of columns**.

For example, an e-commerce system may frequently search orders using both:

```text
customer_id + order_date
```

A composite index can be created specifically for this query pattern.

---

## Example

Suppose we have:

```text
orders

+----------+-------------+------------+--------+
| order_id | customer_id | order_date | status |
+----------+-------------+------------+--------+
| 101      | 101         | 2026-01-05 | Paid   |
| 102      | 102         | 2026-01-08 | Pending|
| 103      | 101         | 2026-02-10 | Paid   |
+----------+-------------+------------+--------+
```

We can create a composite index:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

This index is based on **both `customer_id` and `order_date`**.

A query such as:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01';
```

can potentially benefit from this index.

Conceptually:

```text
(customer_id, order_date)
        ↓
(101, 2026-01-05)
(101, 2026-02-10)
(102, 2026-01-08)
...
```

---

# Why Does Column Order Matter?

This is one of the **most important interview points** about composite indexes.

Consider:

```sql
CREATE INDEX idx_orders
ON orders(customer_id, order_date);
```

The index is organized primarily by:

```text
customer_id
      ↓
order_date
```

In other words, `customer_id` is the **leading/first column** and `order_date` is the second column.

Therefore, it is generally useful for queries such as:

### Query 1 — First column only

```sql
SELECT *
FROM orders
WHERE customer_id = 101;
```

### Query 2 — Both columns

```sql
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01';
```

But consider:

### Query 3 — Second column only

```sql
SELECT *
FROM orders
WHERE order_date >= '2026-01-01';
```

An index beginning with `customer_id` may be less useful for this query because the query does not constrain the index's leading column.

This is related to the **leftmost-prefix principle** for commonly used B-tree composite indexes.

---

# Leftmost-Prefix Principle

For:

```sql
CREATE INDEX idx_orders
ON orders(customer_id, order_date, status);
```

The index can generally support access patterns beginning with the leftmost columns, such as:

```text
(customer_id)
(customer_id, order_date)
(customer_id, order_date, status)
```

But an index beginning with `customer_id` is not automatically equivalent to separate indexes on:

```text
order_date
status
```

For example:

```text
Index:
(customer_id, order_date, status)

Good starting points:
✓ customer_id
✓ customer_id + order_date
✓ customer_id + order_date + status

Not automatically equivalent to:
✗ order_date alone
✗ status alone
```

> The exact behavior depends on the database engine and execution plan, but the leftmost-column rule is an important B-tree indexing concept.

---

# Composite Index vs Multiple Single-Column Indexes

Suppose the query is:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01';
```

You could have:

```text
Index 1 → customer_id
Index 2 → order_date
```

or:

```text
Composite Index → (customer_id, order_date)
```

A composite index can be better suited to this particular query pattern because the database can use the **combined ordering of the columns**.

However:

> **Do not assume a composite index is always better.**

The optimizer's decision depends on factors such as:

* Database engine
* Statistics
* Selectivity
* Query shape
* Data distribution
* Existing indexes
* Workload

The database may choose a single-column index, combine indexes where supported, use the composite index, or perform a table scan.

# Another Example: E-Commerce Products

Suppose an online store frequently searches products by:

```text
category_id + price
```

A composite index could be:

```sql
CREATE INDEX idx_products_category_price
ON products(category_id, price);
```

This can be useful for queries such as:

```sql
SELECT *
FROM products
WHERE category_id = 10
  AND price BETWEEN 500 AND 2000;
```

The index is particularly suited to the access pattern beginning with `category_id`.

---

# Composite Index and Sorting

Composite indexes can also help with sorting when the query's ordering matches the index structure.

For example:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

A query such as:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
ORDER BY order_date;
```

may benefit because rows for the same customer are already organized by `order_date` within the index.

The optimizer still decides whether using the index is cheaper than other execution plans.

---

# Composite Index ≠ Composite Key

These are **different concepts**.

| Composite Index                             | Composite Key                                     |
| ------------------------------------------- | ------------------------------------------------- |
| Index involving multiple columns            | Key consisting of multiple columns                |
| Primarily used for query access/performance | Used to identify rows or enforce a key constraint |
| Does not necessarily enforce uniqueness     | Can uniquely identify a row                       |
| Can exist independently of a key            | Represents a key definition                       |
| Example: `(customer_id, order_date)`        | Example: `(student_id, course_id)`                |

### Composite Index

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

### Composite Key

```sql
CREATE TABLE Enrollments (
    student_id INT,
    course_id INT,
    PRIMARY KEY (student_id, course_id)
);
```

The first is an **index structure**.

The second defines a **key constraint**.

---

# Can a Composite Index Be Unique?

Yes.

A composite index can also enforce uniqueness when created as a `UNIQUE` index.

For example:

```sql
CREATE UNIQUE INDEX idx_user_email_type
ON users(email, email_type);
```

This means the **combination** of `email` and `email_type` must be unique.

For example:

```text
email                email_type
--------------------------------
aaman@example.com    personal    ✓
aaman@example.com    work        ✓
aaman@example.com    personal    ✗ duplicate combination
```

Notice that `email` itself does not have to be unique. The **combination** must be unique.

# Composite Index vs Composite Key — Easy Example

Consider:

```text
Enrollments

student_id | course_id | semester
-----------|-----------|---------
101        | C01       | 2026
101        | C02       | 2026
102        | C01       | 2026
```

A composite key might be:

```text
(student_id, course_id)
```

because together they identify an enrollment.

A composite index could independently be:

```text
(student_id, semester)
```

if queries frequently search by student and semester.

So:

```text
Composite Key
      ↓
Identity / integrity

Composite Index
      ↓
Efficient data access
```

## Common Interview Mistakes

### ❌ Mistake 1: "Composite index means a composite primary key."

False.

They are different concepts.

### ❌ Mistake 2: "Column order doesn't matter."

False.

For a B-tree composite index, the leading column(s) are important.

```text
(customer_id, order_date)
```

is not equivalent to:

```text
(order_date, customer_id)
```

for all query patterns.

### ❌ Mistake 3: "A composite index is always better than two single-column indexes."

False.

The optimizer considers the actual query, statistics, selectivity, and workload.

### ❌ Mistake 4: "Every column in the composite index must be unique."

False.

The combination of columns is indexed; uniqueness exists only if a unique constraint/index is specified.

---

## Important Interview Point

The most important things to remember about composite indexes are:

1. They contain **multiple columns**.
2. They are useful for queries using those columns together.
3. **Column order matters.**
4. The leading column is especially important for B-tree access.
5. A composite index is **not the same as a composite key**.
6. A composite index is not automatically better than multiple single-column indexes.

---

## Interview Takeaway

> **A composite index is an index on multiple columns, designed for query patterns that use those columns together. Column order is critical because a composite B-tree index is organized according to the specified column order.**
