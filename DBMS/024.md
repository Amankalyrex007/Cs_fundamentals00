# Q24. How Do You Decide Which Columns to Index?

You should choose indexes based on **actual query patterns and workload**, not simply because a column exists.

A good index strategy starts with the queries the application actually runs and then validates the decision using execution plans and realistic measurements.

---

## 1. Start With Frequently Queried Columns

Look at columns commonly used in:

* `WHERE`
* `JOIN`
* `ORDER BY`
* `GROUP BY`

For example:

```sql
SELECT *
FROM orders
WHERE customer_id = 101;
```

If this query runs frequently, an index on `customer_id` may be useful:

```sql
CREATE INDEX idx_orders_customer
ON orders(customer_id);
```

Conceptually:

```text
Frequent Query
     ↓
WHERE customer_id
     ↓
Index on customer_id
     ↓
Potentially faster row lookup
```

However, frequent usage alone does not guarantee that an index will help. The optimizer also considers the data distribution and estimated cost.

---

# 2. Consider Selectivity

**Selectivity** describes how effectively a condition narrows down the rows being searched.

For example:

| Column    | Typical Selectivity |
| --------- | ------------------- |
| `user_id` | Usually high        |
| `email`   | Usually high        |
| `gender`  | Often low           |
| `status`  | Often low           |

Suppose:

```text
10,000,000 users
```

and:

```text
WHERE user_id = 101
```

may match only one row.

But:

```text
WHERE gender = 'Male'
```

might match millions of rows.

A highly selective condition often makes an index more attractive because the database can eliminate a large portion of the table.

### Important Nuance

Low-cardinality columns are **not automatically useless to index**.

For example, an index on `status` might still be useful when:

```text
status = 'Pending'
```

matches only a small fraction of a large table, or when the query pattern and database engine make the index beneficial.

The optimizer considers:

* Table size
* Data distribution
* Selectivity
* Statistics
* Query shape
* Database engine
* Estimated execution cost

---

# 3. Look at Combinations of Columns

If queries frequently use multiple columns together, consider a **composite index**.

For example:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01';
```

A suitable composite index might be:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

The column order matters:

```text
(customer_id, order_date)
       ↓
customer_id → order_date
```

This can be particularly useful for queries that begin with `customer_id`.

Do not automatically assume:

```text
(customer_id, order_date)
```

is equivalent to:

```text
(order_date, customer_id)
```

The correct order depends on the actual query patterns.

---

# 4. Consider JOIN Columns

Columns frequently used to join tables can benefit from indexes.

For example:

```sql
SELECT *
FROM orders o
JOIN customers c
  ON o.customer_id = c.id;
```

An appropriate index on:

```text
orders.customer_id
```

can help the database efficiently locate matching orders.

Primary keys and unique constraints are also commonly backed by indexes, depending on the DBMS.

For example:

```text
customers
   │
   └── id → Primary Key

orders
   │
   └── customer_id → Foreign Key
```

The foreign-key column may be a useful indexing candidate, especially when it is frequently used for joins or parent-row updates/deletes. However, **not every foreign key must automatically be indexed**; workload and DBMS behavior matter.

---

# 5. Consider Sorting and Range Queries

Indexes can also help queries involving:

### Sorting

```sql
SELECT *
FROM orders
ORDER BY order_date;
```

An index on `order_date` may help the database avoid or reduce the cost of a separate sorting operation, depending on the query and execution plan.

### Range Queries

```sql
SELECT *
FROM orders
WHERE order_date BETWEEN '2026-01-01'
                      AND '2026-01-31';
```

An index on `order_date` can help the database locate the relevant range efficiently.

This is one reason B-tree indexes are commonly useful for:

```text
=
>
<
>=
<=
BETWEEN
ORDER BY
```

when the query pattern matches the index structure.

---

# 6. Consider Write Frequency

Indexes have a **write cost**.

If a table receives very frequent:

```text
INSERT
UPDATE
DELETE
```

then maintaining many indexes can significantly increase write overhead.

For example:

```text
High-write table
     ↓
INSERT
     ↓
Update table
     +
Update Index 1
     +
Update Index 2
     +
Update Index 3
```

Therefore, don't create an index just because a column is occasionally queried.

You need to balance:

```text
Read performance
       ↕
Write performance
       ↕
Storage
       ↕
Maintenance cost
```

---

# 7. Check the Execution Plan

This is one of the most important **production practices**.

Use your database's query-plan tools, such as:

```sql
EXPLAIN
```

or, depending on the database:

```sql
EXPLAIN ANALYZE
```

Check whether the database:

* Uses the expected index
* Performs a sequential/full-table scan
* Estimates the number of rows correctly
* Spends significant time on a particular operation
* Performs expensive sorting or joins
* Uses an unexpected execution plan

For example:

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 101;
```

The execution plan helps determine whether the index actually improves the query.

> **Creating an index without checking its real effect is not a complete optimization process.**

---

# Practical Index-Selection Process

A practical workflow looks like this:

```text
Identify slow/frequent queries
            ↓
Look at WHERE / JOIN / ORDER BY patterns
            ↓
Check selectivity and data distribution
            ↓
Consider composite indexes
            ↓
Check INSERT/UPDATE/DELETE workload
            ↓
Create the index
            ↓
EXPLAIN / EXPLAIN ANALYZE
            ↓
Measure with realistic data
            ↓
Keep, modify, or remove the index
```

This is better than blindly adding indexes.

---

# Example: Complete Decision

Suppose an application frequently runs:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01'
ORDER BY order_date;
```

You might consider:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

Why?

```text
WHERE customer_id
        +
WHERE order_date
        +
ORDER BY order_date
        ↓
Composite index candidate
```

But you should then verify the execution plan:

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01'
ORDER BY order_date;
```

Then compare performance with realistic production-like data.

---

# Important: Index Design Is Workload-Dependent

There are no universal rules such as:

> ❌ "Index every foreign key."

> ❌ "Index every column used in WHERE."

> ❌ "More indexes always mean faster queries."

These can be useful **starting considerations**, but the correct indexing strategy depends on the workload.

For example:

```text
Read-heavy system
→ More indexes may be acceptable

Write-heavy system
→ Too many indexes may become expensive

Large table + selective query
→ Index may be highly beneficial

Small table
→ Sequential scan may already be cheaper
```

---

# Common Mistakes

### ❌ Mistake 1: Index every column

More indexes increase storage and write-maintenance costs.

### ❌ Mistake 2: Assume every `WHERE` column needs an index

The optimizer may determine that a scan is cheaper.

### ❌ Mistake 3: Ignore column order in composite indexes

For B-tree indexes, the leading columns are particularly important.

### ❌ Mistake 4: Ignore write workload

An index that helps a read-heavy query can still be costly on a heavily written table.

### ❌ Mistake 5: Create an index without measuring

Always validate important indexing decisions using execution plans and realistic benchmarks.

---

## Interview Takeaway

> **I decide which columns to index by analyzing real query patterns, especially `WHERE`, `JOIN`, `ORDER BY`, and range conditions; considering selectivity, composite-index column order, read/write workload, and storage cost; and then validating the decision using execution plans and realistic performance measurements.**
