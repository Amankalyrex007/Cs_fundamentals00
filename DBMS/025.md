# Q25. Why Can Adding More Indexes Make Writes Slower?

Indexes improve **read performance**, but they also have to be maintained whenever the underlying table changes.

Therefore:

```text
More Indexes
     ↓
More Index Maintenance
     ↓
Higher Write Cost
```

---

## Example

Suppose we have:

```text
users

+-----+--------+-------------------+-----------+
| id  | name   | email             | city      |
+-----+--------+-------------------+-----------+
| 101 | Aaman  | aaman@example.com  | Gorakhpur |
| 102 | Rahul  | rahul@example.com  | Lucknow   |
+-----+--------+-------------------+-----------+
```

And we create three indexes:

```text
Index 1 → id
Index 2 → email
Index 3 → city
```

Now consider:

```sql id="gq9t6h"
INSERT INTO users
VALUES (103, 'Priya', 'priya@example.com', 'Delhi');
```

The database must perform the table insertion and maintain the relevant indexes.

Conceptually:

```text id="3c4h7y"
                 INSERT
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
   Update Table  Update      Update
                Index 1     Index 2
                  │
                Update
                Index 3
```

So the database may need to:

1. Insert the row into the table.
2. Add the corresponding entry to the `id` index.
3. Add an entry to the `email` index.
4. Add an entry to the `city` index.

Therefore:

> **The more indexes affected by a write, the more index-maintenance work the database may have to perform.**

---

# Why Does Index Maintenance Cost Time?

An index is itself a data structure.

When a row is inserted or modified, the database may need to:

```text id="wzj6mw"
Locate the correct index position
          ↓
Insert/update the index entry
          ↓
Potentially reorganize index pages
          ↓
Write changes to memory/storage
```

For tree-based indexes, inserting a value can sometimes cause additional structural work, such as page splits.

The exact behavior depends on the database engine and index type.

---

# UPDATE Can Be Even More Expensive

Consider:

```sql id="zv47tj"
UPDATE users
SET email = 'new@example.com'
WHERE id = 101;
```

If `email` is indexed, the database has to maintain the index entry corresponding to the changed value.

Conceptually:

```text id="w5z2hv"
Old email
    ↓
Find old index entry
    ↓
Remove/update old entry
    ↓
Add new index entry
```

If an update changes multiple indexed columns:

```sql id="j5o0s0"
UPDATE users
SET email = 'new@example.com',
    city = 'Delhi'
WHERE id = 101;
```

then multiple indexes may require maintenance:

```text id="7f9mps"
UPDATE
  │
  ├── Table
  ├── Email Index
  └── City Index
```

Therefore, updating indexed columns can be more expensive than updating non-indexed columns.

---

# DELETE Also Requires Maintenance

When a row is deleted:

```sql id="1j15of"
DELETE FROM users
WHERE id = 101;
```

the database must remove the corresponding entries from the relevant indexes as well.

Conceptually:

```text id="5v0h6a"
DELETE row
    │
    ├── Remove from table
    ├── Remove from Index 1
    ├── Remove from Index 2
    └── Remove from Index 3
```

So `DELETE` operations also carry index-maintenance costs.

---

# What Costs Are Involved?

Additional indexes can increase several types of resource usage:

| Cost                      | Effect                                      |
| ------------------------- | ------------------------------------------- |
| **CPU work**              | Maintaining index structures                |
| **Disk I/O**              | Writing index changes                       |
| **Memory/cache pressure** | Indexes consume buffer/cache space          |
| **Storage**               | Each index requires additional space        |
| **Locking/contention**    | May increase depending on DBMS and workload |

The exact impact varies by database engine, hardware, workload, and index type.

---

# Important Nuance

It does **not** mean:

> ❌ "Every additional index makes every write slower by exactly the same amount."

The actual impact depends on:

* Which indexes are affected
* Index type and structure
* Number of indexes
* Table size
* Write frequency
* Database engine
* Hardware
* Memory/cache behavior
* Overall workload

For example, an update to a column that is not indexed may not require modification to unrelated indexes.

---

# Practical Example

Suppose a production table has:

```text id="p3qkz7"
Users
 ├── Index on id
 ├── Index on email
 ├── Index on city
 ├── Index on phone
 ├── Index on username
 ├── Index on status
 ├── Index on created_at
 └── Index on last_login
```

Now imagine the application performs:

```text
50,000 INSERTs/hour
```

Every insert may require maintaining several index structures.

If only two indexes provide meaningful benefits for the application's important queries:

```text id="5z4y8p"
8 indexes
   ↓
2 useful indexes
+
6 potentially unnecessary indexes
```

The additional indexes may provide little read benefit while still imposing storage and maintenance costs.

Therefore:

> **Production systems generally aim for useful indexes rather than the maximum possible number of indexes.**

---

# Read Performance vs Write Performance

Indexes create a fundamental trade-off:

```text id="a1f3n2"
             INDEX
                │
       ┌────────┴────────┐
       ↓                 ↓
 Faster Reads       Slower Writes
       │                 │
    SELECT           INSERT
    JOIN             UPDATE
    ORDER BY         DELETE
    SEARCH           Maintenance
```

For a **read-heavy** application, additional indexes may be worthwhile.

For a **write-heavy** application, excessive indexes can become expensive.

The goal is to find the right balance.

---

# Important Interview Point

An index is not simply a read optimization.

It is a data structure that must be maintained as the underlying data changes.

Therefore:

```text id="yby9kl"
INSERT / UPDATE / DELETE
          ↓
     Table changes
          +
    Index maintenance
          ↓
   Additional write cost
```

---

## Common Interview Mistakes

### ❌ Mistake 1: "Indexes only affect SELECT queries."

False.

Indexes can also affect the cost of `INSERT`, `UPDATE`, and `DELETE`.

### ❌ Mistake 2: "Every index must be updated for every write."

Not necessarily.

Only indexes affected by the changed data need relevant maintenance, and the exact behavior depends on the operation and DBMS.

### ❌ Mistake 3: "More indexes always improve performance."

False.

They may improve some reads while increasing write, storage, and maintenance costs.

### ❌ Mistake 4: "All index updates have the same cost."

False.

Index type, size, structure, workload, and database engine all influence the cost.

---

## Interview Takeaway

> **Adding indexes can make writes slower because `INSERT`, `UPDATE`, and `DELETE` operations may need to maintain the affected index structures. More indexes can therefore mean more CPU work, storage, memory/cache usage, and potentially I/O, creating a fundamental read-performance vs write-performance trade-off.**

### One-Line Memory Trick

```text id="h2r4wc"
More Indexes
     ↓
Faster Potential Reads
     +
More Write Maintenance
     ↓
Read ↔ Write Trade-off
```
