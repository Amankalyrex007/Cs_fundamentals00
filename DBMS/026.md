26.How would you optimize a slow SQL query?
I would measure first rather than immediately adding indexes. The goal is to identify where the query is actually spending time.

Step-by-step approach
1. Reproduce and measure the problem

First, run the query with realistic data and measure:

Execution time
Number of rows returned
Frequency of execution
CPU/I/O usage if available

A query that takes 2 seconds but runs once a day is different from one that takes 200 ms but runs thousands of times per second.

2. Inspect the execution plan

Use:

EXPLAIN

or, where appropriate:

EXPLAIN ANALYZE

Look for expensive operations such as:

Full/sequential table scans
Inefficient joins
Large sorts
Excessive rows being processed
Poor join strategies
Missing or unused indexes
Large intermediate result sets

For example:

EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 101;

The execution plan tells you how the database actually executed the query, rather than how you expect it to execute.

3. Check indexes

If the query frequently filters on:

WHERE customer_id = ?

an appropriate index may help:

CREATE INDEX idx_orders_customer
ON orders(customer_id);

For queries using multiple columns, consider a composite index:

CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);

But don't blindly add indexes. They consume storage and can make writes more expensive.

4. Reduce unnecessary data

Avoid:

SELECT *
FROM orders;

when you only need a few columns:

SELECT order_id, order_date, total
FROM orders;

Also reduce unnecessary rows using appropriate filtering:

WHERE customer_id = 101

rather than retrieving the entire table and filtering in application code.

5. Optimize JOINs

Check whether joins are using appropriate keys and indexes.

For example:

SELECT o.order_id, c.name
FROM orders o
JOIN customers c
  ON o.customer_id = c.id
WHERE o.customer_id = 101;

Make sure the join/filter columns are appropriate for the workload and inspect the execution plan to verify the chosen strategy.

6. Avoid unnecessary operations

Look for things such as:

Unnecessary joins
Repeated subqueries
Unnecessary DISTINCT
Expensive sorting
Functions applied to columns in filtering conditions where they prevent effective index usage
Returning far more rows than the application needs

For example, instead of:

SELECT *
FROM users
WHERE LOWER(email) = 'aaman@example.com';

depending on the DBMS and requirements, consider an appropriate functional/expression index or a schema/query design that supports the lookup efficiently.

7. Consider pagination

If an application displays thousands of rows, don't retrieve everything at once.

For example:

SELECT order_id, order_date
FROM orders
ORDER BY order_date DESC
LIMIT 50;

For very large datasets, keyset/cursor pagination can sometimes scale better than large OFFSET values.

8. Check whether the query is actually the bottleneck

Sometimes the SQL itself isn't the main problem.

Investigate:

Application
    ↓
Connection pool
    ↓
Database
    ↓
Disk / memory / CPU

Potential causes include:

Connection-pool exhaustion
Lock contention
Missing statistics
Insufficient memory
Disk I/O bottlenecks
Blocking transactions
Database server resource saturation
9. Re-test after every meaningful change

After changing an index or rewriting a query:

Measure
   ↓
EXPLAIN / EXPLAIN ANALYZE
   ↓
Change
   ↓
Measure again

Compare execution time and resource usage using realistic workload/data.

Don't assume that a theoretically better query is actually faster.

Practical example

Suppose this query is slow:

SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01'
ORDER BY order_date DESC;

I would investigate:

Execution plan.
How many rows are scanned.
Whether an appropriate composite index exists.
Whether the query really needs every column.
Whether sorting is expensive.
Whether the table has a large amount of data.
Whether locks or other database resources are causing the delay.

A potentially useful index could be:

CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);

But I would verify its benefit with the execution plan and actual workload, rather than assuming it is optimal.

Interview answer

I would first reproduce and measure the slow query, then inspect its execution plan using EXPLAIN/EXPLAIN ANALYZE. I would look for full scans, inefficient joins, expensive sorting, excessive rows, and missing or ineffective indexes. Then I would optimize indexes, query structure, selected columns, filtering, joins, and pagination as appropriate. Finally, I would re-measure under realistic data and workload to verify that the change actually improved performance without creating excessive write or resource costs.
