# Q26. How Would You Optimize a Slow SQL Query?

I would **measure first rather than immediately adding indexes**.

The goal is to identify **where the query is actually spending time** and then make a targeted optimization.

```text
Slow Query
    ↓
Measure
    ↓
Execution Plan
    ↓
Find Bottleneck
    ↓
Optimize
    ↓
Measure Again
```

---

# Step-by-Step Approach

## 1. Reproduce and Measure the Problem

First, run the query with realistic data and measure:

* Execution time
* Number of rows returned
* Frequency of execution
* CPU/I/O usage, if available

For example:

```text
Query A → 2 seconds, runs once per day
Query B → 200 ms, runs 10,000 times per second
```

Query B may have a much larger overall performance impact.

Therefore:

> **Query latency alone is not enough; frequency and resource consumption also matter.**

---

# 2. Inspect the Execution Plan

Use:

```sql
EXPLAIN
```

or, where appropriate:

```sql
EXPLAIN ANALYZE
```

Look for expensive operations such as:

* Full/sequential table scans
* Inefficient joins
* Large sorts
* Excessive rows being processed
* Poor join strategies
* Missing or unused indexes
* Large intermediate result sets

For example:

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 101;
```

The execution plan tells you **how the database actually executed the query**, rather than how you expect it to execute.

Conceptually:

```text
Query
  ↓
Optimizer
  ↓
Execution Plan
  ↓
Scan / Index / Join / Sort
  ↓
Result
```

---

# 3. Check Indexes

If the query frequently filters on:

```sql
WHERE customer_id = ?
```

an appropriate index may help:

```sql
CREATE INDEX idx_orders_customer
ON orders(customer_id);
```

For queries using multiple columns, consider a composite index:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

However:

> **Do not blindly add indexes.**

Indexes consume:

* Storage
* CPU
* Memory/cache
* Write performance
* Maintenance resources

Always verify that the index actually improves the workload.

---

# 4. Reduce Unnecessary Data

Avoid:

```sql
SELECT *
FROM orders;
```

when you only need a few columns:

```sql
SELECT order_id, order_date, total
FROM orders;
```

This can reduce the amount of data the database needs to read and return.

Also reduce unnecessary rows using appropriate filtering:

```sql
SELECT order_id, total
FROM orders
WHERE customer_id = 101;
```

This is generally better than retrieving the entire table and filtering it in application code.

---

# 5. Optimize JOINs

Check whether joins are using appropriate keys and indexes.

For example:

```sql
SELECT o.order_id, c.name
FROM orders o
JOIN customers c
  ON o.customer_id = c.id
WHERE o.customer_id = 101;
```

Investigate:

* Join columns
* Filtering conditions
* Available indexes
* Number of rows entering the join
* Join strategy selected by the optimizer

Then verify the result using the execution plan.

```text
Orders
  ↓
Filter customer_id
  ↓
Join Customers
  ↓
Return required columns
```

The important point is not simply "add an index to every join column," but to determine whether the index and join strategy actually help the workload.

---

# 6. Avoid Unnecessary Operations

Look for:

* Unnecessary joins
* Repeated subqueries
* Unnecessary `DISTINCT`
* Expensive sorting
* Returning more rows than necessary
* Functions applied to columns in filtering conditions that prevent effective index usage

For example:

```sql
SELECT *
FROM users
WHERE LOWER(email) = 'aaman@example.com';
```

Depending on the DBMS and requirements, this may prevent a normal index on `email` from being used effectively.

Possible solutions include an appropriate **functional/expression index** or a schema/query design that supports the lookup efficiently.

The correct solution depends on the database system.

---

# 7. Consider Pagination

If an application displays thousands of rows, don't retrieve everything at once.

For example:

```sql
SELECT order_id, order_date
FROM orders
ORDER BY order_date DESC
LIMIT 50;
```

This limits the number of rows returned.

For very large datasets, **keyset/cursor pagination** can sometimes scale better than large `OFFSET` values.

### Offset Pagination

```sql
SELECT order_id, order_date
FROM orders
ORDER BY order_id
LIMIT 50 OFFSET 100000;
```

Large offsets can require the database to process or skip many rows.

### Keyset Pagination

Conceptually:

```sql
SELECT order_id, order_date
FROM orders
WHERE order_id < 100000
ORDER BY order_id DESC
LIMIT 50;
```

The exact implementation depends on the query and ordering columns.

---

# 8. Check Whether the Query Is Actually the Bottleneck

Sometimes the SQL itself isn't the main problem.

A request may flow through:

```text
Application
     ↓
Connection Pool
     ↓
Database
     ↓
CPU / Memory / Disk
```

Potential causes include:

* Connection-pool exhaustion
* Lock contention
* Missing or stale statistics
* Insufficient memory
* Disk I/O bottlenecks
* Blocking transactions
* Database server resource saturation

For example, a query that normally takes `50 ms` might take `2 seconds` because it is waiting for a lock.

In that case, rewriting the SQL may not solve the real problem.

---

# 9. Re-Test After Every Meaningful Change

After changing an index or rewriting a query:

```text
Measure
   ↓
EXPLAIN / EXPLAIN ANALYZE
   ↓
Make Change
   ↓
Measure Again
   ↓
Compare Results
```

Compare:

* Execution time
* Rows processed
* CPU usage
* I/O
* Execution plan
* Resource consumption

Use realistic data and workload whenever possible.

> **Don't assume that a theoretically better query is actually faster.**

# Practical Example

Suppose this query is slow:

```sql
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01'
ORDER BY order_date DESC;
```

I would investigate:

### 1. Execution plan

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 101
  AND order_date >= '2026-01-01'
ORDER BY order_date DESC;
```

### 2. Rows being scanned

Is the database scanning millions of rows to return only a few hundred?

### 3. Index availability

Is there an appropriate composite index?

A potentially useful candidate is:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

### 4. Selected columns

Does the application really need:

```sql
SELECT *
```

or only:

```sql
SELECT order_id, order_date, total
```

### 5. Sorting

Is the database performing an expensive sort?

### 6. Database resources

Could locks, CPU, memory, or disk I/O be causing the delay?

Then I would re-run the query and compare the execution plan and real performance.

# Important Interview Point

SQL optimization is **not simply "add an index."**

A slow query can be caused by:

```text
Bad query structure
        +
Missing/ineffective indexes
        +
Inefficient joins
        +
Too much data
        +
Expensive sorting
        +
Poor statistics
        +
Locks/contention
        +
Hardware/resource limitations
```

Therefore, optimization should start with **measurement and diagnosis**.

---

# Common Mistakes

### ❌ Mistake 1: Immediately add indexes

Indexes can help, but they are not the solution to every slow query.

### ❌ Mistake 2: Use `SELECT *` everywhere

Returning unnecessary columns increases data processing and transfer.

### ❌ Mistake 3: Ignore the execution plan

Without the plan, you may optimize the wrong part of the query.

### ❌ Mistake 4: Optimize only SQL syntax

The real bottleneck may be locks, I/O, CPU, memory, or connection pooling.

### ❌ Mistake 5: Assume the optimized query is faster

Always measure before and after the change.

### ❌ Mistake 6: Ignore write-side costs

A new index may improve a read query but increase `INSERT`, `UPDATE`, and `DELETE` costs.

```text
☐ Check indexes

☐ Improve filtering
☐ Check sorting
☐ Consider pagination
☐ Check locks and resource usage

```

## Interview Takeaway

> **I would first reproduce and measure the slow query, then inspect its execution plan using `EXPLAIN` or `EXPLAIN ANALYZE`. I would look for full scans, inefficient joins, expensive sorting, excessive rows, and missing or ineffective indexes. Then I would optimize indexes, query structure, selected columns, filtering, joins, and pagination as appropriate. Finally, I would re-measure under realistic data and workload to verify that the change actually improved performance without creating excessive write or resource costs.**
