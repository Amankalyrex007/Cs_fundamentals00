27.What is EXPLAIN/ query execution plan?
A query execution plan is the strategy chosen by the database to execute a SQL query.

EXPLAIN is a command that lets you inspect that plan before or without actually executing the query, depending on the database.

It helps answer:

How will the database execute this query, and what operations will it perform?

Example

Suppose we have:

SELECT *
FROM orders
WHERE customer_id = 101;

We can inspect its plan:

EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 101;

The database may show something conceptually like:

Index Scan
  ↓
idx_orders_customer
  ↓
Matching rows

This tells us that the database plans to use an index rather than scanning the entire table.

What does an execution plan contain?

Depending on the database, it can show information such as:

Scan method
Sequential/full table scan
Index scan
Index-only scan
Join strategy
Nested loop
Hash join
Merge join
Estimated rows
Estimated cost
Sorting
Filtering
Aggregations
Actual execution time and rows, when using an EXPLAIN ANALYZE-type command
EXPLAIN vs EXPLAIN ANALYZE

A common distinction is:

EXPLAIN
SELECT ...

shows the planned execution strategy and estimates.

Where supported:

EXPLAIN ANALYZE
SELECT ...

actually executes the query and reports information about what happened, including actual timing and row counts.

This makes EXPLAIN ANALYZE particularly useful when debugging a slow query, but you should remember that it actually runs the statement. For writes, use the database-specific options carefully if you only want to inspect the plan without changing data.

Example of diagnosing a slow query

Suppose:

SELECT *
FROM orders
WHERE customer_id = 101;

The plan shows:

Sequential Scan on orders
Rows examined: 10,000,000
Rows returned: 50

That may indicate that the database is examining a large amount of data to return relatively few rows.

After creating an appropriate index:

CREATE INDEX idx_orders_customer
ON orders(customer_id);

the plan might instead show:

Index Scan using idx_orders_customer
Rows examined: ~50
Rows returned: 50

The exact plan depends on the DBMS, statistics, data distribution, and cost model.

What should you look for in a plan?

When optimizing a slow query, pay attention to:

Full/sequential table scans on large tables.
Whether expected indexes are actually being used.
Estimated vs actual rows when actual execution information is available.
Expensive joins.
Large sorts or aggregations.
Operations processing far more rows than ultimately returned.
Actual execution time and I/O, where available.
Important interview point

An execution plan is not simply a list of indexes being used. It represents the database's complete strategy for executing the query, including scans, joins, filtering, sorting, aggregation, and other operations.

Interview takeaway

EXPLAIN shows the database's planned execution strategy for a SQL query. By analyzing the execution plan, we can identify inefficient scans, joins, sorting, filtering, and index usage and use that information to optimize slow queries. EXPLAIN ANALYZE, where supported, additionally executes the query and provides actual execution information.
