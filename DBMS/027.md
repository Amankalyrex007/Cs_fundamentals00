# Q27. What Is EXPLAIN / Query Execution Plan?

A **query execution plan** is the strategy chosen by the database to execute a SQL query.

`EXPLAIN` is a command that lets you inspect that plan **without actually executing the query**, depending on the database system and command variant.

It helps answer:

> **How will the database execute this query, and what operations will it perform?**

---

# Example

Suppose we have:

```sql id="t3xvwx"
SELECT *
FROM orders
WHERE customer_id = 101;
```

We can inspect its execution plan using:

```sql id="v8q0ch"
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 101;
```

The database may show something conceptually like:

```text id="f4t0qk"
Index Scan
     ↓
idx_orders_customer
     ↓
Matching rows
```

This indicates that the database plans to use an index rather than scanning the entire table.

However, the exact output and terminology depend on the DBMS.

---

# What Does an Execution Plan Contain?

Depending on the database, an execution plan can show information such as:

### Scan Method

* Sequential/full table scan
* Index scan
* Index-only scan
* Other engine-specific access methods

### Join Strategy

* Nested Loop
* Hash Join
* Merge Join

### Other Operations

* Filtering
* Sorting
* Aggregation
* Grouping
* Materialization
* Subqueries

### Cost and Row Estimates

* Estimated cost
* Estimated rows
* Estimated execution time, where supported

### Actual Execution Information

When using an `EXPLAIN ANALYZE`-type command, the plan may additionally include:

* Actual execution time
* Actual rows
* Loop counts
* Actual vs estimated row counts
* I/O information, depending on the DBMS

---

# EXPLAIN vs EXPLAIN ANALYZE

A common distinction is:

### `EXPLAIN`

```sql id="g5t1cj"
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 101;
```

Typically shows the **planned execution strategy and estimates**.

### `EXPLAIN ANALYZE`

Where supported:

```sql id="8g1i5q"
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 101;
```

Actually executes the query and reports information about what happened, including actual timing and row counts.

This makes `EXPLAIN ANALYZE` particularly useful when debugging slow queries.

> **Important:** `EXPLAIN ANALYZE` actually runs the statement. For `INSERT`, `UPDATE`, or `DELETE`, use database-specific options carefully if you only want to inspect the plan without changing data.

---

# Example: Diagnosing a Slow Query

Suppose:

```sql id="kqq6o1"
SELECT *
FROM orders
WHERE customer_id = 101;
```

The plan might show:

```text id="p1t0t3"
Sequential Scan on orders
Rows examined: 10,000,000
Rows returned: 50
```

This could indicate that the database is examining a very large amount of data to return relatively few rows.

We might investigate whether an appropriate index would help:

```sql id="hlc5sh"
CREATE INDEX idx_orders_customer
ON orders(customer_id);
```

The new plan might instead show something conceptually like:

```text id="uv9lqc"
Index Scan using idx_orders_customer
Rows examined: ~50
Rows returned: 50
```

However, this is only an illustrative example.

The actual plan depends on:

* DBMS
* Statistics
* Data distribution
* Table size
* Index structure
* Query shape
* Cost model

The optimizer may still choose a sequential scan if it estimates that to be cheaper.

---

# Estimated Rows vs Actual Rows

One particularly useful part of an execution plan is comparing **estimated rows** with **actual rows**.

For example:

```text id="gl72cr"
Estimated rows: 50
Actual rows:    50
```

This is generally a good sign that the optimizer's statistics are reasonably accurate for that operation.

But suppose:

```text id="t1r2p3"
Estimated rows: 50
Actual rows:    500,000
```

That's a major difference.

A large estimation error can lead the optimizer to choose an inefficient join strategy or access method.

Therefore:

> **Large differences between estimated and actual rows can be an important clue when diagnosing query performance.**

---

# What Should You Look for in a Plan?

When optimizing a slow query, pay attention to:

### 1. Full/Sequential Table Scans

Especially on very large tables.

```text id="6sk1ju"
Sequential Scan
      ↓
Millions of rows
      ↓
Only a few rows returned
```

This may indicate an opportunity for optimization, although a sequential scan is not automatically bad.

---

### 2. Whether Expected Indexes Are Used

If you created an index expecting it to help, check whether the optimizer actually uses it.

```text id="2g3r3k"
Expected:
Index Scan

Actual:
Sequential Scan
```

This does not automatically mean the optimizer is wrong; the index may genuinely be more expensive for that query.

---

### 3. Estimated vs Actual Rows

Look for large differences:

```text id="m1dykn"
Estimated: 100
Actual:    500,000
```

Such discrepancies can indicate inaccurate or outdated statistics or other estimation challenges.

---

### 4. Expensive Joins

Look for operations such as:

```text id="8h29ll"
Nested Loop
Hash Join
Merge Join
```

and examine how many rows are entering and leaving each join.

A join processing millions of unnecessary rows may be a major bottleneck.

---

### 5. Large Sorts or Aggregations

For example:

```text id="5kly1x"
Sort
 ↓
Millions of rows
 ↓
ORDER BY
```

or:

```text id="t4q9y2"
Aggregation
 ↓
Large intermediate result
```

These operations can consume substantial CPU or memory.

---

### 6. Operations Processing Too Many Rows

Suppose:

```text id="h7i0cz"
Rows processed: 5,000,000
Rows returned:      50
```

The large difference may indicate that filtering or access could be improved.

---

### 7. Actual Execution Time and I/O

Where available, examine:

* Actual execution time
* CPU usage
* I/O
* Buffer/cache activity
* Rows processed

This helps identify where the query actually spends its resources.

---

# How an Execution Plan Helps Optimization

The optimization process can be visualized as:

```text id="5t3mby"
Slow Query
    ↓
EXPLAIN / EXPLAIN ANALYZE
    ↓
Execution Plan
    ↓
Identify Bottleneck
    ├── Scan
    ├── Join
    ├── Sort
    ├── Filter
    └── Aggregation
    ↓
Make Targeted Change
    ↓
Run Plan Again
    ↓
Compare Results
```

This is much better than blindly adding indexes or rewriting SQL without understanding the bottleneck.

---

# Important Interview Point

An execution plan is **not simply a list of indexes being used**.

It represents the database's **complete strategy for executing the query**, including:

```text id="jywz75"
Scan
 ↓
Filter
 ↓
Join
 ↓
Sort
 ↓
Aggregate
 ↓
Return Results
```

It can also contain estimates and, with an `EXPLAIN ANALYZE`-type command, actual execution information.

---

# Common Interview Mistakes

### ❌ Mistake 1: "EXPLAIN always executes the query."

Not generally.

`EXPLAIN` typically shows the plan without executing it, while `EXPLAIN ANALYZE` executes the statement in systems that support it.

### ❌ Mistake 2: "A sequential scan is always bad."

False.

For a small table or a query returning a large percentage of rows, a sequential scan may be cheaper than an index scan.

### ❌ Mistake 3: "If an index exists, the optimizer must use it."

False.

The optimizer chooses the plan it estimates to be cheapest.

### ❌ Mistake 4: "The execution plan only shows indexes."

False.

It can show scans, joins, filters, sorting, aggregation, row estimates, costs, and actual execution information.

---

## Interview Takeaway

> **`EXPLAIN` shows the database's planned execution strategy for a SQL query. By analyzing the execution plan, we can identify inefficient scans, joins, sorting, filtering, row estimates, and index usage and use that information to optimize slow queries. `EXPLAIN ANALYZE`, where supported, additionally executes the query and provides actual execution information.**

### One-Line Memory Trick

```text id="u6m7fa"
EXPLAIN
   ↓
"What plan will the database use?"

EXPLAIN ANALYZE
   ↓
"What actually happened when it ran?"
```
