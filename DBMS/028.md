28.SQL vs NoSQL — when would you choose each?
SQL and NoSQL are different approaches to storing and querying data. The choice should depend on the application's data model, consistency requirements, query patterns, scale, and operational needs, not simply on which database is considered “faster.”

SQL databases

SQL databases are typically relational databases that organize data into tables with defined relationships.

Examples:

PostgreSQL
MySQL
Microsoft SQL Server
Oracle Database

Example:

Customers
----------------
id | name | email

Orders
----------------
id | customer_id | amount

Relationships can be represented using foreign keys and queried using SQL and joins.

When would you choose SQL?

Choose a relational database when you need:

Strong transactional guarantees
Banking
Payments
Order processing
Complex relationships
Many-to-many relationships
Multiple related entities
Complex joins
Structured and well-defined data
When the schema and relationships are reasonably stable.
Strong data integrity
Primary keys
Foreign keys
Unique constraints
Check constraints
Complex querying and reporting
Aggregations
Joins
Filtering
Grouping
NoSQL databases

NoSQL is a broad category of databases that don't primarily use the traditional relational table model.

Common types include:

Type	Example
Document	MongoDB
Key-value	Redis
Wide-column	Cassandra
Graph	Neo4j

A document database might store:

{
  "id": 101,
  "name": "Aaman",
  "orders": [
    {"id": 1, "amount": 500},
    {"id": 2, "amount": 900}
  ]
}
When would you choose NoSQL?

NoSQL can be useful when:

The data structure is flexible or evolving
Different records may have different fields.
The application naturally maps to a document/key-value/graph model
For example, document-oriented application data.
Very large-scale distributed workloads are required
Some NoSQL systems are designed for horizontal scaling across many nodes.
The access patterns are known and specialized
For example, simple key-based lookups.
Very high write/read throughput is required
Depending on the particular NoSQL database and workload.
SQL vs NoSQL
Aspect	SQL	NoSQL
Data model	Relational/tables	Document, key-value, wide-column, graph, etc.
Schema	Usually structured/schema-defined	Often more flexible
Relationships	Strong support for relationships and joins	Varies significantly by database
Transactions	Strong transaction support	Varies by database
Querying	SQL, powerful relational queries	Database-specific APIs/query languages
Scaling	Can scale vertically and horizontally depending on DB	Many systems emphasize horizontal/distributed scaling
Best fit	Structured relational data and complex transactions/queries	Flexible, distributed, specialized access patterns
Important interview point

Don't say:

"SQL is for small data and NoSQL is for big data."

That's an oversimplification.

Modern SQL databases can handle very large systems, and NoSQL databases can also support transactions and structured data depending on the product.

The choice should be based on requirements and workload.

Example decision

Suppose you're building a banking transaction system:

Account
   ↓
Transaction
   ↓
Payment

There are strong consistency, integrity, relationships, and transactional requirements. A relational database may fit naturally.

For a system storing flexible product/catalog documents where different products have substantially different attributes, a document database may be a natural option.

Interview answer

I would choose SQL when the application has structured relational data, strong integrity and transaction requirements, and complex joins or queries. I would consider NoSQL when the data model is naturally document/key-value/wide-column/graph based, the schema needs flexibility, or the workload has distributed scaling and specialized access-pattern requirements. I would make the decision based on workload and requirements rather than assuming one is universally better.
