29.What are common database scaling strategies?
Database scaling means increasing a database system's ability to handle more data, queries, users, and traffic while maintaining acceptable performance and reliability.

The main strategies are vertical scaling, read replicas, partitioning, sharding, caching, and workload separation.

1. Vertical scaling (Scale Up)

Increase the resources of the database server:

CPU ↑
RAM ↑
Storage/IOPS ↑

For example, moving from a server with 16 GB RAM to one with 64 GB RAM.

Advantages:

Simple to implement.
Usually requires fewer application changes.

Limitations:

Hardware has practical limits.
Larger machines can become expensive.
Doesn't by itself eliminate a single-server bottleneck.
2. Read replicas

Create additional database replicas that can handle read traffic.

                 ┌── Read Replica 1
Application ────┼── Read Replica 2
                 └── Primary
                       ↑
                  Writes

The primary handles writes, while replicas can serve appropriate read queries.

Useful for:

Read-heavy applications
Reporting workloads
Applications where some read replication lag is acceptable

Important: Replication is often asynchronous, so a replica may temporarily be behind the primary.

3. Caching

Store frequently accessed data in a cache such as Redis.

Application
    ↓
  Cache
  ↙   ↘
Hit    Miss
 ↓       ↓
Return  Database

For example, instead of repeatedly querying the database for the same product information, the application can serve frequently requested data from cache.

Benefit: Reduces database load and can significantly reduce read latency.

Challenge: Cache invalidation and stale data management.

4. Partitioning

Split a large table into smaller partitions while keeping it logically part of the same database table.

For example, partition orders by year:

Orders
├── 2024 partition
├── 2025 partition
└── 2026 partition

A query for 2026 orders may only need to access the relevant partition through partition pruning, depending on the database and query.

Useful for:

Very large tables
Time-series data
Queries that naturally filter by the partition key
Managing large datasets

Partitioning is different from sharding: partitioning can occur within a database system, while sharding typically distributes data across separate database nodes.

5. Sharding (Horizontal Scaling)

Split data across multiple database nodes.

                    Application
                        ↓
                    Shard Router
                   ↙    ↓    ↘
              Shard 1  Shard 2  Shard 3
              Users    Users    Users
              1–1M     1–1M     1–1M

For example, users could be distributed based on user_id.

Advantages:

Can distribute storage and workload across multiple machines.
Can scale beyond the capacity of a single database server.

Challenges:

More operational complexity.
Choosing a good shard key is important.
Cross-shard queries and transactions can be complicated.
Rebalancing data can be difficult.
6. Separate workloads

Don't necessarily make the same database infrastructure handle every workload.

For example:

                    Primary DB
                   /          \
            Application       Replicas
                               ↓
                         Reporting/Analytics

Transactional workloads and analytical/reporting workloads can be separated so heavy reports don't unnecessarily compete with production transactions.

7. Connection pooling

Applications can use a connection pool instead of creating a new database connection for every request.

Application
     ↓
Connection Pool
 ↓   ↓   ↓   ↓
Database connections

This reduces connection establishment overhead and helps control the number of concurrent database connections.

It is more of a database access/scaling optimization than a way to increase database storage capacity.

Putting the strategies together

A production system might use several strategies simultaneously:

                    Users
                      ↓
                 Application
                      ↓
                   Cache
                  ↙     ↘
               Hit       Miss
                ↓          ↓
             Response   DB Layer
                          ↓
                    ┌─────┴─────┐
                 Primary      Replicas
                 (writes)      (reads)
                    ↓
               Partitioned
                 tables

At much larger scale, sharding can be added:

Application
     ↓
Shard Router
  ↙   ↓   ↘
 S1   S2   S3
How would you choose?
Problem	Possible strategy
Server lacks CPU/RAM/IO capacity	Vertical scaling
Too many read requests	Read replicas / caching
Repeatedly accessed data	Caching
Very large tables	Partitioning
Data/workload exceeds one DB node	Sharding
Reporting affects transactional workload	Workload separation
Too many DB connections	Connection pooling
Important interview point

Scaling is not simply "add more database servers."

A good design starts by identifying the bottleneck:

Slow reads?        → Indexes / cache / replicas
Too many writes?   → Query optimization / batching / partitioning / sharding
Huge tables?       → Partitioning / sharding
Too many connections? → Connection pooling
Heavy analytics?   → Separate analytical workload
Insufficient hardware? → Vertical scaling
Interview takeaway

Common database scaling strategies include vertical scaling, read replicas, caching, partitioning, sharding, workload separation, and connection pooling. The appropriate strategy depends on whether the bottleneck is compute, reads, writes, storage, connections, or workload contention.
