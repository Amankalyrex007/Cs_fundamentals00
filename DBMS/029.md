# Q29. What Are Common Database Scaling Strategies?

**Database scaling** means increasing a database system's ability to handle more **data, queries, users, and traffic** while maintaining acceptable performance and reliability.

The main strategies are:

1. **Vertical Scaling**
2. **Read Replicas**
3. **Caching**
4. **Partitioning**
5. **Sharding**
6. **Workload Separation**
7. **Connection Pooling**

---

# 1. Vertical Scaling (Scale Up)

Vertical scaling means increasing the resources of a database server:

```text
CPU      ↑
RAM      ↑
Storage  ↑
IOPS     ↑
```

For example:

```text
Before → 16 GB RAM
After  → 64 GB RAM
```

### Advantages

* Simple to implement
* Usually requires fewer application changes
* Existing database architecture can often remain unchanged

### Limitations

* Hardware has practical limits
* Larger machines can become expensive
* Does not by itself eliminate a single-server bottleneck

### When useful?

When the database is primarily limited by **CPU, RAM, storage, or I/O capacity** and the current architecture can still scale vertically.

---

# 2. Read Replicas

Create additional database replicas that can handle appropriate **read traffic**.

```text
                    ┌── Read Replica 1
                    │
Application ────────┼── Read Replica 2
                    │
                    └── Primary
                         ↑
                       Writes
```

Typically:

* **Primary** → handles writes
* **Replicas** → handle suitable reads

### Useful for

* Read-heavy applications
* Reporting workloads
* Systems where some replication lag is acceptable

For example, an e-commerce website may send product/catalog reads to replicas while order writes go to the primary.

### Important

Replication is often **asynchronous**, so a replica may temporarily be behind the primary.

This means an application may sometimes need to read from the primary when it requires the most current data.

---

# 3. Caching

Frequently accessed data can be stored in a cache such as **Redis**.

```text
Application
     ↓
   Cache
   ↙   ↘
 Hit    Miss
 ↓       ↓
Return  Database
```

For example, instead of repeatedly querying the database for the same product:

```text
Product ID 101
     ↓
Cache
     ↓
Product information
```

### Benefit

* Reduces database load
* Can significantly reduce read latency
* Helps absorb repeated requests

### Challenge

The main challenge is **cache invalidation and stale data management**.

For example, if a product price changes in the database but the old value remains in the cache, users may temporarily see stale information.

---

# 4. Partitioning

**Partitioning** splits a large table into smaller partitions while keeping it logically part of the same database table.

For example, partition orders by year:

```text
Orders
├── 2024 partition
├── 2025 partition
└── 2026 partition
```

A query such as:

```sql
SELECT *
FROM orders
WHERE order_date >= '2026-01-01'
  AND order_date < '2027-01-01';
```

may only need to access the relevant partition through **partition pruning**, depending on the database and query.

### Useful for

* Very large tables
* Time-series data
* Queries that naturally filter by the partition key
* Managing large datasets

### Partitioning vs Sharding

| Partitioning                         | Sharding                                  |
| ------------------------------------ | ----------------------------------------- |
| Data is divided into partitions      | Data is distributed across database nodes |
| Can occur within one database system | Usually involves multiple database nodes  |
| Often transparent to the application | Often requires routing/distribution logic |
| Useful for managing large tables     | Useful for scaling beyond one node        |

> The exact implementation depends on the database system.

---

# 5. Sharding (Horizontal Scaling)

**Sharding** distributes data across multiple database nodes.

```text
                 Application
                      ↓
                 Shard Router
                ↙     ↓     ↘
             Shard 1 Shard 2 Shard 3
             Users   Users   Users
```

For example, users could be distributed based on `user_id`:

```text
Shard 1 → user_id 1–1,000,000
Shard 2 → user_id 1,000,001–2,000,000
Shard 3 → user_id 2,000,001–3,000,000
```

The exact distribution strategy depends on the chosen **shard key**.

### Advantages

* Distributes storage across multiple machines
* Distributes workload
* Can scale beyond the capacity of a single database server

### Challenges

* More operational complexity
* Choosing a good shard key is critical
* Cross-shard queries can be complicated
* Cross-shard transactions can be difficult
* Rebalancing data can be challenging

A poor shard key can create a **hot shard**, where one node receives disproportionately high traffic.

---

# 6. Separate Workloads

A database system does not necessarily need to handle every workload using the same infrastructure.

For example:

```text
                  Primary DB
                 /          \
          Application       Replicas
                              ↓
                       Reporting/
                       Analytics
```

Transactional workloads and analytical/reporting workloads can be separated.

For example, a large report such as:

```sql
SELECT customer_id, SUM(amount)
FROM orders
GROUP BY customer_id;
```

may generate substantial database work.

Running such workloads on separate infrastructure can prevent heavy analytical queries from unnecessarily competing with production transactions.

---

# 7. Connection Pooling

Applications can use a **connection pool** instead of creating a new database connection for every request.

```text
Application
     ↓
Connection Pool
 ↓   ↓   ↓   ↓
DB connections
     ↓
  Database
```

The pool maintains a controlled number of reusable database connections.

### Benefits

* Reduces connection-establishment overhead
* Reuses existing connections
* Helps control the number of concurrent database connections
* Protects the database from excessive connection creation

> Connection pooling is more accurately a **database access/scaling optimization** than a way to increase database storage capacity.

---

# Putting the Strategies Together

A production system might use several strategies simultaneously:

```text
                    Users
                      ↓
                 Application
                      ↓
                   Cache
                  ↙     ↘
               Hit       Miss
                ↓          ↓
             Response   DB Layer
                          ↓
                    ┌─────┴─────┐
                 Primary      Replicas
                 (writes)      (reads)
                    ↓
               Partitioned
                  tables
```

At much larger scale, **sharding** can also be added:

```text
Application
     ↓
Shard Router
  ↙   ↓   ↘
 S1   S2   S3
```

Each shard may then have its own replicas.

---

# How Would You Choose?

| Problem                                  | Possible Strategy                              |
| ---------------------------------------- | ---------------------------------------------- |
| Server lacks CPU/RAM/I/O capacity        | Vertical scaling                               |
| Too many read requests                   | Read replicas / caching                        |
| Repeatedly accessed data                 | Caching                                        |
| Very large tables                        | Partitioning                                   |
| Data/workload exceeds one DB node        | Sharding                                       |
| Reporting affects transactional workload | Workload separation                            |
| Too many DB connections                  | Connection pooling                             |
| Very large distributed workload          | Sharding + replicas, depending on requirements |

The key is to identify the **actual bottleneck** before choosing a scaling technique.

---

# Scaling Should Start With the Bottleneck

```text
Slow reads?
    ↓
Indexes / Cache / Read Replicas

Too many writes?
    ↓
Query optimization / Batching / Partitioning / Sharding

Huge tables?
    ↓
Partitioning / Sharding

Too many connections?
    ↓
Connection Pooling

Heavy analytics?
    ↓
Workload Separation

Insufficient hardware?
    ↓
Vertical Scaling
```

For example, if the real problem is an inefficient SQL query, adding more database servers may not solve the underlying issue.

---

# Important Interview Point

> **Scaling is not simply "add more database servers."**

A good scaling design starts by identifying the bottleneck:

```text
Compute?
Reads?
Writes?
Storage?
Connections?
Network?
Lock contention?
Analytics?
```

Then choose the strategy that addresses that specific bottleneck.

Also remember that scaling techniques can be combined. A large production system may use **vertical scaling + caching + read replicas + partitioning + connection pooling**, and eventually **sharding** if the workload exceeds the capacity of a single database system.

---

# Common Interview Mistakes

### ❌ Mistake 1: "Read replicas handle writes."

Usually the primary handles writes while replicas serve appropriate reads.

### ❌ Mistake 2: "Partitioning and sharding are the same."

They are related but different. Partitioning divides data within a database system; sharding typically distributes data across multiple database nodes.

### ❌ Mistake 3: "Caching completely removes database load."

Caching reduces load for cacheable/hit requests, but cache misses and invalidation still involve the database.

### ❌ Mistake 4: "More replicas automatically solve scaling."

Replicas primarily help with appropriate read workloads. They do not automatically solve write bottlenecks.

### ❌ Mistake 5: "Sharding is always the best solution."

Sharding introduces significant operational and application complexity and should generally be considered when simpler approaches are insufficient.

---

## Interview Takeaway

> **Common database scaling strategies include vertical scaling, read replicas, caching, partitioning, sharding, workload separation, and connection pooling. The appropriate strategy depends on whether the bottleneck is compute, reads, writes, storage, connections, or workload contention.**

### Easy Memory Trick

```text
Scale Up       → Bigger Server
Read Replicas  → More Read Capacity
Cache          → Avoid Repeated DB Reads
Partitioning   → Split Large Tables
Sharding       → Split Across Nodes
Workload Split → Separate Responsibilities
Pooling        → Control Connections
```
