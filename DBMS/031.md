# Q31. What Is Sharding?

**Sharding** is a database scaling technique where a large dataset is split **horizontally** into smaller pieces called **shards**, and each shard is stored on a different database server or node.

Each shard contains a **subset of rows**, but together all shards represent the complete dataset.

```text
Complete Dataset
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
S1    S2    S3
```

Sharding is primarily used when a database needs to scale **beyond the capacity of a single database server**.

---

# Example

Suppose we have a `users` table containing **100 million users**.

Instead of storing all users on one database server:

```text
                    Users Database
                         |
          +--------------+--------------+
          |              |              |
       Shard 1        Shard 2        Shard 3
      Users 1-33M    Users 34-66M    Users 67-100M
```

Each shard stores only part of the total data.

Together:

```text
Shard 1 + Shard 2 + Shard 3
           ↓
   Complete Users Dataset
```

---

# Shard Key

A **shard key** determines which shard should store a particular row.

For example, we might use `user_id`.

A simple conceptual approach could be:

```text
shard = hash(user_id) % 3
```

For example:

```text
user_id
   ↓
Hash function
   ↓
Shard number
```

> The actual sharding algorithm depends on the database system. The example above is only a simple illustration.

---

# Why Is Sharding Used?

The primary purpose of sharding is to **scale beyond the resources of a single database server**.

It can provide:

### 1. More Storage Capacity

Instead of one server storing the entire dataset:

```text
Server 1 → 1 TB
Server 2 → 1 TB
Server 3 → 1 TB
```

The system can distribute the dataset across multiple machines.

---

### 2. Higher Write Throughput

Writes can potentially be distributed across multiple shards:

```text
Application
     ↓
Shard Router
 ↙    ↓    ↘
S1    S2    S3
```

This can reduce the write pressure on any single database node.

The actual improvement depends heavily on the workload and shard-key distribution.

---

### 3. Higher Read Throughput

Reads can also be distributed across shards when the routing layer can determine the appropriate shard.

---

### 4. Horizontal Scaling

Additional database servers can be added as the dataset and workload grow.

```text
Before:

DB Server
   ↓
Large Dataset


After:

DB 1   DB 2   DB 3
 ↓      ↓      ↓
Data   Data   Data
```

---

# How Does a Query Work?

Suppose the application asks:

```sql
SELECT *
FROM users
WHERE user_id = 12345;
```

If `user_id` is the shard key, the routing layer can determine which shard contains the requested user.

```text
Application
     |
     v
Shard Router
     |
     +----> Shard 1
     |
     +----> Shard 2  <-- user_id = 12345
     |
     +----> Shard 3
```

Only the relevant shard may need to be queried.

This is called **targeted routing** or a targeted query.

---

# What If the Shard Key Is Not Provided?

Consider:

```sql
SELECT *
FROM users
WHERE email = 'aaman@example.com';
```

If `email` is not related to the shard key, the routing layer may not know which shard contains the user.

It may need to query multiple shards:

```text
             Query
               ↓
        ┌──────┼──────┐
        ↓      ↓      ↓
      Shard 1 Shard 2 Shard 3
        ↓      ↓      ↓
             Results
                ↓
             Combine
```

This can be more expensive than a targeted query.

Therefore:

> **Shard-key design should consider the application's most important query patterns.**

---

# Sharding vs Partitioning

| Sharding                                                   | Partitioning                                                    |
| ---------------------------------------------------------- | --------------------------------------------------------------- |
| Data is distributed across multiple database servers/nodes | Data is divided into partitions, often within a database system |
| Primarily used for horizontal scaling across machines      | Used for manageability, performance, and sometimes scaling      |
| Adds distributed-system complexity                         | Usually simpler operationally                                   |
| Requires careful shard-key design                          | Requires partition-key design                                   |
| Cross-node operations may be required                      | Operations can often remain within one database system          |

The exact capabilities and terminology depend on the database system.

---

# Main Challenge: Choosing the Shard Key

Choosing a good **shard key** is one of the most important parts of sharding.

A good shard key should generally:

### 1. Distribute Data Reasonably Evenly

Avoid putting most data on one shard.

```text
Good:

Shard 1 → 33%
Shard 2 → 34%
Shard 3 → 33%
```

---

### 2. Avoid Hot Shards

A **hot shard** is a shard that receives a disproportionately large amount of traffic.

For example:

```text
Shard 1 → 10% traffic
Shard 2 → 10% traffic
Shard 3 → 80% traffic  ❌
```

Adding more shards may not solve the bottleneck if most requests continue going to the same shard.

---

### 3. Match Common Query Patterns

If most queries use `user_id`, using `user_id` as the shard key may allow efficient routing.

```text
WHERE user_id = 12345
        ↓
Determine shard
        ↓
Query one shard
```

---

### 4. Avoid Excessive Cross-Shard Queries

Queries that require data from many shards can become more expensive.

For example:

```text
Shard 1 ─┐
Shard 2 ─┼─→ Query Results → Combine
Shard 3 ─┘
```

This can increase latency and application complexity.

---

# Common Sharding Strategies

The exact options depend on the database, but common approaches include:

### Range-Based Sharding

Data is divided into ranges.

```text
Shard 1 → user_id 1–1M
Shard 2 → user_id 1M–2M
Shard 3 → user_id 2M–3M
```

Simple to understand, but poorly chosen ranges can create hotspots.

---

### Hash-Based Sharding

A hash function determines the shard:

```text
hash(user_id) % N
```

This can distribute data relatively evenly.

However, changing the number of shards may require careful data movement or a more sophisticated hashing strategy.

---

# Important Trade-offs

## Advantages

* **Horizontal scalability**
* Larger total storage capacity
* Workload can be distributed across machines
* Can increase read/write capacity for suitable workloads
* Allows datasets larger than one server's practical capacity

## Disadvantages

* More operational complexity
* Cross-shard joins can be difficult or expensive
* Cross-shard transactions are more complicated
* Rebalancing data can be costly
* Poor shard-key choice can create hotspots
* Queries without the shard key may require multiple shards
* Monitoring and failure handling become more complex

---

# Sharding Example: E-Commerce System

Suppose an e-commerce platform has hundreds of millions of users.

A possible architecture is:

```text
                    Application
                         ↓
                    Shard Router
                   ↙     ↓     ↘
                Shard 1 Shard 2 Shard 3
                  ↓       ↓       ↓
               Users    Users    Users
```

If the application receives:

```sql
SELECT *
FROM users
WHERE user_id = 5000123;
```

The router uses the shard-key logic to determine the appropriate shard.

But a query such as:

```sql
SELECT COUNT(*)
FROM users
WHERE country = 'India';
```

may require work across multiple shards if `country` is not part of the routing strategy.

This illustrates an important point:

> **A shard key affects not only where data is stored, but also how efficiently queries can be routed.**

---

# Sharding Is Not Always the First Scaling Step

Before introducing sharding, simpler approaches may sometimes be sufficient:

```text
Optimize Queries
      ↓
Indexes
      ↓
Caching
      ↓
Read Replicas
      ↓
Partitioning
      ↓
Sharding
```

This is not a mandatory sequence, but it illustrates that sharding introduces significant complexity and should match an actual scaling requirement.

---

# Important Interview Point

Don't describe sharding simply as:

> "Splitting a database into multiple tables."

That is incomplete.

Sharding means:

> **Horizontally distributing rows across multiple database servers/nodes according to a shard key.**

The major architectural concern is that the application or database routing layer must know **where the requested data lives**.

---

# Common Interview Mistakes

### ❌ Mistake 1: "Sharding and partitioning are exactly the same."

They are related concepts, but sharding typically distributes data across separate database nodes.

### ❌ Mistake 2: "More shards always means better performance."

Not necessarily.

Poor shard-key distribution or excessive cross-shard operations can create new bottlenecks.

### ❌ Mistake 3: "Any column can be a good shard key."

A shard key should distribute data well and support important query patterns.

### ❌ Mistake 4: "Sharding eliminates database complexity."

The opposite is often true. Sharding introduces distributed-system concerns such as routing, rebalancing, cross-shard operations, and failure handling.

### ❌ Mistake 5: "Every query only touches one shard."

Only targeted queries can often do that. Queries without sufficient shard-key information may require multiple shards.

---

## Interview Takeaway

> **Sharding means horizontally distributing database rows across multiple database servers using a shard key, allowing the database to scale beyond the resources of a single server. Its main benefits are distributed storage and workload capacity, while its major challenges include shard-key design, cross-shard operations, rebalancing, and increased operational complexity.**
