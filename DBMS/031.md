31.What is sharding?

Sharding is a database scaling technique where a large dataset is split horizontally into smaller pieces called shards, and each shard is stored on a different database server.

Each shard contains a subset of the rows, but together all shards represent the complete dataset.

Example

Suppose we have a users table with 100 million users.

Instead of storing all users on one database server:

                    Users Database
                         |
          +--------------+--------------+
          |              |              |
       Shard 1        Shard 2        Shard 3
      Users 1-33M    Users 34-66M    Users 67-100M

A common approach is to use a shard key, such as user_id:

shard = hash(user_id) % 3

This determines which shard stores each user's data.

Why is sharding used?

Primarily to scale beyond the capacity of a single database server.

It can provide:

More storage capacity
Higher write throughput
Higher read throughput, depending on workload and routing
Horizontal scaling by adding more database servers
How does a query work?

Suppose the application asks:

SELECT * FROM users WHERE user_id = 12345;

The application or database routing layer uses the shard key to determine which shard contains that user.

Application
     |
     v
Shard Router
     |
     +----> Shard 1
     |
     +----> Shard 2  <-- user_id = 12345
     |
     +----> Shard 3

Only the relevant shard needs to be queried if the shard key is known.

Sharding vs partitioning
Sharding	Partitioning
Data is distributed across multiple database servers/nodes	Data is divided into partitions, often within a database system
Primarily used for horizontal scaling across machines	Used for manageability and performance, and sometimes scaling
Adds distributed-system complexity	Usually simpler operationally
Requires careful shard-key design	Requires partition-key design

The exact capabilities and terminology depend on the database system.

Main challenge: choosing the shard key

A good shard key should generally:

distribute data reasonably evenly
avoid creating a hot shard
match common query patterns
avoid excessive cross-shard queries

For example, if almost all traffic targets one shard, adding more shards may not solve the bottleneck.

Important tradeoffs

Advantages

Horizontal scalability
Larger total storage capacity
Workload can be distributed across machines

Disadvantages

More operational complexity
Cross-shard joins can be difficult or expensive
Transactions across shards are more complicated
Rebalancing data can be costly
Poor shard-key choice can create hotspots or uneven distribution
Interview takeaway

Sharding means horizontally distributing database rows across multiple database servers using a shard key, so the database can scale beyond the resources of a single server.
