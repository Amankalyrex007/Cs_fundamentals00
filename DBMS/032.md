32.How would you design a database for a large-scale application?

For a large-scale application, I would start from requirements and access patterns, then choose the database architecture and scale it based on measured workload rather than immediately introducing sharding or NoSQL.

1. Understand the requirements

First identify:

What data needs to be stored?
Read/write ratio
Expected traffic and data volume
Query patterns
Transaction requirements
Consistency requirements
Latency requirements
Availability and durability requirements
Geographic distribution
Security and compliance requirements

For example, an e-commerce system may have:

Users
Products
Orders
Payments
Inventory
Reviews
2. Choose the database model

For highly structured transactional data, I would generally start with a relational database such as PostgreSQL or MySQL.

For example:

Users ───< Orders ───< OrderItems >─── Products

A relational database is useful when we need:

Relationships
Constraints
Transactions
Complex queries
Strong data integrity

Other workloads may justify specialized databases:

Requirement	Possible technology
Relational transactions	PostgreSQL / MySQL
Key-value access	Redis / DynamoDB
Document-oriented data	MongoDB
Search	Elasticsearch/OpenSearch
Analytics	Data warehouse/lakehouse

The choice should be driven by the workload rather than simply by expected scale.

3. Design the schema

Start with a normalized schema to maintain data integrity.

For example:

users
-----
id
name
email
created_at

orders
------
id
user_id
status
total_amount
created_at

order_items
-----------
id
order_id
product_id
quantity
price

Use:

Primary keys
Foreign keys where appropriate
Appropriate constraints
Proper data types
Timestamps
Unique constraints for fields such as email when required
4. Add indexes based on query patterns

Don't index every column.

Suppose we frequently execute:

SELECT *
FROM orders
WHERE user_id = 123
ORDER BY created_at DESC;

A composite index could be useful:

CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at);

I would verify the improvement using EXPLAIN / EXPLAIN ANALYZE.

5. Handle high read traffic

If reads become a bottleneck, possible strategies include:

                Application
                    |
              Load Balancer
                    |
          +---------+---------+
          |                   |
       Primary             Cache
          |
    +-----+-----+
    |           |
 Replica 1   Replica 2

Use:

Caching for frequently accessed data
Read replicas for read-heavy workloads
Connection pooling
Query optimization

One important consideration is replication lag. A read replica may temporarily contain older data than the primary.

6. Handle large datasets

As the dataset grows, consider partitioning.

For example, an orders table could be partitioned by date:

orders
  |
  +-- 2026-01
  +-- 2026-02
  +-- 2026-03
  +-- ...

This can make queries and maintenance more manageable when queries naturally filter by the partition key.

If a single database server eventually becomes insufficient, sharding can distribute data across multiple database servers.

                Application
                     |
                Shard Router
             /        |        \
         Shard 1   Shard 2   Shard 3

The shard key must be chosen carefully to avoid hotspots and excessive cross-shard operations.

7. Design for reliability

For production systems, I would consider:

Database replication
Automated backups
Point-in-time recovery where supported
Failover
Disaster recovery
Multi-zone deployment where appropriate
Monitoring and alerting

Replication should not be treated as a replacement for backups because accidental changes can also be replicated.

8. Monitor the database

Monitor metrics such as:

Query latency
Queries per second
CPU and memory
Disk usage
I/O
Connection count
Lock contention
Replication lag
Slow queries
Cache hit rate

For a slow query, I would inspect its execution plan rather than blindly adding indexes.

9. Consider consistency and transactions

For operations such as payments or inventory updates, I would carefully define transaction boundaries and consistency requirements.

For example:

Create Order
     ↓
Reserve Inventory
     ↓
Record Payment
     ↓
Commit

If operations span multiple independent services/databases, a simple single-database transaction may no longer be sufficient. The architecture may require patterns such as sagas, idempotency, and compensating actions, depending on the workflow.

10. Security

I would also include:

Least-privilege database accounts
Encryption in transit
Encryption at rest where required
Secrets management
Audit logging where required
Input validation
Protection against SQL injection through parameterized queries
Appropriate backup access controls
A practical architecture

A large-scale application might eventually look like:

                    Clients
                       |
                  Load Balancer
                       |
                  Application
                       |
             +---------+---------+
             |                   |
           Cache             Database
                               |
                         Primary DB
                        /          \
                  Replica 1      Replica 2
                       
                  Large dataset
                       |

              If necessary → Sharding

        Backups → Object Storage / DR System

The important point is that I would not start with the most complicated architecture. I would start with a well-designed relational database, proper schema and indexes, then introduce caching, replicas, partitioning, and eventually sharding as actual workload and scale require them.

Interview takeaway

For a large-scale database, I would begin with requirements and access patterns, design a correct schema, choose the appropriate database model, add indexes based on measured queries, use caching and replicas for read scaling, partition large datasets, shard when a single database cannot handle the workload, and build in backup, failover, monitoring, security, and disaster recovery from the beginning.
