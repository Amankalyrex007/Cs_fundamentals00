# Q2. What Are the Four Pillars of OOP?

The **four pillars of Object-Oriented Programming (OOP)** are:

1. **Encapsulation**
2. **Abstraction**
3. **Inheritance**
4. **Polymorphism**

These four concepts provide the foundation for designing and organizing object-oriented software.

```text
                 Four Pillars of OOP
                        │
        ┌───────────────┼───────────────┐
        │               │               │
        ▼               ▼               ▼
  Encapsulation    Abstraction     Inheritance
        │                               │
        └───────────────┬───────────────┘
                        ▼
                  Polymorphism
```

---

# 1. Encapsulation

## What is Encapsulation?

**Encapsulation** means bundling **data and the methods that operate on that data** together inside a class, while controlling how the internal data is accessed.

In simple terms:

> **Encapsulation = Keep data and related behavior together + control access to the data.**

### Real-World Example

Consider a bank account.

You should not be able to arbitrarily change your account balance:

```text
balance = -500000
```

Instead, the account should provide controlled operations such as:

```text
deposit()
withdraw()
get_balance()
```

The object controls how its internal state is modified.

---

## Example in Python

```python
class BankAccount:

    def __init__(self):
        self.__balance = 0

    def deposit(self, amount):
        self.__balance += amount

    def get_balance(self):
        return self.__balance


account = BankAccount()

account.deposit(1000)

print(account.get_balance())
```

### Output

```text
1000
```

Here:

```python
self.__balance
```

is intended to be an internal attribute of the class.

The balance is accessed through:

```python
deposit()
get_balance()
```

rather than being directly manipulated by external code.

### Why is Encapsulation Useful?

Encapsulation helps:

* Protect an object's internal state
* Prevent uncontrolled modification
* Keep related data and behavior together
* Define clear interfaces for interacting with objects
* Reduce dependencies between different parts of a program

### Simple Diagram

```text
        BankAccount
             │
     ┌───────┴────────┐
     │                │
   Data            Methods
     │                │
 __balance       deposit()
                 get_balance()
```

---

# 2. Abstraction

## What is Abstraction?

**Abstraction** means exposing the **essential functionality** of an object while hiding unnecessary implementation details.

In simple terms:

> **Abstraction = Show what an object does, hide how it does it.**

### Real-World Example: Car

When you drive a car, you use:

```text
car.start()
car.accelerate()
car.brake()
```

You don't need to understand every internal operation involving:

* Fuel injection
* Engine timing
* Electrical systems
* Sensors
* Transmission
* Internal combustion

You interact with a simple interface while the complicated implementation remains hidden.

```text
User
 │
 ▼
car.start()
 │
 ▼
┌──────────────────────┐
│ Internal Engine      │
│ Implementation       │
│                      │
│ Sensors              │
│ Fuel System          │
│ Ignition             │
│ Engine Control       │
└──────────────────────┘
```

The user only needs to know **how to use the interface**, not every detail of its implementation.

### Why is Abstraction Useful?

Abstraction helps:

* Reduce complexity
* Hide implementation details
* Provide simpler interfaces
* Make systems easier to use
* Allow implementation details to change without necessarily affecting users of the interface

### Example

```python
car.start()
```

The caller only needs to know that `start()` starts the car.

The caller does not need to know how the operation is implemented internally.

# 3. Inheritance

## What is Inheritance?

**Inheritance** allows one class to derive or reuse properties and behaviors from another class.

In simple terms:

> **Inheritance = Create a new class based on an existing class.**

The existing class is commonly called the **parent/base/superclass**, while the new class is called the **child/derived/subclass**.

### Real-World Example

Consider different types of animals:

```text
                 Animal
                   │
          ┌────────┴────────┐
          │                 │
         Dog               Cat
```

`Dog` and `Cat` are both animals.

The common behavior can be placed in `Animal`.

For example:

```text
Animal
└── speak()

Dog
└── inherits speak()

Cat
└── inherits speak()
```

---

## Example in Python

```python
class Animal:

    def speak(self):
        print("Animal speaks")


class Dog(Animal):
    pass


dog = Dog()

dog.speak()
```

### Output

```text
Animal speaks
```

`Dog` inherits the `speak()` method from `Animal`.

Therefore:

```text
Animal
   │
   │ inheritance
   ▼
  Dog
```

The `Dog` class does not need to redefine `speak()` because it receives that behavior from its parent class.

---

## Why is Inheritance Useful?

Inheritance can help with:

* Code reuse
* Representing relationships between related classes
* Extending existing behavior
* Avoiding unnecessary duplication

For example:

```text
Vehicle
   │
   ├── Car
   ├── Bike
   └── Truck
```

Common functionality can be placed in `Vehicle`, while specialized functionality can be added to each child class.

> **Important:** Inheritance should be used when there is a meaningful relationship between the classes. Deep or unnecessary inheritance hierarchies can make software harder to understand and maintain.

# 4. Polymorphism

## What is Polymorphism?

**Polymorphism** means that the same interface or method call can produce different behavior depending on the object involved.

The word can be understood as:

```text
Poly → Many
Morphism → Forms
```

So polymorphism can be thought of as:

> **One interface, many implementations.**

### Real-World Example

Suppose different animals can make sounds.

```text
Dog → Bark
Cat → Meow
Cow → Moo
```

Each animal provides its own implementation of:

```text
speak()
```

The caller can simply use:

```text
animal.speak()
```

without needing to know the exact type of animal.

---

## Example in Python

```python
class Dog:

    def speak(self):
        print("Bark")


class Cat:

    def speak(self):
        print("Meow")


animals = [Dog(), Cat()]

for animal in animals:
    animal.speak()
```

### Output

```text
Bark
Meow
```

Notice that the same method call is used:

```python
animal.speak()
```

But the result depends on the actual object.

```text
Dog object
    │
    └── speak() → Bark

Cat object
    │
    └── speak() → Meow
```

This is a simple example of **polymorphic behavior**.

# How the Four Pillars Work Together

The four pillars are separate concepts, but they often work together in a real application.

Consider a payment system:

```text
                     Payment
                        │
             ┌──────────┴──────────┐
             │                     │
        CreditCard              PayPal
             │                     │
        process()              process()
```

### Encapsulation

Each payment object keeps its internal data and behavior together.

```text
CreditCard
├── card information
└── process()
```

### Abstraction

The application can work with a simple operation:

```text
process()
```

without needing to know all internal payment-processing details.

### Inheritance

If appropriate, specialized payment classes can derive from a common base class:

```text
Payment
 ├── CreditCard
 └── PayPal
```

### Polymorphism

The application can call:

```python
payment.process()
```

and the behavior depends on the actual payment object.

```text
CreditCard.process() → Credit-card processing

PayPal.process() → PayPal processing
```

# Comparison of the Four Pillars

| Pillar            | Core Idea                               | Main Purpose                   |
| ----------------- | --------------------------------------- | ------------------------------ |
| **Encapsulation** | Bundle and protect data + methods       | Protect object state           |
| **Abstraction**   | Hide unnecessary implementation details | Reduce complexity              |
| **Inheritance**   | Derive behavior from another class      | Reuse/extend behavior          |
| **Polymorphism**  | Same interface, different behavior      | Allow flexible implementations |

```text
     ↓

     ↓

Inheritance
     ↓

     ↓

```

# Common Confusions

## Encapsulation vs Abstraction

These two concepts are often confused.

### Encapsulation

Focuses on **bundling and controlling access to data and behavior**.

```text
"How do I protect and organize this object's state?"
```

### Abstraction

Focuses on **hiding unnecessary implementation complexity**.

```text
"What does the user need to know?"
```

A class can use both concepts at the same time.

---

## Inheritance vs Polymorphism

Inheritance and polymorphism are also related but not identical.

### Inheritance

Describes a relationship between classes:

```text
Dog IS-A Animal
```

### Polymorphism

Describes how different objects can be used through a common interface:

```text
animal.speak()
```

where:

```text
Dog  → Bark
Cat  → Meow
```

Polymorphism can also be achieved in languages and designs without relying exclusively on classical inheritance.

---

# Common Mistakes

### 1. "Encapsulation means making everything private."

Not necessarily.

Encapsulation is broader than simply making fields private. It is about **controlling access to internal state and organizing data with the operations that manage it**.

---

### 2. "Abstraction means hiding all implementation."

No.

Abstraction means hiding **unnecessary details** while exposing the interface or behavior that users of the component need.

---

### 3. "Inheritance is required for polymorphism."

Not always.

Polymorphism can be achieved through different mechanisms depending on the programming language, including interfaces, protocols, duck typing, and other forms of dynamic dispatch.

---

### 4. "Inheritance is always better than composition."

No.

Inheritance and composition solve different design problems.

A common design principle is:

> **Prefer composition over inheritance when composition provides a simpler and more flexible design.**

The correct choice depends on the relationship and requirements of the system.

# Interview Takeaway

A concise interview answer is:

> **The four pillars of OOP are Encapsulation, Abstraction, Inheritance, and Polymorphism. Encapsulation bundles data and behavior while controlling access to internal state.
