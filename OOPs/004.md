# Q4. What Is Encapsulation?

## What Is Encapsulation?

**Encapsulation** is an OOP concept that means **bundling data and the methods that operate on that data into a single unit**, usually a class, while controlling access to the object's internal state.

In simple terms:

> **Encapsulation = Keep an object's internal state controlled and provide well-defined ways to interact with it.**

For example, a `BankAccount` object can contain:

```text id="a7q9m2"
BankAccount
│
├── Data
│   └── balance
│
└── Methods
    ├── deposit()
    ├── withdraw()
    └── get_balance()
```

The `balance` and the operations that modify it belong together.

---

# Why Do We Need Encapsulation?

Without encapsulation, other parts of a program might directly modify an object's internal data in invalid ways.

For example:

```python id="z8p4km"
class BankAccount:

    def __init__(self, balance):
        self.balance = balance
```

Suppose we create an account:

```python id="f7m1qa"
account = BankAccount(1000)
```

If the balance is directly accessible, another part of the program could do:

```python id="c3x8yd"
account.balance = -50000
```

Now the object contains an invalid state:

```text id="2t0n0p"
Bank Account
    │
    └── balance = -50000
```

For a normal bank account, such a state may violate business rules.

The problem is that the object has no control over how its internal state is changed.

---

# Encapsulation Example

We can instead keep the balance internal and provide controlled methods:

```python id="n5q8fz"
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount

    def withdraw(self, amount):
        if 0 < amount <= self.__balance:
            self.__balance -= amount

    def get_balance(self):
        return self.__balance
```

Now the balance is intended to be accessed and modified through methods such as:

```text id="v6f2ak"
deposit()
withdraw()
get_balance()
```

For example:

```python id="8t5x0s"
account = BankAccount(1000)

account.deposit(500)
account.withdraw(200)

print(account.get_balance())
```

### Output

```text id="2g5xrw"
1300
```

The class can validate the requested operation before changing the internal state.

---

# How Encapsulation Works

Encapsulation generally involves two related ideas:

## 1. Bundling

Related **data and behavior** are kept together inside a class.

For example:

```text id="2qf4j6"
BankAccount
│
├── balance
│
├── deposit()
├── withdraw()
└── get_balance()
```

Instead of having bank-account data in one part of the program and unrelated functions modifying it from many places, the class provides a single conceptual unit.

---

## 2. Access Control

The class controls how outside code can access or modify its internal data.

For example:

```text id="j3p8xs"
Outside Code
     │
     ▼
┌───────────────┐
│ BankAccount   │
│               │
│ __balance     │
│               │
│ deposit()     │
│ withdraw()    │
└───────────────┘
```

The outside code interacts with the object's **interface**, rather than depending directly on its internal representation.

---

# Encapsulation in Python

Python provides several mechanisms and conventions for indicating how attributes should be used.

## Public Attribute

```python id="5qj9x2"
self.name
```

A normal attribute is generally considered public.

Example:

```python id="d4n7qa"
class Student:

    def __init__(self, name):
        self.name = name
```

It can normally be accessed directly:

```python id="b8v2mx"
student.name
```

---

## Single Underscore

```python id="j7q4wp"
self._name
```

A single leading underscore conventionally indicates that an attribute is intended for **internal use**.

Example:

```python id="s1z6kd"
class Student:

    def __init__(self, name):
        self._name = name
```

The underscore is primarily a **convention** in Python rather than strict access enforcement.

It communicates:

> "This attribute is intended to be used internally."

---

## Double Underscore

```python id="x8r2pm"
self.__name
```

A double leading underscore triggers **name mangling** in Python.

For example:

```python id="e6q3vt"
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance
```

Python internally transforms the attribute name in a way that helps avoid accidental name collisions with subclasses.

It is important to understand that Python's `__name` syntax is **not the same as a strict private-access mechanism found in some languages**.

---

# Access Control in Different Languages

Different programming languages implement encapsulation differently.

For example, languages such as **Java** and **C++** provide explicit access modifiers such as:

```text id="3s9qga"
public
private
protected
```

Conceptually:

```text id="w2n6jp"
public
   ↓
Accessible according to the language's public-access rules

private
   ↓
Restricted to the defining class/context

protected
   ↓
Restricted according to the language's protected-access rules
```

The exact rules differ between languages, so access-control behavior should always be understood in the context of the specific language.

When using an ATM, you can perform operations such as:

```text id="w5g0cp"
Withdraw Money
Deposit Money
Check Balance
```

But you don't directly manipulate:

```text id="m6c8dy"
Bank Database
Transaction Records
Account Ledger
Security Systems
```

Instead, the ATM provides a controlled interface.

```text id="j8h1xs"
                 User
                   │
                   ▼
                  ATM
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       Withdraw  Deposit  Balance
                   │
                   ▼
          Internal Bank System
```

Similarly, an object can expose specific methods while keeping its internal state and implementation controlled.

# Encapsulation Example: Temperature

Consider a temperature object.

We may want to prevent an invalid temperature from being stored.

```python id="y6c3qp"
class Temperature:

    def __init__(self, celsius):
        self.__celsius = 0
        self.set_temperature(celsius)

    def set_temperature(self, celsius):
        if celsius >= -273.15:
            self.__celsius = celsius

    def get_temperature(self):
        return self.__celsius
```

The class can enforce the rule:

```text id="r2h5sm"
Temperature ≥ -273.15°C
```

Instead of allowing arbitrary modifications, the object controls how its state changes.

This is an example of **validation combined with encapsulation**.

# Benefits of Encapsulation

## 1. Data Protection

Encapsulation helps prevent uncontrolled modification of an object's internal state.

```text id="y9m2qa"
Outside Code
     │
     ▼
Controlled Interface
     │
     ▼
Internal State
```

---

## 2. Maintainability

The internal implementation can change without necessarily changing how other parts of the program interact with the object.

For example, today:

```python id="r7s3mz"
self.__balance
```

might store the balance directly.

Later, the implementation could change to use another internal representation.

As long as the public interface remains compatible:

```text id="q2w8hv"
deposit()
withdraw()
get_balance()
```

other code may not need to know about the internal change.

---

## 3. Validation

Methods can validate input before changing the object's state.

For example:

```python id="m8x1cr"
def withdraw(self, amount):

    if 0 < amount <= self.__balance:
        self.__balance -= amount
```

This prevents invalid operations from being applied.

---

## 4. Modularity

Related data and operations stay together.

```text id="f0k5ns"
BankAccount
├── balance
├── deposit()
├── withdraw()
└── get_balance()
```

This makes the component easier to understand as a unit.

---

## 5. Reduced Coupling

Other parts of the program can depend on the object's **interface** instead of its internal implementation.

For example:

```text id="q7v4ka"
Other Components
       │
       ▼
BankAccount Interface
       │
       ▼
Internal Implementation
```

This can make changes easier to manage.

# Encapsulation vs Abstraction

Encapsulation and abstraction are closely related, but they are **not the same concept**.

## Encapsulation

Focuses on:

> **Bundling data and behavior and controlling access to internal state.**

```text id="c4m9jw"
Encapsulation
     ↓
Data + Methods
     ↓
Controlled Access
```

## Abstraction

Focuses on:

> **Hiding unnecessary implementation complexity and exposing the essential interface.**

```text id="n6s2kp"
Abstraction
     ↓
Hide Complexity
     ↓
Expose Essential Interface
```

### Quick Comparison

| Concept           | Main Focus                                              |
| ----------------- | ------------------------------------------------------- |
| **Encapsulation** | Organizing and controlling access to state and behavior |
| **Abstraction**   | Hiding unnecessary implementation details               |

A class can use **both encapsulation and abstraction** at the same time.

---

# Encapsulation vs Data Hiding

These concepts are related but should not be treated as exactly identical.

**Data hiding** focuses on restricting or discouraging direct access to internal data.

**Encapsulation** is broader: it includes organizing data and behavior together and defining controlled ways to interact with the object's state.

Therefore:

```text id="z7r3pf"
Data Hiding
     ↓
One aspect of
     ↓
Encapsulation
```

# Common Mistakes

## Mistake 1: "Encapsulation simply means making variables private."

Not exactly.

Private or protected access is **one mechanism** that can help achieve encapsulation.

The broader idea is:

```text id="a4x8mq"
Encapsulation
     │
     ├── Bundle data + behavior
     │
     └── Control access to internal state
```

---

## Mistake 2: "Python has exactly the same private/public system as Java."

No.

Python uses conventions and mechanisms such as:

```python id="f2y6qk"
self.name
self._name
self.__name
```

The meaning and enforcement are different from explicit access modifiers in languages such as Java or C++.

---

## Mistake 3: "Encapsulation prevents all changes to internal data."

No.

The purpose is not necessarily to make data completely immutable.

Instead, encapsulation allows the class to **control how state is accessed and changed**.

For example:

```text id="n9b4xt"
deposit(500)
withdraw(200)
```

are controlled state changes.

---

## Mistake 4: "Encapsulation means hiding everything."

No.

A well-designed class should expose the functionality that users of the class actually need.

The goal is not to hide everything; it is to provide a **clear and controlled interface**.

# Key Terms

| Term               | Meaning                                                    |
| ------------------ | ---------------------------------------------------------- |
| **Encapsulation**  | Bundling data and behavior while controlling access        |
| **State**          | Current data stored by an object                           |
| **Data Hiding**    | Restricting or discouraging direct access to internal data |
| **Interface**      | The operations exposed for interacting with an object      |
| **Validation**     | Checking input before changing state                       |
| **Access Control** | Rules governing how internal members can be accessed       |

# Interview Takeaway

> **Encapsulation is the OOP principle of bundling data and the methods that operate on it inside a class while controlling access to the object's internal state. It helps protect data, enforce valid state changes, reduce coupling, improve modularity, and make code easier to maintain.**

### One-Line Answer

> **Encapsulation means keeping an object's data and related behavior together while providing controlled access to its internal state.**
