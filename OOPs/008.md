# Q8. Compile-Time vs Runtime Polymorphism

## Definition

**Compile-time polymorphism** and **runtime polymorphism** are two commonly discussed forms of polymorphism.

The key difference is **when the method or operation to execute is determined**:

```text
Compile-time polymorphism
        ↓
Decision is made during compilation
```

```text
Runtime polymorphism
        ↓
Decision is made while the program is running
```

A simple way to remember:

> **Compile time → Compiler decides**
> **Runtime → Actual object decides**

The exact terminology and mechanisms vary between programming languages, so these concepts should always be explained in the context of the language being used.

---

# Comparison

| Aspect            | Compile-Time Polymorphism                  | Runtime Polymorphism                 |
| ----------------- | ------------------------------------------ | ------------------------------------ |
| Also called       | Static polymorphism                        | Dynamic polymorphism                 |
| Decision time     | Compile time                               | Runtime                              |
| Common mechanism  | Method/function overloading                | Method overriding                    |
| Typical languages | Java, C++, C#                              | Java, C++, Python, etc.              |
| Method selection  | Based on compile-time information          | Based on actual object/runtime type  |
| Flexibility       | More fixed                                 | More dynamic                         |
| Common example    | Same method name with different parameters | Same method overridden by subclasses |

### Quick Difference

```text
Compile-Time
    ↓
Compiler chooses implementation
    ↓
Program executes


Runtime
    ↓
Program executes
    ↓
Actual object determines implementation
```

---

# 1. Compile-Time Polymorphism

In **compile-time polymorphism**, the compiler determines which implementation should be used based on information available during compilation.

A common example is **method overloading**.

---

## Method Overloading

Method overloading means having multiple methods with the same name but different parameter lists, where the programming language supports this feature.

For example, in Java:

```java
class Calculator {

    int add(int a, int b) {
        return a + b;
    }

    int add(int a, int b, int c) {
        return a + b + c;
    }
}
```

The method name is the same:

```text
add()
```

But the parameter lists are different:

```text
add(int, int)
add(int, int, int)
```

Now:

```java
Calculator calculator = new Calculator();

calculator.add(2, 3);
calculator.add(2, 3, 4);
```

The compiler can determine which method is intended from the arguments.

```text
add(2, 3)
    ↓
add(int, int)


add(2, 3, 4)
    ↓
add(int, int, int)
```

---

# Important: Python and Method Overloading

Python does **not** support traditional method overloading in the same way Java or C++ does.

For example:

```python
class Calculator:

    def add(self, a, b):
        return a + b

    def add(self, a, b, c):
        return a + b + c
```

This does **not** create two overloaded methods.

The second definition replaces the first one.

Conceptually:

```text
First add()
     ↓
Defined

Second add()
     ↓
Replaces first add()
```

Python can achieve similar functionality using techniques such as:

* Default arguments
* `*args`
* `**kwargs`
* Other dispatch mechanisms

For example:

```python
class Calculator:

    def add(self, *numbers):
        return sum(numbers)


calculator = Calculator()

print(calculator.add(2, 3))
print(calculator.add(2, 3, 4))
```

Output:

```text
5
9
```

However, this is **not traditional compile-time method overloading** like the Java example.

---

# 2. Runtime Polymorphism

In **runtime polymorphism**, the appropriate implementation is determined while the program is running.

A common mechanism is **method overriding**.

Consider:

```python
class Animal:

    def speak(self):
        print("Some sound")


class Dog(Animal):

    def speak(self):
        print("Bark")


class Cat(Animal):

    def speak(self):
        print("Meow")
```

Now:

```python
animals = [Dog(), Cat()]

for animal in animals:
    animal.speak()
```

Output:

```text
Bark
Meow
```

The same method call:

```python
animal.speak()
```

produces different behavior depending on the actual object.

```text
animal → Dog → Dog.speak()

animal → Cat → Cat.speak()
```

This is an example of **runtime polymorphic behavior**.

---

# How Runtime Polymorphism Works

The basic flow is:

```text
                  animal.speak()
                       │
              ┌────────┴────────┐
              ↓                 ↓
          Dog object        Cat object
              │                 │
              ↓                 ↓
         Dog.speak()        Cat.speak()
              │                 │
              ↓                 ↓
            Bark              Meow
```

The calling code does not need to know the exact concrete type beforehand.

It simply uses the common operation:

```python
animal.speak()
```

The actual object determines the behavior.

---

# Real-World Example: Payment System

Runtime polymorphism is particularly useful when an application supports multiple implementations of the same operation.

For example:

```text
                    Payment
                   /       \
                  ↓         ↓
                 UPI     CreditCard
                  │         │
                  ↓         ↓
                pay()      pay()
```

In Python:

```python
class Payment:

    def pay(self, amount):
        raise NotImplementedError


class UPI(Payment):

    def pay(self, amount):
        print("Paying using UPI")


class CreditCard(Payment):

    def pay(self, amount):
        print("Paying using credit card")
```

The application can define a common function:

```python
def process_payment(payment):
    payment.pay(500)
```

Now:

```python
process_payment(UPI())
process_payment(CreditCard())
```

The function does not need separate logic such as:

```python
if payment_type == "UPI":
    ...

elif payment_type == "CreditCard":
    ...
```

Instead, it simply calls:

```python
payment.pay(500)
```

The actual object determines which implementation is executed.

---

# Why Is Runtime Polymorphism Useful?

Suppose we later add another payment method:

```python
class PayPal(Payment):

    def pay(self, amount):
        print("Paying using PayPal")
```

We can use it with the same function:

```python
process_payment(PayPal())
```

The existing calling code does not need to change.

This provides:

* **Extensibility**
* **Flexibility**
* **Reduced conditional logic**
* **Better maintainability**
* **Loose coupling between caller and implementation**

The calling code depends on the common interface rather than the concrete implementation.

# Compile-Time vs Runtime: Step-by-Step

## Compile-Time Polymorphism

```text
Source Code
     ↓
Compiler examines method call
     ↓
Determines matching method
     ↓
Program executes
```

Example:

```text
add(2, 3)
   ↓
Compiler selects
add(int, int)
```

---

## Runtime Polymorphism

```text
Source Code
     ↓
Program starts
     ↓
Actual object is determined
     ↓
Appropriate implementation is selected
```

Example:

```text
animal.speak()
      ↓
Actual object = Dog
      ↓
Dog.speak()
```

# Key Difference

The easiest way to remember the difference is to focus on **when the decision happens**.

### Compile-Time Polymorphism

```text
Compile
   ↓
Compiler determines method
   ↓
Run program
```

### Runtime Polymorphism

```text
Run program
   ↓
Actual object is known
   ↓
Appropriate method executes
```

# Method Overloading vs Method Overriding

These concepts are commonly associated with the two forms of polymorphism.

| Feature                 | Method Overloading                     | Method Overriding                         |
| ----------------------- | -------------------------------------- | ----------------------------------------- |
| Basic idea              | Same method name, different parameters | Child provides a different implementation |
| Usually associated with | Compile-time polymorphism              | Runtime polymorphism                      |
| Requires inheritance?   | Not necessarily                        | Usually involves inheritance/subtyping    |
| Method signature        | Different parameter lists              | Compatible inherited method               |
| Example                 | `add(int,int)` and `add(int,int,int)`  | `Dog.speak()` overriding `Animal.speak()` |
| Python support          | No traditional overloading             | Yes                                       |

Remember:

```text
Overloading  → usually compile time
Overriding   → usually runtime
```

The word **"usually"** is important because the exact behavior and terminology depend on the programming language.

---

# Language Differences

Different languages implement these concepts differently.

### Java

Java commonly supports:

```text
Compile-time → Method overloading
Runtime      → Method overriding
```

### C++

C++ commonly supports:

```text
Compile-time → Function/method overloading
Runtime      → Virtual function overriding
```

### Python

Python's dynamic nature means the traditional Java/C++ distinction does not map perfectly.

Python supports runtime polymorphic behavior naturally:

```python
animal.speak()
```

It does not support traditional compile-time method overloading based on parameter signatures.

Therefore, it is better to explain these concepts **according to the language being discussed**.

---

# Common Mistake

## Saying "Compile-Time Polymorphism Is Always Overloading"

A better statement is:

> **Method overloading is a common mechanism used to achieve or describe compile-time polymorphism in languages that support it.**

Similarly:

> **Method overriding is a common mechanism for runtime polymorphism.**

These are common mechanisms, not universal definitions across every programming language.

---

# Common Mistake: Treating Python Like Java

Do not write:

```python
class Calculator:

    def add(self, a, b):
        ...

    def add(self, a, b, c):
        ...
```

and claim that Python now has traditional method overloading.

The second method definition replaces the first.

Python instead commonly uses:

```python
*args
```

or default parameters when multiple argument patterns need to be supported.

---

# Common Mistake: Confusing Overloading and Overriding

Remember the difference:

```text
                  Polymorphism
                       │
              ┌────────┴────────┐
              ↓                 ↓
         Overloading        Overriding
              │                 │
              ↓                 ↓
      Different parameters   Different implementation
              │                 │
              ↓                 ↓
       Usually compile       Usually runtime
           time
```

### Example

**Overloading:**

```text
add(a, b)
add(a, b, c)
```

**Overriding:**

```text
Animal.speak()
      ↓
Dog.speak()
```

# Interview Takeaway

> **Compile-time polymorphism is resolved during compilation, commonly through method overloading in languages that support it. Runtime polymorphism is resolved during execution, commonly through method overriding, where different objects provide different implementations of a common interface. The exact mechanisms vary by programming language, so Python's dynamic behavior should not be explained using the same traditional overloading model as Java or C++.**

### Common Interview Follow-Up

**Q: What is the main difference between compile-time and runtime polymorphism?**

**Answer:**

> **The main difference is when the implementation is determined. In compile-time polymorphism, the compiler determines the appropriate method using compile-time information. In runtime polymorphism, the appropriate implementation is determined during execution based on the actual object.**
