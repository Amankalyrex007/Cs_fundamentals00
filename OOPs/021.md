# Q21. Why is Composition Often Preferred Over Inheritance?

## Answer

Composition is often preferred over inheritance because it generally provides:

* **Greater flexibility**
* **Lower coupling**
* **Easier maintenance**
* **Better testability**
* **Easier runtime replacement of behavior**

The basic idea is:

```text
Inheritance = "is-a" relationship

Composition = "has-a" relationship
```

With inheritance, a child class becomes tightly connected to the parent class.

With composition, a class uses other objects as components, which can often be **replaced, modified, or tested independently**.

---

# Example

Suppose we have different notification methods.

## Using Inheritance

We could create separate classes:

```python
class EmailNotification:
    def send(self, message):
        print("Sending email:", message)


class SMSNotification:
    def send(self, message):
        print("Sending SMS:", message)
```

However, imagine that a service needs to support many notification mechanisms:

```text
Email
SMS
Push Notification
WhatsApp
Slack
```

Creating a large inheritance hierarchy just to reuse notification behavior is unnecessary.

Instead, composition allows us to **inject the required notification object**.

---

## Using Composition

```python
class EmailNotification:
    def send(self, message):
        print("Sending email:", message)


class SMSNotification:
    def send(self, message):
        print("Sending SMS:", message)


class NotificationService:
    def __init__(self, notification):
        self.notification = notification

    def send(self, message):
        self.notification.send(message)
```

Now we can use either implementation:

```python
service1 = NotificationService(EmailNotification())
service2 = NotificationService(SMSNotification())

service1.send("Hello")
service2.send("Hello")
```

Output:

```text
Sending email: Hello
Sending SMS: Hello
```

The `NotificationService` does not need to inherit from `EmailNotification` or `SMSNotification`.

It simply **has a notification object**.

```text
NotificationService
        │
        │ has-a
        ▼
   Notification
      /     \
   Email     SMS
```

This is composition.

---

# Why Composition Is Often Preferred

## 1. Lower Coupling

Inheritance creates a strong dependency between child and parent.

```text
Child ── inherits ──> Parent
```

The child depends on the structure and behavior of the parent.

For example:

```python
class Vehicle:
    def start(self):
        print("Vehicle started")


class Car(Vehicle):
    pass
```

`Car` is strongly connected to `Vehicle`.

If the parent class changes its design or behavior, subclasses may also be affected.

With composition:

```text
Service ── has-a ──> Component
```

the component can be developed and changed more independently.

For example:

```python
class Car:
    def __init__(self, engine):
        self.engine = engine

    def start(self):
        self.engine.start()
```

The `Car` does not need to inherit from a particular engine implementation.

---

## 2. Greater Flexibility

A composed object can often be given a different component at runtime.

For example:

```python
service = NotificationService(EmailNotification())
service.send("Hello")
```

Later, we can change the behavior:

```python
service.notification = SMSNotification()

service.send("Hello")
```

Now the same `NotificationService` sends SMS instead of email.

The class itself did not need to change.

```text
Initially:

NotificationService
        │
        ▼
      Email


Later:

NotificationService
        │
        ▼
       SMS
```

This is one of the major advantages of composition: **behavior can be changed by changing the contained object**.

---

## 3. Easier Testing

Composition makes it easier to replace real dependencies with simple test or mock objects.

For example:

```python
class FakeNotification:
    def send(self, message):
        print("Test notification:", message)
```

Then:

```python
service = NotificationService(FakeNotification())

service.send("Testing")
```

Output:

```text
Test notification: Testing
```

We don't need to send a real email or SMS during the test.

This makes unit testing easier because dependencies can be replaced with controlled test implementations.

Conceptually:

```text
Production:

NotificationService
        │
        ▼
 EmailNotification


Testing:

NotificationService
        │
        ▼
 FakeNotification
```

The service can be tested without depending on an external notification system.

---

## 4. Avoids Deep Inheritance Hierarchies

Large inheritance trees can become difficult to understand and maintain.

For example:

```text
Object
  ↓
Vehicle
  ↓
Car
  ↓
ElectricCar
  ↓
LuxuryElectricCar
```

As the hierarchy becomes deeper, understanding where a method or property comes from can become difficult.

There may also be problems when a class needs behavior from multiple unrelated branches.

Composition can instead build behavior from smaller components:

```text
Car
├── Engine
├── Battery
├── Navigation
└── PaymentSystem
```

Each component can have a focused responsibility.

For example:

```python
class Engine:
    def start(self):
        print("Engine started")


class Navigation:
    def navigate(self, destination):
        print("Navigating to", destination)


class Car:
    def __init__(self, engine, navigation):
        self.engine = engine
        self.navigation = navigation

    def start(self):
        self.engine.start()

    def go_to(self, destination):
        self.navigation.navigate(destination)
```

Now `Car` is composed of smaller components.

Each component has a specific responsibility.

---

# 5. Supports the Principle of Programming to Abstractions

Composition works especially well with:

* Interfaces
* Abstract classes
* Protocols
* Duck typing

The main idea is that a class should depend on the **expected behavior**, rather than a specific concrete implementation.

For example:

```text
                 Notification
                      │
              ┌───────┴───────┐
              │               │
            Email             SMS
```

`NotificationService` can depend on the notification behavior:

```python
class NotificationService:
    def __init__(self, notification):
        self.notification = notification

    def send(self, message):
        self.notification.send(message)
```

It doesn't need to know whether the object is:

```text
EmailNotification
SMSNotification
PushNotification
WhatsAppNotification
```

As long as the object provides the required `send()` behavior, the service can use it.

This is closely related to the idea:

> **Program to an abstraction, not a concrete implementation.**

# A More Realistic Example

Consider a payment system.

A poor design might create a large inheritance hierarchy:

```text
Payment
  ↓
OnlinePayment
  ↓
CardPayment
  ↓
CreditCardPayment
```

But payment processing often consists of multiple independent behaviors:

```text
PaymentService
├── PaymentMethod
├── PaymentGateway
├── FraudChecker
└── ReceiptGenerator
```

These components can be composed:

```python
class PaymentService:
    def __init__(self, payment_method, gateway):
        self.payment_method = payment_method
        self.gateway = gateway

    def pay(self, amount):
        payment_data = self.payment_method.create_payment(amount)
        return self.gateway.process(payment_data)
```

Now different payment methods or gateways can be substituted without changing the overall service.

This demonstrates why composition is useful in larger systems.

# Composition vs Inheritance

| Aspect              | Composition                            | Inheritance                                |
| ------------------- | -------------------------------------- | ------------------------------------------ |
| Relationship        | Has-a                                  | Is-a                                       |
| Coupling            | Generally lower                        | Generally higher                           |
| Flexibility         | Usually higher                         | More constrained by hierarchy              |
| Code reuse          | Through contained objects              | Through parent classes                     |
| Runtime replacement | Easier                                 | Usually harder                             |
| Testing             | Dependencies can be substituted easily | Can be more tightly coupled                |
| Structure           | Builds behavior from components        | Builds hierarchy from parent/child classes |
| Best use            | Combining behaviors/components         | Genuine subtype relationships              |

---

# Inheritance Example: When It Makes Sense

Composition is not always better.

Inheritance is appropriate when there is a genuine subtype relationship.

For example:

```text
Animal
├── Dog
├── Cat
└── Bird
```

A `Dog` really **is an** `Animal`.

```python
class Animal:
    def eat(self):
        print("Animal is eating")


class Dog(Animal):
    def bark(self):
        print("Dog is barking")
```

Here:

```text
Dog IS-A Animal
```

The subclass represents a specialized form of the parent.

Another example:

```text
Vehicle
├── Car
└── Bike
```

A `Car` is genuinely a `Vehicle`.

```text
Car IS-A Vehicle
Bike IS-A Vehicle
```

Inheritance can therefore be a good design when the child should conform to the parent's contract and can safely be treated as the parent type.

---

# When Composition Is a Better Fit

Suppose we have:

```text
Car
Engine
```

A car **has an engine**.

It would be conceptually incorrect to model:

```text
Car IS-A Engine
```

Instead:

```text
Car HAS-A Engine
```

So composition is more appropriate:

```python
class Engine:
    def start(self):
        print("Engine started")


class Car:
    def __init__(self, engine):
        self.engine = engine

    def start(self):
        self.engine.start()
```

Usage:

```python
engine = Engine()
car = Car(engine)

car.start()
```

This clearly represents the domain relationship.

---

# Composition vs Inheritance: Easy Rule

A useful first question is:

```text
"Is B an A?"
```

If yes, inheritance **may** be appropriate.

```text
Dog is an Animal
Car is a Vehicle
```

If the answer is:

```text
"Does A have/use B?"
```

then composition may be appropriate.

```text
Car has an Engine
Computer has a CPU
House has Rooms
Order has Payment
```

However, this is only a design guideline. The final choice should also consider coupling, substitutability, lifecycle, flexibility, and the actual domain model.

---

# Important Point

**Composition is not always better.**

Inheritance is appropriate when there is a genuine **"is-a" relationship**:

```text
Dog IS-A Animal

Car IS-A Vehicle
```

If the subclass truly represents a specialized form of the parent and should conform to its contract, inheritance can be a good design.

But using inheritance **only to reuse code** can create unnecessary coupling.

For example, if we only want to reuse a few methods from another class, blindly creating an inheritance relationship may incorrectly suggest that the two classes have an `is-a` relationship.

In such situations, composition is often a cleaner alternative.

---

# Composition and the Single Responsibility Principle

Composition also works well with the idea of giving each class a focused responsibility.

Instead of one huge class:

```text
Application
├── sends emails
├── processes payments
├── generates reports
├── validates users
└── stores files
```

we can compose smaller components:

```text
Application
├── EmailService
├── PaymentService
├── ReportGenerator
├── UserValidator
└── FileStorage
```

Each component can focus on one responsibility.

This can make the overall system easier to:

* Understand
* Test
* Modify
* Extend
* Reuse

# Real-World Analogy

Think about a computer.

A computer is not an instance of a CPU:

```text
Computer IS-A CPU ❌
```

Instead, a computer contains a CPU:

```text
Computer HAS-A CPU ✅
```

Similarly:

```text
Car HAS-A Engine
Phone HAS-A Battery
House HAS-A Rooms
Order HAS-A Payment
```

These are natural composition relationships.

---

# Interview Takeaway

> **Composition is often preferred over inheritance because it reduces coupling, improves flexibility and testability, and avoids rigid inheritance hierarchies.**

However, inheritance remains appropriate when there is a genuine **"is-a" relationship** and substitutability makes sense.

The key distinction is:

```text
Inheritance
    ↓
"is-a"
    ↓
Strong parent-child relationship


Composition
    ↓
"has-a"
    ↓
Objects are combined as components
```

A good rule to remember:

> **Prefer composition when you want to assemble or change behavior; use inheritance when you are modeling a genuine subtype relationship.**
