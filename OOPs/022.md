22.What is the Liskov Substitution Principle?
Answer

The Liskov Substitution Principle (LSP) is the L in the SOLID principles of object-oriented design.

It states:

Objects of a subclass should be replaceable for objects of their superclass without breaking the correctness or expected behavior of the program.

In simple terms:

If B is a subtype of A, then code expecting an A should be able to work correctly when given a B.

Simple example

Suppose we have:

class Bird:
    def fly(self):
        print("Flying")


class Sparrow(Bird):
    def fly(self):
        print("Sparrow is flying")

A function expecting a Bird can safely receive a Sparrow:

def make_bird_fly(bird):
    bird.fly()


make_bird_fly(Sparrow())

This follows LSP because Sparrow satisfies the behavior expected from Bird.

LSP violation example

Consider:

class Bird:
    def fly(self):
        print("Flying")


class Penguin(Bird):
    def fly(self):
        raise Exception("Penguins cannot fly")

Now:

def make_bird_fly(bird):
    bird.fly()


make_bird_fly(Penguin())

The program breaks because Penguin cannot fulfill the behavior that the Bird abstraction promises.

The problem is not simply that a penguin cannot fly. The deeper problem is that the abstraction Bird incorrectly assumes that every bird can fly.

Better design

Separate the concepts:

class Bird:
    def eat(self):
        print("Eating")


class FlyingBird(Bird):
    def fly(self):
        print("Flying")


class Sparrow(FlyingBird):
    pass


class Penguin(Bird):
    pass

Now:

def make_fly(flying_bird):
    flying_bird.fly()


make_fly(Sparrow())

Only objects that actually support the fly() behavior are passed to make_fly().

What does "substitutable" mean?

Suppose we have:

def process_payment(payment):
    payment.pay(100)

If CreditCardPayment is a subtype of Payment, then:

process_payment(CreditCardPayment())

should work wherever:

process_payment(PaymentImplementation())

is expected.

The subclass should not unexpectedly:

Remove expected functionality
Change important behavioral assumptions
Reject valid inputs that the parent accepts
Produce incompatible results
Require stronger conditions than the parent requires
Connection with inheritance

LSP is one reason we should not use inheritance merely for code reuse.

Before creating:

Child → Parent

ask:

Can the child genuinely behave like the parent wherever the parent is expected?

If the answer is no, inheritance may be the wrong relationship.

This connects directly to the previous question about composition vs inheritance: composition can sometimes avoid an inheritance relationship that would violate LSP.

Interview takeaway

Liskov Substitution Principle says that a subclass should be usable wherever its superclass is expected without breaking the program's correctness or expected behavior. A subclass should honor the behavioral contract of its parent.
