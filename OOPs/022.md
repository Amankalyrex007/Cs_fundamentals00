# Q22. What is the Liskov Substitution Principle?

## Answer

The **Liskov Substitution Principle (LSP)** is the **L** in the **SOLID principles** of object-oriented design.

It was introduced by **Barbara Liskov** and is concerned with whether a subtype can safely be used wherever its parent type is expected.

It states:

> **Objects of a subclass should be replaceable for objects of their superclass without breaking the correctness or expected behavior of the program.**

In simple terms:

```text
If B is a subtype of A,

code expecting an A
        ↓
should also work correctly with B
```

The important word is **behavior**.

LSP is not simply about whether one class technically inherits from another. It is about whether the child class **honors the behavioral contract** of the parent class.

---

# Simple Example

Suppose we have:

```python id="3kzq8v"
class Bird:
    def fly(self):
        print("Flying")


class Sparrow(Bird):
    def fly(self):
        print("Sparrow is flying")
```

A function expecting a `Bird` can safely receive a `Sparrow`:

```python id="p8y0ae"
def make_bird_fly(bird):
    bird.fly()


make_bird_fly(Sparrow())
```

Output:

```text
Sparrow is flying
```

This follows LSP because `Sparrow` satisfies the behavior expected from `Bird`.

Conceptually:

```text id="w1h8bf"
Bird
  │
  └── Sparrow
        │
        └── can fly()
```

Whenever code expects a `Bird` that supports `fly()`, a `Sparrow` can be substituted without breaking the expected behavior.

---

# Another Simple Example

Consider a payment system:

```python id="6o5bta"
class Payment:
    def pay(self, amount):
        print("Processing payment:", amount)


class CreditCardPayment(Payment):
    def pay(self, amount):
        print("Paid using credit card:", amount)
```

Now:

```python id="m4jj1q"
def process_payment(payment):
    payment.pay(100)


process_payment(CreditCardPayment())
```

Output:

```text
Paid using credit card: 100
```

The function does not need to know the exact payment implementation.

It only expects an object that follows the `Payment` contract.

```text id="0phx6j"
              Payment
                 │
       ┌─────────┴─────────┐
       │                   │
CreditCardPayment      UPIPayment
       │                   │
       └────── pay() ──────┘
```

As long as each subtype behaves according to the expectations established by `Payment`, they can be substituted safely.

# LSP Violation Example

Consider:

```python id="0l7x8f"
class Bird:
    def fly(self):
        print("Flying")


class Penguin(Bird):
    def fly(self):
        raise Exception("Penguins cannot fly")
```

Now:

```python id="f4tx8c"
def make_bird_fly(bird):
    bird.fly()


make_bird_fly(Penguin())
```

The program breaks.

The problem is not simply that a penguin cannot fly.

The deeper problem is that the abstraction:

```text id="4s3k8h"
Bird
  ↓
fly()
```

incorrectly assumes that **every Bird can fly**.

`Penguin` therefore cannot satisfy the behavioral expectations of this particular `Bird` abstraction.

---

# Why This Violates LSP

Suppose the program says:

```python id="0i1n6k"
def make_bird_fly(bird):
    bird.fly()
```

The function expects:

```text
Bird → fly() should work
```

But when we pass:

```text
Penguin → fly() raises an exception
```

the subtype cannot safely replace the parent type.

```text id="yr2h8w"
Expected:

Bird
 │
 └── fly() → works


Actual:

Penguin
 │
 └── fly() → ❌ unexpected failure
```

Therefore, the inheritance relationship is problematic.

---

# Better Design

Instead of assuming that every bird can fly, we can separate the concepts.

```python id="q3az9w"
class Bird:
    def eat(self):
        print("Eating")


class FlyingBird(Bird):
    def fly(self):
        print("Flying")


class Sparrow(FlyingBird):
    pass


class Penguin(Bird):
    pass
```

Now the hierarchy represents the actual capabilities:

```text id="2g5j9r"
             Bird
            /    \
           /      \
  FlyingBird     Penguin
       │
       └── Sparrow
```

Only `FlyingBird` provides the `fly()` behavior.

Now:

```python id="0qu4h6"
def make_fly(flying_bird):
    flying_bird.fly()


make_fly(Sparrow())
```

This is safe because `Sparrow` is a `FlyingBird` and supports the required behavior.

A `Penguin` is not passed to `make_fly()` because it does not satisfy that abstraction.

---

# What Does "Substitutable" Mean?

Suppose we have:

```python id="4l6z0j"
def process_payment(payment):
    payment.pay(100)
```

If `CreditCardPayment` is a subtype of `Payment`, then:

```python id="g9u7sq"
process_payment(CreditCardPayment())
```

should work wherever a valid `Payment` implementation is expected.

The subclass should not unexpectedly:

* Remove expected functionality
* Change important behavioral assumptions
* Reject valid inputs that the parent accepts
* Produce incompatible results
* Require stronger conditions than the parent requires

In other words:

```text id="7q9zpx"
Parent contract
      ↓
   Expected
   behavior
      ↓
Subclass must honor it
```

---

# Example: Rejecting Valid Inputs

LSP can also be violated when a subclass becomes more restrictive than its parent.

Suppose the parent accepts any positive amount:

```python id="3qly9w"
class Payment:
    def pay(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")

        print("Payment processed:", amount)
```

A valid payment:

```python id="2d4q0r"
payment.pay(100)
```

works.

Now imagine a subclass that unexpectedly rejects amounts below `500`:

```python id="h8k7wq"
class SpecialPayment(Payment):
    def pay(self, amount):
        if amount < 500:
            raise ValueError("Minimum payment is 500")

        print("Payment processed:", amount)
```

The parent allowed:

```text
100
```

but the subtype rejects it.

If code using the parent contract legitimately expects `100` to be accepted, substituting `SpecialPayment` can break that expectation.

This is an example of a subclass **strengthening the requirements** beyond what the parent contract allowed.

---

# Example: Changing Expected Behavior

Consider a storage abstraction:

```python id="k0k7bx"
class FileStorage:
    def save(self, data):
        print("Data saved")
```

Suppose application code expects:

```python id="q8l1rf"
storage.save("user-data")
```

to successfully save the data.

If a subclass silently changes the meaning of `save()`:

```python id="1n3h5u"
class ReadOnlyStorage(FileStorage):
    def save(self, data):
        raise Exception("Saving is not supported")
```

then code expecting a normal writable `FileStorage` cannot safely substitute `ReadOnlyStorage`.

The problem is again the mismatch between the **parent's promised behavior** and the **child's behavior**.

---

# Connection With Inheritance

LSP is one reason we should not use inheritance merely for code reuse.

Before creating:

```text id="k4v5pu"
Child
  │
  └── inherits from
          ↓
        Parent
```

ask:

> **Can the child genuinely behave like the parent wherever the parent is expected?**

If the answer is **no**, inheritance may be the wrong relationship.

For example:

```text id="h2v6dr"
Penguin IS-A Bird
```

is biologically true, but if the `Bird` abstraction requires:

```text
fly()
```

then that abstraction is too broad for all birds.

The solution is not necessarily to remove the real-world relationship. Instead, we should design the software abstraction correctly.

For example:

```text id="n1l0as"
Bird
├── Sparrow
└── Penguin

FlyingBird
└── Sparrow
```

Now the software hierarchy reflects the behavior required by the program.

---

# LSP and Composition

This connects directly to the previous question about **composition vs inheritance**.

Sometimes composition can avoid an inheritance relationship that would violate LSP.

For example, suppose we have:

```python id="2f6k9a"
class Bird:
    def fly(self):
        print("Flying")
```

and we discover that some birds cannot fly.

Instead of forcing every bird to inherit a `fly()` behavior, we can compose capabilities.

For example:

```python id="1e8k6m"
class FlyingCapability:
    def fly(self):
        print("Flying")


class Sparrow:
    def __init__(self):
        self.flying = FlyingCapability()

    def fly(self):
        self.flying.fly()


class Penguin:
    def swim(self):
        print("Swimming")
```

Now flying behavior is a separate capability rather than something every bird must inherit.

This demonstrates an important design idea:

> **Inheritance should represent a valid behavioral subtype relationship, while composition can be used to assemble optional capabilities.**

---

# LSP and the `is-a` Relationship

A common mistake is to think:

> "If B is technically an A in the real world, inheritance must be correct."

That is not always true.

LSP asks a more precise question:

```text
Can B behave like A
under the contract expected by the program?
```

For example:

```text
Penguin is a Bird
```

is true in the real world.

But:

```text
Penguin is a FlyingBird
```

is false.

Therefore, if `FlyingBird` promises `fly()`, `Penguin` should not inherit from `FlyingBird`.

---

# LSP and Polymorphism

LSP is closely connected to polymorphism.

Polymorphism allows us to write:

```python id="r7zjz3"
def process_payment(payment):
    payment.pay(100)
```

and pass different implementations:

```python id="7w3y1e"
process_payment(CreditCardPayment())
process_payment(UPIPayment())
process_payment(PayPalPayment())
```

For this to work safely, each implementation must honor the expected `Payment` behavior.

Therefore:

```text id="k5x1zs"
Polymorphism
     +
Behavioral compatibility
     ↓
Safe substitution
     ↓
LSP
```

LSP helps ensure that polymorphism does not merely work syntactically but also works **correctly according to the expected contract**.

---

# LSP Is About Behavior, Not Just Method Signatures

A common misunderstanding is:

> "If the child has all the same methods as the parent, LSP is satisfied."

Not necessarily.

Consider:

```python id="7u4k9x"
class Payment:
    def pay(self, amount):
        print("Payment successful")
```

A subclass could technically define the same method:

```python id="1n9k3f"
class BadPayment(Payment):
    def pay(self, amount):
        print("Payment failed")
```

The method exists, but the behavior may violate what users of `Payment` expect.

Therefore, LSP is about:

* Expected inputs
* Expected outputs
* Valid states
* Exceptions
* Side effects
* Behavioral guarantees
* Overall contract

The child should preserve the important expectations established by the parent abstraction.

---

# Important Principle

LSP can be summarized as:

```text id="0v2x1d"
If code works correctly with Parent,

replacing Parent with Child

should not unexpectedly break that code.
```

Or more simply:

```text id="l6w5js"
Parent
  ↓
Expected behavior
  ↓
Child must honor it
```

---

# Interview Takeaway

> **The Liskov Substitution Principle says that a subclass should be usable wherever its superclass is expected without breaking the program's correctness or expected behavior.**

A subclass should **honor the behavioral contract** of its parent.

Remember:

```text id="9t4w1n"
LSP
 │
 ├── Child should safely replace Parent
 │
 ├── Child should preserve expected behavior
 │
 ├── Child should not unexpectedly reject valid inputs
 │
 ├── Child should not violate parent guarantees
 │
 └── Inheritance should represent a valid behavioral subtype
```

The key question to ask before using inheritance is:

> **"Can this child genuinely behave like the parent wherever the parent is expected?"**

If not, consider redesigning the abstraction or using **composition** instead.
