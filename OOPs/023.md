23.What are SOLID principles?
Answer

SOLID is a set of five object-oriented design principles that help developers write software that is easier to maintain, extend, test, and understand.

SOLID stands for:

Letter	Principle	Core idea
S	Single Responsibility Principle	A class should have one main responsibility
O	Open/Closed Principle	Open for extension, closed for modification
L	Liskov Substitution Principle	Subtypes should be substitutable for their base types
I	Interface Segregation Principle	Don't force clients to depend on methods they don't need
D	Dependency Inversion Principle	Depend on abstractions rather than concrete implementations
1. S — Single Responsibility Principle (SRP)

A class should have one responsibility and therefore one main reason to change.

Bad design:

class Report:
    def generate(self):
        pass

    def save_to_database(self):
        pass

    def send_email(self):
        pass

This class handles report generation, database storage, and email delivery.

A better design separates these responsibilities:

class ReportGenerator:
    def generate(self):
        pass


class ReportRepository:
    def save(self, report):
        pass


class EmailService:
    def send(self, report):
        pass

This makes each component easier to modify and test.

2. O — Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification.

The goal is to add new behavior without repeatedly changing stable, existing code.

For example, instead of putting every payment type into one large if/elif block:

if payment_type == "card":
    ...
elif payment_type == "upi":
    ...
elif payment_type == "cash":
    ...

we can define a common abstraction:

class Payment:
    def pay(self, amount):
        raise NotImplementedError


class CardPayment(Payment):
    def pay(self, amount):
        print("Card payment")


class UPIPayment(Payment):
    def pay(self, amount):
        print("UPI payment")

A new payment implementation can be added without changing the existing payment classes.

3. L — Liskov Substitution Principle (LSP)

A subclass should be usable wherever its parent type is expected without breaking the program's expected behavior.

For example, if:

class Bird:
    def fly(self):
        pass

and Penguin inherits from Bird but cannot meaningfully support fly(), the hierarchy may violate LSP.

The abstraction should instead model the capabilities correctly.

This is the principle we discussed in the previous question.

4. I — Interface Segregation Principle (ISP)

Clients should not be forced to depend on methods they do not use.

Suppose we have an overly large interface:

Machine
 ├── print()
 ├── scan()
 ├── fax()
 └── copy()

A simple printer that only prints should not be forced to implement scanning, faxing, and copying.

Instead, separate the interfaces:

Printable
Scannable
Faxable
Copyable

A device can then implement only the capabilities it actually supports.

The key idea is:

Prefer small, focused interfaces over large, general-purpose interfaces.

5. D — Dependency Inversion Principle (DIP)

High-level modules should not depend directly on low-level concrete implementations. Both should depend on abstractions.

Instead of:

class EmailService:
    def send(self, message):
        pass


class Notification:
    def __init__(self):
        self.email = EmailService()

Notification is tightly coupled to EmailService.

A better design uses an abstraction:

class NotificationService:
    def send(self, message):
        raise NotImplementedError


class EmailService(NotificationService):
    def send(self, message):
        print("Email sent")


class Notification:
    def __init__(self, service):
        self.service = service

    def send(self, message):
        self.service.send(message)

Now Notification can work with different implementations:

notification = Notification(EmailService())

This also makes testing easier because a mock or fake service can be injected.

SOLID in one example

Imagine an ML prediction system:

                Prediction System
                       |
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   DataLoader      ModelService   PredictionLogger
        |              |
   CSV / DB       Model abstraction
                       |
                ┌──────┴──────┐
                ↓             ↓
             XGBoost        NeuralNet

SOLID principles can help keep responsibilities separated, allow new model types to be added, ensure implementations honor their abstractions, keep interfaces focused, and make dependencies replaceable.

Easy way to remember SOLID
S → One responsibility
O → Extend without unnecessary modification
L → Subtypes must remain substitutable
I → Small, focused interfaces
D → Depend on abstractions
Important interview point

SOLID principles are guidelines, not rigid laws. Applying them mechanically can create unnecessary abstractions and complexity. The goal is to improve design where the complexity of the system justifies it.

Interview takeaway

SOLID is a collection of five OOP design principles that encourage maintainable, extensible, loosely coupled, and testable software. The five principles are SRP, OCP, LSP, ISP, and DIP.
