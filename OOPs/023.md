# Q23. What are SOLID Principles?

## Answer

**SOLID** is a set of five object-oriented design principles that help developers write software that is:

* Easier to maintain
* Easier to extend
* Easier to test
* Easier to understand
* Less tightly coupled
* More adaptable to changing requirements

SOLID is especially useful when designing larger applications where many classes and components interact with each other.

SOLID stands for:

| Letter | Principle                             | Core Idea                                                   |
| ------ | ------------------------------------- | ----------------------------------------------------------- |
| **S**  | Single Responsibility Principle (SRP) | A class should have one main responsibility                 |
| **O**  | Open/Closed Principle (OCP)           | Open for extension, closed for modification                 |
| **L**  | Liskov Substitution Principle (LSP)   | Subtypes should be substitutable for their base types       |
| **I**  | Interface Segregation Principle (ISP) | Don't force clients to depend on methods they don't need    |
| **D**  | Dependency Inversion Principle (DIP)  | Depend on abstractions rather than concrete implementations |

A useful way to visualize SOLID is:

```text
                    SOLID
                      │
       ┌──────────────┼──────────────┐
       │              │              │
      SRP            OCP            LSP
       │              │              │
  One responsibility  Extend      Safe substitution
                      │
                 ┌────┴────┐
                 │         │
                ISP       DIP
                 │         │
            Small APIs   Abstractions
```

# 1. S — Single Responsibility Principle (SRP)

## Definition

> **A class should have one responsibility and therefore one main reason to change.**

The important idea is not that a class must contain only one method.

Instead, its methods should belong to **one closely related responsibility**.

---

## Bad Design

```python id="6p8x3r"
class Report:
    def generate(self):
        pass

    def save_to_database(self):
        pass

    def send_email(self):
        pass
```

This class handles several unrelated responsibilities:

```text id="p5a2c8"
Report
 ├── Generate report
 ├── Save to database
 └── Send email
```

If the database implementation changes, the `Report` class changes.

If email delivery changes, the same class changes.

If report-generation logic changes, it changes again.

Therefore, the class has multiple reasons to change.

---

## Better Design

Separate the responsibilities:

```python id="x9b7m2"
class ReportGenerator:
    def generate(self):
        pass


class ReportRepository:
    def save(self, report):
        pass


class EmailService:
    def send(self, report):
        pass
```

Now:

```text id="2qj4ys"
ReportGenerator
      ↓
Generates report

ReportRepository
      ↓
Stores report

EmailService
      ↓
Sends report
```

Each class has a focused responsibility.

This makes each component easier to:

* Understand
* Modify
* Test
* Reuse

---

## Real-World Example

Imagine an e-commerce application.

A poorly designed class might do everything:

```text id="3p0x7n"
Order
├── Calculate total
├── Save order
├── Send email
├── Process payment
└── Generate invoice
```

A better design could be:

```text id="x5q2ba"
Order
├── OrderCalculator
├── OrderRepository
├── PaymentService
├── EmailService
└── InvoiceGenerator
```

Each component focuses on one responsibility.

### Easy way to remember SRP

```text
SRP
 ↓
One main responsibility
 ↓
One main reason to change
```

---

# 2. O — Open/Closed Principle (OCP)

## Definition

> **Software entities should be open for extension but closed for modification.**

The goal is to add new behavior without repeatedly changing stable, existing code.

This does **not** mean that existing code can never be modified.

It means that a well-designed part of the system should allow new behavior to be added through extension points rather than requiring constant modification of existing logic.

---

## Problematic Design

Suppose we support different payment types:

```python id="4j5zq9"
if payment_type == "card":
    print("Card payment")

elif payment_type == "upi":
    print("UPI payment")

elif payment_type == "cash":
    print("Cash payment")
```

Now suppose we add:

```text
PayPal
Apple Pay
Bank Transfer
Cryptocurrency
```

We repeatedly need to modify the same conditional logic.

This can become difficult to maintain.

---

## Better Design

Define a common abstraction:

```python id="8m1x4v"
class Payment:
    def pay(self, amount):
        raise NotImplementedError


class CardPayment(Payment):
    def pay(self, amount):
        print("Card payment:", amount)


class UPIPayment(Payment):
    def pay(self, amount):
        print("UPI payment:", amount)
```

Now a new payment type can be added:

```python id="0r7c6k"
class PayPalPayment(Payment):
    def pay(self, amount):
        print("PayPal payment:", amount)
```

The existing `CardPayment` and `UPIPayment` classes don't need to be changed.

Conceptually:

```text id="j8w4xs"
Payment
   │
   ├── CardPayment
   ├── UPIPayment
   └── PayPalPayment  ← new extension
```

This is the basic idea behind OCP.

---

## Practical Example

Suppose a machine-learning application supports multiple models:

```text id="2h4m8p"
Model
 ├── XGBoost
 ├── RandomForest
 ├── NeuralNetwork
 └── Transformer
```

A prediction service can work with the common model abstraction.

When a new model is added, the prediction system can be extended instead of rewriting the existing prediction logic.

### Easy way to remember OCP

```text
OCP
 ↓
Add new behavior
 ↓
Without unnecessarily changing stable existing code
```

---

# 3. L — Liskov Substitution Principle (LSP)

## Definition

> **A subclass should be usable wherever its parent type is expected without breaking the program's expected behavior.**

For example, if:

```text id="j4n9xd"
B is a subtype of A
```

then code expecting an `A` should also work correctly when given a `B`.

---

## Example

Suppose:

```python id="3c5m8a"
class Bird:
    def fly(self):
        pass
```

If `Sparrow` inherits from `Bird`:

```python id="8z1v6q"
class Sparrow(Bird):
    def fly(self):
        print("Sparrow is flying")
```

then this should work:

```python id="q2p7wd"
def make_bird_fly(bird):
    bird.fly()


make_bird_fly(Sparrow())
```

The `Sparrow` satisfies the expected behavior.

---

## LSP Violation

Now consider:

```python id="1m8s4z"
class Penguin(Bird):
    def fly(self):
        raise Exception("Penguins cannot fly")
```

Now:

```python id="n5k7x2"
make_bird_fly(Penguin())
```

breaks.

The deeper problem is that the `Bird` abstraction incorrectly assumes that every bird can fly.

A better design is:

```python id="6t2q9w"
class Bird:
    def eat(self):
        print("Eating")


class FlyingBird(Bird):
    def fly(self):
        print("Flying")


class Sparrow(FlyingBird):
    pass


class Penguin(Bird):
    pass
```

Now only objects that actually support `fly()` are passed to functions requiring that capability.

This is the principle discussed in the previous question.

### Easy way to remember LSP

```text
LSP
 ↓
Child should safely replace Parent
 ↓
Without breaking expected behavior
```

# 4. I — Interface Segregation Principle (ISP)

## Definition

> **Clients should not be forced to depend on methods they do not use.**

In simple terms:

> **Prefer small, focused interfaces over large, general-purpose interfaces.**

---

## Problematic Design

Suppose we have an overly large interface:

```text id="c8j4m2"
Machine
├── print()
├── scan()
├── fax()
└── copy()
```

Now imagine a simple printer.

It only supports:

```text
print()
```

But if it is forced to implement:

```text
scan()
fax()
copy()
```

the interface is too large.

---

## Better Design

Separate the interfaces:

```text id="z1r6xq"
Printable
Scannable
Faxable
Copyable
```

For example:

```python id="p3x7m9"
class Printable:
    def print(self):
        pass


class Scannable:
    def scan(self):
        pass


class Faxable:
    def fax(self):
        pass
```

A simple printer only needs the capability it supports.

A multifunction printer can implement multiple capabilities.

```text id="n7w5ka"
SimplePrinter
      │
      └── Printable


OfficeMachine
 ├── Printable
 ├── Scannable
 ├── Faxable
 └── Copyable
```

This avoids forcing classes to implement unnecessary methods.

---

## Real-World Example

Think about a media player.

Instead of one huge interface:

```text id="5c1w9e"
MediaDevice
├── playAudio()
├── recordAudio()
├── recordVideo()
├── streamVideo()
└── print()
```

we can separate capabilities:

```text id="3v8j2k"
AudioPlayer
VideoPlayer
AudioRecorder
VideoRecorder
```

A device implements only what it actually supports.

### Easy way to remember ISP

```text
ISP
 ↓
Don't force unnecessary methods
 ↓
Keep interfaces small and focused
```

# 5. D — Dependency Inversion Principle (DIP)

## Definition

> **High-level modules should not depend directly on low-level concrete implementations. Both should depend on abstractions.**

This is an important principle for reducing coupling.

---

## Problematic Design

Suppose we have:

```python id="5k2m7q"
class EmailService:
    def send(self, message):
        print("Email sent")


class Notification:
    def __init__(self):
        self.email = EmailService()
```

Here, `Notification` is directly coupled to `EmailService`.

```text id="s7q3bx"
Notification
      │
      │ directly depends on
      ▼
EmailService
```

If we later want:

```text
SMS
Push Notification
WhatsApp
Slack
```

we would need to modify `Notification`.

---

## Better Design

Create an abstraction:

```python id="8p4z1m"
class NotificationService:
    def send(self, message):
        raise NotImplementedError


class EmailService(NotificationService):
    def send(self, message):
        print("Email sent:", message)
```

Then inject the dependency:

```python id="6x9k2r"
class Notification:
    def __init__(self, service):
        self.service = service

    def send(self, message):
        self.service.send(message)
```

Now:

```python id="4v8c1s"
notification = Notification(EmailService())

notification.send("Hello")
```

The high-level `Notification` class does not need to know that the implementation is specifically email.

It depends on the expected behavior.

---

## Adding Another Implementation

We can create:

```python id="9m3f7a"
class SMSService(NotificationService):
    def send(self, message):
        print("SMS sent:", message)
```

Then:

```python id="2q6w8n"
notification = Notification(SMSService())

notification.send("Hello")
```

No modification to `Notification` is required.

Conceptually:

```text id="h8s2jd"
             Notification
                   │
                   ▼
          NotificationService
             /          \
            /            \
     EmailService      SMSService
```

This is dependency inversion.

---

## Testing Benefit

DIP also makes testing easier.

We can inject a fake implementation:

```python id="3f6q9x"
class FakeNotificationService(NotificationService):
    def send(self, message):
        print("Fake notification:", message)
```

Then:

```python id="m1z7wc"
notification = Notification(FakeNotificationService())

notification.send("Test")
```

We don't need a real email or SMS service during testing.

This makes the high-level component easier to unit test.

### Easy way to remember DIP

```text
DIP
 ↓
Depend on abstractions
 ↓
Not directly on concrete implementations
```

# SOLID in One Example

Imagine an **ML prediction system**:

```text id="p7m4xa"
                    Prediction System
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
      DataLoader       ModelService    PredictionLogger
          │                │
       CSV / DB      Model abstraction
                           │
                    ┌──────┴──────┐
                    ↓             ↓
                 XGBoost       NeuralNet
```

SOLID principles can help structure this system.

### SRP

Each component has a focused responsibility:

```text id="1q9z3m"
DataLoader
     ↓
Loads data

ModelService
     ↓
Runs prediction

PredictionLogger
     ↓
Logs predictions
```

### OCP

A new model can be added:

```text id="5k8x1r"
Model
├── XGBoost
├── NeuralNet
└── Transformer  ← new
```

without unnecessarily changing stable prediction logic.

### LSP

Each model implementation should behave according to the model abstraction expected by `ModelService`.

### ISP

Instead of one enormous model interface, capabilities can be separated where appropriate:

```text id="0w7n3b"
Predictable
Trainable
Explainable
Serializable
```

A model implements only the capabilities it actually supports.

### DIP

`ModelService` depends on the model abstraction rather than directly on:

```text
XGBoost
```

or:

```text
NeuralNetwork
```

This makes implementations easier to replace.

# How the Five Principles Work Together

SOLID principles are not isolated rules.

They often reinforce one another.

For example:

```text id="7c4n9v"
SRP
 ↓
Separate responsibilities
 ↓
OCP
 ↓
Extend behavior cleanly
 ↓
LSP
 ↓
Keep subtype behavior compatible
 ↓
ISP
 ↓
Keep interfaces focused
 ↓
DIP
 ↓
Make dependencies replaceable
```

Together, they can lead to software that is:

```text id="f8q2ms"
SOLID Design
     │
     ├── Maintainable
     ├── Extensible
     ├── Testable
     ├── Flexible
     └── Loosely coupled
```

# Important Interview Point

SOLID principles are **guidelines, not rigid laws**.

Applying them mechanically can create unnecessary abstractions, extra classes, and complexity.

For example, creating an interface for every single class may make a small application harder to understand rather than easier.

The goal is not:

```text
"Use SOLID everywhere."
```

The goal is:

```text
"Use SOLID where it improves the design."
```

A good developer considers:

* System complexity
* Expected future changes
* Coupling
* Testability
* Reusability
* Team understanding
* Actual business requirements

For a small script, introducing five interfaces and ten abstractions may be unnecessary.

For a large application with many changing requirements, these principles can provide significant value.

# Interview Takeaway

> **SOLID is a collection of five OOP design principles that encourage maintainable, extensible, loosely coupled, and testable software.**

The five principles are:

```text
S → Single Responsibility Principle
O → Open/Closed Principle
L → Liskov Substitution Principle
I → Interface Segregation Principle
D → Dependency Inversion Principle
```

The most important thing is not memorizing the five names.

Understand the design problem each principle tries to solve:

```text
SRP → Too many responsibilities
OCP → Constant modification for new behavior
LSP → Broken substitution between parent and child
ISP → Large interfaces with unnecessary methods
DIP → Tight coupling to concrete implementations
```

> **SOLID is about designing software so that change is easier, dependencies are manageable, and components remain understandable and testable.**
