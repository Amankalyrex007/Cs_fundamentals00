# Q24. Explain Dependency Inversion with an Example.

## Answer

**Dependency Inversion Principle (DIP)** is the **D** in the **SOLID principles**.

It states:

> **High-level modules should not depend directly on low-level modules. Both should depend on abstractions.**

And:

> **Abstractions should not depend on details; details should depend on abstractions.**

The key idea is to prevent important business logic from becoming tightly coupled to specific implementation details.

---

# What Does This Mean?

Consider a notification system.

A high-level class `NotificationService` needs to send notifications.

If it directly creates an `EmailService`, it becomes tightly coupled to email:

```python id="9d8s2k"
class EmailService:
    def send(self, message):
        print("Sending email:", message)


class NotificationService:
    def __init__(self):
        self.email_service = EmailService()

    def notify(self, message):
        self.email_service.send(message)
```

The dependency is:

```text id="j3r8wq"
NotificationService
        │
        │ depends directly on
        ▼
   EmailService
```

This creates a problem.

Suppose we later want to support:

```text id="7k2m5x"
Email
SMS
WhatsApp
Push Notification
```

`NotificationService` would need to know about each concrete implementation.

For example, we might end up with:

```python id="2q7m4s"
class NotificationService:
    def __init__(self, notification_type):
        if notification_type == "email":
            self.service = EmailService()
        elif notification_type == "sms":
            self.service = SMSService()
        elif notification_type == "whatsapp":
            self.service = WhatsAppService()
```

As more notification types are added, the high-level class keeps changing.

This is exactly the kind of tight coupling DIP tries to avoid.

---

# Applying Dependency Inversion

Instead of making `NotificationService` depend directly on `EmailService`, introduce an **abstraction**.

```python id="7v4x1n"
from abc import ABC, abstractmethod


class NotificationSender(ABC):

    @abstractmethod
    def send(self, message):
        pass
```

Now concrete implementations depend on this abstraction:

```python id="0f5p9c"
class EmailService(NotificationSender):
    def send(self, message):
        print("Sending email:", message)


class SMSService(NotificationSender):
    def send(self, message):
        print("Sending SMS:", message)
```

The high-level `NotificationService` also depends on the abstraction:

```python id="k8x3w6"
class NotificationService:
    def __init__(self, sender: NotificationSender):
        self.sender = sender

    def notify(self, message):
        self.sender.send(message)
```

Now we can inject different implementations:

```python id="3h9z5v"
email_sender = EmailService()
sms_sender = SMSService()

email_notification = NotificationService(email_sender)
email_notification.notify("Hello")

sms_notification = NotificationService(sms_sender)
sms_notification.notify("Hello")
```

Output:

```text id="7r4m2p"
Sending email: Hello
Sending SMS: Hello
```

The important part is that `NotificationService` does not need to know whether the sender is:

* Email
* SMS
* WhatsApp
* Push notification
* Fake test implementation

It only expects an object that follows the `NotificationSender` abstraction.

---

# Dependency Structure

Before applying DIP:

```text id="w4q7ns"
NotificationService
        │
        ▼
   EmailService
```

The high-level module is directly coupled to a low-level implementation.

After applying DIP:

```text id="x2m9ka"
              NotificationSender
                ▲           ▲
                │           │
                │           │
        EmailService     SMSService
                ▲           ▲
                 \         /
                  \       /
              NotificationService
```

More conceptually:

```text id="0j7x3c"
             NotificationService
                     │
                     ▼
            NotificationSender
               ▲            ▲
               │            │
               │            │
          EmailService   SMSService
```

Both the high-level module and concrete implementations are connected through the abstraction.

---

# What Exactly Is the "Inversion"?

Normally, without DIP, the dependency direction may look like:

```text id="q3v8md"
High-level module
       │
       ▼
Low-level implementation
```

For example:

```text id="n5w2pr"
NotificationService
       │
       ▼
EmailService
```

The high-level business logic is forced to depend on a concrete detail.

With DIP:

```text id="2c8y7m"
          Abstraction
          ▲        ▲
          │        │
          │        │
   High-level   Low-level
     module    implementation
```

The dependency is inverted around the abstraction.

The important point is:

> The high-level policy should not be forced to depend on low-level implementation details.

---

# Why Is This Useful?

## 1. Loose Coupling

`NotificationService` doesn't need to know how an email or SMS is actually sent.

It only knows:

```python id="1m6x9c"
sender.send(message)
```

It does not need to know whether the implementation internally uses:

```text id="6q4n2z"
SMTP
SMS Gateway
WhatsApp API
Push Notification API
```

This separates **what the system wants to do** from **how the operation is implemented**.

Conceptually:

```text id="v6h8pk"
High-level logic
      │
      ▼
   Abstraction
      ▲
      │
Implementation details
```

---

## 2. Easy to Extend

We can add another implementation:

```python id="8f2q6m"
class WhatsAppService(NotificationSender):
    def send(self, message):
        print("Sending WhatsApp message:", message)
```

Then:

```python id="5w9k3a"
whatsapp_sender = WhatsAppService()

notification = NotificationService(whatsapp_sender)

notification.notify("Hello")
```

Output:

```text id="r4k1z7"
Sending WhatsApp message: Hello
```

We did **not** modify `NotificationService`.

The new behavior was added by creating another implementation of the abstraction.

This also connects to the **Open/Closed Principle**:

```text id="j7p3qx"
New implementation
       ↓
Extend the system
       ↓
Avoid changing stable high-level logic
```

---

# 3. Easier Testing

We can inject a fake implementation:

```python id="6y8m2p"
class FakeSender(NotificationSender):
    def send(self, message):
        print("Test message:", message)
```

Then:

```python id="k5r9x1"
service = NotificationService(FakeSender())

service.notify("Testing")
```

Output:

```text id="p3v7m8"
Test message: Testing
```

This avoids depending on a real email/SMS service during unit tests.

Conceptually:

```text id="c8w2q6"
Production:

NotificationService
        ↓
 EmailService


Testing:

NotificationService
        ↓
 FakeSender
```

This makes testing:

* Faster
* More predictable
* Independent of external services
* Easier to automate

---

# 4. Supports Dependency Injection

The dependency is provided from outside:

```python id="2k6x8q"
NotificationService(email_sender)
```

rather than being created internally:

```python id="9r4m1c"
self.sender = EmailService()
```

This technique is called **dependency injection**.

The class receives the object it needs instead of constructing that object itself.

---

## Without Dependency Injection

```python id="5v7n3m"
class NotificationService:
    def __init__(self):
        self.sender = EmailService()
```

The class decides which implementation to use.

```text id="6c2q8w"
NotificationService
        │
        └── creates → EmailService
```

This increases coupling.

---

## With Dependency Injection

```python id="1p9x4k"
class NotificationService:
    def __init__(self, sender):
        self.sender = sender
```

The caller decides which implementation to provide:

```python id="8m3q7v"
service = NotificationService(EmailService())
```

or:

```python id="6w2r9p"
service = NotificationService(SMSService())
```

or:

```python id="3k8x1m"
service = NotificationService(FakeSender())
```

This gives the system much greater flexibility.

---

# Dependency Inversion vs Dependency Injection

These two terms are related but **not the same**.

| Dependency Inversion                               | Dependency Injection                                 |
| -------------------------------------------------- | ---------------------------------------------------- |
| A design principle                                 | An implementation technique                          |
| Says high-level code should depend on abstractions | Provides dependencies from outside                   |
| Part of SOLID                                      | Commonly used to implement DIP                       |
| Focuses on reducing coupling                       | Focuses on supplying dependencies                    |
| Defines the desired dependency structure           | Provides a practical way to construct that structure |

So:

```text id="2q6z8p"
DIP
 ↓
Design principle

Dependency Injection
 ↓
Technique used to implement the principle
```

A useful way to remember:

> **DIP tells us how dependencies should be structured; dependency injection is one way to supply those dependencies.**

---

# Constructor Injection

The example above uses **constructor injection**:

```python id="7m3x9k"
class NotificationService:
    def __init__(self, sender):
        self.sender = sender
```

The dependency is supplied when the object is created:

```python id="5n8q2w"
service = NotificationService(EmailService())
```

This is one of the most common forms of dependency injection.

Other forms exist, such as:

* Setter injection
* Method injection
* Framework-based dependency injection

But constructor injection is often simple and explicit.

# ML Example

This principle is also useful in ML systems.

Suppose we have a prediction service.

A tightly coupled implementation might look like:

```python id="4k7x2m"
class PredictionService:

    def __init__(self):
        self.model = XGBoostModel()

    def predict(self, X):
        return self.model.predict(X)
```

The problem is that `PredictionService` is directly tied to `XGBoostModel`.

```text id="q9m3v7"
PredictionService
        │
        ▼
  XGBoostModel
```

If we want to use a neural network, we would need to modify the service.

---

# Applying DIP to the ML System

First, define a model abstraction:

```python id="8x2n5p"
class PredictionModel:

    def predict(self, X):
        raise NotImplementedError
```

Then implement different models:

```python id="3m7q1z"
class XGBoostModel(PredictionModel):

    def predict(self, X):
        # XGBoost prediction
        pass


class NeuralNetworkModel(PredictionModel):

    def predict(self, X):
        # Neural network prediction
        pass
```

Now the high-level prediction service depends on the abstraction:

```python id="6p9w4k"
class PredictionService:

    def __init__(self, model: PredictionModel):
        self.model = model

    def predict(self, X):
        return self.model.predict(X)
```

We can now provide different implementations:

```python id="1x8m3q"
xgboost_service = PredictionService(
    XGBoostModel()
)

neural_network_service = PredictionService(
    NeuralNetworkModel()
)
```

The `PredictionService` itself does not need to change.

Conceptually:

```text id="4q7z9m"
                  PredictionModel
                   ▲           ▲
                   │           │
                   │           │
             XGBoostModel   NeuralNetworkModel
                   ▲           ▲
                    \         /
                     \       /
                 PredictionService
```

This makes the prediction layer easier to extend and test.

# Another Practical Example: Database

DIP is especially useful when working with databases.

A tightly coupled service might do this:

```python id="9x3k7p"
class UserService:

    def __init__(self):
        self.database = MySQLDatabase()

    def get_user(self, user_id):
        return self.database.get_user(user_id)
```

Now `UserService` is directly coupled to MySQL.

If we later switch to PostgreSQL or MongoDB, the service needs modification.

Instead, define an abstraction:

```python id="2m8q5v"
class UserRepository:

    def get_user(self, user_id):
        raise NotImplementedError
```

Concrete implementations:

```python id="7p4x1n"
class MySQLRepository(UserRepository):

    def get_user(self, user_id):
        print("Fetching user from MySQL")


class PostgreSQLRepository(UserRepository):

    def get_user(self, user_id):
        print("Fetching user from PostgreSQL")
```

High-level service:

```python id="5q9m2k"
class UserService:

    def __init__(self, repository):
        self.repository = repository

    def get_user(self, user_id):
        return self.repository.get_user(user_id)
```

Now:

```python id="3x7n8p"
service = UserService(MySQLRepository())
```

or:

```python id="8k2m5q"
service = UserService(PostgreSQLRepository())
```

The business logic remains independent of the database implementation.

# DIP and Composition

Dependency inversion works especially well with **composition**.

Instead of:

```text id="v2m8q4"
NotificationService
        │
        └── inherits from EmailService
```

we use:

```text id="p7x3n9"
NotificationService
        │
        └── has-a → NotificationSender
```

The dependency is supplied from outside.

This gives us:

```text id="6q1m8z"
Composition
     +
Abstraction
     +
Dependency Injection
     ↓
Loosely coupled design
```

This is why DIP and the previous concept of **composition over inheritance** are often discussed together.

# Common Mistake

A common misunderstanding is:

> "DIP means never depend on concrete classes."

That is too strict.

The goal is not to eliminate every concrete dependency from the entire program.

Concrete implementations obviously need to exist somewhere.

The important point is that **high-level business logic should not be unnecessarily tied to low-level implementation details**.

For example:

```text id="3v7m1x"
High-level:
OrderService

Abstraction:
PaymentGateway

Details:
StripeGateway
PayPalGateway
RazorpayGateway
```

The `OrderService` can depend on the `PaymentGateway` abstraction while the application's configuration or composition layer chooses the concrete implementation.

# Easy Way to Remember DIP

```text id="n5x8q2"
Without DIP:

High-level
    ↓
Concrete detail


With DIP:

        Abstraction
        ▲        ▲
        │        │
High-level    Detail
```

Or simply:

> **High-level code should depend on what something does, not on exactly how it does it.**

# Interview Takeaway

> **Dependency Inversion means high-level business logic should depend on abstractions rather than concrete implementations. This reduces coupling and makes systems easier to extend, test, and maintain.**

                       ▼
