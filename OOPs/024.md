24.Explain dependency inversion with an example.
Answer

Dependency Inversion Principle (DIP) is the D in the SOLID principles.

It states:

High-level modules should not depend directly on low-level modules. Both should depend on abstractions.

And:

Abstractions should not depend on details; details should depend on abstractions.

What does this mean?

Consider a notification system.

A high-level class NotificationService needs to send notifications. If it directly creates an EmailService, it becomes tightly coupled to email:

class EmailService:
    def send(self, message):
        print("Sending email:", message)


class NotificationService:
    def __init__(self):
        self.email_service = EmailService()

    def notify(self, message):
        self.email_service.send(message)

The dependency is:

NotificationService
        ↓
   EmailService

Now suppose we want to support SMS or WhatsApp. We would have to modify NotificationService.

This violates the spirit of Dependency Inversion.

Applying Dependency Inversion

Instead of making NotificationService depend directly on EmailService, introduce an abstraction.

from abc import ABC, abstractmethod


class NotificationSender(ABC):

    @abstractmethod
    def send(self, message):
        pass


class EmailService(NotificationSender):

    def send(self, message):
        print("Sending email:", message)


class SMSService(NotificationSender):

    def send(self, message):
        print("Sending SMS:", message)


class NotificationService:

    def __init__(self, sender: NotificationSender):
        self.sender = sender

    def notify(self, message):
        self.sender.send(message)

Now we can inject different implementations:

email_sender = EmailService()
sms_sender = SMSService()

email_notification = NotificationService(email_sender)
email_notification.notify("Hello")

sms_notification = NotificationService(sms_sender)
sms_notification.notify("Hello")

The dependency structure becomes:

                 NotificationSender
                  /              \
                 /                \
                ↓                  ↓
        EmailService          SMSService
                ↑                  ↑
                 \                /
                  \              /
               NotificationService

NotificationService depends on the abstraction NotificationSender, rather than directly depending on EmailService.

Why is this useful?
1. Loose coupling

NotificationService doesn't need to know how an email or SMS is actually sent.

It only knows:

sender.send(message)
2. Easy to extend

We can add another implementation:

class WhatsAppService(NotificationSender):

    def send(self, message):
        print("Sending WhatsApp message:", message)

We don't need to modify NotificationService.

3. Easier testing

We can inject a fake implementation:

class FakeSender(NotificationSender):

    def send(self, message):
        print("Test message:", message)


service = NotificationService(FakeSender())
service.notify("Testing")

This avoids depending on a real email/SMS service during unit tests.

4. Supports dependency injection

The dependency is provided from outside:

NotificationService(email_sender)

rather than being created internally:

self.sender = EmailService()

This technique is called dependency injection.

Dependency Inversion vs Dependency Injection

These two terms are related but not the same.

Dependency Inversion	Dependency Injection
A design principle	An implementation technique
Says high-level code should depend on abstractions	Provides dependencies from outside
Part of SOLID	Commonly used to implement DIP
Focuses on reducing coupling	Focuses on supplying dependencies

So:

DIP is the principle; dependency injection is one way to implement it.

ML example

This principle is also useful in ML systems.

Instead of tightly coupling a prediction service to one specific model:

class PredictionService:
    def __init__(self):
        self.model = XGBoostModel()

we can depend on a model abstraction:

class PredictionModel:
    def predict(self, X):
        raise NotImplementedError


class XGBoostModel(PredictionModel):
    def predict(self, X):
        # XGBoost prediction
        pass


class NeuralNetworkModel(PredictionModel):
    def predict(self, X):
        # Neural network prediction
        pass


class PredictionService:
    def __init__(self, model: PredictionModel):
        self.model = model

    def predict(self, X):
        return self.model.predict(X)

Now the prediction service can work with different model implementations without changing its own logic.

Interview takeaway

Dependency Inversion means high-level business logic should depend on abstractions rather than concrete implementations. This reduces coupling and makes systems easier to extend, test, and maintain. Dependency injection is a common technique for achieving this.
