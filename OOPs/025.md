# Q25. What is Coupling and Cohesion?

## Answer

**Coupling** and **cohesion** are important software design concepts used to evaluate how well a system is structured.

A simple rule to remember is:

```text id="q8n3vz"
Low Coupling + High Cohesion
            ↓
Generally better modular design
```

In simple terms:

* **Coupling** → How much one module/class depends on other modules/classes.
* **Cohesion** → How closely the responsibilities inside a module/class belong together.

Another easy way to remember:

```text id="3r6m8p"
Coupling  → Relationship BETWEEN components
Cohesion  → Relationship WITHIN a component
```

---

# 1. Coupling

## Definition

**Coupling** measures the dependency between different components.

Consider two classes:

```text id="m2x7qk"
Class A  ─────────>  Class B
          depends on
```

The stronger the dependency between them, the higher the coupling.

---

## High Coupling

If one class heavily depends on the internal details of another class, they are **tightly coupled**.

```python id="7c4m9x"
class EmailService:
    def send_email(self, message):
        print("Email sent")


class OrderService:
    def __init__(self):
        self.email = EmailService()

    def place_order(self):
        # order logic
        self.email.send_email("Order placed")
```

Here, `OrderService` directly creates and depends on `EmailService`.

```text id="p7z2wk"
OrderService
      │
      │ directly depends on
      ▼
 EmailService
```

If the notification mechanism changes significantly, `OrderService` may need to change too.

For example, suppose the application changes from email to SMS:

```text id="6x4m1q"
EmailService
     ↓
SMSService
```

The `OrderService` may need modification because it directly knows about `EmailService`.

---

## Another Example of High Coupling

Consider:

```python id="n8q5r2"
class MySQLDatabase:
    def save(self, data):
        print("Saving to MySQL")


class UserService:
    def __init__(self):
        self.database = MySQLDatabase()

    def save_user(self, user):
        self.database.save(user)
```

`UserService` is directly coupled to `MySQLDatabase`.

If the application changes to PostgreSQL:

```text id="f4w7s9"
MySQL
  ↓
PostgreSQL
```

the `UserService` may need to change.

This is undesirable when the database is an implementation detail rather than a core part of the business logic.

---

# Low Coupling

We can reduce coupling by depending on an abstraction and injecting the dependency.

```python id="5y2k8m"
class NotificationService:
    def send(self, message):
        pass


class OrderService:
    def __init__(self, notification):
        self.notification = notification

    def place_order(self):
        # order logic
        self.notification.send("Order placed")
```

Now `OrderService` doesn't need to know whether the notification is sent through:

* Email
* SMS
* WhatsApp
* Push notification
* Some fake service used for testing

It only expects:

```python id="8m3q1v"
self.notification.send("Order placed")
```

Conceptually:

```text id="k9p4x6"
                 NotificationService
                         ▲
                         │
                         │ abstraction
                         │
                  OrderService
```

Different implementations can be supplied:

```python id="r6x2q9"
order_service = OrderService(EmailService())
```

or:

```python id="m4z7k1"
order_service = OrderService(SMSService())
```

The `OrderService` itself does not need to change.

---

# Why Low Coupling Is Useful

Low coupling generally makes a system:

* Easier to modify
* Easier to test
* Easier to extend
* Less affected by changes in other components
* Easier to maintain
* Easier to reuse

For example:

```text id="5c9x3m"
Low Coupling

OrderService
      │
      ▼
Notification abstraction
      ▲
      │
 ┌────┴────┐
 │         │
Email      SMS
```

We can change the notification implementation without changing the business logic.

# 2. Cohesion

## Definition

**Cohesion** measures how closely related the responsibilities within a single module or class are.

In simple terms:

> **Cohesion asks whether the things inside a class actually belong together.**

---

# High Cohesion

A class has **high cohesion** when its methods and data are focused on one closely related responsibility.

For example:

```python id="1x7m4p"
class UserValidator:

    def validate_email(self, email):
        pass

    def validate_password(self, password):
        pass

    def validate_username(self, username):
        pass
```

All these methods are related to **user validation**.

Therefore, the class has a focused responsibility.

```text id="9q3w7k"
UserValidator
├── validate_email()
├── validate_password()
└── validate_username()
```

All three operations belong to the same conceptual area.

This is **high cohesion**.

---

# Another Example of High Cohesion

Consider an `OrderCalculator`:

```python id="4n8x2q"
class OrderCalculator:

    def calculate_subtotal(self, items):
        pass

    def calculate_tax(self, subtotal):
        pass

    def calculate_discount(self, subtotal):
        pass

    def calculate_total(self, items):
        pass
```

All methods are related to calculating an order's price.

Therefore:

```text id="p2x5m8"
OrderCalculator
       │
       ├── subtotal
       ├── tax
       ├── discount
       └── total
```

The class has a focused purpose.

---

# Low Cohesion

A class with unrelated responsibilities has **low cohesion**:

```python id="7q1m5z"
class UserManager:

    def validate_user(self):
        pass

    def generate_report(self):
        pass

    def send_email(self):
        pass

    def calculate_salary(self):
        pass
```

These responsibilities are unrelated:

```text id="m8c4x2"
UserManager
├── User validation
├── Report generation
├── Email delivery
└── Salary calculation
```

The class becomes difficult to:

* Understand
* Test
* Modify
* Reuse
* Maintain

This is an example of **low cohesion**.

---

# Better Design

We can separate the responsibilities:

```text id="9v5k2x"
UserValidator
      ↓
User validation

ReportGenerator
      ↓
Report generation

EmailService
      ↓
Email delivery

SalaryCalculator
      ↓
Salary calculation
```

Each component then has a more focused purpose.

For example:

```python id="2m7x4q"
class UserValidator:
    def validate(self, user):
        pass


class ReportGenerator:
    def generate(self, data):
        pass


class EmailService:
    def send(self, message):
        pass


class SalaryCalculator:
    def calculate(self, employee):
        pass
```

Now each class has a clear responsibility.

---

# Coupling vs Cohesion

| Aspect        | Coupling                                 | Cohesion                                     |
| ------------- | ---------------------------------------- | -------------------------------------------- |
| Measures      | Dependency between components            | Relatedness within a component               |
| Desired level | **Low**                                  | **High**                                     |
| Focus         | Relationships between modules            | Responsibilities inside a module             |
| Question      | "How dependent are these components?"    | "Do these responsibilities belong together?" |
| Example       | `OrderService` depends on `EmailService` | `OrderValidator` contains validation logic   |
| Benefit       | Easier changes and testing               | Clearer, focused components                  |

# Easy Way to Remember

Think about a team.

## Low Coupling

Imagine two teams:

```text id="v8m2q6"
Team A  ←────────→  Team B
```

If the teams can work relatively independently, there is lower coupling.

One team's internal implementation does not constantly force changes in the other team.

---

## High Cohesion

Now look inside Team A:

```text id="3x7k1m"
Team A
├── Task 1
├── Task 2
└── Task 3
```

If all three tasks are closely related to the team's purpose, the team has high cohesion.

So:

```text id="n4q9w2"
Coupling asks:

"How dependent are these components on each other?"


Cohesion asks:

"How closely related are the responsibilities inside this component?"
```

---

# Real-World Analogy

Think about a restaurant.

Suppose there are separate teams:

```text id="1q6m8x"
Kitchen Team
Payment Team
Delivery Team
```

If the kitchen team must constantly know the internal implementation details of the payment system, there is unnecessary coupling.

A better design is for them to communicate through clear interfaces.

```text id="f3k7p9"
Kitchen
   │
   ▼
Clear interface
   │
   ▼
Payment System
```

Now consider the kitchen team itself.

If the same team is responsible for:

```text id="z8x2m5"
Cooking food
Managing payroll
Writing advertisements
Maintaining servers
```

its responsibilities are poorly focused.

If instead it focuses on food preparation:

```text id="c5n7q1"
Kitchen
├── Prepare ingredients
├── Cook food
└── Plate food
```

it has much higher cohesion.

---

# Another Technical Example

Consider an ML application.

A highly cohesive component might be:

```text id="8m3x7q"
FeaturePreprocessor
├── handle_missing_values()
├── encode_categories()
├── scale_features()
└── transform()
```

All operations are related to preprocessing.

But if the same class also handles:

```text id="r4k8w2"
FeaturePreprocessor
├── preprocessing
├── model training
├── database storage
├── email notifications
└── report generation
```

the cohesion becomes poor.

A better design would be:

```text id="v7q2m9"
FeaturePreprocessor
ModelTrainer
PredictionService
DatabaseRepository
EmailService
```

Each component has a focused responsibility.

# Connection With SOLID

These concepts appear throughout good OOP design.

## SRP Encourages High Cohesion

The **Single Responsibility Principle** encourages classes to have focused responsibilities.

```text id="2x8m4q"
SRP
 ↓
Focused responsibility
 ↓
High cohesion
```

For example:

```python id="7n5k3m"
class InvoiceGenerator:
    def generate(self, order):
        pass
```

The class is focused on invoice generation.

---

## DIP Helps Reduce Coupling

The **Dependency Inversion Principle** helps high-level modules avoid direct dependencies on concrete implementations.

```text id="9q4x6m"
DIP
 ↓
Depend on abstractions
 ↓
Lower coupling
```

For example:

```python id="1m8k5x"
class OrderService:

    def __init__(self, payment_service):
        self.payment_service = payment_service
```

The service does not need to know which concrete payment implementation is being used.

---

## Composition Can Reduce Coupling

Composition can also help avoid unnecessary dependencies created by inheritance.

Instead of:

```text id="4k7m2q"
Class A
   ↓ inherits
Class B
```

we can use:

```text id="6x9p3v"
Class A
   │
   └── has-a → Component
```

The component can often be replaced independently.

---

## Interfaces and Abstractions

Interfaces and abstractions can separate components cleanly:

```text id="w5m2q8"
OrderService
      │
      ▼
Payment
   ▲     ▲
   │     │
Card    UPI
```

`OrderService` depends on the expected behavior rather than a specific payment implementation.

This can reduce coupling.

---

# Low Coupling + High Cohesion

Good modular design generally aims for:

```text id="7x3m9q"
          Good Design
               │
       ┌───────┴───────┐
       ↓               ↓
  Low Coupling    High Cohesion
       │               │
       ↓               ↓
Less dependency    Focused classes
between modules    with related work
```

This combination makes systems easier to evolve.

For example:

```text id="n8q4x1"
OrderService
      │
      ├── Payment abstraction
      ├── Notification abstraction
      └── Repository abstraction
```

while each component remains focused:

```text id="q6m2z8"
PaymentService
      ↓
Payment-related work

EmailService
      ↓
Notification-related work

OrderRepository
      ↓
Persistence-related work
```

---

# Important Point

Low coupling does **not** mean that classes should have no dependencies.

A useful system naturally contains dependencies.

The goal is to make dependencies:

* Necessary
* Clear
* Stable
* Easy to replace
* Based on appropriate abstractions where useful

Similarly, high cohesion does not mean a class must have only one method.

A class can have many methods as long as they work together toward a closely related responsibility.

For example:

```python id="4z8m2q"
class ShoppingCart:

    def add_item(self, item):
        pass

    def remove_item(self, item):
        pass

    def calculate_total(self):
        pass

    def clear(self):
        pass
```

These methods are all related to managing a shopping cart, so the class can still have high cohesion.

# Common Mistake

A common mistake is to confuse coupling and cohesion.

Remember:

```text id="c3x7m9"
Coupling
   ↓
BETWEEN components


Cohesion
   ↓
WITHIN a component
```

For example:

```text id="p9q2w6"
OrderService ───────> EmailService
       ↑
     Coupling
```

But:

```text id="8m4x1q"
OrderValidator
├── validate_address()
├── validate_items()
└── validate_payment()
       ↑
    Cohesion
```

The first asks how two components depend on each other.

The second asks how closely related the responsibilities inside one component are.

---

# Interview Takeaway

> **Coupling measures how strongly different modules depend on each other, while cohesion measures how closely related the responsibilities within a module are.**

Good software design generally aims for:

```text id="5q8m2x"
LOW COUPLING
      +
HIGH COHESION
      ↓
Better modular design
```

Remember:

```text id="x7n3k9"
Coupling  → Dependency BETWEEN components
Cohesion  → Relatedness WITHIN a component
```

And the relationship with SOLID:

```text id="r2m6q8"
SRP → Encourages high cohesion

DIP → Helps reduce coupling

Composition → Can reduce unnecessary coupling

Abstraction → Separates components cleanly
```

The ultimate goal is not to eliminate coupling or maximize cohesion blindly, but to create **clear, focused, loosely connected components that can evolve independently where practical**.
