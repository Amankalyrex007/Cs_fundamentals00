27.How would you design a class hierarchy for a real-world problem?
Answer

Designing a class hierarchy means identifying common characteristics and behaviors, putting them into a suitable base class, and then creating subclasses for specialized behavior.

A good hierarchy should model genuine “is-a” relationships and avoid inheritance just for code reuse.

Example: Designing a class hierarchy for a payment system

Suppose we are designing a system that supports different payment methods:

Credit Card
UPI
PayPal

We can start with a common abstraction:

                Payment
                   |
        -----------------------
        |          |          |
   CreditCard     UPI       PayPal

The common Payment class can define behavior that every payment method must provide.

from abc import ABC, abstractmethod


class Payment(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(Payment):

    def pay(self, amount):
        print(f"Paid ₹{amount} using Credit Card")


class UPIPayment(Payment):

    def pay(self, amount):
        print(f"Paid ₹{amount} using UPI")


class PayPalPayment(Payment):

    def pay(self, amount):
        print(f"Paid ₹{amount} using PayPal")

Now the client code can work with the common Payment interface:

def process_payment(payment: Payment, amount):
    payment.pay(amount)


process_payment(CreditCardPayment(), 1000)
process_payment(UPIPayment(), 500)
process_payment(PayPalPayment(), 2000)

The caller doesn't need to know the internal implementation of each payment method.

How to design a hierarchy step by step

1. Identify the main entity

Ask: What is the general concept?

Here:

Payment

2. Identify common properties and behaviors

For example:

amount
transaction ID
payment status
pay()
refund()

These may belong to the base abstraction if they genuinely apply to all payment types.

3. Identify specialized entities

Ask: What different types of this entity exist?

Payment
├── CreditCardPayment
├── UPIPayment
└── PayPalPayment

4. Identify behavior that varies

If every payment method performs payment differently, define:

pay()

in the base class and implement it differently in subclasses.

This is where polymorphism becomes useful.

5. Check the “is-a” relationship

Ask:

“Is a UPIPayment actually a Payment?”

Yes.

But:

“Is a PaymentGateway a Payment?”

Not necessarily. A gateway may be a component used by a payment rather than a subtype of it. That may suggest composition instead of inheritance.

A more realistic hierarchy

In a larger system, we might separate the payment method from the payment processor:

                 Payment
                    |
          ---------------------
          |                   |
    CardPayment          UPIPayment
          |
    CardProcessor

Or use composition:

Payment
   |
   +---- PaymentMethod
   |
   +---- PaymentProcessor

This can be preferable when components may change independently.

For example:

class PaymentProcessor:

    def process(self, method, amount):
        method.pay(amount)


class PaymentMethod(ABC):

    @abstractmethod
    def pay(self, amount):
        pass

Now the processor depends on an abstraction rather than a specific payment implementation.

Important design principles

When designing a class hierarchy, consider:

Principle	Question to ask
Inheritance	Is there a genuine “is-a” relationship?
Encapsulation	What data should each class own?
Abstraction	What common interface should be exposed?
Polymorphism	What behavior varies between subclasses?
Composition	Should some relationships be “has-a” instead?
Liskov Substitution	Can every subclass safely be used as the base type?
Single Responsibility	Does each class have a focused responsibility?
Common mistake

A common mistake is creating a deep hierarchy just to avoid duplicate code:

A
└── B
    └── C
        └── D
            └── E

Inheritance should primarily represent a meaningful subtype relationship, not merely shared code.

If two classes simply need the same functionality, composition, helper classes, or dependency injection may be better.

Interview takeaway

When asked to design a class hierarchy, use this thought process:

Identify entities → find common behavior → create abstractions → identify specialized subclasses → apply polymorphism → verify “is-a” relationships → prefer composition where inheritance creates unnecessary coupling.
