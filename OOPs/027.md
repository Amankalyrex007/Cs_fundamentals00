# Q27. How would you design a class hierarchy for a real-world problem?

## Answer

Designing a **class hierarchy** means identifying common characteristics and behaviors, putting them into a suitable base class or abstraction, and then creating subclasses for specialized behavior.

A good hierarchy should model genuine **“is-a” relationships** and avoid inheritance just for code reuse.

A useful design process is:

```text
Identify entities
       ↓
Find common behavior
       ↓
Create abstraction
       ↓
Identify specialized types
       ↓
Apply polymorphism
       ↓
Check "is-a" relationship
       ↓
Prefer composition where appropriate
```

---

# Example: Designing a Class Hierarchy for a Payment System

Suppose we are designing a system that supports different payment methods:

* Credit Card
* UPI
* PayPal

We can start with a common abstraction:

```text
                    Payment
                       │
          ┌────────────┼────────────┐
          │            │            │
     CreditCard       UPI         PayPal
```

The common `Payment` class can define behavior that every payment method must provide.

```python
from abc import ABC, abstractmethod


class Payment(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(Payment):

    def pay(self, amount):
        print(f"Paid ₹{amount} using Credit Card")


class UPIPayment(Payment):

    def pay(self, amount):
        print(f"Paid ₹{amount} using UPI")


class PayPalPayment(Payment):

    def pay(self, amount):
        print(f"Paid ₹{amount} using PayPal")
```

Now the client code can work with the common `Payment` interface:

```python
def process_payment(payment: Payment, amount):
    payment.pay(amount)


process_payment(CreditCardPayment(), 1000)
process_payment(UPIPayment(), 500)
process_payment(PayPalPayment(), 2000)
```

### Output

```text
Paid ₹1000 using Credit Card
Paid ₹500 using UPI
Paid ₹2000 using PayPal
```

The caller doesn't need to know the internal implementation of each payment method.

Conceptually:

```text
process_payment()
       │
       ▼
    Payment
       │
 ┌─────┼──────┐
 ▼     ▼      ▼
Card   UPI   PayPal
```

This is an example of **polymorphism**.

The same method call:

```python
payment.pay(amount)
```

can produce different behavior depending on the actual payment object.

# How to Design a Hierarchy Step by Step

## 1. Identify the Main Entity

Ask:

> **What is the general concept?**

Here:

```text
Payment
```

This is the common concept represented by all supported payment methods.

---

# 2. Identify Common Properties and Behaviors

Ask:

> **What characteristics or operations genuinely apply to all types?**

For example:

```text
amount
transaction ID
payment status
pay()
refund()
```

These may belong to the base abstraction if they genuinely apply to all payment types.

For example:

```python
class Payment(ABC):

    @abstractmethod
    def pay(self, amount):
        pass

    @abstractmethod
    def refund(self, amount):
        pass
```

However, we should not put something into the base class merely because it exists in one or two subclasses.

The behavior should genuinely belong to the abstraction.

---

# 3. Identify Specialized Entities

Ask:

> **What different types of this entity exist?**

For our payment system:

```text
Payment
├── CreditCardPayment
├── UPIPayment
└── PayPalPayment
```

Each subclass represents a specific kind of payment.

The important relationship is:

```text
CreditCardPayment IS-A Payment
UPIPayment       IS-A Payment
PayPalPayment    IS-A Payment
```

This is a good candidate for inheritance.

---

# 4. Identify Behavior That Varies

Ask:

> **Which behavior is common conceptually but implemented differently by each subclass?**

If every payment method performs payment differently, define:

```python
pay()
```

in the base abstraction and implement it differently in subclasses.

```text
Payment
   │
   └── pay()
       │
       ├── CreditCard → Card payment logic
       ├── UPI        → UPI payment logic
       └── PayPal     → PayPal payment logic
```

This is where **polymorphism** becomes useful.

The caller can write:

```python
payment.pay(amount)
```

without knowing which implementation will execute.

---

# 5. Check the "Is-A" Relationship

This is one of the most important steps.

Ask:

> **"Is a UPIPayment actually a Payment?"**

Yes.

Therefore:

```text
UPIPayment IS-A Payment
```

Inheritance makes sense.

But consider:

> **"Is a PaymentGateway a Payment?"**

Not necessarily.

A payment gateway is generally a component or service that may be **used by** a payment system.

That suggests a **composition** relationship rather than inheritance.

Instead of:

```text
Payment
   ↑
PaymentGateway
```

we may have:

```text
Payment
   │
   └── uses → PaymentGateway
```

This distinction is extremely important when designing real-world class hierarchies.

# A More Realistic Hierarchy

In a larger system, we might separate the **payment method** from the **payment processor**.

For example:

```text
                 Payment
                    │
          ┌─────────┴─────────┐
          │                   │
    CardPayment          UPIPayment
          │
          ▼
    CardProcessor
```

However, even this can become unnecessarily complicated if `CardProcessor` is modeled as part of the inheritance hierarchy.

A cleaner approach may be to use **composition**:

```text
PaymentProcessor
       │
       ├── uses → PaymentMethod
       │
       └── processes → amount
```

For example:

```python
from abc import ABC, abstractmethod


class PaymentMethod(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CardPayment(PaymentMethod):

    def pay(self, amount):
        print(f"Card payment: ₹{amount}")


class UPIPayment(PaymentMethod):

    def pay(self, amount):
        print(f"UPI payment: ₹{amount}")


class PaymentProcessor:

    def process(self, method: PaymentMethod, amount):
        method.pay(amount)
```

Now:

```python
processor = PaymentProcessor()

processor.process(CardPayment(), 1000)
processor.process(UPIPayment(), 500)
```

The relationship becomes:

```text
             PaymentProcessor
                    │
                    │ uses
                    ▼
              PaymentMethod
                 ▲       ▲
                 │       │
             Card       UPI
```

This can be preferable when the processor and payment methods may change independently.

---

# Why Composition Can Be Better Here

Suppose we later introduce:

```text
FraudDetectionService
TransactionLogger
CurrencyConverter
PaymentProcessor
```

These are not necessarily types of `Payment`.

Instead, they are components that collaborate with the payment system.

A possible design is:

```text
PaymentProcessor
      │
      ├── PaymentMethod
      ├── FraudDetector
      ├── TransactionLogger
      └── CurrencyConverter
```

This is composition:

```text
PaymentProcessor HAS-A PaymentMethod
PaymentProcessor HAS-A FraudDetector
PaymentProcessor HAS-A TransactionLogger
```

This avoids forcing unrelated components into an inheritance hierarchy.

# Example: E-Commerce Product Hierarchy

The same thought process can be applied to another real-world problem.

Suppose an e-commerce application sells:

```text
Physical Product
Digital Product
Subscription Product
```

We might start with:

```text
                    Product
                       │
          ┌────────────┼────────────┐
          │            │            │
       Physical      Digital     Subscription
       Product       Product       Product
```

Common properties might include:

```text
product_id
name
price
```

Common behavior could include:

```text
get_price()
```

But specialized behavior may differ.

For example:

```python
from abc import ABC, abstractmethod


class Product(ABC):

    def __init__(self, name, price):
        self.name = name
        self.price = price

    @abstractmethod
    def deliver(self):
        pass


class PhysicalProduct(Product):

    def deliver(self):
        print("Ship product to customer")


class DigitalProduct(Product):

    def deliver(self):
        print("Provide download link")


class SubscriptionProduct(Product):

    def deliver(self):
        print("Activate subscription")
```

Now the application can work with:

```python
def deliver_product(product: Product):
    product.deliver()
```

without knowing the exact product type.

This demonstrates:

```text
Abstraction
     +
Inheritance
     +
Polymorphism
```

# Important Design Principles

When designing a class hierarchy, consider:

| Principle                 | Question to Ask                                     |
| ------------------------- | --------------------------------------------------- |
| **Inheritance**           | Is there a genuine "is-a" relationship?             |
| **Encapsulation**         | What data should each class own?                    |
| **Abstraction**           | What common interface should be exposed?            |
| **Polymorphism**          | What behavior varies between subclasses?            |
| **Composition**           | Should some relationships be "has-a" instead?       |
| **Liskov Substitution**   | Can every subclass safely be used as the base type? |
| **Single Responsibility** | Does each class have a focused responsibility?      |

---

# Liskov Substitution Check

After creating a hierarchy, ask:

> **Can every subclass safely be used wherever the base class is expected?**

For example:

```python
def process_payment(payment: Payment):
    payment.pay(1000)
```

If we pass:

```python
process_payment(CreditCardPayment())
process_payment(UPIPayment())
process_payment(PayPalPayment())
```

each object should behave as a valid `Payment`.

If a subclass violates the expectations of `Payment`, the hierarchy may be poorly designed.

This is the **Liskov Substitution Principle (LSP)**.

---

# Avoid Deep Inheritance Hierarchies

A common mistake is creating a deep hierarchy just to avoid duplicate code:

```text
A
└── B
    └── C
        └── D
            └── E
```

Deep hierarchies can make a system:

* Difficult to understand
* Difficult to modify
* Tightly coupled
* Difficult to test
* Sensitive to changes in base classes

Inheritance should primarily represent a **meaningful subtype relationship**, not merely shared code.

---

# Don't Use Inheritance Just for Code Reuse

Suppose two classes both need logging:

```text
OrderService
UserService
```

It does not automatically mean:

```text
        Logger
       /      \
OrderService  UserService
```

Instead, composition may be more appropriate:

```text
OrderService ──→ Logger
UserService  ──→ Logger
```

For example:

```python
class Logger:

    def log(self, message):
        print(message)


class OrderService:

    def __init__(self, logger):
        self.logger = logger

    def create_order(self):
        self.logger.log("Order created")


class UserService:

    def __init__(self, logger):
        self.logger = logger

    def create_user(self):
        self.logger.log("User created")
```

Both services **use** a logger; neither service **is a logger**.

Therefore, composition is a better representation of the relationship.

# A Practical Class-Hierarchy Design Process

When solving an interview design problem, you can follow this sequence:

```text
1. Identify the main entity
          ↓
2. Identify common properties
          ↓
3. Identify common behavior
          ↓
4. Identify specialized types
          ↓
5. Check genuine "is-a" relationships
          ↓
6. Identify varying behavior
          ↓
7. Use polymorphism where appropriate
          ↓
8. Check Liskov Substitution
          ↓
9. Move "has-a" relationships to composition
          ↓
10. Keep responsibilities focused
```

This process prevents you from immediately jumping into inheritance without understanding the domain.

# Example Design Thought Process

Suppose the interviewer says:

> "Design a system for different types of employees."

Instead of immediately writing code, first identify the domain:

```text
Employee
   │
   ├── Developer
   ├── Manager
   └── Designer
```

Then ask:

### What is common?

```text
name
employee_id
salary
work()
```

### What varies?

```text
Developer → writes code
Manager   → manages team
Designer  → designs UI
```

### Is the relationship valid?

```text
Developer IS-A Employee
Manager   IS-A Employee
Designer  IS-A Employee
```

Yes.

Therefore, inheritance and polymorphism may be appropriate.

But suppose every employee also has:

```text
Laptop
PayrollAccount
Address
```

These are not subclasses of `Employee`.

They are components or associated objects:

```text
Employee
   │
   ├── has-a → Laptop
   ├── has-a → PayrollAccount
   └── has-a → Address
```

This is where **composition and association** become useful.

---

# Class Hierarchy vs Object Collaboration

A strong design does not focus only on inheritance.

There are two separate questions:

### 1. What is this object?

This may suggest inheritance.

```text
Dog IS-A Animal
```

### 2. What does this object use?

This may suggest composition.

```text
Car HAS-A Engine
OrderService HAS-A PaymentService
PaymentProcessor HAS-A PaymentMethod
```

A good design uses both when appropriate.

```text
Inheritance
    ↓
"What kind of thing is this?"

Composition
    ↓
"What does this thing use or contain?"
```

---

# Common Mistake

A common mistake is creating a hierarchy like:

```text
A
├── B
│   └── C
└── D
```

without first checking whether the relationships actually represent the domain.

Another common mistake is assuming:

> **"If two classes share code, they should inherit from the same base class."**

That is not necessarily true.

Shared code can often be extracted into:

* A helper class
* A utility
* A service
* A composed component
* A dependency injected into both classes

Inheritance should represent a meaningful **type relationship**.

---

# Interview-Friendly Checklist

When asked to design a class hierarchy, ask yourself:

```text
1. What is the main entity?
2. What properties are common?
3. What behavior is common?
4. What behavior varies?
5. What specialized types exist?
6. Is the relationship genuinely "is-a"?
7. Can subclasses safely replace the base type?
8. Should any relationship instead be "has-a"?
9. Is each class focused on one responsibility?
10. Is the hierarchy becoming unnecessarily deep?
```

# Interview Takeaway

When asked to design a class hierarchy, use this thought process:

```text
Identify entities
       ↓
Find common behavior
       ↓
Create abstractions
       ↓
Identify specialized subclasses
       ↓
Apply polymorphism
       ↓
Verify "is-a" relationships
       ↓
Check Liskov Substitution
       ↓
Prefer composition where inheritance creates
unnecessary coupling
```

The most important rule is:

> **Use inheritance when there is a genuine "is-a" relationship, and use composition when one object primarily uses, contains, or collaborates with another object.**

A strong real-world design is therefore not simply a large inheritance tree. It is a combination of:

```text
Abstraction
     +
Inheritance
     +
Polymorphism
     +
Composition
     +
Encapsulation
     +
Clear responsibilities
```

This produces a class structure that is easier to understand, extend, test, and maintain.
