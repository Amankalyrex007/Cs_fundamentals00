# Q28. What OOP principles have you actually used in your project?

## Answer

In a real project, I would explain OOP principles through **how they solved practical design problems**, rather than simply listing the four pillars.

For example, in an **AI/ML project such as a machine-learning prediction system**, I could explain my usage like this:

```text
ML Prediction System
        │
        ├── Encapsulation
        ├── Abstraction
        ├── Inheritance
        ├── Polymorphism
        └── Composition
```

The important part is not just saying:

> "I used OOP."

Instead, explain:

> **What problem did the principle solve, and why was it useful?**

---

# 1. Encapsulation

I used **encapsulation** to keep related data and operations together inside classes.

For example, a model class can manage its own preprocessing, training, and prediction:

```python id="c7m2px"
class MLModel:

    def __init__(self, model):
        self._model = model

    def train(self, X, y):
        self._model.fit(X, y)

    def predict(self, X):
        return self._model.predict(X)
```

The calling code doesn't need to directly manipulate the model's internal state.

For example:

```python id="p4x8kn"
model = MLModel(my_model)

model.train(X_train, y_train)
predictions = model.predict(X_test)
```

Instead of allowing the rest of the application to directly perform:

```python id="6qz1wr"
model._model.fit(...)
model._model.predict(...)
```

the class exposes controlled operations:

```text id="2n7vxm"
MLModel
├── train()
└── predict()
```

This keeps the model-related behavior in one place.

### Why I used it

Encapsulation helps:

* Reduce accidental modification
* Keep implementation details inside the class
* Provide controlled access to internal state
* Improve maintainability
* Keep related data and behavior together

---

# 2. Abstraction

I used **abstraction** when different implementations needed to follow the same interface.

For example:

```python id="8m4qyx"
from abc import ABC, abstractmethod


class Model(ABC):

    @abstractmethod
    def predict(self, X):
        pass
```

Different models can implement the same `predict()` operation:

```python id="w6r2kp"
class ClassificationModel(Model):

    def predict(self, X):
        # classification logic
        pass


class RegressionModel(Model):

    def predict(self, X):
        # regression logic
        pass
```

The rest of the application can interact with `Model` without depending on the exact implementation.

For example:

```python id="n9x3vc"
def run_prediction(model: Model, X):
    return model.predict(X)
```

The function doesn't need to know whether the model is:

```text id="q5m8zr"
ClassificationModel
       or
RegressionModel
       or
FutureModel
```

It only needs to know that the object follows the `Model` interface.

### Why I used it

Abstraction makes the system:

* Easier to extend
* Easier to replace components
* Less dependent on implementation details
* Easier to test
* Easier to maintain

---

# 3. Inheritance

I used **inheritance** when there was a genuine **"is-a" relationship**.

For example:

```python id="j3x7mb"
class BaseModel:

    def save(self):
        print("Saving model")


class ClassificationModel(BaseModel):

    def predict(self, X):
        pass


class RegressionModel(BaseModel):

    def predict(self, X):
        pass
```

Here:

```text id="8z2kqf"
ClassificationModel IS-A BaseModel
RegressionModel    IS-A BaseModel
```

Both specialized models inherit common functionality from `BaseModel`.

Therefore, they can use:

```python id="2c9pwx"
model.save()
```

without duplicating the implementation.

---

## However, I Would Not Overuse Inheritance

I would avoid using inheritance merely to reuse a few lines of code.

For example, if two unrelated classes both need logging:

```text id="5m7qvx"
OrderService ──→ Logger
UserService  ──→ Logger
```

they do not need to inherit from `Logger`.

Composition or dependency injection would usually be more appropriate.

The key question is:

> **Is this object genuinely a specialized form of the base object?**

If yes, inheritance may be appropriate.

If the relationship is:

> **"This object uses another object"**

then composition may be a better choice.

---

# 4. Polymorphism

**Polymorphism** allows the same interface to work with different implementations.

For example:

```python id="u4k8nc"
models = [
    ClassificationModel(),
    RegressionModel()
]

for model in models:
    model.predict(X)
```

The calling code uses:

```python id="7m2xqp"
model.predict(X)
```

without needing to know which concrete model it is dealing with.

Conceptually:

```text id="f9q3vw"
              Model
                │
       ┌────────┴────────┐
       │                 │
Classification       Regression
       │                 │
       └──── predict() ──┘
```

The same operation:

```python id="2h7zmk"
predict()
```

can have different implementations.

---

## Why I Used Polymorphism

Without polymorphism, we might end up writing conditional logic such as:

```python id="a4v6rx"
if model_type == "classification":
    # classification logic

elif model_type == "regression":
    # regression logic
```

As the application grows:

```text id="8k3m2q"
if classification
elif regression
elif clustering
elif neural_network
elif random_forest
...
```

This can become difficult to maintain.

With polymorphism:

```python id="q6x1zn"
model.predict(X)
```

the concrete object decides which implementation should execute.

Adding a new model can therefore require less modification to the calling code.

---

# 5. Composition

In practical projects, I would also mention **composition**, even though it is not one of the four OOP pillars.

For example, an ML prediction service might contain separate components:

```text id="m8q2vp"
PredictionService
│
├── Preprocessor
├── Model
└── Logger
```

```python id="r5k9xc"
class PredictionService:

    def __init__(self, preprocessor, model, logger):
        self.preprocessor = preprocessor
        self.model = model
        self.logger = logger

    def predict(self, X):
        X_processed = self.preprocessor.transform(X)

        prediction = self.model.predict(X_processed)

        self.logger.log(prediction)

        return prediction
```

Here:

```text id="2v7mqa"
PredictionService
      │
      ├── has-a → Preprocessor
      ├── has-a → Model
      └── has-a → Logger
```

`PredictionService` is not a type of `Preprocessor`, `Model`, or `Logger`.

Instead, it **uses** them.

This is composition.

---

# Why Composition Is Useful Here

Suppose we want to replace:

```text id="x5q9nz"
StandardScaler
```

with:

```text id="3m8vkc"
MinMaxScaler
```

We can provide another preprocessor without changing the overall structure of `PredictionService`.

Similarly, we could replace:

```text id="6q2xmw"
Logger
```

with:

```text id="7p4kzn"
FileLogger
DatabaseLogger
CloudLogger
```

The components can evolve independently.

This gives us flexibility.

---

# Putting the Principles Together

A realistic ML system might look like this:

```text id="j8q4xm"
                 PredictionService
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
    Preprocessor      Model         Logger
                        │
                 ┌──────┴──────┐
                 │             │
                 ▼             ▼
          Classification   Regression
```

Different OOP principles appear at different levels.

### Encapsulation

`PredictionService` keeps its components and prediction workflow together.

```text id="k7m2qx"
PredictionService
├── preprocessor
├── model
├── logger
└── predict()
```

### Abstraction

`Model` can define a common interface:

```text id="v3x8np"
Model
   │
   └── predict()
```

### Inheritance

Specialized models can inherit from a common base when there is a genuine subtype relationship:

```text id="q2m7cw"
Model
├── ClassificationModel
└── RegressionModel
```

### Polymorphism

The application can call:

```python id="x9k4mp"
model.predict(X)
```

regardless of the concrete model.

### Composition

`PredictionService` contains:

```text id="5v8q2m"
Preprocessor
Model
Logger
```

rather than inheriting from them.

# A More Realistic Example

Suppose our ML system supports different preprocessing strategies.

We can define an abstraction:

```python id="n7q3vx"
from abc import ABC, abstractmethod


class Preprocessor(ABC):

    @abstractmethod
    def transform(self, X):
        pass
```

Then implement different preprocessors:

```python id="m2k8zc"
class StandardPreprocessor(Preprocessor):

    def transform(self, X):
        print("Applying standard scaling")
        return X


class NormalizationPreprocessor(Preprocessor):

    def transform(self, X):
        print("Applying normalization")
        return X
```

Now `PredictionService` doesn't need to know which preprocessing technique is being used:

```python id="4x9qwp"
class PredictionService:

    def __init__(self, preprocessor, model):
        self.preprocessor = preprocessor
        self.model = model

    def predict(self, X):
        X_processed = self.preprocessor.transform(X)
        return self.model.predict(X_processed)
```

We can change the preprocessing strategy:

```python id="r6m1zn"
service = PredictionService(
    StandardPreprocessor(),
    ClassificationModel()
)
```

or:

```python id="8q3vkp"
service = PredictionService(
    NormalizationPreprocessor(),
    ClassificationModel()
)
```

The `PredictionService` itself does not need to change.

This demonstrates how **abstraction + polymorphism + composition** can work together.

# How I Would Explain This in an Interview

A strong concise answer would be:

“In my project, I used encapsulation to keep model-related state and operations together, abstraction to define common interfaces for components such as models or preprocessors, inheritance where there was a genuine common base behavior, and polymorphism to allow different implementations to be used through the same interface.

I also used composition extensively—for example, a prediction service can contain a preprocessor, model, and logger. This allowed each component to be replaced or tested independently.

Overall, these principles helped keep the code modular, testable, loosely coupled, and easier to extend.”

The important thing is to connect every principle to an actual **design decision or problem it solved**, rather than simply naming the four pillars.
