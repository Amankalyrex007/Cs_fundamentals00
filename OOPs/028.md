28.What OOP principles have you actually used in your project?
Answer

In a real project, I would explain OOP principles through how they solved practical design problems, rather than simply listing the four pillars.

For example, in an AI/ML project such as a machine-learning prediction system, I could explain my usage like this:

1. Encapsulation

I used encapsulation to keep related data and operations together inside classes.

For example, a model class can manage its own preprocessing, training, and prediction:

class MLModel:
    def __init__(self, model):
        self._model = model

    def train(self, X, y):
        self._model.fit(X, y)

    def predict(self, X):
        return self._model.predict(X)

The calling code doesn't need to directly manipulate the model's internal state.

Why I used it:
It reduces accidental modification and keeps implementation details inside the class.

2. Abstraction

I used abstraction when different implementations needed to follow the same interface.

For example:

from abc import ABC, abstractmethod


class Model(ABC):

    @abstractmethod
    def predict(self, X):
        pass

Different models can implement the same predict() operation:

class ClassificationModel(Model):

    def predict(self, X):
        # classification logic
        pass


class RegressionModel(Model):

    def predict(self, X):
        # regression logic
        pass

The rest of the application can interact with Model without depending on the exact implementation.

Why I used it:
It makes the system easier to extend and replace components.

3. Inheritance

I used inheritance when there was a genuine “is-a” relationship.

For example:

class BaseModel:
    def save(self):
        print("Saving model")


class ClassificationModel(BaseModel):
    def predict(self, X):
        pass


class RegressionModel(BaseModel):
    def predict(self, X):
        pass

Both specialized models inherit common functionality from BaseModel.

However, I would avoid using inheritance merely to reuse a few lines of code. In those situations, composition is often more appropriate.

4. Polymorphism

Polymorphism allows the same interface to work with different implementations.

For example:

models = [
    ClassificationModel(),
    RegressionModel()
]

for model in models:
    model.predict(X)

The calling code uses:

model.predict(X)

without needing to know which concrete model it is dealing with.

Why I used it:
It reduces conditional logic such as:

if model_type == "classification":
    ...
elif model_type == "regression":
    ...

and makes adding another model type easier.

5. Composition

In practical projects, I would also mention composition, even though it is not one of the four pillars.

For example, an ML prediction service might contain separate components:

PredictionService
├── Preprocessor
├── Model
└── Logger
class PredictionService:

    def __init__(self, preprocessor, model, logger):
        self.preprocessor = preprocessor
        self.model = model
        self.logger = logger

    def predict(self, X):
        X_processed = self.preprocessor.transform(X)
        prediction = self.model.predict(X_processed)

        self.logger.log(prediction)

        return prediction

Here, PredictionService has a preprocessor, model, and logger rather than inheriting from them.

This usually gives better flexibility because each component can be replaced independently.

How I would answer this in an interview

A strong concise answer would be:

“In my project, I used encapsulation to keep model-related state and operations together, abstraction to define common interfaces for components such as models or preprocessors, inheritance where there was a genuine common base behavior, and polymorphism to allow different implementations to be used through the same interface. I also used composition extensively—for example, a prediction service can contain a preprocessor, model, and logger. This helped keep the code modular, testable, and easier to extend.”

Interview takeaway

Don't just say “I used all four OOP principles.” The interviewer is usually testing whether you understand why you used them.
