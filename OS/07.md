# Q7. What is Context Switching?

## Definition

**Context switching** is the process by which the operating system **saves the execution state of one process or thread and restores the saved state of another**, allowing the CPU to switch between them.

The saved execution state can include information such as:

* Program counter
* CPU registers
* Stack-related information
* Process/thread state
* Scheduling-related information
* Address-space-related state when required

The information required to resume execution later is maintained by the OS using structures such as the **PCB** for processes and corresponding thread-related context.

```text
Running Task A
      ↓
Save Context A
      ↓
Select Task B
      ↓
Restore Context B
      ↓
Running Task B
```

---

# Simple Example

Suppose the CPU is executing **Process A**:

```text
CPU → Process A
```

The scheduler decides that **Process B** should run.

Conceptually:

```text
Process A
    ↓
Save its context
    ↓
PCB / Thread Context
    ↓
Load Process B's context
    ↓
CPU → Process B
```

Later, the OS may switch back:

```text
Process B
    ↓
Save its context
    ↓
Restore Process A's context
    ↓
CPU → Process A
```

Because the OS can repeatedly perform these switches, multiple processes or threads can **make progress while sharing the CPU**.

---

# What Is a Context?

A **context** is the information needed to describe the current execution state of a process or thread.

It may include:

```text
Execution Context
│
├── Program Counter
├── CPU Registers
├── Stack-related state
├── Process/Thread State
├── Scheduling Information
└── Address-space-related state
```

For example, if a process was executing instruction number `5000` when it was interrupted, the program counter must be saved so that the process can later resume from the appropriate point.

---

# What Happens During a Context Switch?

Conceptually, the following sequence occurs:

### 1. A Scheduling Event Occurs

A context switch may be triggered by events such as:

* Timer interrupt
* Higher-priority runnable task
* Process blocking for I/O
* Process becoming runnable
* System calls or other scheduling-related events

### 2. Current Task Is Stopped

The OS stops the currently running process or thread.

```text
CPU → Process A
        ↓
   Scheduling Event
```

### 3. Its Execution State Is Saved

The OS saves the relevant CPU state so the task can continue later.

```text
Process A
    ↓
Save Context
    ↓
PCB / Thread Context
```

### 4. Scheduling Information Is Updated

The OS updates the task's state and other scheduling information.

For example:

```text
Running → Ready
```

or:

```text
Running → Waiting
```

depending on why it stopped running.

### 5. Another Runnable Task Is Selected

The scheduler chooses another process or thread.

```text
Ready Queue
│
├── Process B ← Selected
├── Process C
└── Process D
```

### 6. Selected Task's Context Is Restored

The OS restores the saved execution state of Process B.

```text
PCB / Thread Context
        ↓
Restore Context
        ↓
CPU
        ↓
Process B
```

### 7. Execution Resumes

Process B continues from the appropriate saved execution point.

---

# Why Is Context Switching Needed?

A CPU may have many runnable processes or threads but only a limited number of CPU cores.

For example, on a **single-core CPU**:

```text
Time →
──────────────────────────────────────>

Process A | Process B | Process A | Process C
          ↑            ↑           ↑
        Switch       Switch      Switch
```

The CPU rapidly switches between tasks.

This creates the appearance that multiple processes are running simultaneously, even though only one can execute on that single CPU core at any instant.

---

# Context Switching on Multi-Core Systems

On a multi-core system, multiple threads can actually execute at the same time.

For example:

```text
Core 1 → Thread A
Core 2 → Thread B
Core 3 → Thread C
Core 4 → Thread D
```

This is **parallel execution**.

However, context switching is still necessary when the scheduler changes which task should run on a particular core.

For example:

```text
Core 1

Thread A
   ↓
Context Switch
   ↓
Thread C
```

So, multi-core systems do not eliminate context switching.

---

# Context Switching Overhead

A context switch is **not free**.

The OS may need to:

* Save CPU registers
* Restore CPU registers
* Save and restore execution state
* Update scheduling information
* Change address-space-related state when required
* Interact with memory-management mechanisms
* Cause effects on CPU caches and translation-related state

Therefore:

```text
Too Many Context Switches
          ↓
More OS/Scheduling Work
          ↓
Less CPU Time for Application Work
          ↓
Potential Performance Reduction
```

### Example

Suppose a CPU spends too much time switching:

```text
Task A → Switch → Task B → Switch → Task C
   ↑                                ↓
   └──────── Frequent Switching ────┘
```

The CPU may spend a significant amount of time managing execution changes instead of performing useful application work.

This is one reason why **excessive context switching can hurt performance**.

> The exact cost depends heavily on the CPU architecture, operating system, workload, and whether the switch requires changes to memory-management state.

---

# Process vs Thread Context Switching

Both **processes and threads** can be context-switched.

## Process Context Switching

Switching between processes may require changing **address-space-related state**, because separate processes normally have separate virtual address spaces.

```text
Process A
Address Space A
      ↓
 Context Switch
      ↓
Process B
Address Space B
```

This can introduce additional overhead.

## Thread Context Switching

Threads belonging to the same process generally share the same address space.

```text
Process
│
├── Thread A
└── Thread B
```

Switching between these threads can therefore be lighter in some systems because the address space may remain the same.

```text
Thread A
   ↓
Context Switch
   ↓
Thread B
```

> However, "thread switching is always cheap" is too strong. The actual cost depends on the OS, CPU architecture, runtime, scheduling state, and whether the threads belong to the same process.

---

# Context Switching vs Scheduling

These concepts are related but different.

### Scheduling

**Scheduling** is the decision about **which runnable process/thread should run next**.

### Context Switching

**Context switching** is the mechanism of **saving the current execution context and restoring another context**.

```text
Scheduler
   ↓
Chooses Process B
   ↓
Context Switch
   ↓
CPU runs Process B
```

So:

> **Scheduling decides who runs; context switching helps the CPU switch to that task.**

---

# Context Switching vs Concurrency

Context switching enables multiple tasks to make progress over time, but it does **not** necessarily mean they execute at exactly the same instant.

### Single Core

```text
A → B → A → C → B
```

This is **concurrent execution through scheduling**.

Only one task executes at a particular instant on that core.

### Multiple Cores

```text
Core 1 → Thread A
Core 2 → Thread B
```

The threads can actually execute **in parallel**.

Therefore:

```text
Concurrency ≠ Always Parallelism
```

Context switching can support concurrency, while multiple cores can additionally provide parallel execution.

---

# Real-World Example

Consider a web server running on a single CPU core:

```text
Web Server Process
│
├── Thread 1 → Request A
├── Thread 2 → Request B
└── Thread 3 → Request C
```

If Thread 1 waits for a database response:

```text
Thread 1
   ↓
Waiting for DB
   ↓
CPU can run Thread 2
```

Later:

```text
Thread 2
   ↓
Context Switch
   ↓
Thread 3
```

When the database response arrives, Thread 1 can become runnable again and may later receive CPU time.

This allows the system to keep making progress instead of leaving the CPU idle while other runnable work exists.

# Simple Analogy

Imagine a student working on three assignments.

```text
Assignment A
     ↓
Save current page
     ↓
Work on Assignment B
     ↓
Save current page
     ↓
Return to Assignment A
     ↓
Continue from saved page
```

The **saved page and notes** represent the execution context.

The student switching between assignments represents a **context switch**.

The student does not restart Assignment A from the beginning; they continue from the saved state.

---

# Important Interview Point

A context switch does **not** mean the process starts again.

Instead:

```text
Process A
   ↓
Running
   ↓
Context Switch
   ↓
Ready / Waiting
   ↓
Later Selected
   ↓
Restore Context
   ↓
Continue from Previous State
```

The saved context allows the process or thread to **resume execution from where it previously stopped**.

---

# Interview Takeaway

> **Context switching is the process of saving the state of a running process or thread and restoring the state of another so the CPU can switch execution between them. It enables multitasking and concurrency but introduces overhead.**

### Quick Memory Trick

**Context Switch = Save → Switch → Restore**

```text
Current Task
     ↓
Save Context
     ↓
Select Next Task
     ↓
Restore Context
     ↓
Run Next Task
```

### Common Follow-Up: Why Is Context Switching Generally Expensive?

Because the OS must **save and restore execution state**, update scheduling information, and potentially change memory-management and cache-related state. These operations consume CPU and system resources that could otherwise be used for application work.
