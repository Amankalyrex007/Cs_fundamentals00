9.What is a user-level vs kernel-level thread?
The main difference is who manages the threads: the application/runtime or the operating system kernel.

User-level threads

User-level threads (ULTs) are managed by a user-space thread library or runtime, without requiring the kernel to manage each thread individually.

Application
    |
 User-level
 thread library
    |
    +-- Thread 1
    +-- Thread 2
    +-- Thread 3
    |
   OS
    |
 Kernel-level execution

The application/runtime handles operations such as thread creation, scheduling, and switching.

Advantages:

Thread creation and switching can be relatively fast.
Scheduling can be customized by the runtime.
Less kernel involvement.

Disadvantages:

If the underlying kernel execution unit blocks on a blocking system call, multiple user threads may be affected depending on the threading model.
With a pure many-to-one model, user threads cannot achieve true parallel execution across multiple CPU cores.
Kernel-level threads

Kernel-level threads (KLTs) are managed and scheduled by the operating system kernel.

Operating System Kernel
    |
    +-- Thread 1
    +-- Thread 2
    +-- Thread 3

The kernel knows about these threads and can schedule them independently on available CPU cores.

Advantages:

Threads can run in parallel on multiple CPU cores.
If one thread blocks for I/O, the kernel can schedule another runnable thread.
The OS can schedule threads according to its scheduling policies.

Disadvantages:

Creating and managing threads generally involves more OS overhead than purely user-space management.
Context switching can involve kernel operations.
Comparison
User-level threads	Kernel-level threads
Managed by user-space runtime/library	Managed by OS kernel
Kernel may not see each user thread, depending on model	Kernel knows about each thread
Generally lower management overhead	Generally higher management overhead
Scheduling can be controlled by runtime	Scheduling is controlled by OS
Pure many-to-one model cannot use multiple cores in parallel	Can execute threads on multiple cores
Blocking behavior depends strongly on threading model	Kernel can schedule other threads when one blocks
Important: Many-to-one, one-to-one, and many-to-many

Threading models determine how user threads map to kernel threads:

Many-to-One

User:    T1 T2 T3 T4
              |
              v
Kernel:       K1

All user threads map to one kernel thread, so true parallelism isn't possible.

One-to-One

User:    T1   T2   T3
          |    |    |
          v    v    v
Kernel:  K1   K2   K3

Each user thread maps to a kernel thread, allowing parallel execution on multiple cores.

Many-to-Many

User:    T1 T2 T3 T4 T5
          \ |  | /  /
           \|  |/  /
Kernel:     K1 K2 K3

Multiple user threads are mapped onto multiple kernel threads.

The exact threading model depends on the operating system and runtime.

Simple analogy

Think of a company:

User-level threads: The application has its own manager who assigns tasks to workers.
Kernel-level threads: The operating system itself knows about the workers and schedules them.
Interview takeaway

User-level threads are managed primarily by a user-space runtime or library, while kernel-level threads are managed by the operating system. User-level management can reduce overhead, while kernel-level threads provide direct OS scheduling and can execute independently across multiple CPU cores.
