# Q10. What is CPU Scheduling?

## Definition

**CPU scheduling** is the process by which the operating system selects **which ready process or thread should get the CPU next**.

Since multiple processes or threads may be ready to run while a CPU core can execute only a limited amount of work at a time, the **OS scheduler** decides:

* Who runs next
* When they run
* How long they can run
* When a running task should be interrupted
* Which CPU/core should execute a runnable task on a multi-core system

The scheduler therefore acts as a mechanism for **sharing CPU resources among runnable tasks**.

---

# 1. Basic CPU Scheduling Flow

A simplified view is:

```text
        Processes / Threads
                |
                v
          +-------------+
          | Ready Queue |
          +-------------+
                |
                v
        +----------------+
        | CPU Scheduler  |
        +----------------+
                |
                v
              CPU
```

For example, suppose three processes are ready:

```text
+-----------+    +-----------+    +-----------+
| Process A |    | Process B |    | Process C |
+-----------+    +-----------+    +-----------+
        \              |              /
         \             |             /
          +------------+------------+
                       |
                       v
               CPU Scheduler
                       |
                       v
                  CPU → A
```

The scheduler chooses **Process A** according to the scheduling policy.

When A:

* finishes,
* blocks for I/O,
* yields,
* or is preempted,

the scheduler may select another runnable process.

For example:

```text
CPU:
A → A → A → A
          |
          | A blocks / time slice expires
          v
B → B → B
          |
          v
C → C
```

The exact sequence depends on the scheduling algorithm and system conditions.

---

# 2. What is the Ready Queue?

The **ready queue** contains processes or threads that are:

> **Ready to execute but currently waiting for CPU time.**

For example:

```text
Ready Queue

+-------+    +-------+    +-------+    +-------+
|   A   | →  |   B   | →  |   C   | →  |   D   |
+-------+    +-------+    +-------+    +-------+
```

These processes are not necessarily waiting for I/O.

They are waiting primarily for an opportunity to execute on a CPU.

### Important distinction

```text
Ready
  ↓
Waiting for CPU

Blocked/Waiting
  ↓
Waiting for some event
such as I/O completion
```

For example:

```text
Process A → Ready → waiting for CPU
Process B → Blocked → waiting for disk I/O
```

When B's I/O completes:

```text
Disk I/O complete
       |
       v
Blocked B
       |
       v
Ready B
       |
       v
Ready Queue
```

---

# 3. Why is CPU Scheduling Needed?

The scheduler tries to use CPU resources efficiently while providing desirable system behavior.

Important goals include:

### 1. High CPU Utilization

Keep the CPU busy as much as practical.

```text
CPU:
████████████████████
```

A CPU sitting idle while runnable work exists is generally undesirable.

However, 100% CPU utilization is not automatically the goal in every workload. For example, a system may intentionally leave capacity available for responsiveness or power management.

---

### 2. High Throughput

**Throughput** is the amount of work completed during a given period.

For example:

```text
System A:
100 tasks completed / second

System B:
150 tasks completed / second
```

System B has higher throughput for that workload.

The exact measurement depends on what the system considers a completed unit of work.

---

### 3. Low Waiting Time

**Waiting time** measures how long a process spends waiting in the ready queue for CPU time.

Example:

```text
Process A arrives
      |
      v
Ready Queue
      |
      | waits 5 ms
      v
CPU
```

Its CPU waiting time includes that 5 ms.

A good scheduling policy may try to reduce unnecessary waiting.

---

### 4. Low Turnaround Time

**Turnaround time** measures the total time from when a process arrives/submits until it completes.

```text
Arrival                         Completion
  |                                  |
  v                                  v
  +----------------------------------+
              Turnaround
```

For a batch workload, lower turnaround time can be particularly important.

---

### 5. Low Response Time

**Response time** measures how quickly a process receives its **first CPU service** after becoming ready/arriving.

This is particularly important for interactive systems.

For example:

```text
User clicks button
      |
      v
Application becomes runnable
      |
      | 20 ms
      v
Application starts processing
```

That initial delay contributes to response time.

Response time is different from turnaround time.

A program can start responding quickly but still take a long time to completely finish.

---

### 6. Fairness

The scheduler should avoid indefinitely ignoring runnable processes.

For example:

```text
A → A → A → A → A → A → ...
```

If B and C are continuously ready but never receive CPU time, the system may experience **starvation**.

A fair scheduling policy attempts to ensure that runnable tasks eventually receive CPU time, although the exact definition of fairness depends on the system.

---

# 4. Scheduling Goals Can Conflict

There is no single scheduling algorithm that maximizes every metric simultaneously.

For example:

```text
Want:
High throughput
Low waiting time
Low response time
Low turnaround time
High fairness
```

Improving one metric may sometimes hurt another.

### Example

Suppose:

```text
A = very long CPU-bound process
B = short interactive task
```

If the scheduler lets A run for a very long time:

```text
A ───────────────────────────────>
                                 |
                                 v
                                B
```

A may achieve good CPU efficiency, but B's response time can become poor.

With preemption:

```text
A ────────┐
          |
          v
B ────>
          |
          v
A ───────────────>
```

B responds sooner, but additional switching can introduce overhead.

Therefore:

> **CPU scheduling is a trade-off between competing performance and fairness goals.**

---

# 5. Preemptive vs Non-Preemptive Scheduling

One of the most important CPU scheduling classifications is whether the OS can **preempt** a running task.

---

## 5.1 Non-Preemptive Scheduling

In **non-preemptive scheduling**, once a process gets the CPU, it generally keeps it until it:

* Finishes execution, or
* Voluntarily blocks/waits, such as for I/O.

Conceptually:

```text
A ───────────────────────> finishes
                             |
                             v
                             B
```

The OS does not normally forcibly take the CPU away from A while A is running.

### Example

Suppose:

```text
A = 5 ms CPU burst
B = 2 ms CPU burst
```

If A starts first:

```text
0ms              5ms       7ms
|----------------|---------|
       A              B
```

B must wait until A gives up the CPU.

### Advantages

* Simpler scheduling behavior
* Less preemption-related overhead
* Fewer forced context switches

### Disadvantages

* A long-running process can delay short tasks
* Interactive response can become poor
* Convoy effects can occur with some policies

---

# 6. Preemptive Scheduling

In **preemptive scheduling**, the OS can interrupt a running process/thread and give the CPU to another runnable task.

Conceptually:

```text
A ─────────┐
           | preempt
           v
B ────────────────>
                  |
                  v
A resumes ────────>
```

A may be preempted because:

* Its time quantum expires
* A higher-priority task becomes runnable
* The scheduler determines another task should run
* Other scheduling events occur

Modern general-purpose operating systems commonly use **preemptive scheduling**.

---

## Example

Suppose:

```text
A = CPU-bound task
B = interactive task
```

The scheduler may do:

```text
A → A → A → A
             |
             | preempt
             v
             B → B
                    |
                    v
                    A → A → A
```

This allows B to receive CPU time without waiting for A to finish completely.

---

# 7. Preemptive vs Non-Preemptive

| Feature                        | Preemptive     | Non-Preemptive                   |
| ------------------------------ | -------------- | -------------------------------- |
| OS can interrupt running task  | Yes            | Generally no                     |
| CPU can be forcibly reassigned | Yes            | No                               |
| Response for interactive tasks | Usually better | Can be worse                     |
| Scheduling complexity          | Higher         | Simpler                          |
| Forced context switches        | Possible       | Less common                      |
| Modern general-purpose OS      | Common         | Less common as the overall model |
| Example concept                | Round Robin    | FCFS, non-preemptive SJF         |

> Some scheduling algorithms exist in both preemptive and non-preemptive forms, so the algorithm name alone does not always tell you whether preemption occurs.

---

# 8. Common CPU Scheduling Algorithms

Several classic scheduling algorithms are commonly studied in Operating Systems.

| Algorithm                     | Basic Idea                                          |
| ----------------------------- | --------------------------------------------------- |
| **FCFS**                      | First process to arrive runs first                  |
| **SJF**                       | Run process with the shortest expected CPU burst    |
| **SRTF**                      | Preemptive shortest-remaining-time approach         |
| **Round Robin**               | Give each runnable process a fixed time quantum     |
| **Priority Scheduling**       | Prefer processes based on priority                  |
| **Multilevel Queue**          | Separate processes into different scheduling queues |
| **Multilevel Feedback Queue** | Processes can move between queues based on behavior |

Let's understand each one.

---

# 9. FCFS — First-Come, First-Served

**FCFS** schedules processes in the order they arrive.

Example:

```text
Arrival order:

A → B → C
```

CPU execution:

```text
A → B → C
```

If:

```text
A = 8 ms
B = 2 ms
C = 1 ms
```

then:

```text
0       8      10     11
|-------|-------|------|
    A       B      C
```

### Advantage

Simple and easy to implement.

### Problem

A long process arriving first can make many short processes wait.

This is commonly associated with the **convoy effect**.

---

# 10. SJF — Shortest Job First

**Shortest Job First (SJF)** chooses the process with the shortest expected CPU burst.

Example:

```text
A = 8 ms
B = 2 ms
C = 4 ms
```

If all are ready:

```text
B → C → A
```

because:

```text
2 ms < 4 ms < 8 ms
```

SJF can provide low average waiting time under its assumptions, but the scheduler needs an estimate of future CPU burst lengths.

---

# 11. SRTF — Shortest Remaining Time First

**Shortest Remaining Time First (SRTF)** is the preemptive form related to SJF.

The scheduler considers the **remaining CPU time** of processes.

Example:

```text
A has 8 ms remaining
B has 3 ms remaining
```

If B becomes ready:

```text
A ─────────┐
           |
           | B arrives
           v
B ─────────────>
           |
           v
A resumes
```

The scheduler can preempt A because B has a shorter remaining CPU burst.

---

# 12. Round Robin Scheduling

**Round Robin (RR)** gives each runnable process a fixed amount of CPU time called a **time quantum**.

Suppose:

```text
Processes:
A
B
C

Time quantum = 2 ms
```

The scheduler may execute:

```text
A → B → C → A → B → C → ...
```

For example:

```text
0    2    4    6    8    10   12
|----|----|----|----|----|----|
 A    B    C    A    B    C
```

If A needs only 1 ms during its turn, it may finish early and the scheduler can move to the next runnable task.

---

## Why is Round Robin useful?

It is particularly useful for interactive/time-sharing workloads because one runnable process should not normally monopolize the CPU.

For example:

```text
A = CPU-heavy application
B = terminal application
C = browser task
```

Instead of:

```text
A ─────────────────────────────>
B waits...
C waits...
```

Round Robin can provide:

```text
A → B → C → A → B → C
```

This can improve responsiveness and fairness.

---

## Important: Time Quantum Trade-off

The time quantum matters.

### Very small quantum

```text
A → B → C → A → B → C → ...
```

There may be many context switches.

This increases scheduling/context-switch overhead.

### Very large quantum

Round Robin begins behaving more like FCFS for many workloads.

So:

> **A smaller quantum can improve responsiveness but increase switching overhead; a larger quantum reduces switching frequency but can increase waiting/response time for other tasks.**

---

# 13. Priority Scheduling

In **Priority Scheduling**, the scheduler selects processes according to their priority.

Conceptually:

```text
High Priority
     ↓
    P1
     ↓
Medium Priority
     ↓
    P2
     ↓
Low Priority
     ↓
    P3
```

If P1 has higher scheduling priority than P2 and both are runnable, P1 may be selected first.

Priority scheduling can be:

* Preemptive
* Non-preemptive

depending on the implementation.

### Problem: Starvation

If high-priority tasks continuously arrive:

```text
High → High → High → High → ...
```

a low-priority process may wait for a very long time.

This is called **starvation**.

### Common solution: Aging

**Aging** gradually increases the effective priority of a waiting task so that it eventually receives CPU time.

Conceptually:

```text
P3 priority:
10 → 11 → 12 → 13 → ...
```

The exact mechanism depends on the scheduler.

---

# 14. Multilevel Queue Scheduling

In **Multilevel Queue Scheduling**, processes are divided into separate queues.

For example:

```text
+--------------------------+
| Interactive Processes    |
+--------------------------+
             |
             v
+--------------------------+
| Batch Processes          |
+--------------------------+
             |
             v
+--------------------------+
| Background Processes     |
+--------------------------+
```

Different queues may use different scheduling policies.

For example:

```text
Interactive Queue → Round Robin
Batch Queue       → FCFS
```

The queues themselves also need a policy determining how CPU time is shared between them.

---

# 15. Multilevel Feedback Queue (MLFQ)

**Multilevel Feedback Queue** is more flexible because processes can **move between queues based on their observed behavior**.

For example:

```text
High-priority queue
        |
        | CPU-intensive behavior
        v
Medium-priority queue
        |
        | continues consuming CPU
        v
Low-priority queue
```

A process that frequently yields or waits for I/O may remain in a higher-priority queue, depending on the policy.

Conceptually:

```text
        +----------------+
        | High Priority  |
        +----------------+
              |
              | CPU-heavy
              v
        +----------------+
        | Medium Priority|
        +----------------+
              |
              v
        +----------------+
        | Low Priority   |
        +----------------+
```

MLFQ is useful because it attempts to distinguish different workload behaviors without requiring perfect knowledge of future CPU bursts.

---

# 16. Important CPU Scheduling Metrics

Scheduling algorithms are evaluated using several important metrics.

Suppose we have:

```text
Arrival Time
     ↓
Process becomes ready
     ↓
Waiting / Running
     ↓
First CPU Start
     ↓
More execution
     ↓
Completion
```

We can calculate several measurements.

---

## 16.1 Arrival Time

**Arrival Time** is the time when a process enters the system/ready state for scheduling purposes.

For example:

```text
Process A arrives at 3 ms

Arrival Time = 3 ms
```

---

## 16.2 Completion Time

**Completion Time** is the time when the process finishes execution.

Example:

```text
Process A completes at 12 ms

Completion Time = 12 ms
```

---

# 17. Turnaround Time

**Turnaround Time** is the total time from arrival until completion.

Formula:

```text
Turnaround Time
= Completion Time − Arrival Time
```

### Example

Suppose:

```text
Arrival Time = 2 ms
Completion Time = 10 ms
```

Then:

```text
Turnaround Time
= 10 − 2
= 8 ms
```

Diagram:

```text
Arrival                         Completion
  |                                 |
  v                                 v
  +---------------------------------+
               8 ms
```

---

# 18. Waiting Time

**Waiting Time** is the total time spent waiting for CPU execution.

For the simplified CPU scheduling model:

```text
Waiting Time
= Turnaround Time − CPU Burst Time
```

### Example

Suppose:

```text
Turnaround Time = 10 ms
CPU Burst Time  = 4 ms
```

Then:

```text
Waiting Time
= 10 − 4
= 6 ms
```

That 6 ms represents time the process spent not executing on the CPU, including relevant ready-queue waiting under this model.

---

# 19. Response Time

**Response Time** is the time from arrival until the process gets CPU for the **first time**.

Formula:

```text
Response Time
= First CPU Start Time − Arrival Time
```

### Example

Suppose:

```text
Arrival Time      = 5 ms
First CPU Start   = 8 ms
```

Then:

```text
Response Time
= 8 − 5
= 3 ms
```

So the process waited 3 ms before receiving its first CPU service.

---

# 20. Waiting Time vs Response Time

These two are commonly confused.

### Response Time

Measures:

> **How long until I start running for the first time?**

### Waiting Time

Measures:

> **How much total time did I spend waiting for CPU service?**

Example:

```text
Arrival
  |
  | 2 ms
  v
First CPU execution
  |
  | runs
  v
Preempted
  |
  | waits 3 ms
  v
Runs again
  |
  v
Completion
```

Here:

```text
Response Time = initial wait
Waiting Time  = total CPU-ready waiting
```

So response time and waiting time are not the same metric.

---

# 21. Complete Scheduling Example

Suppose three processes arrive at time 0:

| Process | Arrival Time | CPU Burst |
| ------- | -----------: | --------: |
| A       |         0 ms |      5 ms |
| B       |         0 ms |      3 ms |
| C       |         0 ms |      2 ms |

Suppose we use **FCFS**:

```text
A → B → C
```

The Gantt chart is:

```text
0        5        8       10
|--------|--------|--------|
    A        B        C
```

### Process A

```text
Completion = 5
Turnaround = 5 − 0 = 5
Waiting    = 5 − 5 = 0
Response   = 0 − 0 = 0
```

### Process B

```text
Completion = 8
Turnaround = 8 − 0 = 8
Waiting    = 8 − 3 = 5
Response   = 5 − 0 = 5
```

### Process C

```text
Completion = 10
Turnaround = 10 − 0 = 10
Waiting    = 10 − 2 = 8
Response   = 8 − 0 = 8
```

This example demonstrates how the scheduling order directly affects waiting and response times.

---

# 22. Average Scheduling Metrics

We can calculate average values across processes.

For example:

```text
Average Waiting Time
=
Sum of Waiting Times / Number of Processes
```

Using the previous example:

```text
Waiting times:

A = 0
B = 5
C = 8
```

Therefore:

```text
Average Waiting Time
= (0 + 5 + 8) / 3
= 13 / 3
≈ 4.33 ms
```

Similar calculations can be performed for:

* Average turnaround time
* Average response time

These values help compare scheduling algorithms for a particular workload.

---

# 23. Scheduling on Multi-Core Systems

In a multi-core CPU, multiple runnable threads can execute simultaneously.

For example:

```text
Ready Threads:

T1   T2   T3   T4   T5
 |    |    |    |    |
 +----+----+----+----+
          |
          v
     OS Scheduler
       /   |   \
      /    |    \
     v     v     v
   Core1 Core2 Core3
    T1    T3    T4
```

The remaining runnable threads may wait for CPU availability.

Scheduling on multi-core systems can involve additional concerns such as:

* Load balancing
* Processor affinity
* Cache locality
* NUMA considerations
* Per-CPU run queues

These details depend heavily on the operating system and hardware architecture.

---

# 24. Scheduler vs Context Switch

These concepts are related but **not identical**.

### Scheduler

The scheduler decides:

> **Which runnable task should run next?**

### Context Switch

The context switch performs the transition:

> **Save the current execution context and restore another task's context.**

Conceptually:

```text
Runnable Tasks
      |
      v
Scheduler
      |
      | chooses B
      v
Context Switch
      |
      v
CPU executes B
```

Therefore:

```text
Scheduling = decision
Context switch = execution of the switch
```

A scheduling decision does not necessarily imply a costly switch if the same task continues running.

---

# 25. Important: CPU Scheduling vs Process Scheduling

In modern systems, it is often more precise to talk about scheduling **threads or schedulable execution entities**, rather than only processes.

A process can contain multiple threads:

```text
Process P
   |
   +-- T1
   +-- T2
   +-- T3
```

The OS may schedule individual threads onto CPUs:

```text
T1 → Core 1
T2 → Core 2
T3 → Core 3
```

So when learning CPU scheduling, remember:

> **The fundamental schedulable unit is often a thread, although textbook discussions frequently use “process” for simplicity.**

---

# 26. Common Scheduling Problems

### 1. Starvation

A process waits indefinitely because other tasks are repeatedly favored.

```text
P1 → runs
P2 → runs
P1 → runs
P2 → runs
P3 → waits...
```

P3 may experience starvation.

---

### 2. Convoy Effect

A long CPU-bound process can cause many shorter processes to wait behind it.

```text
Long task
████████████████████

Short task  → waiting
Short task  → waiting
Short task  → waiting
```

This is particularly associated with FCFS scheduling.

---

### 3. Excessive Context Switching

If the scheduler switches too frequently:

```text
A → B → A → C → B → A → C → ...
```

too much CPU time may be spent on scheduling/context-switch overhead rather than useful application work.

---

# 27. Important Trade-off: CPU-Bound vs I/O-Bound Tasks

Different processes behave differently.

### CPU-bound process

Spends most of its time performing computation.

```text
CPU ███████████████████
```

Examples:

* Video encoding
* Large mathematical computation
* Scientific simulation

### I/O-bound process

Frequently waits for I/O.

```text
CPU → I/O wait → CPU → I/O wait → CPU
```

Examples:

* Database client
* Network application
* File-processing application

A good scheduler attempts to handle these different behaviors effectively.

For example, allowing an I/O-bound interactive task to run promptly can improve responsiveness while CPU-bound work continues using available CPU capacity.

---

# 28. Real-World Example

Imagine a laptop running:

```text
Browser
Music Player
Code Editor
Background Update
File Compression
```

Many runnable threads may exist.

The scheduler continuously decides which runnable threads should receive CPU time.

Conceptually:

```text
             Ready Threads
                   |
                   v
            OS Scheduler
                   |
       +-----------+-----------+
       |           |           |
       v           v           v
    Core 1      Core 2      Core 3
       |           |           |
    Browser      Editor      Music
```

Meanwhile, a background update may be waiting, and the file compressor may consume CPU when scheduling policy permits.

This is why multiple applications can appear to run simultaneously even though each individual CPU core can execute only a limited number of hardware threads at once.

# 30. Interview Takeaway

> **CPU scheduling is the OS mechanism for selecting which ready process or thread should execute on the CPU next.**

Its major goals include:

```text
High CPU Utilization
        +
High Throughput
        +
Low Waiting Time
        +
Low Turnaround Time
        +
Low Response Time
        +
Fairness
```

But these goals can conflict, so CPU scheduling is fundamentally a **trade-off problem**.

### Remember the core flow:

```text
Processes / Threads
        |
        v
   Ready Queue
        |
        v
 CPU Scheduler
        |
        v
      CPU
```

### Most important formulas:

```text
Turnaround Time
= Completion Time − Arrival Time

Waiting Time
= Turnaround Time − CPU Burst Time

Response Time
= First CPU Start Time − Arrival Time
```

### Most important classification:

```text
                CPU Scheduling
                      |
          +-----------+-----------+
          |                       |
     Non-Preemptive          Preemptive
          |                       |
 CPU keeps control          OS can interrupt
 until block/finish         and schedule another
```

### Memory Trick

> **Scheduling = Who runs next?**
> **Preemption = Can the OS take the CPU away?**
> **Waiting Time = How long did it wait for CPU?**
> **Turnaround Time = Arrival to completion**
> **Response Time = Arrival to first CPU service**
