# Q12. Preemptive vs Non-Preemptive Scheduling?

The key difference between **preemptive** and **non-preemptive CPU scheduling** is:

> **Can the operating system forcibly take the CPU away from a currently running process/thread?**

```text
                 CPU Scheduling
                       |
             +---------+---------+
             |                   |
             v                   v
       Preemptive          Non-Preemptive
             |                   |
       OS can interrupt    Task normally keeps CPU
       running task        until finish/block
```

This distinction affects:

* Responsiveness
* Context-switch frequency
* Scheduling overhead
* Waiting time
* System complexity
* Interactive performance
* How quickly high-priority work can execute

---

# 1. Preemptive Scheduling

## Definition

In **preemptive scheduling**, the operating system can **interrupt a currently running process or thread** and assign the CPU to another ready task.

Conceptually:

```text
Process A is running
        |
        v
Process B becomes ready
        |
        v
Scheduler decides to preempt A
        |
        v
CPU → Process B
        |
        v
A resumes later
```

Timeline:

```text
Time →

A A A A | B B B | A A A A
        ^
        |
     preemption
```

A does not need to finish before B gets an opportunity to run.

---

# 2. Example of Preemptive Scheduling

Suppose a CPU-bound process A is running:

```text
A ───────────────────────────────>
```

Now an important or interactive process B becomes ready:

```text
A ──────┐
        |
        | B becomes ready
        v
B ─────────────>
               |
               v
A resumes ───────────────>
```

The scheduler can interrupt A and give CPU time to B.

This is one of the main reasons preemptive scheduling is useful for **interactive and time-sharing systems**.

---

# 3. Why is Preemptive Scheduling Useful?

Imagine a system running a long CPU-bound process:

```text
A ─────────────────────────────────────>
```

While A is running, the user clicks a button and an interactive application becomes runnable:

```text
User action
    |
    v
Process B becomes ready
```

With preemptive scheduling:

```text
A ──────────┐
            |
            v
B ────>
            |
            v
A resumes ─────────────>
```

B does not necessarily have to wait for A to finish.

This can make the system feel much more responsive.

---

# 4. Examples of Preemptive Scheduling

Common textbook examples include:

### Round Robin

Each process gets a fixed time quantum.

```text
A → B → C → A → B → C
```

When A's quantum expires, the scheduler can preempt it.

---

### Shortest Remaining Time First (SRTF)

If a new process has a shorter remaining CPU burst:

```text
A remaining = 7 ms
B remaining = 2 ms
```

the scheduler may preempt A:

```text
A ─────┐
       |
       v
B ────>
       |
       v
A resumes
```

---

### Preemptive Priority Scheduling

If a higher-priority process becomes ready:

```text
A = lower priority
B = higher priority
```

the scheduler may do:

```text
A ──────┐
        |
        v
B ─────────>
           |
           v
A resumes
```

---

# 5. Advantages of Preemptive Scheduling

## 1. Better Responsiveness

Interactive applications can receive CPU time without waiting for long-running processes to finish.

For example:

```text
Browser
Terminal
Code Editor
```

can remain responsive even when a CPU-heavy background task is running.

---

## 2. Better Sharing of CPU Time

Multiple runnable processes can get regular opportunities to execute.

```text
A → B → C → A → B → C
```

This is particularly useful in time-sharing systems.

---

## 3. High-Priority Tasks Can Run Sooner

Suppose:

```text
A → currently running
B → higher priority
```

When B becomes runnable, the scheduler may preempt A:

```text
A ─────┐
       |
       v
B ─────────>
```

This allows the system to react to priority differences.

---

## 4. Suitable for Interactive Systems

Interactive applications care heavily about **response time**.

Examples:

* GUI applications
* Terminals
* Web browsers
* Editors
* Interactive development tools

A preemptive scheduler can prevent a single CPU-bound process from continuously monopolizing a CPU.

---

# 6. Disadvantages of Preemptive Scheduling

## 1. More Context Switches

Because the OS can interrupt running tasks:

```text
A → B → A → C → B → A
```

there may be more context switches.

A context switch requires saving the current execution state and restoring another task's state.

---

## 2. Context-Switch Overhead

A context switch itself does not perform useful application work.

Conceptually:

```text
Application work
      |
      v
Save context
      |
      v
Scheduler
      |
      v
Restore context
      |
      v
Application work
```

Frequent switching can therefore reduce the fraction of CPU time spent doing useful work.

The actual cost depends on the OS, CPU architecture, workload, and implementation.

---

## 3. Synchronization Becomes Important

Preemption can expose race conditions when multiple threads share data.

For example:

```text
Shared counter = 10
```

Thread A:

```text
read counter → 10
```

Before A updates it, the scheduler switches to B:

```text
Thread B:
read counter → 10
write counter → 11
```

A resumes:

```text
write counter → 11
```

The expected result might have been:

```text
12
```

but the result is:

```text
11
```

This is a **race condition**.

Therefore, multithreaded programs may require:

* Mutexes
* Semaphores
* Atomic operations
* Condition variables
* Other synchronization mechanisms

> The need for synchronization is fundamentally about **concurrent access to shared state**; preemption makes such interleavings possible even on a single CPU core.

---

## 4. Scheduling is More Complex

The OS must handle situations such as:

* When to preempt
* Which task should run next
* Priority changes
* Timer interrupts
* CPU affinity
* Multiple runnable threads
* Synchronization and blocking

Therefore, preemptive scheduling is generally more complex than basic non-preemptive scheduling.

---

# 7. Non-Preemptive Scheduling

## Definition

In **non-preemptive scheduling**, once a process/thread gets the CPU, it generally keeps it until it:

* Finishes, or
* Voluntarily blocks/waits, such as for I/O.

Conceptually:

```text
Process A gets CPU
        |
        v
A continues running
        |
        +------> finishes
        |
        +------> blocks/waits
        |
        v
Scheduler selects B
```

The OS generally does not forcibly take the CPU away from A while A is executing.

---

# 8. Example of Non-Preemptive Scheduling

Suppose A gets the CPU:

```text
A ───────────────────>
```

B becomes ready while A is still running:

```text
A ───────────────────────>
        ^
        |
   B becomes ready
```

B must wait:

```text
A ───────────────────────>
                          |
                          v
                          B ─────>
```

A eventually:

```text
A → finishes
```

Then:

```text
Scheduler → B
```

---

# 9. Examples of Non-Preemptive Scheduling

### FCFS

First process to arrive runs first and normally continues until completion/blocking.

```text
A → B → C
```

---

### Basic SJF

The shortest expected CPU burst is selected, but once selected, it generally runs until completion/blocking.

```text
C → B → A
```

---

### Non-Preemptive Priority Scheduling

The highest-priority ready process is selected, but once it starts, it generally keeps the CPU until it finishes or blocks.

```text
High Priority → Medium → Low
```

---

# 10. Advantages of Non-Preemptive Scheduling

## 1. Simpler Scheduling

The scheduler does not need to forcibly interrupt a running task.

The basic flow is:

```text
Select
  ↓
Run
  ↓
Finish/block
  ↓
Select next
```

This simplifies the scheduling model.

---

## 2. Fewer Forced Context Switches

Since the OS does not routinely preempt a running process, there can be fewer forced context switches.

For example:

```text
A ───────────────>
                 |
                 v
                 B
```

rather than:

```text
A → B → A → C → B
```

However, the exact number of context switches still depends on blocking, completion, and implementation details.

---

## 3. Lower Scheduling Overhead

Fewer forced scheduling decisions and context switches can reduce overhead.

This can be useful for workloads where responsiveness is less important than simple, predictable execution.

---

# 11. Disadvantages of Non-Preemptive Scheduling

## 1. Poorer Response Time for Interactive Workloads

Suppose a long CPU-bound process is running:

```text
A ─────────────────────────────>
```

An interactive process B becomes ready:

```text
B → waiting...
```

B may have to wait until A finishes or blocks.

This can make interactive applications feel slow.

---

## 2. Long-Running Processes Can Delay Other Processes

Consider:

```text
A = 20 ms
B = 2 ms
C = 1 ms
```

If A starts first:

```text
A ────────────────────> B → C
```

B and C have very small workloads but must wait for A.

---

## 3. Convoy Effect

FCFS is a classic example.

A long process can create a queue of short processes:

```text
Long process
A ─────────────────────>

Short B → waiting
Short C → waiting
Short D → waiting
```

This is called the **convoy effect**.

---

# 12. Preemptive vs Non-Preemptive Comparison

| Feature                           | Preemptive                       | Non-Preemptive                   |
| --------------------------------- | -------------------------------- | -------------------------------- |
| Can OS interrupt running process? | Yes                              | Generally no                     |
| CPU can be forcibly reassigned?   | Yes                              | Generally no                     |
| Responsiveness                    | Usually better                   | Usually lower                    |
| Context switches                  | Potentially more                 | Usually fewer                    |
| Scheduling complexity             | Higher                           | Simpler                          |
| Scheduling overhead               | Generally higher                 | Generally lower                  |
| Interactive workloads             | Well suited                      | Can perform poorly               |
| Long-running process              | Can be interrupted               | Can delay others                 |
| Example                           | Round Robin                      | FCFS                             |
| Typical use                       | Interactive/time-sharing systems | Simpler/batch-oriented workloads |

> “Higher” and “lower” here are general tendencies, not universal performance guarantees.

---

# 13. Simple Example

Suppose:

```text
A starts running
B arrives later
```

---

## Preemptive

```text
Time →

A A A A | B B B | A A A
        ^
        |
     Preemption
```

Detailed flow:

```text
A starts
   ↓
B arrives
   ↓
Scheduler decides to preempt A
   ↓
CPU → B
   ↓
B finishes/blocks
   ↓
A resumes
```

The scheduler can interrupt A.

---

## Non-Preemptive

```text
Time →

A A A A A A A A | B B B
                  ^
                  |
              A finishes
```

Detailed flow:

```text
A starts
   ↓
B arrives
   ↓
A continues
   ↓
A finishes/blocks
   ↓
Scheduler selects B
```

B cannot forcibly take the CPU away from A.

---

# 14. Important Connection to Context Switching

Preemption frequently causes a context switch.

For example:

```text
A running
   |
   v
Timer / scheduling event
   |
   v
Preempt A
   |
   v
Save A's context
   |
   v
Select B
   |
   v
Restore B's context
   |
   v
B runs
```

This introduces overhead.

However:

> **Preemption and context switching are not exactly the same thing.**

Preemption means:

> The current task is involuntarily stopped so another task can run.

Context switching means:

> The CPU execution context is changed from one task to another.

A context switch can occur for reasons other than time-slice expiration, such as blocking or yielding.

---

# 15. Preemption and Time Quantum

Round Robin provides a useful example.

Suppose:

```text
Time quantum = 2 ms
```

A process A runs:

```text
A A
```

After 2 ms:

```text
Quantum expires
       ↓
A may be preempted
       ↓
B gets CPU
```

Then:

```text
A → B → C → A
```

This is how time slicing helps prevent one runnable process from monopolizing the CPU.

---

# 16. What Happens if a Process Blocks?

Preemption is not the only way a CPU can move to another task.

Suppose A is running:

```text
A ─────────>
```

A requests disk I/O:

```text
A → Disk I/O
```

A becomes blocked:

```text
A → Blocked
```

The scheduler can select B:

```text
A → Blocked
       |
       v
Scheduler → B
```

This can happen even in a system using a non-preemptive scheduling policy because A **voluntarily gave up the CPU by blocking**.

This is an important interview distinction.

---

# 17. Preemptive vs Non-Preemptive: Interactive Example

Imagine a code editor and a CPU-heavy compression task.

```text
Compression → CPU-bound
Code Editor → Interactive
```

Suppose compression starts first:

```text
Compression
████████████████████████
```

Then the user presses a key.

The editor needs CPU time.

### Preemptive scheduling

```text
Compression ─────┐
                 |
                 v
Editor ───>
                 |
                 v
Compression ─────────>
```

The editor can receive CPU time quickly.

### Non-preemptive scheduling

```text
Compression ─────────────────>
                               |
                               v
                            Editor
```

The editor may have to wait for the compression task to finish or block.

This illustrates why preemption is strongly associated with responsive general-purpose systems.

---

# 18. Important Interview Nuance

Do not say:

> “Preemptive scheduling is always better.”

That is too broad.

Preemptive scheduling provides benefits such as:

* Better responsiveness
* Better time sharing
* Ability to react to priority changes

But it also introduces:

* Context-switch overhead
* More scheduling complexity
* More synchronization/interleaving concerns

Similarly, do not say:

> “Non-preemptive scheduling is always faster.”

It may have lower scheduling overhead, but a long-running task can cause very high waiting and response times for other tasks.

Therefore:

> **The appropriate scheduling strategy depends on the workload and system goals.**

---

# 19. Important Interview Nuance: Process vs Thread

Preemption can apply to **threads as well as processes**.

Modern operating systems commonly schedule individual threads or other schedulable execution entities.

For example:

```text
Process P
   |
   +-- Thread T1
   +-- Thread T2
   +-- Thread T3
```

The scheduler may run:

```text
T1 → CPU
T2 → CPU
T3 → CPU
```

and preempt one thread in favor of another.

Therefore, saying only:

> “The scheduler switches processes”

is often an oversimplification.

A more precise statement is:

> **The OS scheduler selects runnable execution entities, commonly threads, for CPU execution.**

---

# 20. Real-World Example

Suppose a computer is running:

```text
Browser
Code Editor
Music Player
Video Encoder
Background Backup
```

Several threads may be runnable.

A preemptive scheduler can distribute CPU time:

```text
Browser → CPU
Editor  → CPU
Encoder → CPU
Music   → CPU
Backup  → CPU
```

If the encoder is CPU-heavy, it does not necessarily get to monopolize a CPU simply because it started first.

The scheduler can periodically interrupt runnable tasks and select other tasks according to its scheduling policy.

# 23. Interview Takeaway

> **Preemptive scheduling allows the OS to interrupt a running process/thread and give the CPU to another runnable task, improving responsiveness and CPU sharing but potentially increasing context-switch and scheduling overhead.**

> **Non-preemptive scheduling lets the running task retain the CPU until it finishes or blocks, making the scheduling model simpler and often reducing forced context switches, but potentially increasing waiting and response times.**

### Memory Trick

```text
Preemptive
= OS can "take" the CPU

Non-Preemptive
= Task keeps CPU until finish/block
```

### One-line interview answer

> **The key difference is that preemptive scheduling allows the OS to forcibly interrupt a running task, while non-preemptive scheduling generally waits for the running task to finish or block before selecting another task.**
