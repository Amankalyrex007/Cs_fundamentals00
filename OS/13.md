# Q13. What is Starvation?

## Definition

**Starvation** is a scheduling or resource-allocation problem in which a **process or thread waits for an indefinitely long time** because other processes or threads continuously get the CPU or resources it needs.

In CPU scheduling, the process is usually **ready to run**, but the scheduler repeatedly chooses other processes instead.

> **Simple definition:**
> Starvation occurs when a process keeps waiting because the scheduling or resource-allocation policy repeatedly favors other processes.

---

## Example: Starvation in Priority Scheduling

Consider the following processes:

| Process | Priority |
| ------- | -------: |
| P1      |      Low |
| P2      |     High |
| P3      |     High |
| P4      |     High |

Suppose the scheduler always gives the CPU to a high-priority process.

If high-priority processes continuously arrive or remain runnable, the CPU may repeatedly execute:

```text
P2 → P3 → P4 → P2 → P3 → P4 → ...
```

Meanwhile, P1 remains ready but does not get CPU time:

```text
P1 → waiting → waiting → waiting → waiting → ...
```

This situation is called **starvation**.

### Why is P1 starving?

P1 is not blocked or sleeping. It is **ready to execute**, but the scheduler repeatedly selects higher-priority processes.

Conceptually:

```text
                Ready Queue
        ┌────────────────────────┐
        │ P1 - Low Priority      │
        │ P2 - High Priority     │
        │ P3 - High Priority     │
        │ P4 - High Priority     │
        └───────────┬────────────┘
                    ↓
              CPU Scheduler
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
   High-priority tasks     P1
      keep running       keeps waiting
```

If this continues indefinitely, P1 may never receive the CPU.

---

# Why Does Starvation Occur?

Starvation generally occurs when a scheduling or resource-allocation policy is **unfair** to some processes.

### 1. Priority Scheduling

A low-priority process may repeatedly be bypassed by higher-priority processes.

Example:

```text
P1 → Priority 10
P2 → Priority 2
P3 → Priority 1
```

If lower numerical values represent higher priority, the scheduler may repeatedly choose P2 and P3 while P1 waits.

---

### 2. Poor Scheduling Policies

A scheduling policy may favor some processes so strongly that other processes receive very little or no CPU time.

For example, an improperly designed priority system could continuously favor a particular class of tasks.

---

### 3. Continuous Arrival of Higher-Priority Tasks

Suppose P1 is waiting:

```text
P1 → waiting
```

Then a high-priority process arrives:

```text
P2 → high priority
```

The scheduler executes P2.

Before P1 gets the CPU, another high-priority process arrives:

```text
P3 → high priority
```

Then another:

```text
P4 → high priority
```

This could continue:

```text
P2 → P3 → P4 → P5 → P6 → ...
                         ↓
                        P1
                     still waiting
```

If the stream of higher-priority work continues indefinitely, P1 can starve.

---

### 4. Unfair Resource Allocation

Starvation is not limited to CPU scheduling.

It can also occur when processes repeatedly compete for resources such as:

* Locks
* Semaphores
* I/O resources
* Database resources
* Memory
* Other shared resources

For example, suppose several threads repeatedly compete for a lock:

```text
Thread A ─┐
Thread B ─┼──→ Shared Lock
Thread C ─┘
```

If the locking policy repeatedly allows A and B to acquire the lock while C keeps losing the race, C can experience starvation.

Therefore:

> **Starvation can result from unfair CPU scheduling as well as unfair resource allocation.**

---

# How Can Starvation Be Prevented?

## 1. Aging

A common solution to starvation in **priority scheduling** is called **aging**.

### What is Aging?

**Aging gradually increases the priority of a process the longer it waits.**

This prevents a low-priority process from remaining low priority forever.

For example, suppose lower numerical values mean higher priority:

### Initially

```text
P1 → Priority 10
```

P1 waits for some time.

### After waiting

```text
P1 → Priority 8
```

After waiting longer:

```text
P1 → Priority 5
```

Eventually:

```text
P1 → Priority 2
```

Now P1 has become important enough to receive CPU time.

```text
Low Priority
     ↓
P1 = 10
     ↓ aging
P1 = 8
     ↓ aging
P1 = 5
     ↓ aging
P1 = 2
     ↓
   CPU
```

### Important Note

The exact direction of priority values depends on the scheduling system.

For example:

```text
Lower number = Higher priority
```

may be used in one system, while another system may use:

```text
Higher number = Higher priority
```

The important concept is:

> **The longer a process waits, the more its scheduling priority should improve.**

---

## 2. Fair Scheduling

Scheduling policies can also reduce starvation by providing some degree of **fairness**.

Instead of allowing certain processes to dominate the CPU indefinitely, the scheduler can ensure that runnable processes eventually receive CPU time.

For example, **Round Robin** gives each runnable process a time quantum:

```text
P1 → P2 → P3 → P1 → P2 → P3 → ...
```

This prevents one process from continuously monopolizing the CPU under the basic Round Robin model.

However, fairness depends on the actual scheduling system and workload.

---

## 3. Fair Resource Allocation

For shared resources such as locks or semaphores, resource-allocation policies can be designed to avoid repeatedly favoring the same thread.

For example, a fair queue could serve waiting threads approximately in arrival order:

```text
Waiting Queue:

T1 → T2 → T3 → T4

       ↓

Resource

       ↓

T1 → T2 → T3 → T4
```

This reduces the possibility that T4 repeatedly loses access to the resource.

---

# Starvation vs Deadlock

Starvation and deadlock both involve processes waiting, but they are fundamentally different.

| Starvation                                                 | Deadlock                                                           |
| ---------------------------------------------------------- | ------------------------------------------------------------------ |
| A process waits for an excessively long or indefinite time | A group of processes is stuck waiting for each other               |
| Other processes may continue running                       | The involved processes cannot make progress                        |
| Often caused by unfair scheduling or resource allocation   | Often caused by circular resource dependencies                     |
| One process may repeatedly lose access to CPU/resource     | Multiple processes can form a waiting cycle                        |
| Aging can help with scheduling starvation                  | Deadlock prevention, avoidance, detection, or recovery may be used |

---

## Example of Starvation

Suppose:

```text
P1 → low priority
P2 → high priority
P3 → high priority
```

The scheduler continuously chooses high-priority processes:

```text
P2 → P3 → P2 → P3 → P2 → P3 → ...
```

P1 remains ready:

```text
P1 → waiting → waiting → waiting → ...
```

Other processes are still making progress.

Therefore, this is **starvation**.

---

## Example of Deadlock

Consider two processes:

```text
P1 holds Resource A
P2 holds Resource B

P1 needs B
P2 needs A
```

Diagram:

```text
P1 ──holds──→ A
│
└──needs──→ B
             ↑
             │
P2 ──holds──→ B
│
└──needs──→ A
```

Neither process can continue.

```text
P1 waits for P2
P2 waits for P1
```

This is a **deadlock**.

The key difference is:

> In starvation, **some processes may continue making progress while one process keeps waiting**.

> In deadlock, the involved processes are **stuck because they are waiting on each other**.

---

# Starvation vs Blocking

Another useful interview distinction is between **normal blocking** and starvation.

A process may temporarily block because it is waiting for:

* I/O
* A lock
* A resource
* A condition
* An event

That does **not automatically mean starvation**.

For example:

```text
P1 → waits for disk I/O
     ↓
I/O completes
     ↓
P1 → Ready
     ↓
P1 → CPU
```

This is normal blocking.

Starvation occurs when a process remains unable to obtain the required CPU/resource for an excessively long or indefinite period because other processes are repeatedly favored.

---

# Starvation in CPU Scheduling

A typical starvation scenario looks like this:

```text
        New high-priority tasks
        ↓
   ┌────┴────┐
   ↓         ↓
   P2        P3
   ↓         ↓
   └────┬────┘
        ↓
       CPU
        ↑
        │
       P1
   low priority
        │
        ↓
     waiting
```

If new high-priority tasks keep entering the system, P1 may continuously lose the CPU.

This is why scheduling algorithms often consider **fairness** in addition to metrics such as:

* CPU utilization
* Throughput
* Waiting time
* Turnaround time
* Response time

---

# Starvation in Multithreaded Programs

Starvation can also happen in multithreaded applications.

Suppose several threads compete for a lock:

```text
        Shared Lock
             │
      ┌──────┼──────┐
      ↓      ↓      ↓
     T1     T2     T3
```

If the synchronization mechanism repeatedly favors T1 and T2:

```text
T1 → lock
T2 → lock
T1 → lock
T2 → lock
T1 → lock
...
```

while T3 keeps waiting:

```text
T3 → waiting → waiting → waiting → ...
```

T3 can experience **lock starvation**.

This demonstrates that starvation is a broader concept than CPU scheduling.

---

# Starvation vs Deadlock vs Livelock

For interviews, it is useful to distinguish these three conditions:

| Condition      | What happens?                                                                 | Can other work continue?                            |
| -------------- | ----------------------------------------------------------------------------- | --------------------------------------------------- |
| **Starvation** | One or more processes wait indefinitely because others are repeatedly favored | Yes, often                                          |
| **Deadlock**   | Processes wait for each other in a cycle                                      | Involved processes cannot progress                  |
| **Livelock**   | Processes keep changing state/responding but make no useful progress          | They are active, but useful progress does not occur |

### Easy way to remember

```text
Starvation → "I keep waiting."

Deadlock   → "We are waiting for each other."

Livelock   → "We keep moving, but get nowhere."
```

---

# Real-World Analogy

Imagine a hospital emergency queue.

There are two types of patients:

```text
High-priority patients
Low-priority patient
```

If every time the low-priority patient reaches the front, another high-priority patient arrives and is always served first:

```text
High → High → High → High → High → ...
                         ↑
                    Low patient
                      waiting
```

The low-priority patient may wait indefinitely.

This is similar to **starvation in priority scheduling**.

Aging would be similar to gradually increasing the importance of the waiting patient so that they eventually receive service.

# Important Interview Points

### 1. Starvation is different from deadlock

Starvation does not necessarily mean that all processes are stuck.

```text
Starvation:
P1 waits
P2/P3/P4 continue running
```

Deadlock:

```text
P1 waits for P2
P2 waits for P1
→ neither progresses
```

---

### 2. Aging is a common solution

In priority scheduling:

```text
Longer waiting time
        ↓
Higher priority
        ↓
Eventually scheduled
```

Aging helps provide fairness.

---

### 3. Starvation can occur outside CPU scheduling

It can happen with:

* CPU scheduling
* Locks
* Semaphores
* I/O resources
* Memory/resource allocation
* Other shared resources

---

### 4. Starvation does not mean the process is terminated

A starving process may remain:

```text
Ready → Ready → Ready → Ready → ...
```

without getting enough CPU time.

It still exists and is waiting for an opportunity to proceed.

---

# Interview Takeaway

> **Starvation occurs when a process or thread waits indefinitely because the scheduling or resource-allocation policy repeatedly favors other processes or threads.**

A common solution in **priority scheduling** is **aging**, where the priority of a waiting process gradually improves over time.

### One-line memory trick

```text
Starvation = "Others keep getting the resource, while I keep waiting."
Aging      = "The longer I wait, the higher my priority becomes."
```

### Quick Revision

```text
Starvation
    │
    ├── Process/thread waits for too long
    │
    ├── Others repeatedly get CPU/resource
    │
    ├── Common cause → unfair scheduling/allocation
    │
    ├── Common solution → Aging
    │
    └── Different from Deadlock
          ├── Starvation → others may progress
          └── Deadlock → involved processes are stuck
```
