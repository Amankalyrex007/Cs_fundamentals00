# Q16. What is a Race Condition?

## Definition

A **race condition** occurs when multiple threads or processes access a **shared resource concurrently**, and the final result depends on the **timing or order** in which their operations execute.

In simple terms:

> **Two or more threads “race” to access or modify the same shared resource, and the program may produce an incorrect or unpredictable result depending on the execution order.**

Race conditions are one of the most common problems in **concurrent and multithreaded programs**.

---

# Simple Example

Suppose two threads increment the same shared variable:

```text
counter = 0
```

### Thread 1

```text
counter = counter + 1
```

### Thread 2

```text
counter = counter + 1
```

We might expect:

```text
counter = 2
```

because two threads each add `1`.

However, the operation:

```text
counter = counter + 1
```

is not necessarily one indivisible/atomic operation.

Conceptually, it can be broken into:

```text
1. Read counter
2. Add 1
3. Write counter
```

So:

```text
counter = counter + 1
```

can conceptually become:

```text
Read
  ↓
Add
  ↓
Write
```

If two threads interleave these operations incorrectly, a race condition can occur.

---

# Race Condition Example

Initially:

```text
counter = 0
```

Now suppose Thread 1 and Thread 2 execute concurrently.

A possible execution is:

| Step | Thread | Operation    | Value |
| ---: | ------ | ------------ | ----: |
|    1 | T1     | Read counter |     0 |
|    2 | T2     | Read counter |     0 |
|    3 | T1     | Add 1        |     1 |
|    4 | T2     | Add 1        |     1 |
|    5 | T1     | Write 1      |     1 |
|    6 | T2     | Write 1      |     1 |

Final result:

```text
counter = 1
```

But we expected:

```text
counter = 2
```

The update from Thread 1 was effectively lost.

This is often called a **lost update**.

---

# Why Does This Happen?

The key problem is that both threads can observe and modify the same shared value before either operation is safely completed.

The intended execution is:

```text
T1:
Read 0
Add 1
Write 1

T2:
Read 1
Add 1
Write 2
```

Result:

```text
counter = 2
```

But concurrent execution may produce:

```text
T1 → Read 0
T2 → Read 0
T1 → Write 1
T2 → Write 1
```

Result:

```text
counter = 1
```

Therefore:

> The final result depends on **which thread executes which operation first**.

That timing dependency is the core idea behind a race condition.

---

# Visual Representation

Without synchronization:

```text
             Shared counter
                   │
          ┌────────┴────────┐
          ↓                 ↓
        Thread 1          Thread 2
          │                 │
       Read 0            Read 0
          │                 │
       Add 1             Add 1
          │                 │
       Write 1           Write 1
          │                 │
          └────────┬────────┘
                   ↓
             counter = 1
```

Expected:

```text
counter = 2
```

Actual result:

```text
counter = 1
```

---

# Why Is It Called a "Race"?

The threads are effectively **racing to access or modify shared state**.

For example:

```text
Thread 1 ────────────────┐
                         ├──→ Shared Resource
Thread 2 ────────────────┘
```

Whichever operation happens first can affect what the other thread observes.

The problem is not simply that two threads exist.

The problem is:

```text
Concurrent execution
        +
Shared mutable state
        +
Unsafe synchronization
        ↓
Race condition
```

---

# Conditions That Commonly Lead to a Race Condition

A race condition typically involves the following factors.

## 1. Shared Mutable Data

Two or more threads/processes must be able to access the same mutable resource.

Examples:

* Shared counter
* Shared array
* Shared object
* Shared file
* Database record
* Shared memory
* Global variable

For example:

```text
counter
balance
inventory
queue
```

---

## 2. Concurrent Execution

Multiple execution flows must be able to overlap in time.

For example:

```text
Thread 1 ────────→
Thread 2 ────────→
```

On a multicore CPU, they may execute simultaneously.

On a single CPU core, their instructions may be interleaved through scheduling and preemption.

Either way, unsafe interleavings can create race conditions.

---

## 3. At Least One Operation Modifies the Shared Resource

For example:

```text
counter++
```

or:

```text
balance = balance - 100
```

or:

```text
inventory = inventory - 1
```

Read-only concurrent access does not create the same data race problem because the shared data is not being modified.

---

## 4. Insufficient Synchronization

If threads modify shared state without appropriate synchronization, their operations can interfere with each other.

For example:

```text
Thread 1 → counter += 1
Thread 2 → counter += 1
```

without a suitable synchronization mechanism can produce incorrect results.

---

# Another Real-World Example: Bank Account

Suppose:

```text
balance = ₹1000
```

Two threads simultaneously withdraw ₹700.

### Thread 1

```text
Read balance → ₹1000
Check → enough money
Subtract ₹700
Write → ₹300
```

### Thread 2

At nearly the same time:

```text
Read balance → ₹1000
Check → enough money
Subtract ₹700
Write → ₹300
```

Both threads may believe that ₹1000 is available.

Final balance could become:

```text
₹300
```

even though two withdrawals of ₹700 were accepted.

The expected result, if both withdrawals are supposed to be processed atomically, would be that the second withdrawal is rejected because only ₹300 remains.

This demonstrates why race conditions can be dangerous in real systems.

---

# Another Example: Inventory System

Suppose an online store has:

```text
inventory = 1
```

Two customers attempt to purchase the final item at almost the same time.

```text
Customer A → Check inventory → 1
Customer B → Check inventory → 1
```

Both see that the item is available.

Then:

```text
Customer A → inventory = 0
Customer B → inventory = 0
```

Both orders may be accepted even though only one item existed.

This is a race condition caused by unsynchronized access to shared inventory state.

---

# How Can Race Conditions Be Prevented?

Race conditions can be prevented or controlled using appropriate **synchronization mechanisms**.

Common techniques include:

* Mutex / Lock
* Semaphore
* Monitor
* Atomic operations
* Thread-safe data structures
* Message passing, where appropriate
* Transactional/concurrency-control mechanisms in systems such as databases

The correct mechanism depends on the problem and execution environment.

---

# 1. Mutex / Lock

A **mutex** allows only one thread at a time to enter a protected critical section.

For example:

```text
lock.acquire()

try:
    counter += 1
finally:
    lock.release()
```

Conceptually:

```text
Thread 1 → acquire lock → modify counter → release lock

Thread 2 → wait for lock → modify counter → release lock
```

Only one thread modifies the shared counter at a time.

Therefore, the increment becomes effectively protected from conflicting concurrent updates.

---

# Race Condition With a Lock

Without a lock:

```text
T1 → Read → Add → Write
T2 → Read → Add → Write
```

The operations can interleave:

```text
T1 → Read
T2 → Read
T1 → Write
T2 → Write
```

With a lock:

```text
T1 → Lock → Read → Add → Write → Unlock
                                  ↓
T2 ───────────────────────────→ Lock
                                ↓
                              Read
                                ↓
                              Add
                                ↓
                              Write
                                ↓
                             Unlock
```

This ensures that only one thread enters the protected section at a time.

---

# 2. Semaphore

A **semaphore** is another synchronization mechanism used to control access to shared resources.

Unlike a basic mutex, a counting semaphore can allow a limited number of threads to access a resource simultaneously.

For example, suppose a system has three identical connections:

```text
Available connections = 3
```

A semaphore can allow up to three threads to use them at once.

For a binary semaphore:

```text
0 → unavailable
1 → available
```

it can behave similarly to an exclusive access mechanism, although mutexes and binary semaphores have different semantics and ownership rules in many systems.

---

# 3. Atomic Operations

An **atomic operation** is performed as one indivisible operation from the perspective of other threads.

For example, many systems provide an atomic increment operation:

```text
atomic_increment(counter)
```

Conceptually:

```text
counter = counter + 1
```

is performed safely without allowing another thread to observe an unsafe intermediate state.

Atomic operations are particularly useful for simple shared-state operations such as:

```text
increment
decrement
compare-and-swap
exchange
```

The exact atomic operations available depend on the programming language, runtime, and hardware.

---

# 4. Thread-Safe Data Structures

Instead of manually protecting every access, a program can use data structures designed for concurrent access.

Examples include:

```text
Concurrent Queue
Concurrent Map
Thread-safe Counter
```

Such structures internally use appropriate synchronization or atomic techniques.

This can reduce the chance of introducing synchronization bugs into application code.

---

# 5. Message Passing

Another approach is to reduce direct sharing.

Instead of multiple threads modifying the same data:

```text
Thread 1 ──┐
           ├──→ Shared Memory
Thread 2 ──┘
```

they can communicate through messages:

```text
Thread 1 → Message Queue → Thread 2
```

This approach can reduce shared-memory race conditions.

Message passing is especially common in systems and architectures that emphasize isolated components or actors.

---

# Critical Section

A common interview follow-up is:

> **What is a critical section?**

A **critical section** is the part of a program where shared resources are accessed or modified and therefore may require synchronization.

For example:

```text
counter += 1
```

could be part of a critical section.

Conceptually:

```text
┌──────────────────────────────┐
│      Critical Section        │
│                              │
│    Read shared data          │
│    Modify shared data        │
│    Write shared data         │
│                              │
└──────────────────────────────┘
```

The goal is often to ensure that incompatible operations do not execute concurrently.

With a mutex:

```text
Lock
  ↓
┌──────────────────┐
│ Critical Section │
└──────────────────┘
  ↓
Unlock
```

---

# Critical Section vs Race Condition

These are related but different concepts.

| Critical Section                                 | Race Condition                                            |
| ------------------------------------------------ | --------------------------------------------------------- |
| Part of a program that accesses shared resources | A concurrency bug caused by unsafe timing/interleaving    |
| Describes a region of code                       | Describes a problem/condition                             |
| May require synchronization                      | Often occurs when synchronization is missing or incorrect |
| Example: `counter += 1`                          | Example: two threads lose an update                       |

Simple relationship:

```text
Shared Resource
      ↓
Critical Section
      ↓
Needs correct synchronization
      ↓
Without proper protection
      ↓
Race Condition
```

---

# Race Condition vs Deadlock

Race conditions and deadlocks are both concurrency problems, but they are different.

| Race Condition                                   | Deadlock                                                                       |
| ------------------------------------------------ | ------------------------------------------------------------------------------ |
| Result depends on execution timing/order         | Threads/processes wait indefinitely                                            |
| Can produce incorrect or unpredictable results   | Can cause involved threads/processes to stop making progress                   |
| Usually involves unsynchronized shared state     | Often involves circular resource/lock dependencies                             |
| Synchronization/atomic operations can prevent it | Lock ordering, avoidance, detection, timeouts, etc. can help prevent/handle it |
| Main issue: incorrect interleaving               | Main issue: indefinite waiting                                                 |

### Race condition

```text
T1 ──→ shared data ←── T2
         ↓
   unsafe interleaving
         ↓
    wrong result
```

### Deadlock

```text
T1 holds Lock A
   ↓
needs Lock B
   ↑
held by T2
   ↑
T2 needs Lock A

→ circular waiting
```

---

# Race Condition vs Starvation

It is also useful to distinguish race conditions from starvation.

| Race Condition                          | Starvation                                                        |
| --------------------------------------- | ----------------------------------------------------------------- |
| Outcome depends on concurrent timing    | A process/thread waits for an excessively long or indefinite time |
| Often produces incorrect state/result   | Main issue is lack of progress/access                             |
| Caused by unsafe concurrent access      | Often caused by unfair scheduling/resource allocation             |
| Locks, atomic operations, etc. can help | Aging/fair scheduling can help                                    |

For example:

```text
Race condition:
"Who writes the shared value first?"

Starvation:
"Why does this thread never get CPU/resource access?"
```

---

# Race Condition Does Not Require Multiple CPU Cores

An important OS interview point is that a race condition can occur even on a **single-core CPU**.

Why?

Because threads can be **interleaved** due to:

* Preemptive scheduling
* Interrupts
* Context switches
* Thread yielding

For example:

```text
Single CPU Core

T1 → Read
     ↓
   Context Switch
     ↓
T2 → Read
     ↓
   Context Switch
     ↓
T1 → Write
     ↓
   Context Switch
     ↓
T2 → Write
```

Even though only one instruction stream executes at a time, the operations can be interleaved in an unsafe order.

On a multicore system, the problem can also arise from **true simultaneous execution**.

---

# Race Condition vs Data Race

These terms are related but are not always perfectly interchangeable.

A **data race**, in the language/concurrency-model sense, generally refers to concurrent conflicting memory accesses where at least one access is a write and the accesses are not properly synchronized according to the language's memory model.

**Race condition** is a broader term for situations where program correctness depends on the timing/order of concurrent operations.

For interviews:

> A data race is a specific form of concurrency problem involving unsynchronized conflicting memory accesses, while race condition is the broader concept of timing-dependent behavior.

The exact terminology can vary between programming languages and systems.

---

# Important Synchronization Principle

The goal of synchronization is not simply:

> "Make everything execute one at a time."

Instead, the goal is:

> **Protect shared state where necessary while allowing as much safe concurrency as possible.**

For example, if two threads work on completely independent data:

```text
T1 → Data A
T2 → Data B
```

there may be no reason to serialize them.

But if both modify:

```text
Shared Counter
```

appropriate synchronization may be necessary.

---

# Common Mistakes

### Mistake 1: Thinking Every Concurrent Program Has a Race Condition

Concurrency alone does not automatically create a race condition.

```text
Concurrent execution
      ≠
Race condition
```

A race condition requires an unsafe dependency on timing/order, typically involving shared state or another shared resource.

---

### Mistake 2: Thinking `counter++` Is Always Atomic

In many programming environments, a normal increment should **not** be assumed to be atomic merely because it appears as one line of code.

Conceptually:

```text
counter++
```

may involve:

```text
Read → Modify → Write
```

Use the language/runtime's documented atomic operations or synchronization mechanisms when concurrent access is involved.

---

### Mistake 3: Thinking a Lock Makes Everything Automatically Correct

Locks help only when:

* The correct shared state is protected.
* All relevant accesses use compatible synchronization.
* Locking is done consistently.
* The lock is released correctly.
* The locking strategy does not introduce deadlocks or excessive contention.

Incorrect synchronization can still produce bugs.

# Interview Takeaway

> **A race condition is a concurrency bug where the outcome depends on the timing or ordering of concurrent operations on shared resources. If multiple threads access shared mutable data without proper synchronization, their operations may interleave in an unsafe way and produce an incorrect or unpredictable result.**

Common solutions include:

* **Mutex/locks**
* **Semaphores**
* **Monitors**
* **Atomic operations**
* **Thread-safe data structures**
* **Message passing**
