# Q17. What is a Critical Section?

## Definition

A **critical section** is a part of a program where a **shared resource is accessed or modified**, and therefore it must be protected so that multiple threads or processes do not execute the sensitive operations unsafely at the same time.

The goal is to ensure **mutual exclusion when required** and maintain the consistency of shared data.

> **Simple definition:**
> A critical section is the portion of code that accesses shared data/resources and requires appropriate synchronization to prevent unsafe concurrent access.

---

# Example

Suppose multiple threads update a shared counter:

```python
counter += 1
```

Conceptually, this operation may involve:

```text id="m4g1j7"
Read counter
     ↓
Add 1
     ↓
Write counter
```

If multiple threads perform this operation concurrently without synchronization, their operations can interleave incorrectly.

The code that reads, modifies, and writes `counter` can therefore be treated as a **critical section**.

---

# Without Synchronization

Suppose two threads execute:

```text id="v8g0kf"
counter += 1
```

at the same time.

Conceptually:

```text id="q1a5hl"
Thread 1 ──┐
           │
           ├──→ Shared counter
           │
Thread 2 ──┘
```

A possible unsafe execution is:

```text id="2j4v3k"
Initial:
counter = 0

Thread 1 → Read 0
Thread 2 → Read 0
Thread 1 → Add 1
Thread 2 → Add 1
Thread 1 → Write 1
Thread 2 → Write 1
```

Final result:

```text id="i5k6b2"
counter = 1
```

But we expected:

```text id="9xxw9a"
counter = 2
```

This can produce a **race condition**.

---

# With a Lock

A lock can protect the critical section:

```python
lock.acquire()

# Critical section
counter += 1

lock.release()
```

Conceptually:

```text id="7i8l1f"
Thread 1
   │
   ↓
Acquire Lock
   │
   ↓
┌─────────────────────┐
│  Critical Section   │
│                     │
│  counter += 1       │
│                     │
└─────────────────────┘
   │
   ↓
Release Lock
   │
   ↓
Thread 2 can enter
```

Only one thread at a time can execute the protected section when using an appropriate exclusive lock.

A safer programming pattern is generally:

```python
lock.acquire()

try:
    # Critical section
    counter += 1
finally:
    lock.release()
```

The `finally` block ensures that the lock is released even if an error occurs.

Many languages also provide higher-level constructs such as `with`, `synchronized`, or scoped lock guards to make this pattern safer.

---

# Why Is a Critical Section Important?

Multiple threads may share resources such as:

* Variables
* Objects
* Arrays
* Files
* Database records
* Queues
* Memory structures
* Counters
* Hardware resources

If multiple execution flows modify the same resource without proper coordination, the resource can become inconsistent.

For example:

```text id="mbw8x3"
Thread 1 ──→ Shared Bank Balance ←── Thread 2
```

Both threads may attempt to modify the balance simultaneously.

Therefore, the sensitive operations may need to be placed inside a critical section.

---

# Critical Section Example: Bank Account

Suppose:

```text id="my9n9r"
balance = ₹1000
```

Two threads try to withdraw money.

A withdrawal operation may conceptually be:

```text id="y0s8cx"
Read balance
     ↓
Check balance
     ↓
Subtract amount
     ↓
Write new balance
```

This sequence should be treated as an atomic logical operation when concurrent withdrawals are possible.

A protected version might look conceptually like:

```python
lock.acquire()

try:
    if balance >= amount:
        balance -= amount
finally:
    lock.release()
```

The lock protects the critical section so that two threads do not simultaneously make decisions based on the same outdated balance.

---

# Critical Section Example: Inventory

Suppose an online store has:

```text id="d9m0k8"
inventory = 1
```

Two customers attempt to purchase the final item.

Without proper synchronization:

```text id="x9u0na"
Thread 1 → Check inventory → 1
Thread 2 → Check inventory → 1

Thread 1 → Purchase
Thread 2 → Purchase
```

Both threads may believe the item is available.

The operation:

```text id="1v0slc"
Check inventory
      +
Update inventory
```

may need to be protected as a critical section.

With appropriate synchronization:

```text id="5l4m4j"
Thread 1 → Lock → Check → Update → Unlock
Thread 2 →             Wait
                         ↓
                      Lock
                         ↓
                       Check
                         ↓
                    Item unavailable
```

This prevents the unsafe interleaving.

# Critical Section Requirements

A good solution to the **critical-section problem** generally aims for three important properties:

1. **Mutual Exclusion**
2. **Progress**
3. **Bounded Waiting**

These are classic operating-system concepts and are important interview topics.

---

# 1. Mutual Exclusion

**Mutual exclusion** means that at most **one process/thread** can execute the critical section at a time when exclusive access is required.

For example:

```text id="u8s4cw"
Critical Section

      ┌─────────┐
      │   T1    │
      └─────────┘
           ↓
        executing

T2 → waiting
T3 → waiting
```

T2 and T3 cannot enter the same mutually exclusive critical section simultaneously.

After T1 leaves:

```text id="8e5n6m"
T1 → exits
     ↓
T2 → enters
```

### Main idea

```text id="y0v6i4"
Only one at a time
        ↓
Mutual Exclusion
```

---

# 2. Progress

**Progress** means that if no process/thread is currently inside the critical section, the decision about **which waiting process gets to enter next** should not be postponed unnecessarily.

For example:

```text id="h9i2s0"
Critical Section
      ↓
   empty
      ↓
T1 and T2 are waiting
      ↓
One should be allowed to enter
```

A system should not unnecessarily prevent all waiting processes from making progress when the critical section is free.

### Simple idea

```text id="q6u8q4"
Nobody is inside
       ↓
Someone is waiting
       ↓
Allow an eligible process/thread to enter
```

---

# 3. Bounded Waiting

**Bounded waiting** means that a process/thread should not wait indefinitely to enter the critical section after requesting access.

Suppose:

```text id="d8e4n1"
T1 → waiting
T2 → repeatedly enters
T3 → repeatedly enters
T1 → still waiting
```

If T1 can be postponed forever, the system violates the fairness goal represented by bounded waiting.

A bounded-waiting solution ensures there is a limit on how many times other processes can enter before a waiting process gets its turn, under the assumptions of the synchronization algorithm.

### Simple idea

```text id="q7k7j4"
Request access
      ↓
Wait
      ↓
Eventually enter
      ↓
No indefinite waiting
```

---

# The Three Requirements Together

```text id="z5q7bw"
             Critical Section
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
 Mutual Exclusion  Progress  Bounded Waiting
        │           │           │
        ↓           ↓           ↓
 One at a time   No unnecessary   No indefinite
                  blocking          waiting
```

These properties form the classic requirements for solving the critical-section problem.

---

# Critical Section vs Race Condition

These concepts are closely related but are **not the same**.

| Critical Section                                      | Race Condition                                          |
| ----------------------------------------------------- | ------------------------------------------------------- |
| A section of code accessing shared resources          | A concurrency bug caused by unsafe concurrent access    |
| Identifies where protection may be needed             | Describes the problem that can occur                    |
| It is part of program logic                           | It is an incorrect/unsafe concurrency situation         |
| Can be protected using locks or other synchronization | Can be prevented/reduced through proper synchronization |
| Example: `counter += 1`                               | Example: two threads lose a counter update              |

### Simple relationship

```text id="1v4k29"
Shared Resource
      ↓
Sensitive Access Code
      ↓
Critical Section
      ↓
Needs Proper Synchronization
      ↓
Without Proper Protection
      ↓
Race Condition
```

However, simply declaring a piece of code a "critical section" does not automatically make it safe. The synchronization mechanism must actually protect all relevant accesses correctly.

---

# Critical Section vs Lock

Another important distinction:

> **A critical section is the code/region that needs protection. A lock is one mechanism used to provide that protection.**

For example:

```text id="j5y2bq"
Critical Section:
    counter += 1
```

Lock:

```text id="8l2f3k"
lock.acquire()
      ↓
Critical Section
      ↓
lock.release()
```

Therefore:

```text id="z6z8xw"
Critical Section ≠ Lock
```

Instead:

```text id="d0g2r5"
Critical Section
       +
Synchronization Mechanism
       ↓
Safe concurrent access
```

---

# Common Synchronization Mechanisms

Critical sections can be protected using different synchronization techniques depending on the problem.

### 1. Mutex / Lock

Allows one thread at a time to enter an exclusive critical section.

```text id="5k6f9c"
T1 → Lock → Critical Section → Unlock
T2 → Wait → Lock → Critical Section → Unlock
```

---

### 2. Semaphore

A semaphore can control access to a resource.

A binary semaphore can provide one-at-a-time access in some designs, while a counting semaphore can allow a limited number of threads to access a resource simultaneously.

```text id="i6q8bs"
Semaphore count = 3

T1 → Resource
T2 → Resource
T3 → Resource

T4 → waits
```

---

### 3. Monitor

A **monitor** is a higher-level synchronization abstraction that combines shared data with operations that control access to that data.

Many programming languages provide monitor-like constructs through synchronization primitives.

Conceptually:

```text id="tqf7f7"
        Monitor
      ┌───────────┐
      │ Shared    │
      │ Data      │
      │           │
      │ Methods   │
      └───────────┘
           ↑
     controlled access
```

---

### 4. Atomic Operations

For simple shared-state operations, atomic operations can sometimes avoid the need for a traditional lock.

For example:

```text id="gk3e5b"
atomic_increment(counter)
```

The operation is performed atomically according to the relevant language/runtime/hardware guarantees.

---

### 5. Message Passing

Instead of allowing many threads to directly modify the same shared memory, components can communicate using messages.

```text id="kj7y72"
Thread A
   │
   ↓
Message Queue
   │
   ↓
Thread B
```

This can reduce shared-memory synchronization problems.

---

# Critical Section and Context Switching

A context switch can occur around a critical section.

For example:

```text id="2b3n9p"
T1 enters critical section
        ↓
T1 gets preempted
        ↓
T2 runs
        ↓
T1 later resumes
```

If T1 holds a lock during the context switch, T2 may be unable to enter the protected section and may have to wait.

Therefore, excessive lock holding can lead to:

* Lock contention
* Poor CPU utilization
* Increased waiting
* Reduced throughput

This is one reason critical sections should generally be **as small as practical**, while still protecting the complete shared operation.

---

# Critical Section Should Protect the Correct Operation

Suppose we have:

```text id="a6y0gs"
Read balance
Check balance
Subtract amount
Write balance
```

Protecting only:

```text id="8f6a0u"
Write balance
```

may not be enough.

Another thread could change the balance between the check and the update.

The logically related operations may need to be protected together:

```text id="g8j8wt"
Lock
  ↓
Read balance
  ↓
Check balance
  ↓
Subtract amount
  ↓
Write balance
  ↓
Unlock
```

This is an important principle:

> **The critical section should cover the complete operation whose correctness depends on shared state remaining consistent.**

---

# Critical Section on Single-Core vs Multi-Core Systems

A critical section is important even on a **single-core CPU**.

Why?

Because threads can be interleaved:

```text id="8c7s89"
T1 → Read
    ↓
Context Switch
    ↓
T2 → Read
    ↓
Context Switch
    ↓
T1 → Write
    ↓
Context Switch
    ↓
T2 → Write
```

Although only one thread executes at an instant, the interleaving can still cause incorrect results.

On a multicore system, threads may also execute truly simultaneously:

```text id="7h0azq"
Core 1 → T1 ──┐
              ├──→ Shared Data
Core 2 → T2 ──┘
```

Therefore, synchronization is required in both environments when shared state is accessed concurrently.

---

# Critical Section vs Normal Code

Not every line of code is a critical section.

For example:

```python
x = 10
y = 20
z = x + y
```

If these variables are local to one thread and not shared, there may be no need for synchronization.

But:

```python
shared_counter += 1
```

may require protection if multiple threads can modify `shared_counter`.

The key question is:

> **Is this operation accessing shared mutable state in a way that can be affected by concurrent execution?**

---

# Example: Thread-Safe Counter

Suppose we want two threads to increment a counter 1000 times each.

Unsafe conceptual version:

```python
counter = 0

# Thread 1
for i in range(1000):
    counter += 1

# Thread 2
for i in range(1000):
    counter += 1
```

We might expect:

```text id="8n8y8v"
counter = 2000
```

But without appropriate synchronization, the result may be lower because updates can be lost.

A lock-protected version is conceptually:

```python
counter = 0

for i in range(1000):
    lock.acquire()
    try:
        counter += 1
    finally:
        lock.release()
```

Now each update is protected from conflicting concurrent updates.

The exact syntax and best implementation depend on the programming language.

---

# Important Interview Distinction

### Is a critical section always protected by a lock?

**No.**

A lock is one common synchronization mechanism, but critical sections can be protected using:

* Mutexes
* Semaphores
* Monitors
* Atomic operations
* Read-write locks
* Other synchronization mechanisms
* Message passing/designs that avoid shared mutable state

The important concept is **correct synchronization**, not a specific primitive.

---

# Common Mistakes

### Mistake 1: Critical Section = Entire Program

Incorrect.

A critical section is only the portion that needs protection because it accesses shared resources.

```text id="c2m3tb"
Entire Program
│
├── Normal Code
├── Normal Code
├── Critical Section  ← protected
├── Normal Code
└── Normal Code
```

---

### Mistake 2: Critical Section and Race Condition Are the Same

They are not.

```text id="2m8v9n"
Critical Section → Code region

Race Condition   → Concurrency bug
```

---

### Mistake 3: A Lock Automatically Prevents All Concurrency Problems

A lock can prevent certain race conditions, but poor locking can introduce other problems such as:

* Deadlock
* Starvation
* Lock contention
* Reduced parallelism

For example:

```text id="d8q8xw"
T1 → Lock A → waits for B
T2 → Lock B → waits for A
```

This can create a deadlock.
