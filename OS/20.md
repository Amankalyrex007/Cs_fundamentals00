20.Mutex vs semaphore?
Both are synchronization mechanisms, but they solve slightly different problems.

Feature	Mutex	Semaphore
Main purpose	Provide exclusive access	Control limited concurrent access
Access allowed	Typically 1 thread	N threads, depending on count
Concept	Lock/unlock	Acquire/release permits
Counter	Usually binary state: locked/unlocked	Has a counter
Ownership	Typically owned by the thread that locks it	No ownership requirement in the same sense
Typical use	Protect a critical section/shared variable	Limit access to a resource pool
Example	Protecting counter += 1	Allowing only 5 DB connections
Example

Mutex:

Mutex = unlocked

Thread 1 → lock → critical section → unlock
Thread 2 → waits

Only one thread can execute the protected section at a time.

Semaphore(3):

Semaphore = 3

Thread 1 → acquire → 2
Thread 2 → acquire → 1
Thread 3 → acquire → 0
Thread 4 → waits

Three threads can access the resource concurrently.

Simple way to remember

Mutex = “Only one at a time.”
Semaphore = “Only up to N at a time.”

Interview example

If you have a shared counter, a mutex is usually appropriate because the update should be protected from concurrent modification.

If you have a database connection pool with 10 connections, a semaphore can limit concurrent access to 10 connections.

Important distinction

A binary semaphore can look similar to a mutex, but they are not conceptually identical. A mutex normally has ownership semantics—the thread that acquires it is expected to release it—whereas a semaphore represents permits/resources and does not generally have the same ownership concept.

Interview takeaway

Use a mutex when you need exclusive ownership of a critical section; use a semaphore when you need to control the number of threads that can access a resource concurrently.
