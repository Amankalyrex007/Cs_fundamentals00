# Q26. What is Paging?

**Paging** is a memory-management technique in which:

* **Virtual memory** is divided into fixed-size blocks called **pages**.
* **Physical memory (RAM)** is divided into fixed-size blocks called **frames**.
* The **OS maps virtual pages to physical frames** using a **page table**.

The important point is that a process's pages **do not need to be stored in consecutive locations in physical memory**.

This allows the OS to use available RAM efficiently while giving each process a convenient virtual address space.

---

## Basic Idea of Paging

Suppose a process has four virtual pages:

```text
Virtual Memory              Physical Memory (RAM)

Page 0  ─────────────────→  Frame 3
Page 1  ─────────────────→  Frame 7
Page 2  ─────────────────→  Frame 1
Page 3  ─────────────────→  Frame 5
```

Notice that the pages are stored in **different frames**.

They do not need to be arranged like:

```text
Page 0 → Frame 0
Page 1 → Frame 1
Page 2 → Frame 2
Page 3 → Frame 3
```

Instead, the OS can place each page wherever a suitable free frame is available.

### Why is this useful?

Without paging, a process might need one large **contiguous region** of physical memory.

With paging:

```text
Process requires 16 KB

        ↓

4 pages × 4 KB

        ↓

Page 0 → Frame 20
Page 1 → Frame 5
Page 2 → Frame 31
Page 3 → Frame 12
```

The physical frames can be scattered throughout RAM.

---

# How Paging Works

Paging mainly involves four components:

1. **Virtual address**
2. **Page table**
3. **Physical frames**
4. **MMU (Memory Management Unit)**

The general flow is:

```text
CPU generates Virtual Address
            │
            ▼
        MMU
            │
            ├── Page Number ──→ Page Table ──→ Frame Number
            │
            └── Page Offset ────────────────→ Same Offset
                                             │
                                             ▼
                                  Physical Address
```

The OS creates and manages the page tables, while the hardware **MMU** performs address translation during memory access.

---

# Virtual Address Structure

A virtual address is typically divided into two important parts:

```text
Virtual Address

┌────────────────────┬────────────────────┐
│    Page Number     │    Page Offset     │
└────────────────────┴────────────────────┘
          │                    │
          │                    └── Exact location
          │                        inside the page
          │
          └── Identifies the virtual page
```

### Page Number

The **page number** tells us which virtual page contains the requested address.

The page table uses this page number to find the corresponding physical frame.

### Page Offset

The **page offset** tells us the exact byte/location inside that page.

An important property is:

> **The page offset does not change during address translation.**

Only the page number is translated into a frame number.

---

# Page Table

The **page table** stores the mapping between virtual pages and physical frames.

For example:

| Virtual Page | Physical Frame |
| -----------: | -------------: |
|       Page 0 |        Frame 3 |
|       Page 1 |        Frame 7 |
|       Page 2 |        Frame 1 |
|       Page 3 |        Frame 5 |

So if the CPU generates an address belonging to **Page 2**, the page table tells the MMU:

```text
Virtual Page 2 → Physical Frame 1
```

The offset inside the page remains unchanged.

Therefore:

```text
Virtual Address
      │
      ├── Page Number → Page Table → Frame Number
      │
      └── Offset ───────────────────────┐
                                        │
                                        ▼
                              Physical Address
```

---

# Example: 16 KB Process with 4 KB Pages

Suppose:

```text
Page Size = 4 KB
Process Virtual Memory = 16 KB
```

Number of pages:

```text
16 KB / 4 KB = 4 pages
```

Therefore:

```text
Virtual Memory

Page 0 → 4 KB
Page 1 → 4 KB
Page 2 → 4 KB
Page 3 → 4 KB
```

These pages can be placed anywhere in RAM.

For example:

```text
Virtual Pages             Physical Frames

Page 0 ────────────────→  Frame 8
Page 1 ────────────────→  Frame 2
Page 2 ────────────────→  Frame 15
Page 3 ────────────────→  Frame 5
```

The process still sees a logically continuous virtual address space:

```text
0 KB ─────────────────────── 16 KB
```

But its physical pages may be scattered:

```text
RAM:

Frame 0
Frame 1
Frame 2  ← Page 1
Frame 3
Frame 4
Frame 5  ← Page 3
...
Frame 8  ← Page 0
...
Frame 15 ← Page 2
```

This is one of the major benefits of paging.

---

# Address Translation Example

Suppose:

```text
Page size = 4 KB
```

A process accesses virtual address:

```text
Virtual Address = 5000 bytes
```

Since:

```text
4 KB = 4096 bytes
```

we can determine:

```text
Page Number = 5000 / 4096 = Page 1
Offset      = 5000 - 4096
            = 904 bytes
```

Suppose the page table contains:

```text
Page 1 → Frame 7
```

Then the physical address is:

```text
Frame 7 + Offset 904
```

Because each frame is 4096 bytes:

```text
Physical Address
= 7 × 4096 + 904
= 29,576 bytes
```

So:

```text
Virtual Address 5000
        │
        ▼
Page 1 + Offset 904
        │
        ▼
Page Table
        │
        ▼
Frame 7 + Offset 904
        │
        ▼
Physical Address 29,576
```

### Important

The offset **904 remains unchanged**.

Only:

```text
Page 1 → Frame 7
```

is translated.

# What Happens if a Page Isn't in RAM?

Sometimes the CPU accesses a page that is currently **not present in physical memory**.

This causes a **page fault**.

A page fault does **not necessarily mean something has gone wrong**. In a virtual-memory system, page faults are a normal mechanism used for demand paging.

The general process is:

```text
CPU requests page
       │
       ▼
Is page present in RAM?
       │
   ┌───┴────┐
   │        │
  YES       NO
   │        │
   ▼        ▼
Access    Page Fault
RAM          │
             ▼
       OS handles fault
             │
             ▼
      Find free frame
       or choose victim
             │
             ▼
      Load required page
       into physical RAM
             │
             ▼
      Update page table
             │
             ▼
      Retry interrupted
          operation
```

---

# Steps During a Page Fault

When a required page is not present, the OS generally performs these steps:

### 1. Find the required page

The OS determines where the required page is stored, often in a backing store such as a swap area or a mapped file.

### 2. Find a free frame

If a free physical frame is available, it can be used.

```text
Free Frame 12
      ↑
Required Page → Frame 12
```

### 3. If no free frame exists, choose a victim page

The OS may need to remove another page from RAM.

For example:

```text
RAM

Frame 5  → Page A
Frame 6  → Page B
Frame 7  → Page C  ← Victim
Frame 8  → Page D
```

If Page E is required:

```text
Page E needs a frame
       ↓
Evict Page C
       ↓
Load Page E into Frame 7
```

The choice of which page to evict is determined by a **page replacement algorithm**.

Examples include:

* FIFO
* LRU
* Clock/Second-Chance
* Other OS-specific policies

### 4. Load the required page

The OS brings the required page into the selected frame.

### 5. Update the page table

For example:

```text
Before:

Page 4 → Not Present

After:

Page 4 → Frame 7
```

The page table's status/presence information is updated accordingly.

### 6. Continue execution

The CPU retries the instruction that needed the page.

---

# Page Fault Does Not Always Mean Disk Access

A useful interview nuance:

> A page fault means the required page is not currently mapped/present in the expected physical memory, but it does **not always imply reading the page from disk**.

For example, the page might be:

* backed by a file,
* newly allocated and represented by a zero-filled page,
* shared with another mapping,
* or otherwise handled without ordinary swap-in.

So avoid saying:

> "Every page fault means the OS reads from disk."

A better statement is:

> "A page fault causes the OS to resolve the missing page, which may require storage I/O depending on where the page is backed."

# Page Table Entry

A page table entry usually contains more than just a frame number.

Conceptually, it may contain:

```text
Page Table Entry

┌─────────────────────────────────────┐
│ Frame Number                        │
│ Present / Valid Bit                 │
│ Protection Bits                     │
│ Access / Reference Information      │
│ Dirty / Modified Information        │
│ Other Architecture-specific Flags   │
└─────────────────────────────────────┘
```

For example:

```text
Virtual Page 5
      │
      ▼
┌──────────────────────────┐
│ Frame = 12               │
│ Present = 1              │
│ Read/Write = Allowed     │
│ User/Kernel = User       │
│ Dirty = 0                │
└──────────────────────────┘
```

The exact fields depend on the architecture and operating system.

---

# What is the Role of the MMU?

The **MMU (Memory Management Unit)** is hardware responsible for performing virtual-to-physical address translation.

The CPU generates a virtual address:

```text
Virtual Address
      │
      ▼
     MMU
      │
      ▼
Page Table / TLB
      │
      ▼
Physical Address
      │
      ▼
     RAM
```

This translation happens for normal memory accesses.

The OS manages the memory-management structures, while the hardware performs the fast translation during execution.

---

# What is a TLB?

A **TLB (Translation Lookaside Buffer)** is a small, fast hardware cache that stores recently used virtual-page-to-physical-frame translations.

Without a TLB, the system might need to consult the page table repeatedly.

With a TLB:

```text
CPU
 │
 ▼
Virtual Address
 │
 ▼
TLB
 │
 ├── Hit ──────→ Frame found quickly
 │
 └── Miss
       │
       ▼
   Page Table
       │
       ▼
   Translation
       │
       ▼
   TLB updated
```

### TLB Hit

If the translation is already in the TLB:

```text
Virtual Page 5 → Frame 12
```

the hardware can obtain the mapping quickly.

### TLB Miss

If the mapping is not present in the TLB, the system needs to obtain the translation from the relevant page-table structure, after which the TLB may be updated.

### Important

A **TLB miss is not the same as a page fault**.

| TLB Miss                                             | Page Fault                                              |
| ---------------------------------------------------- | ------------------------------------------------------- |
| Translation not found in TLB                         | Required page is not currently present/mapped as needed |
| Usually resolved by obtaining page-table translation | Requires OS-level page-fault handling                   |
| Can be relatively inexpensive                        | Can be extremely expensive if storage I/O is needed     |

This distinction is frequently asked in interviews.

---

# Why Paging Reduces External Fragmentation

Without paging, a process may need a large contiguous physical memory region.

Suppose RAM contains:

```text
Used | Free | Used | Free | Used | Free
```

There may be enough total free memory, but not enough **contiguous** free memory for a large allocation.

Paging avoids this requirement.

A process can use:

```text
Page 0 → Frame 2
Page 1 → Frame 15
Page 2 → Frame 7
Page 3 → Frame 20
```

Therefore, its physical memory does not need to be contiguous.

### Important nuance

Paging largely eliminates **external fragmentation**, but it can still have **internal fragmentation**.

Because pages have fixed size, the final page of a process may not be completely filled.

For example:

```text
Page Size = 4 KB
Process requires = 10 KB

Pages required = 3

Page 0 → 4 KB
Page 1 → 4 KB
Page 2 → 2 KB used + 2 KB unused
```

The unused portion inside the last allocated page is internal fragmentation.

---

# Paging and Process Isolation

Paging also helps provide **memory protection and process isolation**.

Suppose:

```text
Process A:

Virtual Page 0 → Frame 10


Process B:

Virtual Page 0 → Frame 25
```

Both processes can use the same virtual address:

```text
Virtual Address 0
```

but it can translate to different physical memory.

Therefore:

```text
Process A
Virtual 0 ──→ Physical Frame 10


Process B
Virtual 0 ──→ Physical Frame 25
```

This helps prevent one process from directly accessing another process's private memory, subject to the OS and hardware protection mechanisms.

---

# Paging vs Contiguous Allocation

| Feature                | Contiguous Allocation                        | Paging                    |
| ---------------------- | -------------------------------------------- | ------------------------- |
| Physical memory        | Must be contiguous for allocation            | Can be scattered          |
| Allocation unit        | Variable-sized region                        | Fixed-size pages/frames   |
| External fragmentation | Can occur significantly                      | Largely avoided           |
| Address translation    | Simpler                                      | Requires page mapping     |
| Page table             | Not required for basic contiguous allocation | Required                  |
| Memory flexibility     | Lower                                        | Higher                    |
| Translation overhead   | Lower                                        | TLB helps reduce overhead |

---

# Advantages of Paging

### 1. Avoids the need for contiguous physical memory

Pages can be placed in any suitable free frames.

```text
Page 0 → Frame 4
Page 1 → Frame 20
Page 2 → Frame 8
```

---

### 2. Supports Virtual Memory

Paging is one of the primary mechanisms used to implement virtual memory.

It allows only the currently needed pages to be kept in RAM while other pages may remain backed elsewhere.

---

### 3. Reduces External Fragmentation

Because physical memory is allocated in fixed-size frames, the OS does not need one large contiguous free region for every process.

---

### 4. Allows Pages to Be Managed Independently

Individual pages can have different states.

For example:

```text
Page 0 → RAM
Page 1 → RAM
Page 2 → Not currently present
Page 3 → RAM
```

The OS can manage them independently.

---

### 5. Supports Memory Isolation

Page tables and protection bits help the OS control which memory regions a process can access.

---

### 6. Supports Sharing

Paging can also allow controlled sharing of physical pages.

For example, two processes may map the same read-only physical page containing shared code:

```text
Process A ──┐
            ├──→ Physical Frame 30
Process B ──┘
```

This can reduce unnecessary duplication of memory.

---

# Disadvantages of Paging

### 1. Page Tables Require Additional Memory

Each process needs page-table structures.

For systems with very large virtual address spaces, a single flat page table could be large.

Therefore, modern systems commonly use techniques such as:

* multi-level page tables,
* hierarchical page tables,
* architecture-specific paging structures.

---

### 2. Address Translation Adds Overhead

Every virtual memory access needs translation.

The **TLB** reduces this overhead by caching frequently used translations.

```text
CPU
 │
 ▼
TLB
 │
 ├── Hit → Fast translation
 │
 └── Miss → Page-table lookup
```

---

### 3. Page Faults Can Be Very Expensive

If resolving a page fault requires storage I/O, it can be dramatically slower than accessing RAM.

Conceptually:

```text
CPU → Cache → RAM → Storage
          increasingly slower
```

The exact latency depends heavily on hardware and workload.

---

### 4. Excessive Page Faults Can Cause Thrashing

If a system spends most of its time moving pages between RAM and backing storage instead of executing useful instructions, it may experience **thrashing**.

```text
Too many active pages
        ↓
Many page faults
        ↓
Frequent page movement
        ↓
Less useful CPU work
        ↓
Performance collapses
```

Thrashing is generally associated with a working set that cannot fit effectively in available physical memory.

---

# Paging and Thrashing

Consider a system running several memory-intensive applications.

If the combined working sets require more physical memory than is available:

```text
Process A → many active pages
Process B → many active pages
Process C → many active pages
              ↓
        RAM becomes pressured
              ↓
       Frequent page faults
              ↓
       Frequent page replacement
              ↓
          Thrashing
```

The CPU may spend significant time waiting for memory-management operations instead of performing useful application work.

---

# Paging vs Virtual Memory

This is an important **interview distinction**.

### Virtual Memory

Virtual memory is the **overall memory abstraction and management mechanism** that gives processes virtual address spaces independent of physical RAM layout.

### Paging

Paging is a **memory-management technique** that divides memory into fixed-size pages and frames and maps them using page tables.

Therefore:

```text
Virtual Memory
      │
      ├── Paging
      │
      ├── Page Tables
      │
      ├── Address Translation
      │
      ├── Demand Paging
      │
      └── Backing Storage mechanisms
```

A useful way to remember it:

> **Virtual memory is the concept/abstraction; paging is a major mechanism used to implement it.**

Do not say:

> "Paging and virtual memory are exactly the same thing."

They are closely related, but they are not identical concepts.

---

# Paging vs Segmentation

Another common interview comparison:

| Feature       | Paging                        | Segmentation                     |
| ------------- | ----------------------------- | -------------------------------- |
| Division      | Fixed-size pages              | Variable-size logical segments   |
| Physical unit | Frames                        | Segment allocation               |
| Based on      | Fixed size                    | Logical program structure        |
| Fragmentation | Mainly internal fragmentation | Can cause external fragmentation |
| Example       | Page 0, Page 1                | Code, Data, Stack                |
| Address       | Page number + offset          | Segment number + offset          |

For example:

```text
Paging:

Process
 ├── Page 0
 ├── Page 1
 ├── Page 2
 └── Page 3
```

Whereas segmentation may conceptually divide a program into:

```text
Process
 ├── Code Segment
 ├── Data Segment
 ├── Heap Segment
 └── Stack Segment
```

Modern systems commonly rely heavily on paging for virtual-memory implementation.

# Common Interview Mistakes

### ❌ Mistake 1: Page and frame are the same thing

They are not.

```text
Page  → Unit of virtual memory
Frame → Unit of physical memory
```

---

### ❌ Mistake 2: Pages must be contiguous in RAM

False.

Pages can be mapped to arbitrary available frames.

---

### ❌ Mistake 3: Every page fault means the program crashed

False.

Page faults are a normal part of virtual-memory systems.

---

### ❌ Mistake 4: Every page fault requires disk access

Not necessarily.

The OS may resolve some faults without ordinary storage I/O.

---

### ❌ Mistake 5: TLB miss = page fault

False.

```text
TLB miss
    ↓
Translation not in TLB
```

while:

```text
Page fault
    ↓
Required page is not currently present/mapped as required
```

A TLB miss can occur even when the page is already in RAM.

---

### ❌ Mistake 6: Paging eliminates all fragmentation

Not exactly.

Paging largely avoids **external fragmentation**, but **internal fragmentation** can still occur.

---

### ❌ Mistake 7: Virtual address is the physical address

False.

```text
Virtual Address
      ↓
Address Translation
      ↓
Physical Address
```

```text
Virtual Memory
      ↓
Divided into Pages
      ↓
Physical RAM
      ↓
Divided into Frames
      ↓
Page Table
      ↓
Page → Frame Mapping
      ↓
MMU performs translation
      ↓
TLB speeds up translation
      ↓
Missing Page → Page Fault
```

### Key terms

| Term                 | Meaning                                            |
| -------------------- | -------------------------------------------------- |
| **Page**             | Fixed-size block of virtual memory                 |
| **Frame**            | Fixed-size block of physical RAM                   |
| **Page Table**       | Maps virtual pages to physical frames              |
| **Page Number**      | Identifies a virtual page                          |
| **Offset**           | Identifies a location inside the page              |
| **MMU**              | Hardware that performs address translation         |
| **TLB**              | Cache of recent address translations               |
| **Page Fault**       | Required page is not currently present as needed   |
| **Page Replacement** | Selecting a page/frame to evict                    |
| **Thrashing**        | Excessive paging that severely reduces useful work |

# Interview Takeaway

> **Paging divides virtual memory into fixed-size pages and physical memory into equal-size frames. The OS uses page tables to map virtual pages to physical frames, allowing pages to be stored non-contiguously in RAM. The MMU performs address translation, while the TLB speeds up frequently used translations. If a required page is not present, a page fault occurs and the OS handles it.**

### Memory Trick

```text
PAGE → FRAME → TABLE → TRANSLATE → FAULT
```

Or simply:

> **Page = virtual, Frame = physical, Page Table = mapping, TLB = fast translation, Page Fault = page missing.**
