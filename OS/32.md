# Q32. What is Fragmentation?

**Fragmentation** is a memory-management problem where available memory is used inefficiently because memory is divided into pieces that cannot be used effectively.

In simple words:

> **Fragmentation means memory exists, but some of it is wasted or difficult to use efficiently.**

There are two main types:

1. **Internal Fragmentation**
2. **External Fragmentation**

The key difference is **where the wasted space exists**.

```text
Internal Fragmentation
        ↓
Wasted space INSIDE an allocated block

External Fragmentation
        ↓
Free space BETWEEN allocated blocks
```

---

# 1. Internal Fragmentation

**Internal fragmentation** occurs when the memory-management system allocates a block that is larger than the amount of memory actually required.

The unused space is **inside the allocated block**.

### Example

Suppose:

```text
Frame size = 4 KB
Process needs = 3 KB
```

The system must allocate the complete 4 KB frame.

```text
┌────────────────────┐
│ Used: 3 KB         │
│                    │
│ Unused: 1 KB       │ ← Internal Fragmentation
└────────────────────┘
       4 KB frame
```

The process uses only 3 KB, but the complete 4 KB block is allocated.

Therefore:

```text
Internal fragmentation
= Allocated space − Actually used space
```

In this example:

```text
4 KB − 3 KB = 1 KB
```

So **1 KB is internally wasted**.

---

# Why Is It Called "Internal"?

Because the wasted space is located **inside the block that has already been allocated**.

```text
Allocated Block
┌─────────────────────────┐
│ Used        │ Wasted    │
│             │           │
└─────────────────────────┘
              ↑
       Inside allocation
```

The operating system cannot normally give that unused portion to another unrelated allocation because the entire block has already been assigned.

---

# Internal Fragmentation and Paging

Internal fragmentation is commonly associated with **fixed-size allocation**, particularly **paging**.

In paging:

```text
Virtual memory → Fixed-size pages
Physical memory → Fixed-size frames
```

For example:

```text
Page size = 4 KB
```

Suppose the last page of a process requires only:

```text
1 KB
```

The OS still allocates a complete:

```text
4 KB page/frame
```

Conceptually:

```text
Last Page / Frame

┌────────────────────┐
│ Used: 1 KB         │
├────────────────────┤
│ Unused: 3 KB       │
└────────────────────┘
```

The unused 3 KB represents **internal fragmentation**.

---

# Another Internal Fragmentation Example

Suppose a system allocates memory in blocks of:

```text
8 KB
```

A process requests:

```text
6 KB
```

The allocator provides:

```text
8 KB
```

Therefore:

```text
Allocated = 8 KB
Used      = 6 KB
Wasted    = 2 KB
```

That 2 KB is internal fragmentation.

---

# Important Point About Paging

Paging does **not** require physical memory for a process to be contiguous.

Pages can be placed in different frames:

```text
Page 0 → Frame 7
Page 1 → Frame 2
Page 2 → Frame 10
Page 3 → Frame 4
```

This eliminates the need for one large contiguous physical region.

However, because pages have a fixed size, the final page of a process may not be completely filled.

Therefore:

> **Paging avoids external fragmentation of physical allocation, but it can still have internal fragmentation.**

---

# 2. External Fragmentation

**External fragmentation** occurs when enough free memory exists overall, but the free memory is divided into multiple **small, non-contiguous blocks**.

The problem is not unused space inside an allocated block.

The problem is:

> **Free space exists between allocated blocks, but it is scattered.**

### Example

```text
┌──────┬──────┬──────┬──────┬──────┐
│ Used │ Free │ Used │ Free │ Used │
└──────┴──────┴──────┴──────┴──────┘
         ↑            ↑
       Free         Free
       block        block
```

Suppose the free blocks are:

```text
4 KB + 6 KB + 5 KB
```

Total free memory:

```text
4 + 6 + 5 = 15 KB
```

Now suppose a process requires:

```text
10 KB contiguous memory
```

There is 15 KB of free memory in total, but there is no **single contiguous 10 KB block**.

Therefore, the allocation may fail under a contiguous-allocation scheme.

This is **external fragmentation**.

---

# Why Is It Called "External"?

Because the wasted/free space is **outside the allocated blocks**.

```text
┌────────┬───────┬────────┬───────┬────────┐
│  Used  │ Free  │  Used  │ Free  │  Used  │
└────────┴───────┴────────┴───────┴────────┘
           ↑               ↑
       External        External
       free space      free space
```

The free regions are external to the allocated memory blocks.

---

# External Fragmentation Example

Imagine a memory region of 20 KB:

```text
Initially:

┌────────────────────────────────────┐
│            Free 20 KB              │
└────────────────────────────────────┘
```

Now allocate:

```text
A = 5 KB
B = 5 KB
C = 5 KB
```

Memory might look like:

```text
┌───────┬───────┬───────┬────────────┐
│ A 5KB │ B 5KB │ C 5KB │ Free 5KB   │
└───────┴───────┴───────┴────────────┘
```

Now suppose B is released:

```text
┌───────┬───────────┬───────┬─────────┐
│ A 5KB │ Free 5KB  │ C 5KB │ Free 5KB│
└───────┴───────────┴───────┴─────────┘
```

Total free memory:

```text
5 KB + 5 KB = 10 KB
```

But it is split into two separate regions.

If a new process needs:

```text
8 KB contiguous
```

the allocation cannot use both free blocks together under a contiguous-allocation requirement.

This is external fragmentation.

---

# Internal vs External Fragmentation

| Aspect                                   | Internal Fragmentation             | External Fragmentation                  |
| ---------------------------------------- | ---------------------------------- | --------------------------------------- |
| **Wasted space**                         | Inside allocated block             | Between allocated blocks                |
| **Free space location**                  | Within an allocation               | Outside allocations                     |
| **Typical cause**                        | Fixed-size allocation              | Variable-size contiguous allocation     |
| **Common example**                       | Paging                             | Segmentation / contiguous allocation    |
| **Main problem**                         | Allocated block is not fully used  | Free memory is not contiguous           |
| **Can total free memory be sufficient?** | Not the main issue                 | Yes                                     |
| **Typical solution**                     | Choose appropriate block/page size | Compaction or non-contiguous allocation |

# Visual Difference

### Internal Fragmentation

```text
Allocated Block

┌─────────────────────┐
│       Used          │
├─────────────────────┤
│      Wasted         │
└─────────────────────┘
         ↑
    Inside block
```

### External Fragmentation

```text
┌───────┬───────┬───────┬───────┬───────┐
│ Used  │ Free  │ Used  │ Free  │ Used  │
└───────┴───────┴───────┴───────┴───────┘
           ↑              ↑
        Outside        Outside
        allocation     allocation
```

### Memory Trick

> **Internal = Inside**
> **External = Outside**

This is one of the easiest ways to remember the difference.

# How Can Fragmentation Be Reduced?

## 1. Reducing Internal Fragmentation

Internal fragmentation can be reduced by choosing appropriate allocation/block sizes.

For example:

```text
Very large fixed block
        ↓
More unused space
        ↓
Higher internal fragmentation
```

Smaller allocation units can reduce average wasted space, but they may introduce other overheads.

In paging, reducing page size can reduce internal fragmentation in some cases, but it can also increase:

* Number of pages
* Page-table size
* Translation overhead
* TLB pressure

Therefore, page size is a system-design trade-off.

---

# 2. Reducing External Fragmentation

One traditional technique is **compaction**.

### Compaction

Compaction moves allocated blocks so that scattered free spaces are combined into one larger free region.

Before compaction:

```text
┌──────┬──────┬──────┬──────┬──────┐
│ Used │ Free │ Used │ Free │ Used │
└──────┴──────┴──────┴──────┴──────┘
         4 KB          6 KB
```

After compaction:

```text
┌──────┬──────┬──────┬───────────────┐
│ Used │ Used │ Used │    Free       │
└──────┴──────┴──────┴───────────────┘
                     ← larger block →
```

The scattered free regions have been combined.

### Problem with Compaction

Compaction itself has overhead because the OS may need to **move allocated memory contents** and update relevant references/metadata.

Therefore:

> Compaction can reduce external fragmentation, but it is not free.

---

# Paging and External Fragmentation

Paging is particularly useful because physical frames do not need to be contiguous.

Suppose a process requires four pages:

```text
Page 0 → Frame 8
Page 1 → Frame 2
Page 2 → Frame 15
Page 3 → Frame 5
```

The pages are scattered across physical memory, but the process can still use them through page-table translation.

```text
Virtual Pages              Physical Frames

Page 0 ─────────────────→ Frame 8
Page 1 ─────────────────→ Frame 2
Page 2 ─────────────────→ Frame 15
Page 3 ─────────────────→ Frame 5
```

Therefore, a large contiguous free physical-memory block is not required.

This is why:

> **Paging avoids external fragmentation of physical memory allocation.**

But remember:

```text
Paging
  ↓
No external fragmentation in frame allocation
  +
Possible internal fragmentation
```

---

# Segmentation and External Fragmentation

Segmentation uses **variable-sized logical segments**.

For example:

```text
Code    = 20 KB
Data    = 10 KB
Stack   = 8 KB
Heap    = 15 KB
```

Because segment sizes vary, allocating and freeing them can create holes:

```text
┌────────┬──────┬────────┬──────┬────────┐
│ Code   │ Free │ Data   │ Free │ Stack  │
└────────┴──────┴────────┴──────┴────────┘
```

These holes can lead to **external fragmentation**.

This is one reason fixed-size paging is attractive for physical memory management.

---

# Fragmentation in Dynamic Memory Allocation

External fragmentation is not limited to operating-system memory management.

It can also appear in dynamic memory allocators.

Suppose a program repeatedly performs:

```text
Allocate A
Allocate B
Allocate C
Free B
Allocate D
Free A
...
```

The heap may eventually contain many differently sized free regions.

Conceptually:

```text
Heap:

┌─────┬─────┬──────┬────┬───────┬─────┐
│Used │Free │ Used │Free│ Used   │Free │
└─────┴─────┴──────┴────┴───────┴─────┘
```

Even if the total free memory is large, finding a suitable contiguous region for a large allocation can become difficult.

Memory allocators use various strategies and data structures to manage this problem.

---

# Fragmentation and Allocation Strategy

Different allocation strategies can influence fragmentation.

For variable-sized contiguous allocation, common strategies include:

### First Fit

Choose the first sufficiently large free block.

```text
Free blocks:
5 KB, 20 KB, 8 KB

Request = 7 KB

First suitable block = 20 KB
```

### Best Fit

Choose the smallest free block that is large enough.

```text
Free blocks:
5 KB, 20 KB, 8 KB

Request = 7 KB

Best suitable block = 8 KB
```

### Worst Fit

Choose the largest available block.

```text
Free blocks:
5 KB, 20 KB, 8 KB

Request = 7 KB

Largest block = 20 KB
```

These strategies have different fragmentation and performance characteristics.

There is no universally best strategy for every workload.

---

# Internal Fragmentation vs External Fragmentation in Paging

Suppose:

```text
Page size = 4 KB
```

and a process requires:

```text
10 KB
```

It needs:

```text
Page 1 = 4 KB
Page 2 = 4 KB
Page 3 = 2 KB used
```

Therefore:

```text
Total allocated = 12 KB
Actually needed = 10 KB
Unused          = 2 KB
```

The final 2 KB is **internal fragmentation**.

```text
Page 1
┌──────────┐
│ 4 KB used│
└──────────┘

Page 2
┌──────────┐
│ 4 KB used│
└──────────┘

Page 3
┌──────────┐
│ 2 KB used│
│ 2 KB free│ ← Internal fragmentation
└──────────┘
```

Notice that there is no requirement for these pages to be physically adjacent.

---

# Important Interview Nuance

A common statement is:

> “Paging completely eliminates fragmentation.”

This is **incorrect**.

A more accurate statement is:

> **Paging eliminates external fragmentation in physical memory allocation because pages can occupy non-contiguous frames, but paging can still experience internal fragmentation.**

---

# Another Important Nuance

External fragmentation is particularly relevant when the allocation system requires **contiguous memory**.

If memory can be allocated in non-contiguous units, scattered free space can often be used more effectively.

For example:

```text
Contiguous allocation:

Need 10 KB
↓
Must find one 10 KB block


Paging:

Need 10 KB
↓
Can use multiple 4 KB frames/pages
```

This is one of the fundamental advantages of paging.

---

# Fragmentation vs Memory Leak

These concepts are often confused.

### Fragmentation

Memory exists but is used inefficiently.

```text
Memory exists
    ↓
Poorly arranged / partially wasted
    ↓
Fragmentation
```

### Memory Leak

A program has allocated memory that it no longer needs but has failed to reclaim in a manually managed environment, or continues to retain objects unnecessarily in a managed environment.

```text
Memory allocated
    ↓
No longer useful
    ↓
Still retained
    ↓
Memory usage grows
```

Therefore:

> **Fragmentation is about how usable memory is organized or wasted; a memory leak is about memory remaining allocated/reachable when it should no longer be needed.**

---

# Fragmentation vs Thrashing

These are also different.

### Fragmentation

Memory is being used inefficiently.

### Thrashing

The system is experiencing excessive paging/page faults.

They can be related indirectly, but they are not the same problem.

```text
Fragmentation
     ↓
Memory allocation inefficiency


Thrashing
     ↓
Excessive page faults
     ↓
Excessive paging
     ↓
Severe performance degradation
```

# Real-World Analogy

Imagine a parking lot.

### Internal Fragmentation

A car is given a large parking space but occupies only part of it.

```text
┌──────────────────┐
│ 🚗               │
│    Unused space  │
└──────────────────┘
```

The wasted space is **inside the allocated parking spot**.

### External Fragmentation

The parking lot has many small empty spaces:

```text
🚗 | Empty | 🚗 | Empty | 🚗
```

There may be enough total empty space for a large vehicle, but there is no single sufficiently large contiguous spot.

That is similar to **external fragmentation**.

## Interview Takeaway

> **Internal fragmentation wastes space inside allocated memory blocks, while external fragmentation occurs when free memory is scattered into small, non-contiguous blocks.**

### One-line Interview Answer

> **Internal fragmentation is wasted space inside allocated blocks, whereas external fragmentation is free memory scattered between allocated blocks, making large contiguous allocations difficult.**

### Must-Remember Points

* **Internal = wasted space inside an allocated block.**
* **External = scattered free space outside allocated blocks.**
* **Paging can have internal fragmentation.**
* **Paging avoids external fragmentation of physical frame allocation.**
* **Variable-sized contiguous allocation can suffer from external fragmentation.**
* **Compaction can reduce external fragmentation but has overhead.**
* **Fragmentation is different from memory leaks and thrashing.**
